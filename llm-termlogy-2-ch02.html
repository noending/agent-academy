模型能力评测与可信度

本章目标：能设计小规模评测，识别不公平比较，给出有证据的选型结论。

公开基准：它们到底在测什么？

想象你要给一个学生写推荐信，你会怎么描述他的能力？你可能会说“数学不错，但语文一般”。LLM 也一样，没有一个单一分数能概括所有能力。公开基准就是给模型出的“标准化考卷”，每张考卷测不同的能力维度。

先看几个最常被引用的：

  • MMLU：像“高考综合卷”，覆盖57个学科（数学、历史、法律、医学等），全是四选一选择题。它测的是广博的知识面，但几乎不测推理深度和生成能力。
  • GPQA：像“研究生入学考试”，题目由领域专家编写，设计成“谷歌搜不到答案”。它测的是专家级推理，难度远高于 MMLU。
  • AIME：美国数学邀请赛，15道填空，答案都是0-999的整数。它测的是多步数学推理，对模型来说极难，近年才被突破。
  • HumanEval：给函数签名和文档字符串，让模型补全代码，用单元测试判分。它测的是短代码生成，但题目短、场景简单，和真实工程差距大。
  • SWE-bench：从真实 GitHub 仓库提取 issue 和对应修复，让模型生成补丁，跑测试验证。它测的是真实软件工程能力，难度高，更接近实际开发。

关键点：每个基准都有明确的“测什么”和“不能说明什么”。比如 MMLU 高分不代表会写代码，SWE-bench 高分也不代表能和你流畅对话。选型时，先问“我的业务场景最像哪个基准”，而不是只看排行榜。

下面是一个最小示例，用 Python 模拟计算 MMLU 准确率：

# 模拟 MMLU 评测：4选1，计算准确率
import random

# 假设有 100 道题，模型预测和标准答案
random.seed(42)
num_questions = 100
labels = [random.randint(0, 3) for _ in range(num_questions)]  # 标准答案 0-3
# 模拟一个“还不错”的模型，70% 概率答对
preds = [labels[i] if random.random() < 0.7 else random.randint(0, 3) for i in range(num_questions)]

correct = sum(p == l for p, l in zip(preds, labels))
accuracy = correct / num_questions
print(f"MMLU 准确率: {accuracy:.2%}")  # 输出类似 71.00%

注意：真实评测中，还要考虑提示词格式、few-shot 示例数量等，这些都会影响分数。

评测可信度：分数背后的陷阱

你看到两个模型在 MMLU 上分别是 85% 和 84%，能直接说第一个更好吗？不一定。评测结果可能被多种因素扭曲，就像考试作弊或泄题一样。

常见陷阱：

  • 数据污染：训练数据里混入了测试题。模型可能“背过答案”，分数虚高。检测方法：看模型在扰动题目（如改数字）上的表现是否骤降。
  • 测试集泄漏：测试集被用于调参或模型选择，导致过拟合。正确做法是严格划分开发集和测试集，测试集只在最后用一次。
  • 样本过少：只测 20 道题，随机波动可能让分数差 10%。一般建议至少几百个样本，并用置信区间报告。
  • 只报告最好结果：跑多次取最高分，忽略方差。应该报告平均值和标准差。
  • 提示词与推理预算不公平：给模型 A 精心设计的提示词和更多推理步数，模型 B 用默认设置，比较就不公平。必须控制变量。

举个例子：假设两个模型真实能力相同，但测试集只有 50 题，准确率都是 80%。由于随机性，一个可能考 86%，另一个 74%。用下面代码模拟：

import random

def eval_model(true_acc, n=50):
    return sum(random.random() < true_acc for _ in range(n)) / n

random.seed(0)
# 两个模型真实准确率都是 0.8
scores_a = [eval_model(0.8) for _ in range(5)]
scores_b = [eval_model(0.8) for _ in range(5)]
print("模型A 5次评测:", [f"{s:.0%}" for s in scores_a])
print("模型B 5次评测:", [f"{s:.0%}" for s in scores_b])
# 输出可能显示 A 最高 88%，B 最低 72%，但真实能力相同

结论：比较模型时，必须确保测试条件一致，并报告不确定性。否则你的选型结论可能只是噪声。

人工评测与 LLM-as-a-Judge：如何让评判更可靠

很多任务没有标准答案，比如“写一封友好的客户邮件”。这时需要人工评分，但人工贵且慢。于是有了 LLM-as-a-Judge：用另一个大模型当裁判，给回答打分或排序。

它像请了一个“助教”来批改作业，但助教也有偏见：可能偏爱长回答、偏爱自己家族的模型、对某些格式敏感。所以必须设计防偏机制：

  • 盲评：裁判不知道哪个回答来自哪个模型，避免品牌偏见。
  • 随机顺序：交换两个回答的呈现顺序，消除位置偏见。
  • 重复测试：同一对回答多次评判，看一致性。
  • 人工校验：抽样一部分让人类专家复核，校准裁判的可靠性。

下面是一个简化的 LLM-as-a-Judge 流程示例（用伪代码表示）：

# 模拟 LLM-as-a-Judge 盲评流程
import random

def judge(answer_a, answer_b, model_name):
    # 真实裁判会调用 LLM API，这里用随机模拟
    # 假设裁判有 60% 概率选更好的那个，但不知道模型名
    return random.choice(["A", "B"])

def blind_compare(model1_answers, model2_answers, n_trials=5):
    wins = {"model1": 0, "model2": 0}
    for i in range(len(model1_answers)):
        for _ in range(n_trials):
            # 随机交换顺序
            if random.random() < 0.5:
                a, b = model1_answers[i], model2_answers[i]
                mapping = {"A": "model1", "B": "model2"}
            else:
                a, b = model2_answers[i], model1_answers[i]
                mapping = {"A": "model2", "B": "model1"}
            winner = judge(a, b, "judge_model")
            wins[mapping[winner]] += 1
    return wins

# 模拟两个模型的回答
m1 = ["回答1-模型1", "回答2-模型1"]
m2 = ["回答1-模型2", "回答2-模型2"]
random.seed(1)
result = blind_compare(m1, m2)
print("盲评胜场:", result)

LLM-as-a-Judge 适合快速迭代和粗筛，但不能完全替代人工，尤其是高风险场景。最终选型报告里，最好同时给出自动指标和人工评估结果。

实操：设计一次小规模业务评测

现在把前面知识串起来。假设你要为“企业客服助手”选型，候选模型 A 和 B。你需要设计一个评测，用证据说话。

步骤：

  1. 定义能力维度：根据业务，确定关键维度，比如“回答准确性”、“语气友好度”、“拒绝不当请求”。
  2. 收集业务样本：从真实客服日志中抽取 100 条用户问题，覆盖常见和边缘情况。
  3. 划分开发集和测试集：用 50 条做开发集，用来调试提示词和评分标准；另外 50 条做测试集，只在最终比较时用。
  4. 设计评分标准：每个维度 1-5 分，并写清楚评分细则。例如准确性：5=完全正确，3=部分正确，1=错误。
  5. 运行评测：对两个模型使用相同的提示词和推理预算，生成回答。
  6. 评分：先用 LLM-as-a-Judge 盲评，再人工校验 20% 的样本。
  7. 分析失败类型：统计错误类别，比如“答非所问”、“信息过时”、“语气生硬”。
  8. 得出结论：基于测试集分数和失败分析，给出选型建议。

下面是一个简化的评测脚本框架：

# 业务评测框架示例
import random

# 模拟 50 条测试样本，每条有标准答案和两个模型的回答
test_samples = [
    {"question": f"问题{i}", "reference": f"参考答案{i}",
     "model_a": f"模型A回答{i}", "model_b": f"模型B回答{i}"}
    for i in range(50)
]

def score_answer(answer, reference):
    # 模拟评分：随机 1-5 分
    return random.randint(1, 5)

random.seed(42)
scores_a, scores_b = [], []
for sample in test_samples:
    scores_a.append(score_answer(sample["model_a"], sample["reference"]))
    scores_b.append(score_answer(sample["model_b"], sample["reference"]))

avg_a = sum(scores_a) / len(scores_a)
avg_b = sum(scores_b) / len(scores_b)
print(f"模型A 平均分: {avg_a:.2f}")
print(f"模型B 平均分: {avg_b:.2f}")

# 简单失败分析：统计低分（<=2）数量
fail_a = sum(1 for s in scores_a if s <= 2)
fail_b = sum(1 for s in scores_b if s <= 2)
print(f"模型A 低分样本数: {fail_a}")
print(f"模型B 低分样本数: {fail_b}")

记住：测试集是最终裁判，开发集用来迭代。不要用测试集调提示词，否则结论不可信。

常见误区

  • 只看排行榜总分就选模型：不同基准测的能力不同，MMLU 高不代表代码或对话好，必须匹配业务场景。
  • 用测试集调参后还报告测试集分数：这会导致过拟合，分数虚高，应该用开发集调参，测试集只用于最终评估。
  • 认为 LLM-as-a-Judge 完全客观：裁判模型有位置偏见、长度偏见等，必须盲评、随机顺序、重复测试并人工校验。

自测

为什么不能直接用 MMLU 分数来预测模型在客服对话中的表现？

答案：MMLU 是四选一知识题，主要测广博知识，不测多轮对话、语气、拒绝不当请求等客服核心能力。客服表现需要专门设计对话评测。

在设计模型比较实验时，如何避免不公平比较？

答案：确保两个模型使用相同的提示词、推理预算、测试样本和评分标准；采用盲评和随机顺序；报告多次运行的平均值和方差；严格划分开发集和测试集。
