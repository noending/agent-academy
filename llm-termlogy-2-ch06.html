综合项目：企业助手选型

本章目标：完成从需求到选型报告的完整项目，给出有证据的推荐方案。

需求梳理明确企业场景与约束条件→方案调研收集候选助手与能力数据→评测对比按统一指标实测打分→证据汇总整理数据支撑推荐结论→选型报告输出有据可查的推荐方案
本章走通从需求到选型报告的完整链路，每一步都用证据说话。

从需求到验收标准：把业务语言翻译成可测量的指标

想象你要装修房子，设计师问你“想要什么风格”，你说“要好看、要实用、要便宜”。设计师如果直接开工，最后大概率双方都不满意。选型也是一样：业务方说“要准、要快、要便宜”，这不是需求，这是愿望。工程决策的第一步，是把愿望翻译成可测量的数字。

具体怎么做？以“企业知识库问答 + 订单分析助手”为例，把模糊诉求拆成三类可测量约束：效果（知识库问答答案正确率、订单字段提取的 F1）、性能（P95 延迟、QPS 吞吐）、成本（每千次调用成本、月度 TCO）。每一类都要落到一个数字上，比如“知识库问答答案正确率 ≥ 90%”“订单字段提取 F1 ≥ 0.95”“P95 延迟 ≤ 3s”“单次调用成本 ≤ 0.01 元”。

这些数字合起来就是 SLO（Service Level Objective，服务等级目标）。注意 SLO 不是拍脑袋写的，它来自业务后果：如果订单字段提取 F1 只有 0.90，意味着每 100 单有 10 单需要人工复核，按每天 5000 单算就是 500 次人工介入，这才是业务方真正在意的成本。所以写 SLO 时要追问一句“达不到会怎样”，把后果反推成阈值。

关键结论：没有验收标准的选型是主观偏好，有验收标准的选型才是工程决策。验收标准一旦写死，后面所有评测、对比、报告都有了统一的标尺，争论也会从“我觉得 A 好”变成“A 在哪个指标上没达标”。

准备脱敏测试数据：让评测可复现、可对比

验收标准是尺子，测试数据就是被量的东西。如果每次评测用的数据都不一样，结果就无法对比，选型就退化成“这次跑出来好像还行”。所以评测数据必须固定、可复现，同时必须脱敏（Anonymized Data）：替换真实姓名、手机号、订单号，但保留分布特征——文本长度、字段格式、噪声程度都要和真实流量一致。

为什么保留分布这么重要？举个反例：如果你把测试样本都换成“客户A买了1台X100，订单号ORD-0001”这种规整短句，模型在评测里能拿 0.98 的 F1，但真实流量里有“麻烦帮我看下上周那个加急的、要五块 H100 的单子，单号好像是 ORD 开头尾号 1002”这种口语化长句，上线后 F1 可能掉到 0.85。评测数据失真，评测结论就无法外推。

数据要覆盖五类任务，每类 30~50 条并标注标准答案：订单信息提取、结构化 JSON 输出、知识库问答、异常解释、受控工具调用。下面是一个最小可运行示例，输入是两条脱敏样本，输出是每条样本的字段级准确率：

python
import json, re

# 脱敏后的测试样本（姓名/单号已替换，但保留句式与长度分布）
test_cases = [
    {"input": "客户张三买了2台A100，订单号ORD-1001，要求3天内发货",
     "expected": {"customer": "张三", "quantity": 2, "product": "A100", "order_id": "ORD-1001"}},
    {"input": "李四下单5块H100，订单号ORD-1002，加急",
     "expected": {"customer": "李四", "quantity": 5, "product": "H100", "order_id": "ORD-1002"}},
]

def extract(text):
    # 这里用正则模拟模型输出；真实场景替换为 API 调用
    return {
        "customer": re.search(r"客户?(\w+?)(?:买|下单)", text).group(1),
        "quantity": int(re.search(r"(\d+)(?:台|块)", text).group(1)),
        "product": re.search(r"(A100|H100)", text).group(1),
        "order_id": re.search(r"ORD-\d+", text).group(0),
    }

def score(pred, gold):
    # 字段级准确率：预测字段与标准答案完全一致的占比
    correct = sum(1 for k in gold if pred.get(k) == gold[k])
    return correct / len(gold)

for case in test_cases:
    pred = extract(case["input"])
    print(case["input"][:20], "->", score(pred, case["expected"]))
# 预期输出：两条样本均打印 1.0（四个字段全部命中）

这段代码的价值不在于正则写得多好，而在于它把“评测”变成了一个可重复执行的函数：换模型只换 extract，数据、打分逻辑、输出格式都不变，结果天然可对比。

关键结论：脱敏数据既要保护隐私，又要保留真实分布，否则评测结果无法外推。建议把测试集版本化（如 eval_v1.jsonl），每次选型对比都引用同一版本。

比较模型与性能成本：设计评测并估算部署资源

有了尺子和数据，接下来是“怎么量”。很多团队只测单条请求的延迟，这就像只测空载汽车油耗——一上高速堵车就完全不是那个数。真实评测要同时测四件事：效果（准确率/F1）、延迟（P50/P95，而不是平均值）、吞吐（QPS）、成本（按 token 计费或按 GPU 小时折算）。为什么强调 P95？因为平均值会掩盖长尾：100 次请求里 95 次 1 秒、5 次 10 秒，平均值约 1.45 秒看起来很美，但那 5 次才是用户投诉的来源。

如果考虑自建部署，还要估算显存。经验公式是：显存 ≈ 参数量 × 精度字节数 × 1.2（框架与激活开销），高并发时再单独加 KV Cache。例如 7B 模型 FP16 约 14GB，INT8 约 7GB，INT4 约 3.5GB；13B 模型 INT8 约 13GB，乘 1.2 后约 15.6GB，单张 24GB 卡放得下，但并发上来后 KV Cache 会继续吃显存，可能就需要多卡或量化（具体数值随框架与上下文长度变化，待核实）。

下面是一个评测脚本骨架，输入是模型调用函数和测试集，输出效果与延迟分位数：

python
import time, statistics

def evaluate(model_fn, cases):
    scores, latencies = [], []
    for c in cases:
        t0 = time.time()
        pred = model_fn(c["input"])
        latencies.append(time.time() - t0)
        scores.append(score(pred, c["expected"]))
    latencies.sort()
    return {
        "accuracy": sum(scores) / len(scores),
        "p50_latency": statistics.median(latencies),
        "p95_latency": latencies[int(len(latencies) * 0.95) - 1],
    }

# 用法：result = evaluate(model_fn, test_cases); print(result)
# 预期输出形如 {'accuracy': 0.94, 'p50_latency': 0.8, 'p95_latency': 2.3}

成本要算 TCO 而不是单价。API 场景：若每千 token 收费 0.002 元，平均每次请求 500 token，则单次 0.001 元；日调用 10 万次，日成本 100 元，月成本约 3000 元。自建场景：按 GPU 小时费 × 24 × 30 折算，再加上运维人力、重试与缓存带来的额外调用、GPU 折旧。一个常见陷阱是只比 API 单价，忽略了失败重试：如果工具调用失败率 5%，实际调用量就多 5%，成本同步上浮。

关键结论：选型要算 TCO，不只看单价；延迟和吞吐必须用真实并发压测，不能只看单条测试。

撰写选型报告：结构、证据与适用边界

选型报告不是“我推荐 A”的一句话，而是一条完整的证据链：从业务约束出发，经过评测方法和数据，到结果、成本、硬件，最后落到推荐和边界。决策者读报告时脑子里只有三个问题——“为什么选它”“什么情况下不选它”“还有什么没验证”。报告结构就要直接回答这三问。

推荐结构九段：业务约束与验收标准、评测方法与脱敏数据说明、效果结果（表格对比）、性能结果（延迟/吞吐）、成本估算与 TCO、硬件需求、推荐方案、适用边界（Applicability Boundary）、待验证风险（Risks to Validate）。其中效果对比表是核心证据，示例如下：

模型提取 F1问答准确率P95 延迟单次成本
模型A0.960.912.1s0.001元
模型B0.930.881.2s0.0005元

看这张表怎么下结论？如果验收标准是“提取 F1 ≥ 0.95 且问答准确率 ≥ 0.90”，模型B 两项都不达标，直接出局，哪怕它更便宜更快；模型A 两项都过线，但 P95 2.1s 距离 3s 阈值只剩 0.9s 余量，这就是要在报告里写明的风险点。如果业务是“高并发、可接受人工复核”，那模型B 反而可能更合适——同一个表，在不同验收标准下会得出不同推荐，这正是报告必须写清约束的原因。

适用边界要写成可操作的句子，例如“模型A 适合高准确率、中低并发场景；当 QPS 超过 X 或长尾订单格式占比超过 Y% 时需重新评测”（X、Y 需用压测数据填充，待核实）。待验证风险至少覆盖：长尾订单格式、工具调用失败率、数据漂移。每条风险要写清验证方式和触发条件，而不是只列名词。

关键结论：报告的价值在于证据链完整、边界清晰、风险可追踪，而不是给出一个绝对答案。

常见误区

  • 错误理解：只看模型跑分（如 MMLU）就做选型，认为分数高的模型一定更适合业务。→ 后果：跑分高但业务数据分布不同，上线后订单提取 F1 可能从评测的 0.95 掉到 0.85，人工复核量翻倍，选型结论被推翻。→ 正确做法：先写业务验收标准（SLO），再用与真实流量同分布的脱敏数据做任务级评测，跑分只作为初筛参考。
  • 错误理解：用未脱敏的真实数据做评测，觉得“真实才准”。→ 后果：姓名、手机号、订单号进入评测日志和第三方 API，造成隐私泄露；且数据一旦需要清理或替换，历史结果无法复现，前后对比失效。→ 正确做法：评测前统一脱敏，替换 PII 但保留长度、格式、噪声分布，并把测试集版本化固定下来。
  • 错误理解：只算 API 单价，忽略 TCO 和并发下的延迟劣化。→ 后果：单价 0.0005 元的模型看似便宜，但加上 5% 失败重试、缓存未命中、运维人力和 GPU 折旧后，实际月成本可能反超；单条测试 1.2s 的模型在 50 并发下 P95 可能劣化到 5s，直接违反 SLO。→ 正确做法：按 TCO 口径估算（含重试、缓存、运维、折旧），并用真实并发压测测 P95 和 QPS。

自测

某团队用 100 条规整短句评测两个模型，模型A 提取 F1=0.97、模型B F1=0.94，于是选了 A。上线一个月后 A 的人工复核率反而高于 B。请分析可能原因，并说明评测设计上应如何改进。

答案：推理过程：第一步，评测数据是“规整短句”，与真实流量的口语化长句分布不一致，F1 高只说明模型在简单分布上强，不能外推到真实流量。第二步，两个模型在长尾格式（口语化、多字段混杂、噪声）上的表现可能反转，A 可能在长尾上更差，导致人工复核率更高。第三步，改进方向：按真实流量分布构造脱敏测试集，显式加入长尾样本并单独统计长尾子集 F1；同时把“人工复核率”作为业务侧验收指标纳入评测，而不是只看整体 F1。结论：评测数据的分布代表性比样本数量更关键。

估算 13B 模型 INT8 部署显存时，为什么不能只算 13GB？请给出估算思路，并说明什么情况下单张 24GB 卡可能不够。

答案：推理过程：第一步，参数量 × 精度字节 = 13B × 1 字节 ≈ 13GB，这是权重本身。第二步，运行时还有框架开销、激活值，经验上乘 1.2 左右，约 15.6GB。第三步，高并发或长上下文时 KV Cache 会显著增长，它随并发数和上下文长度线性上升，这部分要单独估算。第四步，当 15.6GB 加上 KV Cache 和其他开销超过 24GB 时，单卡就不够，需要多卡、降低并发或进一步量化。注意具体系数随框架和上下文长度变化，应以实测为准（待核实）。

选型报告里“适用边界”和“待验证风险”看起来都是“说缺点”，为什么反而必须写？请结合决策场景说明。

答案：推理过程：第一步，任何模型都有能力边界，报告如果不写，决策者会默认“什么场景都能用”，一旦遇到长尾订单或高并发就误用，故障成本远高于选型成本。第二步，适用边界把“什么时候该重新评测”变成可执行条件，让后续团队知道触发点。第三步，待验证风险列出尚未被评测覆盖的假设（如工具调用失败率、数据漂移），并给出验证方式，使决策可追踪、可迭代。第四步，从决策角度看，一份只讲优点的报告无法支撑风险审批，写明边界和风险反而提升报告可信度。结论：边界和风险不是减分项，而是证据链完整性的组成部分。

任务：为“企业知识库问答 + 订单分析助手”写一个可运行的最小选型评测脚本：构造 4 条脱敏测试样本（覆盖订单提取与结构化输出两类任务），实现两个模拟模型（模型A 准确但慢、模型B 快但偶有字段错误），输出每个模型的字段级准确率、P50/P95 延迟和单次成本估算，并据此给出推荐结论。验收标准：脚本可直接运行，输出包含两个模型的 accuracy、p50、p95、cost 四项，且推荐结论与验收标准（accuracy ≥ 0.9 且 p95 ≤ 3s）一致。

参考方案：

python
import time, statistics, json

# 1) 脱敏测试样本：覆盖订单提取与结构化输出
test_cases = [
    {"input": "客户张三买了2台A100，订单号ORD-1001",
     "expected": {"customer": "张三", "quantity": 2, "product": "A100", "order_id": "ORD-1001"}},
    {"input": "李四下单5块H100，订单号ORD-1002",
     "expected": {"customer": "李四", "quantity": 5, "product": "H100", "order_id": "ORD-1002"}},
    {"input": "王五采购1台A100，订单号ORD-1003",
     "expected": {"customer": "王五", "quantity": 1, "product": "A100", "order_id": "ORD-1003"}},
    {"input": "赵六下单3块H100，订单号ORD-1004",
     "expected": {"customer": "赵六", "quantity": 3, "product": "H100", "order_id": "ORD-1004"}},
]

def parse(text):
    # 简易解析，模拟模型抽取结构化字段
    import re
    return {
        "customer": re.search(r"客户?(\w+?)(?:买|下单|采购)", text).group(1),
        "quantity": int(re.search(r"(\d+)(?:台|块)", text).group(1)),
        "product": re.search(r"(A100|H100)", text).group(1),
        "order_id": re.search(r"ORD-\d+", text).group(0),
    }

def model_a(text):
    # 模型A：准确但慢（模拟 0.05s 延迟）
    time.sleep(0.05)
    return parse(text)

def model_b(text):
    # 模型B：快但偶有字段错误（模拟 0.01s 延迟，第2条样本数量错）
    time.sleep(0.01)
    pred = parse(text)
    if "ORD-1002" in text:
        pred["quantity"] = 4  # 模拟抽取错误
    return pred

def score(pred, gold):
    correct = sum(1 for k in gold if pred.get(k) == gold[k])
    return correct / len(gold)

def evaluate(model_fn, cases, cost_per_call):
    scores, latencies = [], []
    for c in cases:
        t0 = time.time()
        pred = model_fn(c["input"])
        latencies.append(time.time() - t0)
        scores.append(score(pred, c["expected"]))
    latencies.sort()
    return {
        "accuracy": round(sum(scores) / len(scores), 3),
        "p50": round(statistics.median(latencies), 3),
        "p95": round(latencies[int(len(latencies) * 0.95) - 1], 3),
        "cost": cost_per_call,
    }

results = {
    "模型A": evaluate(model_a, test_cases, 0.001),
    "模型B": evaluate(model_b, test_cases, 0.0005),
}
print(json.dumps(results, ensure_ascii=False, indent=2))

# 2) 按验收标准推荐：accuracy >= 0.9 且 p95 <= 3s
for name, r in results.items():
    ok = r["accuracy"] >= 0.9 and r["p95"] <= 3.0
    print(name, "达标" if ok else "不达标")

# 预期输出：模型A accuracy=1.0、模型B accuracy≈0.938（1条样本错1个字段）
# 两者 p95 均远小于 3s，均达标；若业务要求零字段错误，则推荐模型A
