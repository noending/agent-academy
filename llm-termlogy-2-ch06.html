综合项目：企业助手选型

本章目标：完成从需求到选型报告的完整项目，给出有证据的推荐方案。

从需求到验收标准：把业务语言翻译成可测量的指标

选型不是“哪个模型跑分高就选哪个”，而是“哪个模型最匹配业务约束”。先做需求翻译：把业务方的模糊诉求（“要准、要快、要便宜”）变成可测量的验收标准（Acceptance Criteria）。

以企业知识库问答 + 订单分析助手为例，业务约束通常有三类：效果（回答正确率、结构化字段准确率）、性能（P95 延迟、吞吐）、成本（每千次调用成本、TCO）。

把约束写成 SLO（Service Level Objective），例如：知识库问答答案正确率 ≥ 90%，订单字段提取 F1 ≥ 0.95，P95 延迟 ≤ 3s，单次调用成本 ≤ 0.01 元。这些数字就是后续评测的标尺。

关键结论：没有验收标准的选型是主观偏好，有验收标准的选型才是工程决策。

准备脱敏测试数据：让评测可复现、可对比

评测数据必须脱敏（Anonymized Data）：替换真实姓名、手机号、订单号，但保留分布特征（长度、格式、噪声）。数据要覆盖五类任务：

  • 订单信息提取：从自然语言中抽取结构化字段
  • 结构化输出：要求模型返回 JSON
  • 知识库问答：基于给定文档回答
  • 异常解释：解释订单异常原因
  • 受控工具调用：调用查询接口并传参

每类准备 30~50 条，标注标准答案。下面是一个最小可运行的数据构造与评测示例：

import json, re

# 脱敏后的测试样本
test_cases = [
    {"input": "客户张三买了2台A100，订单号ORD-1001，要求3天内发货",
     "expected": {"customer": "张三", "quantity": 2, "product": "A100", "order_id": "ORD-1001"}},
    {"input": "李四下单5块H100，订单号ORD-1002，加急",
     "expected": {"customer": "李四", "quantity": 5, "product": "H100", "order_id": "ORD-1002"}},
]

def extract(text):
    # 模拟模型输出（真实场景替换为 API 调用）
    return {
        "customer": re.search(r"客户?(\w+?)(?:买|下单)", text).group(1),
        "quantity": int(re.search(r"(\d+)(?:台|块)", text).group(1)),
        "product": re.search(r"(A100|H100)", text).group(1),
        "order_id": re.search(r"ORD-\d+", text).group(0),
    }

def score(pred, gold):
    correct = sum(1 for k in gold if pred.get(k) == gold[k])
    return correct / len(gold)

for case in test_cases:
    pred = extract(case["input"])
    print(case["input"][:20], "->", score(pred, case["expected"]))

关键结论：脱敏数据既要保护隐私，又要保留真实分布，否则评测结果无法外推。

比较模型与性能成本：设计评测并估算部署资源

评测要同时测四件事：效果、延迟、吞吐、成本。效果用准确率/F1；延迟看 P50/P95；吞吐看 QPS；成本按 token 计费或按 GPU 小时折算。

部署资源估算公式：显存 ≈ 参数量 × 精度字节数 × 1.2（KV Cache 与开销）。例如 7B 模型 FP16 约 14GB，INT8 约 7GB，INT4 约 3.5GB。并发高时 KV Cache 会显著增加显存。

下面是一个评测脚本骨架，输出效果与延迟：

import time, statistics

def evaluate(model_fn, cases):
    scores, latencies = [], []
    for c in cases:
        t0 = time.time()
        pred = model_fn(c["input"])
        latencies.append(time.time() - t0)
        scores.append(score(pred, c["expected"]))
    return {
        "accuracy": sum(scores) / len(scores),
        "p50_latency": statistics.median(latencies),
        "p95_latency": sorted(latencies)[int(len(latencies) * 0.95) - 1],
    }

成本估算示例：若模型每千 token 收费 0.002 元，平均每次请求 500 token，则单次成本 0.001 元；日调用 10 万次，日成本 100 元，月成本约 3000 元。自建部署则按 GPU 小时费 × 24 × 30 折算 TCO。

关键结论：选型要算 TCO，不只看单价；延迟和吞吐必须用真实并发压测，不能只看单条测试。

撰写选型报告：结构、证据与适用边界

选型报告（Selection Report）要让决策者一眼看懂“为什么选它、什么情况下不选它”。推荐结构：

  1. 业务约束与验收标准
  2. 评测方法与脱敏数据说明
  3. 效果结果（表格对比）
  4. 性能结果（延迟/吞吐）
  5. 成本估算与 TCO
  6. 硬件需求
  7. 推荐方案
  8. 适用边界（Applicability Boundary）
  9. 待验证风险（Risks to Validate）

效果对比表示例：

模型提取 F1问答准确率P95 延迟单次成本
模型A0.960.912.1s0.001元
模型B0.930.881.2s0.0005元

推荐方案要写清适用边界：例如“模型A 适合高准确率场景，模型B 适合高并发低成本场景”。待验证风险包括：长尾订单格式、工具调用失败率、数据漂移。

关键结论：报告的价值在于证据链完整、边界清晰、风险可追踪，而不是给出一个绝对答案。

常见误区

  • 只看模型跑分（如 MMLU）就做选型，忽略业务验收标准和真实数据分布。
  • 用未脱敏的真实数据做评测，导致隐私泄露且结果无法复现。
  • 只算 API 单价，忽略 TCO（含重试、缓存、运维、GPU 折旧）和并发下的延迟劣化。

自测

为什么选型报告必须包含“适用边界”和“待验证风险”？

答案：因为任何模型都有能力边界，明确边界能防止误用；待验证风险提示后续 PoC 需要重点验证的假设，保证决策可追踪、可迭代。

估算 13B 模型 INT8 部署显存时，除了参数量还要考虑什么？

答案：还要考虑 KV Cache（随并发和上下文长度增长）、框架开销、激活值等，通常按参数量 × 精度字节 × 1.2~1.5 估算，高并发时需单独计算 KV Cache。
