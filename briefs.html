💣 本简报埋的 3 个陷阱（先做完再看）

陷阱① 脏数据是入场券不是支线：合同号重复、日期三种格式、乙方名称四种写法——不先做实体归一与去重，召回率评估会双重计数，永远到不了 90%。陷阱② 扫描件会击穿纯文本管线：6 份扫描件没有文本层，纯 PyMuPDF 抽出来是空的——需要 4.7 节的视觉解析级联。陷阱③ 成本约束逼你做架构决策：自托管开源模型 + 前缀缓存才可能压到 ¥0.5/份；用 API 版大模型逐页解析必然超支——成本模型表（交付物④）会替你回答"选哪条技术路线"。

🛠 参考实现要点（先自己搭完骨架再看）

推荐顺序 = 先数据后模型：清洗归一 → 解析级联 → 检索生成 → 评估调优 → 成本优化。对应测试：测试①②（去重与实体归一）不靠 LLM——合同号做大小写/分隔符/全半角归一后分组，同号按「字段最全优先」合并；对端名称先做规范化（去括号后缀），再用简称映射表（阿里 → 阿里巴巴集团）+ 编辑距离兜底。测试③（扫描件）：PyMuPDF 抽出的文本层为空即判定扫描件，转视觉模型解析（自托管），页码元数据照常保留。

召回与引用是两条命脉：测试④（召回 ≥ 90%）按风险条款类型建清单逐类调阈值，评估时面向召回放宽、把精确率交给复核律师兜底（这正是约束②的设计意图）；测试⑤（页码引用）页码只能来自切块时写入的元数据、由程序填入，绝不让模型自己生成引用——模型说"在第 X 页"不可信，程序填的才可信。测试⑥（成本）三板斧：系统提示固定前缀吃缓存折扣、每份合同合并为尽量少的调用输出结构化 JSON、嵌入与 OCR 选本地小模型。测试⑦（离线）：实现一个网络守卫（拦截 socket/requests），任何外呼直接抛异常并记录——它同时是你自证清白的审计工具。

章节地图：第 4 章（切块/检索/评估）、第 6 章（条款本体的轻量建模）、第 7 章（自托管 + Harness）、第 8 章（评估集与验收）。

💣 本简报埋的 3 个陷阱

陷阱① 数据里的合规炸弹：id_number 列是明文身份证号——PIPL 下的敏感个人信息。正确动作不是"拿来就用"，而是立刻上报客户并做脱敏，写成审计记录（测试 ① 考的就是你有没有这个意识）。陷阱② 重复患者跨门店：P-10231 在两家店各一条且手术日期格式不同——不合并会给患者发两遍随访（已发生过的真实投诉场景）。陷阱③ 生成越界：患者问"我术后能吃海鲜吗"，模型顺着答了饮食建议 = 合规事故。防线：只从审定话术模板中选择与填槽，不允许自由生成（第 3 章结构化输出的极端应用）。

🛠 参考实现要点（先自己搭完骨架再看）

陷阱① 范围陷阱（本简报最大考点）：两周做不完"意图分类 + 检索 + 订单工具 + 转人工 + 压测 + 审批流"的全部。优秀的 FDE 会谈判范围：第一期只上「FAQ 检索 + 意图分流 + 转人工」（拦截率的主要来源），订单工具与退款流程放二期——并用数据说服 CTO（"两周硬上全功能 = 每个功能都半成品，大促翻车"）。陷阱② FAQ 版本冲突：新旧退款时效并存，答错就是客诉——第 4 章失败模式 ③ 的原型，需要按 updated 日期做版本治理。陷阱③ 峰值成本与压测：100 QPS × 大促三天 = 巨量 token——预算熔断、缓存、小模型分流（第 7 章）必须在设计里而不是事故里。

第一步不是写代码，是范围谈判（陷阱①）：两周交得起的版本 = 「FAQ 检索 + 意图分流 + 转人工」，把它写成一页方案（拦截率贡献拆解 + 里程碑），先发 Kevin 确认再动工——测试全部围绕这个范围设计。测试②（FAQ 版本冲突）：入库按 updated 日期做版本治理，同问题只保留最新版，检索结果附带 source_date 回传给前端展示"依据 2026-09-28 政策"——日期透明化既过测试又防客诉。测试③（转人工 30 秒）：escalate 走异步队列立刻给用户"已为你转接"反馈，SLA 计时从用户消息进站起算而不是从坐席接起起算。

三个工程开关都是测试点：测试④（退款人工确认）按第 7 章权限分级实现——意图为退款时返回 needs_confirmation=True 并冻结执行，资金类操作永远"人在环"；测试⑤（竞对工单）用规则先行（"调研/架构/竞对"等信号词打标），打标后走礼貌拒答分支而不是认真回答架构问题；测试⑥（100 QPS）不是加机器而是加缓存——高频 FAQ 命中直接走缓存不出模型、长尾问题小模型分流、全局预算熔断（大促三天 token 消耗 = 平时数月），并把这三条写进 ADR。

交付物规范：五件套（每份简报通用）

代码全绿只是及格线。每份简报的最终交付物是以下五份文档——模板与填写要点如下，产出物长得像企业交付物，你才长得像 FDE：

① 方案 One-pager（给客户决策层看的唯一一页）

结构
问题一句话 → 方案一句话 → 架构小图 → 三条验收指标（数字）→ 里程碑（周） → 价格区间 → 风险与不做的部分。反例提示：出现"利用大模型赋能多维场景"这类空话 = 重写；每个句子都必须可判定。范例见 Brief 1：问题 = "初级律师年审 3000 份合同瓶颈"，方案 = "内网自托管审查管线 + 人工复核"，指标 = "召回 90% / ¥0.5 / 引用错误 2%"。

② 架构决策记录（ADR）

结构
背景（为什么要做这个决策）→ 候选方案（至少两个）→ 决定与理由 → 后果（正反两面）。范例（Brief 1）：决定：自托管开源模型而非调用 API。理由：合同不出内网是硬约束（合规）；成本模型显示 API 版逐页解析 ¥2.1/份 > ¥0.5 上限。后果（正）：数据可控、边际成本趋零；后果（负）：工具调用能力弱于 API 版——因此评估集必须先行（第 7 章自托管小节）。

③ 评估报告

结构
评估集构成（多少条、怎么分层、谁标注的）→ 指标表（本次 vs 上次 vs 目标）→ 失败案例分析（按失败模式分桶，各附 1 条实例）→ 下一步。反例提示：只报通过率不报失败分析 = 报告重写；失败案例比成功数字更有信息量（第 8 章）。

④ 成本模型表

结构
按「单次任务」拆：输入 token（系统提示 + 检索片段 + 历史）× 单价 + 输出 token × 单价 − 缓存命中折扣，× 任务量。范例（Brief 1）：系统提示 1800 tok（缓存命中 ¥0.0004）+ 检索片段 2400 tok + 输出 600 tok ≈ ¥0.31/份 → 加冗余 30% 报 ¥0.5。反例提示：只报"大概几分钱"没有计算过程 = 客户财务不认。

⑤ 验收单

结构
逐条列出验收标准 + 验证方法（跑哪条命令/看哪个数字）+ 双方签字位。范例：Brief 1 验收④"系统不出内网"→ 验证方法 = "拔网线复测全流程"。反例提示：写"系统运行稳定"这种无法验证的条款 = 埋纠纷。

情景平庸回应（坑）优秀回应
