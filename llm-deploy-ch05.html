模型评估与优化

本章目标：学会设计评估方案，并进行量化、剪枝与蒸馏优化

定评估方案明确指标与数据划分→量化评估跑分定位性能瓶颈→剪枝瘦身去掉冗余参数降成本→蒸馏提效小模型学大模型能力→复评迭代回测对比再优化
先量化找瓶颈，再剪枝蒸馏，复评闭环迭代优化模型。

评估指标：从困惑度到人工评估

模型训完了，怎么知道它好不好？先建立一个直觉：把语言模型想象成一个永远在玩“猜下一个词”游戏的考生。如果它总能胸有成竹地押中答案，说明它“懂”这段文本；如果它每次都一脸茫然地在很多候选词之间犹豫，说明它没学好。困惑度（Perplexity, PPL）衡量的正是这种“犹豫程度”：PPL 越低，模型对文本的预测越笃定。数学上，PPL 是交叉熵损失的指数：PPL = exp(loss)。比如 loss=2.0，PPL≈7.39，可以粗略理解为模型在每一步平均在 7.39 个词里犹豫；若 loss 降到 1.0，PPL≈2.72，犹豫范围缩小到不到 3 个词，这就是一个可感知的前后对比。

但 PPL 只反映语言建模能力，不直接对应任务效果。一个 PPL 很低的模型可能只是擅长复述训练语料里的常见句式，遇到需要推理的选择题照样答错。所以还需要准确率（Accuracy）：分类任务看分类正确率，选择题看选项命中率，代码任务看通过率。对于开放式生成任务，准确率往往无法自动计算，需要人工或模型辅助判断，这时就要引入评分 rubric（评分细则）。

最后是人工评估：让标注员对流畅性、相关性、事实性、安全性逐项打分。人工评估成本高、主观性强，但最贴近真实用户体验。实践中常采用“自动指标粗筛 + 人工精评”的组合：先用 PPL 和准确率快速筛掉明显不合格的候选，再对 Top 候选做人工打分。关键结论是：没有任何单一指标能代表模型质量，评估方案必须多指标交叉验证。

下面这段代码可以直接运行，输入是一句英文，输出是 GPT-2 在这句话上的 loss 与 PPL。注意运行前需安装 torch 与 transformers，首次运行会下载模型权重。

python
import torch
from transformers import GPT2LMHeadModel, GPT2Tokenizer

model = GPT2LMHeadModel.from_pretrained('gpt2')
tokenizer = GPT2Tokenizer.from_pretrained('gpt2')

text = "The quick brown fox jumps over the lazy dog."
inputs = tokenizer(text, return_tensors='pt')
with torch.no_grad():
    outputs = model(**inputs, labels=inputs['input_ids'])
loss = outputs.loss
ppl = torch.exp(loss)
print(f'Loss: {loss.item():.4f}, Perplexity: {ppl.item():.2f}')

运行后你会看到类似 Loss: 3.2xxx, Perplexity: 2x.xx 的输出（具体数值随模型版本略有差异）。这里有一个极易踩的坑：PPL 必须在同一 tokenizer 和同一数据集上比较才有意义。同一句话，用词表 5 万的 tokenizer 可能切成 12 个 token，用词表 3 万的 tokenizer 可能切成 15 个 token，每步预测的难度尺度完全不同，算出的 PPL 不可直接对比。

基准测试：MMLU、GSM8K、HumanEval

光看 PPL 不够，因为 PPL 回答不了“这个模型会不会做数学题、会不会写代码”。业界用基准测试（Benchmark）来横向对比模型能力，可以把它理解为给模型准备的一套标准化考卷：同一套题、同一套评分规则，不同模型考出来的分数才有可比性。常见的有三类代表：

  • MMLU：57 个学科的多选题，考知识广度，用准确率衡量。
  • GSM8K：小学数学应用题，考多步推理，看最终答案是否正确。
  • HumanEval：Python 函数补全，用 pass@k 衡量，即生成 k 个答案至少一个通过测试的概率。

设计评估方案时有两个隐蔽的陷阱。第一是数据污染：如果训练集混入了测试题，模型相当于提前背过答案，分数会虚高，这种分数在真实场景中毫无意义。第二是提示词敏感：few-shot 示例的数量、格式、甚至答案的书写风格都会显著影响结果，同一个模型换一种提示模板，GSM8K 分数可能相差好几个点。所以报告结果时必须写清楚评测配置：几 shot、什么模板、什么解码参数。结论：benchmark 分数不是模型能力的绝对真值，而是“特定配置下的测量值”。

下面是一个 GSM8K 评估的骨架代码。输入是测试集题目，输出是准确率。注意其中 generated 目前是占位符，需要替换成你自己的模型调用；评分逻辑是检查标准答案（#### 后面的数字）是否出现在生成文本中。

python
# 以 GSM8K 为例，用 few-shot 提示评估准确率（简化版）
from datasets import load_dataset

dataset = load_dataset('gsm8k', 'main', split='test[:20]')

def build_prompt(question):
    return f"Q: {question}\nA: Let's think step by step."

correct = 0
for ex in dataset:
    prompt = build_prompt(ex['question'])
    # 这里替换成你的模型调用，返回生成文本
    generated = "..."  # model.generate(prompt)
    # GSM8K 答案在 '####' 后面
    gold = ex['answer'].split('####')[-1].strip()
    if gold in generated:
        correct += 1

print(f'Accuracy: {correct / len(dataset):.2%}')

实际评测中，GSM8K 常用 8-shot，HumanEval 用 pass@1 或 pass@10。注意 gold in generated 这种字符串匹配是粗糙的近似，可能把“答案 42 出现在推理过程里但最终答错”的情况误判为正确，生产环境应做更严格的答案抽取。不要只看一个 benchmark 的分数就下结论，要结合知识、推理、代码等多个维度综合判断。

模型量化：GPTQ、AWQ、GGUF

模型太大跑不动？先理解量化的直觉：模型权重原本用 FP16 存储，每个数占 16 位；如果改成 INT4，每个数只占 4 位，理论上显存直接降到四分之一。这就像把高清照片压成缩略图——大部分场景下你根本看不出差别，但文件小了一大截。量化（Quantization）做的就是这件事：把 FP16 权重压成 INT8/INT4，显存减半甚至更多。主流方案有三条路线：

  • GPTQ：逐层量化，用校准数据最小化重构误差，适合 GPU 推理。
  • AWQ：激活感知权重量化，保护重要通道，精度通常比 GPTQ 略好。
  • GGUF：llama.cpp 的格式，支持 CPU/GPU 混合推理，适合本地部署。

量化不是免费的午餐：4-bit 量化通常损失 1~3 个点（具体幅度随模型与任务差异较大，待核实），但换来的显存和速度提升通常很划算。选择时先看硬件：GPU 用 GPTQ/AWQ，Mac/CPU 用 GGUF。下面这段代码演示用 auto-gptq 加载 4-bit 量化模型并生成一句话，输入是一个英文问题，输出是模型续写的文本。运行前需安装 auto-gptq 并有可用的 CUDA 环境。

python
# 用 auto-gptq 加载 4-bit 量化模型（需先安装 auto-gptq）
from transformers import AutoTokenizer
from auto_gptq import AutoGPTQForCausalLM

model_name = "TheBloke/Llama-2-7B-Chat-GPTQ"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoGPTQForCausalLM.from_quantized(
    model_name,
    device="cuda:0",
    use_safetensors=True,
    quantize_config=None
)

inputs = tokenizer("Explain quantization in one sentence.", return_tensors="pt").to("cuda:0")
out = model.generate(**inputs, max_new_tokens=50)
print(tokenizer.decode(out[0], skip_special_tokens=True))

如果要用 GGUF，可以用 llama-cpp-python，它不需要 GPU，在笔记本上就能跑。输入是一个问答提示，输出是模型续写的回答片段：

python
from llama_cpp import Llama

llm = Llama(model_path="./llama-2-7b-chat.Q4_K_M.gguf", n_ctx=2048)
out = llm("Q: What is quantization? A:", max_tokens=64)
print(out['choices'][0]['text'])

量化后一定要重新跑评估，确认精度下降在可接受范围内。一个实用的做法是：量化前后各跑一遍同一套 benchmark，把差值记录下来，作为是否上线的决策依据。

剪枝与知识蒸馏

除了量化，还有两条压缩路线：剪枝（Pruning）和知识蒸馏（Knowledge Distillation）。先给直觉：剪枝像给一棵树修剪枝叶，去掉对结果贡献小的部分；蒸馏像让一个新手（学生模型）跟着一位老专家（教师模型）学习，新手不仅学专家最终给出的答案，还学专家在犹豫时对各选项的偏好程度。

剪枝是去掉不重要的权重或结构。非结构化剪枝把小的权重置零，但稀疏矩阵在普通硬件上不一定加速，因为硬件仍然按稠密矩阵的方式计算；结构化剪枝直接删掉整个注意力头或 FFN 通道，能真正减小模型体积和计算量。剪枝后通常要微调恢复精度，否则性能会明显下降。

知识蒸馏是让小的“学生模型”模仿大的“教师模型”。核心是让学生输出的概率分布（软标签）接近教师，而不是只拟合硬标签。为什么软标签更有信息量？举个例子：一张猫的图片，硬标签只说“这是猫”，而教师的软标签可能说“80% 是猫、15% 是狗、5% 是狐狸”，这 15% 的狗就告诉学生“猫和狗长得有点像”，这就是所谓的暗知识。损失函数通常是：L = α * CE(student, hard_label) + (1-α) * KL(student_soft, teacher_soft)，其中 soft 是带温度 T 的 softmax。温度 T 越高，概率分布越平滑，暗知识越明显。

下面这段代码可以直接运行，输入是随机生成的 student/teacher logits 和标签，输出是蒸馏损失值。它演示了软标签 KL 损失与硬标签交叉熵的组合方式，注意 KL 项乘了 T*T 来补偿温度缩放带来的梯度尺度变化。

python
import torch
import torch.nn.functional as F

def distillation_loss(student_logits, teacher_logits, labels, T=2.0, alpha=0.7):
    # 软标签损失：KL 散度，注意 log_softmax 和 softmax 的配合
    soft_student = F.log_softmax(student_logits / T, dim=-1)
    soft_teacher = F.softmax(teacher_logits / T, dim=-1)
    kd_loss = F.kl_div(soft_student, soft_teacher, reduction='batchmean') * (T * T)
    # 硬标签损失
    ce_loss = F.cross_entropy(student_logits, labels)
    return alpha * ce_loss + (1 - alpha) * kd_loss

# 假设 batch_size=4, num_classes=10
student_logits = torch.randn(4, 10)
teacher_logits = torch.randn(4, 10)
labels = torch.tensor([1, 2, 3, 4])
loss = distillation_loss(student_logits, teacher_logits, labels)
print(f'Distillation loss: {loss.item():.4f}')

实践中，蒸馏常和量化、剪枝组合使用：先蒸馏得到小模型，再量化部署。温度 T 一般取 2~5，alpha 取 0.5~0.9，需要根据任务调。注意 alpha 的语义在不同实现中可能相反（有的代码用 alpha 加权蒸馏项），复现论文时要先确认定义，避免调参方向搞反。

常见误区

  • 错误理解：困惑度越低模型效果一定越好。→ 后果：可能选出一个 PPL 很低但在下游任务上表现平平的模型，甚至因为 tokenizer 不同而做出错误对比。→ 正确做法：PPL 只作为语言建模能力的参考，必须结合任务准确率和人工评估；且只在同一 tokenizer、同一数据集上比较 PPL。
  • 错误理解：量化一定会大幅掉点，所以不敢用。→ 后果：白白放弃显存和速度收益，部署成本居高不下。→ 正确做法：4-bit 量化在多数任务上只损失 1~3 个点（待核实具体幅度），配合 AWQ/GPTQ 校准可以做到接近无损；量化后跑一遍同一套 benchmark 量化前后对比，用数据决定是否上线。
  • 错误理解：知识蒸馏只是让学生拟合教师的硬标签。→ 后果：丢掉了软标签里的暗知识，学生模型效果明显不如预期，调参也找不到方向。→ 正确做法：核心是软标签（概率分布）提供的暗知识，用带温度 T 的 softmax 计算 KL 损失，并合理调节 T 与 alpha。

自测

为什么不同 tokenizer 的模型困惑度不能直接比较？请结合 PPL 的计算公式说明推理过程。

答案：PPL = exp(交叉熵损失)，而交叉熵是逐 token 计算的负对数概率平均。推理链条是：不同 tokenizer 把同一段文本切成的 token 数量和粒度不同 → 每步预测的难度和损失尺度不同 → 交叉熵的数值基准不同 → 取指数后的 PPL 自然不可比。例如同一句话被切成 12 个 token 和 15 个 token，模型面对的预测任务本身就不同，所以只有在同一 tokenizer、同一数据集上算出的 PPL 才有比较意义。

GPTQ、AWQ、GGUF 三种量化方案分别适合什么场景？如果团队要在 Mac 笔记本上做本地演示，应该选哪个，为什么？

答案：推理过程：先看三者的定位——GPTQ 是逐层量化、用校准数据最小化重构误差，面向 GPU 推理；AWQ 是激活感知量化、保护重要通道，同样面向 GPU 且精度通常略优；GGUF 是 llama.cpp 的格式，支持 CPU/GPU 混合推理。再对照场景：Mac 笔记本没有 NVIDIA GPU，无法高效运行 GPTQ/AWQ 的 CUDA 内核，而 GGUF 通过 llama.cpp 可以在 CPU 上推理。所以本地演示应选 GGUF，代价是推理速度和大模型支持能力受硬件限制。

在知识蒸馏中，软标签相比硬标签多提供了什么信息？温度 T 起什么作用？如果把 T 设为 1 会怎样？

答案：推理过程：硬标签只告诉学生“正确答案是哪个”，软标签给出教师对每个类别的概率分布，例如“80% 猫、15% 狗、5% 狐狸”，其中的非最大概率项揭示了类别之间的相似性，这就是暗知识。温度 T 作用在 softmax 上：T 越大分布越平滑，暗知识越明显；T 越小分布越尖锐。若 T=1，softmax 退化为普通形式，分布接近 one-hot，软标签携带的暗知识大幅减少，蒸馏退化为近似硬标签训练，失去蒸馏的核心优势。因此实践中 T 一般取 2~5。

动手练习（带参考方案）

任务：使用 HuggingFace 的 transformers 加载一个小型因果语言模型（如 distilgpt2），在 wikitext-2 测试集上计算困惑度；然后使用 bitsandbytes 进行 8-bit 量化加载，再次计算困惑度，对比两者的 PPL 和显存占用。验收标准：能打印出 FP32 与 8-bit 两个 PPL 数值，并说明 8-bit 的 PPL 上升幅度是否在可接受范围内。

参考方案：

python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
from datasets import load_dataset

model_name = 'distilgpt2'
tokenizer = AutoTokenizer.from_pretrained(model_name)

# 加载 wikitext-2 测试集
dataset = load_dataset('wikitext', 'wikitext-2-raw-v1', split='test')
text = '\n\n'.join(dataset['text'])
encodings = tokenizer(text, return_tensors='pt')
max_length = 1024
stride = 512

# 计算 PPL 的函数
def compute_ppl(model, encodings):
    model.eval()
    nlls = []
    for i in range(0, encodings.input_ids.size(1), stride):
        begin_loc = max(i + stride - max_length, 0)
        end_loc = min(i + stride, encodings.input_ids.size(1))
        trg_len = end_loc - i
        input_ids = encodings.input_ids[:, begin_loc:end_loc]
        target_ids = input_ids.clone()
        target_ids[:, :-trg_len] = -100
        with torch.no_grad():
            outputs = model(input_ids, labels=target_ids)
            neg_log_likelihood = outputs.loss * trg_len
        nlls.append(neg_log_likelihood)
    ppl = torch.exp(torch.stack(nlls).sum() / end_loc)
    return ppl.item()

# FP32 模型
model_fp32 = AutoModelForCausalLM.from_pretrained(model_name)
ppl_fp32 = compute_ppl(model_fp32, encodings)
print(f'FP32 PPL: {ppl_fp32:.2f}')

# 8-bit 量化模型
model_8bit = AutoModelForCausalLM.from_pretrained(model_name, load_in_8bit=True, device_map='auto')
ppl_8bit = compute_ppl(model_8bit, encodings)
print(f'8-bit PPL: {ppl_8bit:.2f}')

# 显存对比（需在 GPU 上运行）
if torch.cuda.is_available():
    print(f'FP32 显存: {torch.cuda.max_memory_allocated() / 1024**2:.1f} MB')

预期结果：8-bit 量化的 PPL 略高于 FP32（通常差距小于 0.5，具体随模型与数据而异，待核实），但显存占用减少约一半。注意：bitsandbytes 需要 GPU 环境，CPU 上可用 GGUF 替代；显存对比部分需在 GPU 上运行才有意义。
