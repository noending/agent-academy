模型评估与优化

本章目标：学会设计评估方案，并进行量化、剪枝与蒸馏优化

评估指标：从困惑度到人工评估

模型训完了，怎么知道它好不好？最直接的指标是困惑度（Perplexity, PPL）。它衡量模型对文本的“惊讶程度”：PPL 越低，说明模型越能预测下一个词。数学上，PPL 是交叉熵损失的指数：PPL = exp(loss)。比如 loss=2.0，PPL≈7.39，可以粗略理解为模型在每一步平均在 7.39 个词里犹豫。

但 PPL 只反映语言建模能力，不直接对应任务效果。所以还需要准确率（Accuracy），比如分类任务、选择题、代码通过率等。对于生成式任务，准确率往往需要人工或模型辅助判断。

最后是人工评估：让标注员对流畅性、相关性、事实性、安全性打分。人工评估成本高，但最贴近真实体验。实践中常采用“自动指标粗筛 + 人工精评”的组合。

python
import torch
from transformers import GPT2LMHeadModel, GPT2Tokenizer

model = GPT2LMHeadModel.from_pretrained('gpt2')
tokenizer = GPT2Tokenizer.from_pretrained('gpt2')

text = "The quick brown fox jumps over the lazy dog."
inputs = tokenizer(text, return_tensors='pt')
with torch.no_grad():
    outputs = model(**inputs, labels=inputs['input_ids'])
loss = outputs.loss
ppl = torch.exp(loss)
print(f'Loss: {loss.item():.4f}, Perplexity: {ppl.item():.2f}')

运行这段代码，你会得到 GPT-2 在这句话上的困惑度。注意：PPL 必须在同一 tokenizer 和同一数据集上比较才有意义，不同分词器算出的 PPL 不可直接对比。

基准测试：MMLU、GSM8K、HumanEval

光看 PPL 不够，业界用基准测试（Benchmark）来横向对比模型能力。常见的有：

  • MMLU：57 个学科的多选题，考知识广度，用准确率衡量。
  • GSM8K：小学数学应用题，考多步推理，看最终答案是否正确。
  • HumanEval：Python 函数补全，用 pass@k 衡量，即生成 k 个答案至少一个通过测试的概率。

设计评估方案时要注意：数据污染（训练集混入测试题）会让分数虚高；提示词敏感（few-shot 示例数量、格式）会显著影响结果。所以报告结果时要写清楚评测配置。

python
# 以 GSM8K 为例，用 few-shot 提示评估准确率（简化版）
from datasets import load_dataset

dataset = load_dataset('gsm8k', 'main', split='test[:20]')

def build_prompt(question):
    return f"Q: {question}\nA: Let's think step by step."

correct = 0
for ex in dataset:
    prompt = build_prompt(ex['question'])
    # 这里替换成你的模型调用，返回生成文本
    generated = "..."  # model.generate(prompt)
    # GSM8K 答案在 '####' 后面
    gold = ex['answer'].split('####')[-1].strip()
    if gold in generated:
        correct += 1

print(f'Accuracy: {correct / len(dataset):.2%}')

实际评测中，GSM8K 常用 8-shot，HumanEval 用 pass@1 或 pass@10。不要只看一个 benchmark 的分数就下结论，要结合多个维度。

模型量化：GPTQ、AWQ、GGUF

模型太大跑不动？量化（Quantization）把 FP16 权重压成 INT8/INT4，显存直接减半甚至更多。主流方案：

  • GPTQ：逐层量化，用校准数据最小化重构误差，适合 GPU 推理。
  • AWQ：激活感知权重量化，保护重要通道，精度通常比 GPTQ 略好。
  • GGUF：llama.cpp 的格式，支持 CPU/GPU 混合推理，适合本地部署。

量化不是免费的午餐：4-bit 量化通常损失 1~3 个点，但换来的显存和速度提升很划算。选择时先看硬件：GPU 用 GPTQ/AWQ，Mac/CPU 用 GGUF。

python
# 用 auto-gptq 加载 4-bit 量化模型（需先安装 auto-gptq）
from transformers import AutoTokenizer
from auto_gptq import AutoGPTQForCausalLM

model_name = "TheBloke/Llama-2-7B-Chat-GPTQ"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoGPTQForCausalLM.from_quantized(
    model_name,
    device="cuda:0",
    use_safetensors=True,
    quantize_config=None
)

inputs = tokenizer("Explain quantization in one sentence.", return_tensors="pt").to("cuda:0")
out = model.generate(**inputs, max_new_tokens=50)
print(tokenizer.decode(out[0], skip_special_tokens=True))

如果要用 GGUF，可以用 llama-cpp-python：

python
from llama_cpp import Llama

llm = Llama(model_path="./llama-2-7b-chat.Q4_K_M.gguf", n_ctx=2048)
out = llm("Q: What is quantization? A:", max_tokens=64)
print(out['choices'][0]['text'])

量化后一定要重新跑评估，确认精度下降在可接受范围内。

剪枝与知识蒸馏

除了量化，还有两条压缩路线：剪枝（Pruning）和知识蒸馏（Knowledge Distillation）。

剪枝是去掉不重要的权重或结构。非结构化剪枝把小的权重置零，但稀疏矩阵在普通硬件上不一定加速；结构化剪枝直接删掉整个注意力头或 FFN 通道，能真正减小模型。剪枝后通常要微调恢复精度。

知识蒸馏是让小的“学生模型”模仿大的“教师模型”。核心是让学生输出的概率分布（软标签）接近教师，而不是只拟合硬标签。损失函数通常是：L = α * CE(student, hard_label) + (1-α) * KL(student_soft, teacher_soft)，其中 soft 是带温度 T 的 softmax。

python
import torch
import torch.nn.functional as F

def distillation_loss(student_logits, teacher_logits, labels, T=2.0, alpha=0.7):
    # 软标签损失：KL 散度，注意 log_softmax 和 softmax 的配合
    soft_student = F.log_softmax(student_logits / T, dim=-1)
    soft_teacher = F.softmax(teacher_logits / T, dim=-1)
    kd_loss = F.kl_div(soft_student, soft_teacher, reduction='batchmean') * (T * T)
    # 硬标签损失
    ce_loss = F.cross_entropy(student_logits, labels)
    return alpha * ce_loss + (1 - alpha) * kd_loss

# 假设 batch_size=4, num_classes=10
student_logits = torch.randn(4, 10)
teacher_logits = torch.randn(4, 10)
labels = torch.tensor([1, 2, 3, 4])
loss = distillation_loss(student_logits, teacher_logits, labels)
print(f'Distillation loss: {loss.item():.4f}')

实践中，蒸馏常和量化、剪枝组合使用：先蒸馏得到小模型，再量化部署。温度 T 一般取 2~5，alpha 取 0.5~0.9，需要根据任务调。

常见误区

  • 困惑度越低模型效果一定越好——PPL 只反映语言建模能力，不直接对应下游任务准确率，且不同 tokenizer 的 PPL 不可比。
  • 量化一定会大幅掉点——4-bit 量化在多数任务上只损失 1~3 个点，配合 AWQ/GPTQ 校准可以做到几乎无损。
  • 知识蒸馏只是让学生拟合教师的硬标签——核心是软标签（概率分布）提供的暗知识，温度 T 和 alpha 的调节很关键。

自测

为什么不同 tokenizer 的模型困惑度不能直接比较？

答案：因为困惑度是交叉熵的指数，而交叉熵基于 token 级别的概率。不同 tokenizer 把同一段文本切成的 token 数量和粒度不同，导致每步预测的难度和损失尺度不同，因此 PPL 不可直接对比。

GPTQ、AWQ、GGUF 三种量化方案分别适合什么场景？

答案：GPTQ 适合 GPU 推理，精度较好；AWQ 也是 GPU 推理，激活感知，通常精度略优于 GPTQ；GGUF 适合 CPU/GPU 混合或本地部署（llama.cpp），对硬件要求低。

任务：使用 HuggingFace 的 transformers 加载一个小型因果语言模型（如 distilgpt2），在 wikitext-2 测试集上计算困惑度；然后使用 bitsandbytes 进行 8-bit 量化加载，再次计算困惑度，对比两者的 PPL 和显存占用。

参考方案：

参考代码： ```python import torch from transformers import AutoModelForCausalLM, AutoTokenizer from datasets import load_dataset model_name = 'distilgpt2' tokenizer = AutoTokenizer.from_pretrained(model_name) # 加载 wikitext-2 测试集 dataset = load_dataset('wikitext', 'wikitext-2-raw-v1', split='test') text = '\n\n'.join(dataset['text']) encodings = tokenizer(text, return_tensors='pt') max_length = 1024 stride = 512 # 计算 PPL 的函数 def compute_ppl(model, encodings): model.eval() nlls = [] for i in range(0, encodings.input_ids.size(1), stride): begin_loc = max(i + stride - max_length, 0) end_loc = min(i + stride, encodings.input_ids.size(1)) trg_len = end_loc - i input_ids = encodings.input_ids[:, begin_loc:end_loc] target_ids = input_ids.clone() target_ids[:, :-trg_len] = -100 with torch.no_grad(): outputs = model(input_ids, labels=target_ids) neg_log_likelihood = outputs.loss * trg_len nlls.append(neg_log_likelihood) ppl = torch.exp(torch.stack(nlls).sum() / end_loc) return ppl.item() # FP32 模型 model_fp32 = AutoModelForCausalLM.from_pretrained(model_name) ppl_fp32 = compute_ppl(model_fp32, encodings) print(f'FP32 PPL: {ppl_fp32:.2f}') # 8-bit 量化模型 model_8bit = AutoModelForCausalLM.from_pretrained(model_name, load_in_8bit=True, device_map='auto') ppl_8bit = compute_ppl(model_8bit, encodings) print(f'8-bit PPL: {ppl_8bit:.2f}') # 显存对比（需在 GPU 上运行） if torch.cuda.is_available(): print(f'FP32 显存: {torch.cuda.max_memory_allocated() / 1024**2:.1f} MB') ``` 预期结果：8-bit 量化的 PPL 略高于 FP32（通常差距 <0.5），但显存占用减少约一半。注意：bitsandbytes 需要 GPU 环境，CPU 上可用 GGUF 替代。
