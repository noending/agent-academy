2.1 认识 DeepSeek API

DeepSeek 提供 OpenAI 兼容的 HTTP 接口：你用官方 openai SDK，只需把 base_url 指向 DeepSeek。 这件小事的意义深远——引擎可以即插即换，这正是第 7 章 Harness 思维的伏笔。

deepseek-chatdeepseek-reasoner
定位通用对话 + 工具调用（V3 系列引擎，非思考模式）深度思考模式：先输出长思维链再作答
思维链无有，通过 reasoning_content 字段返回
适合Agent 主循环的绝大多数步骤：快、便宜、可并行复杂的任务规划、疑难推理、反思总结
延迟低较高（要"想"很久）

模型名与能力更新很快（例如思考模型对 Function Calling 的支持在不同版本间有变化），以 官方 API 文档 为准。本站的方法论不随版本失效。

2.4 组装：90 行以内的极简 Agent

下面是完整、可直接运行的代码。逐行读懂它，你就读懂了所有 Agent 框架的心脏：

python · minimal_agent.py 完整代码
"""minimal_agent.py —— 90 行以内的 DeepSeek 工具调用智能体"""
import json, os
from openai import OpenAI

client = OpenAI(api_key=os.environ["DEEPSEEK_API_KEY"],
                base_url="https://api.deepseek.com")
MODEL = "deepseek-chat"

# ── 1. 工具的真实实现（第 1 章说过：执行权永远在你手里）──────
def get_weather(city: str, date: str) -> dict:
    # 真实项目里这里调用天气 API；教学里返回固定值
    return {"city": city, "date": date, "weather": "小雨",
            "temp": "12~20°C", "advice": "建议带伞"}

def add_reminder(time: str, content: str) -> dict:
    return {"ok": True, "msg": f"已在 {time} 创建提醒：{content}"}

TOOL_IMPL = {"get_weather": get_weather, "add_reminder": add_reminder}

# ── 2. 工具声明（上一节写好的 TOOLS_SPEC，原样粘进来）────────
TOOLS_SPEC = [ ... ]   # 两个工具的 JSON Schema：从 2.3 节原样复制替换此占位，否则 NameError

# ── 3. 系统提示：给大脑立规矩 ─────────────────────────────
SYSTEM = ("你是一个严谨的生活助理。涉及实时信息必须调用工具查询，"
          "禁止编造。拿到结果后用简洁的中文回答。")

def run_agent(user_input: str, max_steps: int = 8) -> str:
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user", "content": user_input}]
    for _ in range(max_steps):                 # 保险丝：防止无限循环烧钱
        resp = client.chat.completions.create(
            model=MODEL, messages=messages, tools=TOOLS_SPEC)
        msg = resp.choices[0].message

        if not msg.tool_calls:                 # 模型不再要求工具 = 循环终止
            return msg.content

        messages.append(msg)                   # 关键！先把 assistant 消息放回数组
        for tc in msg.tool_calls:              # 可能有多个工具调用，逐个执行
            name = tc.function.name
            try:
                args = json.loads(tc.function.arguments or "{}")
                result = TOOL_IMPL[name](**args)
            except Exception as e:             # 工具报错也作为"观察"回传，
                result = {"error": f"{type(e).__name__}: {e}"}  # 让模型自己想办法
            messages.append({
                "role": "tool",
                "tool_call_id": tc.id,         # 与请求对账的凭证
                "content": json.dumps(result, ensure_ascii=False),
            })
    return "已达最大步数，任务未完成。"

if __name__ == "__main__":
    print(run_agent("明天北京天气怎么样？我想晨跑，怕淋雨。"))

运行后 Agent 内部发生的事（正是第 1 章模拟器里看到的那一幕）：

text · 运行轨迹
第 1 轮: 模型要求 get_weather(city=北京, date=明天)
        → 执行 → 回填 {"weather": "小雨", ...}
第 2 轮: 模型要求 add_reminder(time=明早 07:00, content=带伞)
        → 执行 → 回填 {"ok": true}
第 3 轮: 模型不再要求工具，返回最终回答
"明天北京有小雨，气温 12~20°C，不建议晨跑，已为你设置带伞提醒 ☂️"
新手必踩的五个坑（每个都值一次 debug 半小时）

① 忘记先 messages.append(msg)：直接回填 tool 结果会得到 400 错误——API 要求 tool 消息前必须有带对应 tool_calls 的 assistant 消息。
② 忘记 arguments 是字符串：要 json.loads 之后才能 **args。
③ 工具抛异常直接崩掉循环：应该把异常打包成 {"error": ...} 回传，模型常常能自行纠正（比如换个参数重试）。
④ 没有最大步数保险丝：模型陷入循环时，账单会替你记住这个疏忽。
⑤ 中文乱码：json.dumps 记得 ensure_ascii=False。

2.5 让 Agent 更可靠的五个细节

  1. 工具描述 = 给模型的使用说明书

    模型选工具、填参数全靠 description。五条原则：说清「做什么」；说清「什么时候该用（以及不该用）」；参数描述给示例值；风格统一；宁缺毋滥——不注册当前任务用不到的工具。

  2. 结构化输出

    需要机器可读的结果时用 response_format={"type": "json_object"}（JSON 模式），并在提示词里包含 "json" 字样。比在自由文本里猜格式可靠得多。

  3. 温度与终止

    Agent 主循环建议低温度（0~0.3）——你要的是稳定执行，不是文采。

  4. 失败也是信息

    把工具错误、达到步数上限等情况显式告诉模型，给它自我修复的机会；同时把这些事件记入日志（第 5 章的可观测性）。

  5. 控制上下文体积

    每轮循环都把全部历史发回去。工具结果很长时先做裁剪（比如只保留 JSON 的关键字段），否则 token 费用随步数平方级膨胀——省钱的机制见第 7 章的上下文缓存。

2.6 流式输出：打字机效果的原理

你在各种 AI 产品里看到的「逐字吐出」，不是模型在逐字思考，而是传输层把完整回复切成小段（delta）推给你——Server-Sent Events。加上 stream=True 即可：

python · stream_demo.py
stream = client.chat.completions.create(
    model=MODEL,
    messages=[{"role": "user", "content": "写一首关于智能体的七言绝句"}],
    stream=True,                          # 关键开关
)

full = ""
for chunk in stream:
    delta = chunk.choices[0].delta        # 每个片段只带增量内容
    if delta.content:
        print(delta.content, end="", flush=True)   # 打字机效果
        full += delta.content
print()
两个工程细节

① 流式模式下工具调用同样分片到达（delta.tool_calls），需要按 index 把 id、函数名、arguments 碎片拼回完整调用——第 7 章的 Harness 会统一封装这件事；现在先用非流式把核心逻辑学扎实，流式只是传输优化，不改变 Agent Loop 的语义。
② 想在流式里拿到 token 用量，传 stream_options={"include_usage": True}，最后一个 chunk 会携带 usage。

2.7 网络会失败：超时、重试与指数退避

真实世界里的 API 调用会碰到三种失败：超时（网络抖动）、429 限流（请求太快）、5xx（服务端故障）。生产级代码必须处理它们，标准做法是指数退避重试：

python · retry.py —— 十行防御
import time, random
from openai import APITimeoutError, APIConnectionError, RateLimitError

def call_llm_with_retry(client, max_retries: int = 3, **kwargs):
    """只对无副作用的 LLM 调用使用；带副作用的工具执行不要盲目重试"""
    for attempt in range(max_retries):
        try:
            return client.chat.completions.create(**kwargs)
        except RateLimitError:                    # 429：等待后重试
            wait = min(2 ** attempt + random.random(), 30)  # 指数退避 + 随机抖动
            time.sleep(wait)
        except (APITimeoutError, APIConnectionError):
            if attempt == max_retries - 1:
                raise                             # 重试耗尽，向上抛出
            time.sleep(2 ** attempt)
    raise RuntimeError(f"重试 {max_retries} 次后仍失败")

# 用法：把原来直接调 client.chat.completions.create(...) 的地方换成
# call_llm_with_retry(client, model=MODEL, messages=messages, tools=TOOLS_SPEC)
重试的边界：幂等性

「Chat Completions 请求」没有副作用，失败了重试毫无风险；但「工具执行」可能有副作用——给 add_reminder 的调用重试一次，可能创建两条提醒。传输层重试只包住 API 调用，永远不要包住工具执行；工具自身的失败交给模型在下一轮循环里处理（把错误作为观察回传），那是「任务层韧性」，第 5 章的反思机制会展开。

点击展开：同构的 JavaScript 实现
javascript · minimal-agent.mjs
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.DEEPSEEK_API_KEY,
  baseURL: "https://api.deepseek.com",
});
const MODEL = "deepseek-chat";

const TOOL_IMPL = {
  get_weather: ({ city, date }) =>
    ({ city, date, weather: "小雨", temp: "12~20°C" }),
  add_reminder: ({ time, content }) =>
    ({ ok: true, msg: `已在 ${time} 创建提醒：${content}` }),
};
// TOOLS_SPEC 与 Python 版完全相同（JSON Schema 是跨语言标准），此处省略

export async function runAgent(userInput, maxSteps = 8) {
  const messages = [
    { role: "system", content: "你是一个严谨的生活助理，实时信息必须查工具。" },
    { role: "user", content: userInput },
  ];
  for (let i = 0; i < maxSteps; i++) {
    const resp = await client.chat.completions.create({
      model: MODEL, messages, tools: TOOLS_SPEC,
    });
    const msg = resp.choices[0].message;
    if (!msg.tool_calls) return msg.content;
    messages.push(msg);
    for (const tc of msg.tool_calls) {
      let result;
      try {
        result = TOOL_IMPL[tc.function.name](JSON.parse(tc.function.arguments || "{}"));
      } catch (e) {
        result = { error: `${e.name}: ${e.message}` };
      }
      messages.push({ role: "tool", tool_call_id: tc.id, content: JSON.stringify(result) });
    }
  }
  return "已达最大步数";
}

    在 run_agent 的每一轮循环里打印当轮的 token 用量（resp.usage.prompt_tokens / completion_tokens），观察它如何随步数增长。

点击展开：练习 1–5 参考答案与要点

练习 1（get_time 工具）：无参数工具的 schema 里 properties 留空对象即可。要点在于体会：模型看到工具描述后会自己决定何时调用，你不需要写任何判断逻辑。

练习 2（安全的计算器）：绝不要对模型生成的字符串用 eval（那是把提示注入直接变成代码执行）。用 ast 白名单：

python · calculate 参考实现
import ast, operator

SAFE_OPS = {ast.Add: operator.add, ast.Sub: operator.sub,
            ast.Mult: operator.mul, ast.Div: operator.truediv,
            ast.Pow: operator.pow}

def calculate(expr: str) -> dict:
    def ev(node):
        if isinstance(node, ast.Constant) and isinstance(node.value, (int, float)):
            return node.value
        if isinstance(node, ast.BinOp) and type(node.op) in SAFE_OPS:
            return SAFE_OPS[type(node.op)](ev(node.left), ev(node.right))
        raise ValueError(f"不支持的表达式元素: {ast.dump(node)[:50]}")
    return {"expr": expr, "result": ev(ast.parse(expr, mode="eval").body)}

练习 3（max_steps=1）：观察到的应是：第一轮返回 tool_calls、工具执行完，循环就结束了——最终输出是「已达最大步数」。教训：步数预算不是越紧越好，它是「成本上限」与「任务完成率」之间的显式权衡，生产系统要按任务难度分配预算。

练习 4（空工具问天气）：模型要么礼貌拒答，要么（更常见）语气笃定地编一个。这印证了第 1 章实验里的幻觉机制：没有 Observation 锚点时，模型只能靠训练记忆作答。

练习 5（token 统计）：参考实现（放进循环里）：

自测

回填工具结果时，tool_call_id 的作用是什么？什么情况下它会变得极其重要？

答案：它是工具结果与请求的对账凭证。当模型一次返回多个 tool_calls（并行工具调用）时，你的代码会执行多个工具、产生多个结果，API 靠 tool_call_id 把每条 role=tool 消息对应回正确的调用。对不上会直接 400。

为什么必须先把 assistant 消息（含 tool_calls）append 进数组，再回填 tool 结果？

答案：因为 OpenAI 兼容 API 对消息序列有硬约束：每条 role=tool 消息的前面，必须紧邻着一条包含对应 tool_calls 的 assistant 消息。语义上也合理——"模型请求调用 → 世界给出结果"必须成对出现，否则对话历史在逻辑上是断裂的。

什么任务适合 deepseek-chat，什么任务值得换 deepseek-reasoner？

答案：主循环里"看历史 → 选工具 → 填参数"这类高频、模式化的决策用 deepseek-chat：快、便宜、工具调用稳定。一次性的重决策——复杂任务拆解规划、多步推理校验、失败后的反思——值得升级 reasoner，用高延迟换推理质量。成熟的 harness 常常两者混用（第 7 章）。
