LLM基础与生态

本章目标：理解LLM核心概念、发展历程与主流模型架构

LLM是什么从概率预测到通用生成→发展历程规模跃迁推动能力涌现→主流架构Transformer解码器成主流→模型生态开源闭源分层并存→选型落地按场景匹配模型与成本
先懂原理与演进，再看架构与生态，最终落到模型选型。

1.1 什么是大语言模型：从“接龙”到通用智能

你可以把大语言模型（LLM）想象成一个超级“文字接龙”高手：给它一段上文，它预测下一个最可能出现的词。这个直觉非常重要，因为LLM 的一切能力，都建立在对下一个 token 的预测之上。但神奇的是，当这个“接龙”游戏玩到千亿参数、万亿 token 的规模时，模型就涌现出了生成、理解、推理三大核心能力。换句话说，接龙本身很简单，难的是在足够大的规模上把接龙做到极致，从而“逼”出更高层次的能力。

具体来看这三大能力：生成是写文章、写代码、翻译、总结，本质是条件概率建模 P(下一个词 | 上文)；理解是能回答“这段话在说什么”“这句话是正面还是负面”，靠的是预训练中学到的语义表示；推理是做数学题、逻辑推断、多步规划，这是规模带来的“涌现能力”（Emergent Ability）。举个直观的例子：给模型输入“今天天气真不错，我们去公园”，它预测下一个词是“散步”的概率远高于“股票”，这就是生成；而如果问它“这句话是正面还是负面”，它能输出“正面”，这就是理解。两者共享同一套参数，只是任务形式不同。

LLM 的底座是 Transformer 架构，核心是 自注意力机制（Self-Attention）：每个词都能“看到”序列中所有其他词，并动态决定关注谁。相比 RNN 必须按顺序一个词一个词处理，自注意力可以并行计算，这让训练超大模型成为可能。你可以这样类比：RNN 像传话游戏，信息要一个个传下去，传得越远越容易失真；自注意力像开圆桌会议，每个人都能直接听到所有人的发言，并自己判断谁的话最重要。

训练流程通常分两步：预训练（Pre-training） 在海量无标注文本上学习语言规律，然后通过指令微调（SFT）、RLHF 等对齐技术，让模型学会“听懂人话”。预训练像是让模型读完整个图书馆，学会语言的统计规律；对齐则像是给这个博学的“书呆子”做岗前培训，教它怎么礼貌、准确地回答用户问题。

下面是一个最小可运行的“下一个词预测”示例，用 Hugging Face 加载一个小模型，直观感受 LLM 的生成过程。输入是一句英文提示，预期输出是模型续写的一段文字（每次运行可能不同，因为开启了采样）：

python
from transformers import pipeline

# 加载一个小型因果语言模型（首次运行会自动下载）
generator = pipeline("text-generation", model="gpt2")

prompt = "Large language models are"
output = generator(prompt, max_new_tokens=20, do_sample=True, temperature=0.8)

print(output[0]["generated_text"])
# 示例输出：Large language models are becoming increasingly powerful...

运行后你会发现，模型只是根据上文“续写”，但续写质量已经能支撑很多实际应用。把 do_sample 改成 False，输出会变得确定（贪心解码），这正好说明“预测下一个词”是一个概率分布上的选择过程。

1.2 发展简史：从 Transformer 到 GPT、LLaMA、DeepSeek

LLM 的爆发不是一夜之间发生的，而是一条清晰的技术演进线。理解这条线，能帮你在选型和读论文时快速定位“这个技术解决的是哪个阶段的问题”。关键节点可以串成一条线：

  1. 2017 · Transformer：Google 发表《Attention Is All You Need》，提出完全基于自注意力的架构，抛弃 RNN，奠定一切基础。
  2. 2018 · BERT &amp; GPT-1：BERT 用 Encoder 做理解，GPT 用 Decoder 做生成，两条路线分道扬镳。
  3. 2020 · GPT-3：1750 亿参数，首次展示“少样本学习”（Few-shot Learning），提示词工程开始流行。
  4. 2022 · ChatGPT：引入 RLHF，把 GPT-3.5 变成对话助手，LLM 正式出圈。
  5. 2023 · LLaMA 系列：Meta 开源 LLaMA、Llama 2，引爆开源社区，让“自己微调大模型”成为可能。
  6. 2024-2025 · Qwen、DeepSeek：国产模型崛起，DeepSeek 用 MoE（混合专家）和高效训练把成本打下来，性能对标一线闭源模型。

这条线背后有两个趋势：一是模型越来越大、越来越强；二是开源与闭源的差距在快速缩小。对工程师来说，这意味着你既可以用 API 快速上线，也可以基于开源模型做私有化部署和深度定制。一个具体的对比：2018 年的 GPT-1 约 1.17 亿参数，而 2020 年的 GPT-3 达到 1750 亿参数，两年间规模增长了约 1500 倍——这种量变最终引发了能力上的质变。

下面用代码查看一个开源模型的架构配置，理解“Decoder-only”长什么样。输入是模型名称，预期输出是模型类型、隐藏层维度、层数、注意力头数等配置信息：

python
from transformers import AutoConfig

config = AutoConfig.from_pretrained("Qwen/Qwen2.5-0.5B")
print("模型类型:", config.model_type)          # qwen2
print("隐藏层维度:", config.hidden_size)      # 896
print("层数:", config.num_hidden_layers)      # 24
print("注意力头数:", config.num_attention_heads)  # 14
print("是否使用 MoE:", getattr(config, "num_experts", None))

通过配置你能看到：现代 LLM 基本都是 Decoder-only 结构，堆叠几十层 Transformer Block，每层包含自注意力和前馈网络。这里的 0.5B 表示约 5 亿参数，属于“小模型”，适合本地实验；而一线大模型动辄数百亿甚至上千亿参数，部署成本完全不同。

1.3 主流模型对比：GPT、Claude、LLaMA、Qwen 怎么选

选模型就像选车：没有最好的，只有最适合场景的。有人追求性能（跑车），有人追求性价比（家用车），有人必须能自己修（开源）。下面从几个维度对比主流模型：

模型开源/闭源特点典型场景
GPT 系列闭源综合能力最强，生态最成熟通用对话、Agent、复杂推理
Claude 系列闭源长上下文、安全性好、写作强长文档分析、代码、合规场景
LLaMA 系列开源社区生态庞大，微调资源多私有化部署、学术研究
Qwen 系列开源中文强、尺寸全、工具调用好中文应用、RAG、Agent

选择时问自己三个问题：1）数据能不能出内网？不能就选开源私有化。2）预算多少？闭源 API 按量付费，开源要算 GPU 成本。3）任务难度？简单任务小模型够用，复杂推理才上大模型。举个数字化的例子：如果每天有 10 万次简单问答请求，全部走顶级闭源大模型，成本可能是走小模型的数倍甚至更多；而其中真正需要复杂推理的请求可能只占 10%，这就是路由策略的价值所在。

实际工程中常用“路由”策略：简单请求走小模型，复杂请求走大模型，兼顾成本和效果。下面是一个极简的模型路由示例。输入是两条不同复杂度的问题，预期输出是它们分别被路由到不同的模型：

python
def route_model(query: str) -> str:
    """根据问题复杂度选择模型"""
    complex_keywords = ["推理", "证明", "代码", "分析", "为什么"]
    if any(kw in query for kw in complex_keywords) or len(query) > 100:
        return "gpt-4o"          # 复杂任务用大模型
    return "qwen2.5-7b"          # 简单任务用小模型

queries = ["今天天气怎么样", "请证明勾股定理并给出代码实现"]
for q in queries:
    print(f"问题: {q} -> 路由到: {route_model(q)}")

核心原则：不要用大炮打蚊子，也不要用弹弓打坦克。路由规则本身可以很简单（关键词、长度），也可以训练一个分类器来判断复杂度，这取决于你的业务规模。

1.4 典型应用场景：对话、编程、RAG、Agent

LLM 落地主要有四大场景，难度和工程复杂度依次递增。你可以把它们理解成一座四层楼：一楼是对话，二楼是编程，三楼是 RAG，四楼是 Agent，越往上对系统设计能力要求越高。

  • 对话（Chat）：最基础，客服、助手、陪聊。核心是提示词设计和多轮上下文管理。
  • 编程（Coding）：代码补全、生成、审查、单测。代表产品 GitHub Copilot、Cursor。
  • RAG（检索增强生成）：先检索知识库，再让 LLM 基于检索结果回答。解决“模型不知道私有知识”和“幻觉”问题，是企业落地最火的方案。
  • Agent（智能体）：让 LLM 自主规划、调用工具、多步执行。比如“帮我订机票并安排行程”，需要 LLM + 工具 + 记忆 + 规划。

这四者不是互斥的，而是层层叠加：对话是交互层，RAG 是知识层，Agent 是行动层，编程是垂直应用。一个成熟的 AI 产品往往是“Agent 调度 + RAG 供知识 + 对话做交互”。举个具体例子：用户问“我们公司上季度的报销政策是什么，帮我算一下这次出差能报多少”，Agent 负责拆解任务，RAG 负责从内部文档检索报销政策，对话层负责把结果组织成自然语言回复。

下面用 20 行代码实现一个最小 RAG 流程，感受“检索 + 生成”的威力。输入是一个关于 RAG 的问题，预期输出是拼好的提示词，其中包含了从知识库检索到的最相关的一条资料：

python
from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity

# 模拟知识库
knowledge = [
    "LLM 全链路包括预训练、微调、部署和运维。",
    "RAG 通过检索外部知识来增强生成，减少幻觉。",
    "Agent 能调用工具并自主规划任务步骤。",
]

# 1. 检索：用 TF-IDF 找最相关的知识
def retrieve(query, docs, top_k=1):
    vectorizer = TfidfVectorizer()
    tfidf = vectorizer.fit_transform(docs + [query])
    sims = cosine_similarity(tfidf[-1], tfidf[:-1])[0]
    top_idx = sims.argsort()[::-1][:top_k]
    return [docs[i] for i in top_idx]

# 2. 生成：把检索结果拼进提示词（这里用模拟输出）
query = "RAG 是怎么减少幻觉的？"
context = retrieve(query, knowledge)
prompt = f"基于以下资料回答问题：\n{context[0]}\n\n问题：{query}\n回答："
print(prompt)
# 实际项目中把 prompt 发给 LLM 即可

这个例子虽然简单，但已经包含了 RAG 的核心思想：先检索、后生成，让模型“有据可依”。对比一下：没有 RAG 时，模型可能凭空编造一个答案；有了 RAG，答案被约束在检索到的资料范围内，幻觉显著减少。后续章节会深入向量数据库、Embedding、重排序等工程细节。

常见误区

  • 误区：LLM 真的“理解”了语言。错误理解：把模型输出的流畅回答当成它具备人类意义上的理解和常识。会导致什么后果：过度信任模型输出，在医疗、法律、财务等高风险场景直接采信，放大幻觉带来的损失。正确做法：把 LLM 看作基于统计规律的概率预测器，对关键结论做事实核查，并用 RAG、工具调用、人工审核等手段兜底。
  • 误区：参数越大模型一定越好。错误理解：只看参数量做选型，认为 70B 一定优于 7B。会导致什么后果：为简单任务付出数倍推理成本，延迟变高、体验变差，预算浪费。正确做法：综合评估数据质量、训练方法、对齐策略和推理优化；小模型在特定领域微调后完全可以超过通用大模型，应按任务难度做路由。
  • 误区：开源模型等于免费。错误理解：以为下载开源权重就没有成本。会导致什么后果：低估 GPU 推理成本、部署运维和微调人力，规模大时总成本可能反而高于 API。正确做法：把授权费、GPU 成本、运维人力、微调投入一起算总账，再和闭源 API 的按量付费做对比。

自测

LLM 的三大核心能力是什么？它们和“预测下一个词”有什么关系？

答案：三大核心能力是生成、理解、推理。推理过程：首先，预训练的唯一训练目标就是给定上文预测下一个 token，所以模型的所有参数都是为这个目标优化的。生成是直接续写，最直接对应预测下一个词；理解不是单独训练出来的，而是在预测任务中为了降低损失，模型被迫学到词与词之间的语义关系，形成语义表示，所以理解是预测任务的“副产品”；推理则是在模型规模（参数、数据）增大后，从预测任务中涌现出的多步能力，它并非显式编程实现，而是规模带来的质变。因此三者共享同一套参数和同一个训练目标，只是表现层次不同。

什么场景下你会优先选择开源模型而不是闭源 API？请至少说出两个理由。

答案：推理过程：选型的核心是权衡数据、成本、定制和部署约束。第一，数据隐私和合规要求高、数据不能出内网时，只能私有化部署开源模型，闭源 API 无法满足。第二，需要深度定制时，比如领域微调、修改模型结构、控制推理过程，开源模型才允许你动权重和代码。第三，长期高频调用时，自建推理集群的边际成本可能低于按量付费的 API，规模越大越明显。第四，需要离线或边缘部署时，API 依赖网络，开源模型可以本地运行。所以只要命中数据不出内网或深度定制这两条中的任意一条，就应优先考虑开源模型。

RAG 为什么能减少幻觉？它和直接让 LLM 回答有什么区别？

答案：推理过程：幻觉的根源之一是模型参数里没有某些私有或时效性知识，它只能靠统计规律“编”一个看起来合理的答案。RAG 的做法是先把用户问题拿去检索外部知识库，找到相关文档片段，再把这些片段拼进提示词，让模型基于给定资料回答。区别在于：直接回答时，模型的输出只受参数记忆约束，没有依据就容易编造；RAG 回答时，答案被约束在检索到的资料范围内，相当于给模型提供了“开卷考试”的参考材料，从而显著降低编造空间。但要注意，RAG 不是万能的：如果检索没召回正确资料，或者模型不遵循资料，仍可能出错，所以还需要重排序、引用溯源等工程手段配合。

动手练习（带参考方案）

练习 · 搭建一个最小可运行的 LLM 调用脚本：使用 Hugging Face transformers 加载一个开源小模型（如…

任务：搭建一个最小可运行的 LLM 调用脚本：使用 Hugging Face transformers 加载一个开源小模型（如 Qwen/Qwen2.5-0.5B-Instruct 或 gpt2），实现一个命令行对话循环，支持多轮上下文，并打印每轮耗时。要求：1）能连续对话；2）输入 'exit' 退出；3）记录并输出每轮生成耗时。验收标准：运行脚本后能连续进行至少两轮问答，第二轮回答能体现对第一轮上下文的记忆，且每轮都打印出耗时。

参考方案：

python
import time
from transformers import pipeline

# 加载对话模型（首次运行会自动下载，约 1GB）
generator = pipeline(
    "text-generation",
    model="Qwen/Qwen2.5-0.5B-Instruct",
    device_map="auto"  # 有 GPU 自动用 GPU
)

messages = []
print("输入 exit 退出对话。")

while True:
    user_input = input("\n你: ").strip()
    if user_input.lower() == "exit":
        print("再见！")
        break

    messages.append({"role": "user", "content": user_input})

    start = time.time()
    output = generator(
        messages,
        max_new_tokens=256,
        do_sample=True,
        temperature=0.7,
        return_full_text=False
    )
    elapsed = time.time() - start

    reply = output[0]["generated_text"]
    messages.append({"role": "assistant", "content": reply})

    print(f"助手: {reply}")
    print(f"[本轮耗时: {elapsed:.2f}s]")

# 说明：
# 1. messages 列表保存多轮上下文，实现连续对话；
# 2. time.time() 记录生成前后时间差；
# 3. 生产环境需加入上下文长度截断、异常处理和流式输出。
