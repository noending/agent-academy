算力硬件测评

本章目标：掌握GPU等硬件选型与性能测评方法

需求拆解明确模型规模与算力缺口→硬件选型对比GPU显存带宽与成本→基准测评跑分与真实负载双验证→瓶颈定位找出算力或显存短板→选型定案按性价比锁定配置
从需求出发选硬件，用测评验证，再反馈修正选型。

硬件核心指标：算力、显存、带宽、功耗

选GPU就像选一辆跑长途的货车：马力（算力）决定它能跑多快，货厢大小（显存）决定一次能装多少货，装卸通道的宽度（带宽）决定货物进出有多快，而油耗（功耗）决定你长期养它的成本。只看马力大就下单，很可能买回一辆货厢装不下你的模型、或者通道太窄导致马力空转的车。理解这四个指标的相互关系，是硬件选型的第一步。

具体来看，算力（FLOPS）是每秒浮点运算次数，常见单位有TFLOPS（万亿次）和PFLOPS（千万亿次）。这里最容易踩的坑是精度：同一块卡在FP32、FP16、INT8下的算力数字差别很大，低精度算力通常更高，而LLM推理常用FP16或INT8，所以对比参数时必须先对齐精度口径。例如A100的FP32算力约19.5 TFLOPS，但它的Tensor Core在FP16下能提供远高于此的算力（具体数值随稀疏性与精度口径不同，待核实）。显存（VRAM）则是模型参数、中间激活值和KV Cache的落脚点，单位GB；显存不够，模型根本加载不了，会直接报OOM（Out of Memory），这是硬门槛而非性能问题。

真正决定推理速度的往往是显存带宽（Memory Bandwidth），单位GB/s。原因在于大模型推理是内存密集型任务：每生成一个token，都要把整个模型权重从显存读一遍到计算核心。以A100 80GB为例，其带宽约1555GB/s，而H100提升到约3.35TB/s，后者在同等条件下搬运权重的速度翻倍以上，这正是很多推理场景中H100吞吐显著更高的关键。最后是功耗（TDP），单位W，A100约400W、H100约700W；功耗越高，对电源、散热和机房PUE（能源使用效率）的要求越高，电费也越贵。选型时要把这四个指标放在一起权衡：先看显存能否装下模型，再看带宽是否匹配吞吐目标，最后用算力和功耗核算成本。

主流AI芯片：NVIDIA GPU、TPU、昇腾、寒武纪

如果把AI芯片比作手机操作系统，那么生态往往比单点参数更能决定你的开发体验。目前市场百花齐放，但各家在软件栈、适用场景和获取难度上差异很大，选型时不能只盯着纸面算力。

NVIDIA GPU是绝对主流，从消费级RTX 4090到数据中心级A100/H100都有覆盖。它的核心优势是CUDA生态成熟，几乎所有主流框架都优先支持，遇到问题也最容易找到资料和社区答案；缺点是在出口管制背景下高端卡获取困难、价格昂贵。Google TPU是专为TensorFlow/JAX设计的ASIC，通过Google Cloud使用，规模化训练成本低，但生态相对封闭，不适合通用计算。华为昇腾（Ascend）是国产代表，昇腾910用于训练、310用于推理，配套CANN软件栈和MindSpore框架，在国产化替代场景中应用广泛。寒武纪（Cambricon）的思元系列覆盖云端和边缘，生态相对较小但也在逐步完善。

选型建议可以归纳为一条决策链：如果追求生态和开发效率，优先NVIDIA；如果受限于供应链或需要国产化，考虑昇腾；如果已经在Google Cloud上，TPU是不错的选择。对于初学者，建议从NVIDIA GPU入手，因为学习资料最多、踩坑成本最低。需要提醒的是，国产芯片在特定场景下已有不错表现，生态也在持续完善，选型时应结合真实业务负载实测，而不是凭印象下结论。

测评工具：MLPerf、CUDA基准、实际模型推理测试

纸面参数就像汽车出厂标称的油耗，实际开起来受路况、驾驶习惯影响很大。GPU的真实性能同样受软件优化、散热、驱动版本等因素影响，所以必须实测。常用测评方法可以按「标准化程度」从高到低分为三类，各自解决不同层次的问题。

MLPerf是行业公认的AI基准测试，涵盖训练和推理，它定义了标准任务（如ResNet-50、BERT、GPT-3），各家厂商提交成绩，可比性强，适合企业采购参考；但跑一次成本高，不适合个人快速验证。CUDA基准如bandwidthTest测显存带宽、deviceQuery看设备信息、nvprof或nsight做性能分析，适合快速验证硬件是否正常。实际模型推理测试最贴近业务：用你自己的模型和数据集测吞吐量（tokens/s）和延迟（ms/token），可以借助transformers+torch写脚本，或使用vLLM、TensorRT-LLM等推理引擎。

下面是一个最小可运行的GPU推理测速脚本，使用Hugging Face的gpt2模型。它的输入是一段固定提示词，预期输出是生成50个token的耗时与吞吐量（tokens/s）。脚本先做3次预热以排除冷启动影响，再正式计时，这样测出的数字才可比。

python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
import time

model_name = "gpt2"  # 可换成更大模型

tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name).to("cuda")
model.eval()

input_text = "The future of AI is"
inputs = tokenizer(input_text, return_tensors="pt").to("cuda")

# 预热：排除冷启动与显存分配抖动
with torch.no_grad():
    for _ in range(3):
        _ = model.generate(**inputs, max_new_tokens=10)

# 正式测速
start = time.time()
with torch.no_grad():
    outputs = model.generate(**inputs, max_new_tokens=50)
end = time.time()

generated_tokens = outputs.shape[1] - inputs.input_ids.shape[1]
print(f"生成 {generated_tokens} 个token，耗时 {end-start:.2f} 秒")
print(f"吞吐量: {generated_tokens/(end-start):.2f} tokens/s")

运行前确保已安装torch和transformers，并且有可用的CUDA环境。这个脚本会输出生成速度和吞吐量，你可以调整max_new_tokens和模型大小来对比不同硬件。注意：单次测量波动较大，正式测评应多次运行取平均值。

实战：使用MLPerf或自定义脚本测评GPU

有了工具，还要有流程。一次可信的GPU测评，本质上是一次控制变量的实验：先确认硬件状态，再分层测试，最后与预期对比找差距。下面这套四步流程适合个人或小团队快速上手。

  1. 环境检查：运行nvidia-smi查看GPU型号、显存、功耗，运行nvcc --version查看CUDA版本，确保驱动与框架匹配。
  2. 带宽测试：编译并运行CUDA样例中的bandwidthTest，得到实际显存带宽，与官方标称值对比。
  3. 推理测试：用上一节的脚本，分别测试小模型（如gpt2）和大模型（如facebook/opt-1.3b），记录吞吐量和延迟。
  4. 对比分析：将结果与官方参数对比，看是否达到预期；如果差距大，检查散热、驱动、是否启用了Tensor Core等。

对于企业级测评，可以申请MLPerf推理基准的代码在本地运行。MLPerf推理有多个场景：SingleStream（单流低延迟）、MultiStream（多流）、Server（在线服务）和Offline（离线批处理），分别对应不同业务需求。例如Server场景模拟在线服务，关注延迟和吞吐的平衡；Offline场景则追求最大吞吐，适合离线批处理任务。

注意：测评时要控制变量，比如固定batch size、输入长度、精度（FP16/INT8），否则结果不可比。举个具体例子：同一块卡在batch size=1和batch size=32下，吞吐量可能相差数倍，若不注明batch size，两个数字放在一起比较毫无意义。另外，多次测量取平均值，避免冷启动影响，才能得到稳定可信的结论。

常见误区

  • 错误理解：显存越大越好，其他指标不重要。→ 后果：只盯着显存买卡，可能买到带宽不足的型号，大显存却喂不快数据，GPU利用率长期偏低，推理吞吐远低于预期。→ 正确做法：先确认显存能装下目标模型（含KV Cache），再重点评估带宽是否匹配吞吐目标，最后结合算力和功耗核算总成本。
  • 错误理解：FLOPS越高，模型推理就越快。→ 后果：按峰值算力选型，实际部署后发现速度不达预期，因为大模型推理是内存密集型任务，瓶颈常在带宽而非算力。→ 正确做法：把FLOPS当作理论峰值参考，用真实模型和真实输入长度做端到端实测，以tokens/s和ms/token作为最终判断依据。
  • 错误理解：国产芯片完全不能用，只能选NVIDIA。→ 后果：在供应链受限或国产化要求的场景下错失可行方案，或被迫接受更高成本。→ 正确做法：昇腾等国产芯片在特定场景下已有不错表现，生态也在完善，应结合真实业务负载实测，并综合考虑政策与供应链因素后再决策。

自测

为什么说对于大模型推理，显存带宽往往比算力更重要？请结合「每生成一个token要读一遍权重」这一事实说明。

答案：推理时每生成一个token，都需要把整个模型权重从显存搬运到计算核心一次。假设模型权重为W字节、带宽为B GB/s，那么仅搬运权重就需要约W/B秒，这段时间计算核心基本在等数据。如果带宽不足，算力再高也只能空转；反之带宽充足，计算核心才能被持续喂饱。因此推理吞吐的上限往往由带宽决定，算力只有在数据供给跟得上时才能发挥作用。这也解释了为什么H100相对A100的带宽提升（约1555GB/s到约3.35TB/s）对推理吞吐影响显著。

MLPerf基准测试主要用来衡量什么？它的SingleStream、Server、Offline场景分别对应什么业务需求？

答案：MLPerf用来衡量AI硬件和软件在训练和推理任务上的性能，通过定义标准任务（如ResNet-50、BERT、GPT-3）让不同厂商的成绩具备可比性。SingleStream模拟单条请求的低延迟场景，对应交互式单用户应用；Server模拟在线服务，关注在延迟约束下的吞吐与并发平衡；Offline模拟离线批处理，追求最大吞吐量。选择哪个场景的成绩作为参考，取决于你的业务是重延迟还是重吞吐。

做GPU推理测评时，为什么必须先预热并固定batch size、输入长度和精度？如果不这样做会怎样？

答案：预热是为了排除冷启动影响：首次运行包含显存分配、内核编译、缓存填充等一次性开销，直接计时会显著高估耗时。固定batch size、输入长度和精度则是控制变量：同一块卡在batch size=1和batch size=32下吞吐可能相差数倍，FP16与INT8的结果也不可比。如果不控制这些变量，测出的数字既不能横向对比不同硬件，也不能纵向对比同一硬件的不同配置，结论会失去意义。正确做法是固定这些参数、多次测量取平均值后再比较。

任务：使用Hugging Face的transformers库，在本地GPU上分别测试gpt2模型和facebook/opt-1.3b模型的推理速度，记录生成50个token的耗时和吞吐量（tokens/s），并对比两个模型的结果。验收标准：脚本能独立运行并打印两个模型的耗时与吞吐量，且gpt2的吞吐量应明显高于opt-1.3b。

参考方案：

python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer
import time

def benchmark(model_name, max_new_tokens=50):
    tokenizer = AutoTokenizer.from_pretrained(model_name)
    model = AutoModelForCausalLM.from_pretrained(model_name).to("cuda")
    model.eval()

    input_text = "The future of AI is"
    inputs = tokenizer(input_text, return_tensors="pt").to("cuda")

    # 预热：排除冷启动与显存分配抖动
    with torch.no_grad():
        for _ in range(3):
            _ = model.generate(**inputs, max_new_tokens=10)

    # 正式测速
    start = time.time()
    with torch.no_grad():
        outputs = model.generate(**inputs, max_new_tokens=max_new_tokens)
    end = time.time()

    generated_tokens = outputs.shape[1] - inputs.input_ids.shape[1]
    throughput = generated_tokens / (end - start)
    print(f"{model_name}: 生成 {generated_tokens} tokens, "
          f"耗时 {end-start:.2f}s, 吞吐量 {throughput:.2f} tokens/s")
    return throughput

if __name__ == "__main__":
    benchmark("gpt2")
    benchmark("facebook/opt-1.3b")

运行前确保已安装torch和transformers，并且CUDA可用。预期gpt2的吞吐量会明显高于opt-1.3b，因为模型更小、每步需要搬运的权重更少。你可以进一步调整max_new_tokens或batch size来观察变化，但对比时务必保持这些参数一致。
