第1章 · LLM基础与生态

本章目标：理解LLM核心概念、发展历程与主流模型架构

1.1 什么是大语言模型：从“接龙”到通用智能

你可以把大语言模型（LLM）想象成一个超级“文字接龙”高手：给它一段上文，它预测下一个最可能出现的词。但神奇的是，当这个“接龙”游戏玩到千亿参数、万亿token的规模时，模型就涌现出了生成、理解、推理三大核心能力。

  • 生成：写文章、写代码、翻译、总结，本质是条件概率建模 P(下一个词 | 上文)。
  • 理解：能回答“这段话在说什么”“这句话是正面还是负面”，靠的是预训练中学到的语义表示。
  • 推理：做数学题、逻辑推断、多步规划，这是规模带来的“涌现能力”（Emergent Ability）。

LLM 的底座是 Transformer 架构，核心是 自注意力机制（Self-Attention）：每个词都能“看到”序列中所有其他词，并动态决定关注谁。相比 RNN 的顺序处理，自注意力可以并行计算，这让训练超大模型成为可能。

训练流程通常分两步：预训练（Pre-training） 在海量无标注文本上学习语言规律，然后通过指令微调（SFT）、RLHF 等对齐技术，让模型学会“听懂人话”。

下面是一个最小可运行的“下一个词预测”示例，用 Hugging Face 加载一个小模型，直观感受 LLM 的生成过程：

from transformers import pipeline

# 加载一个小型因果语言模型（首次运行会自动下载）
generator = pipeline("text-generation", model="gpt2")

prompt = "Large language models are"
output = generator(prompt, max_new_tokens=20, do_sample=True, temperature=0.8)

print(output[0]["generated_text"])
# 示例输出：Large language models are becoming increasingly powerful...

运行后你会发现，模型只是根据上文“续写”，但续写质量已经能支撑很多实际应用。记住：LLM 的一切能力，都建立在对下一个 token 的预测之上。

1.2 发展简史：从 Transformer 到 GPT、LLaMA、DeepSeek

LLM 的爆发不是一夜之间发生的，关键节点可以串成一条线：

  1. 2017 · Transformer：Google 发表《Attention Is All You Need》，提出完全基于自注意力的架构，抛弃 RNN，奠定一切基础。
  2. 2018 · BERT & GPT-1：BERT 用 Encoder 做理解，GPT 用 Decoder 做生成，两条路线分道扬镳。
  3. 2020 · GPT-3：1750 亿参数，首次展示“少样本学习”（Few-shot Learning），提示词工程开始流行。
  4. 2022 · ChatGPT：引入 RLHF，把 GPT-3.5 变成对话助手，LLM 正式出圈。
  5. 2023 · LLaMA 系列：Meta 开源 LLaMA、Llama 2，引爆开源社区，让“自己微调大模型”成为可能。
  6. 2024-2025 · Qwen、DeepSeek：国产模型崛起，DeepSeek 用 MoE（混合专家）和高效训练把成本打下来，性能对标一线闭源模型。

这条线背后有两个趋势：一是模型越来越大、越来越强；二是开源与闭源的差距在快速缩小。对工程师来说，这意味着你既可以用 API 快速上线，也可以基于开源模型做私有化部署和深度定制。

下面用代码查看一个开源模型的架构配置，理解“Decoder-only”长什么样：

from transformers import AutoConfig

config = AutoConfig.from_pretrained("Qwen/Qwen2.5-0.5B")
print("模型类型:", config.model_type)          # qwen2
print("隐藏层维度:", config.hidden_size)      # 896
print("层数:", config.num_hidden_layers)      # 24

通过配置你能看到：现代 LLM 基本都是 Decoder-only 结构，堆叠几十层 Transformer Block，每层包含自注意力和前馈网络。

1.3 主流模型对比：GPT、Claude、LLaMA、Qwen 怎么选

选模型就像选车：没有最好的，只有最适合场景的。下面从几个维度对比主流模型：

模型开源/闭源特点典型场景
GPT 系列闭源综合能力最强，生态最成熟通用对话、Agent、复杂推理
Claude 系列闭源长上下文、安全性好、写作强长文档分析、代码、合规场景
LLaMA 系列开源社区生态庞大，微调资源多私有化部署、学术研究
Qwen 系列开源中文强、尺寸全、工具调用好中文应用、RAG、Agent

选择时问自己三个问题：1）数据能不能出内网？不能就选开源私有化。2）预算多少？闭源 API 按量付费，开源要算 GPU 成本。3）任务难度？简单任务小模型够用，复杂推理才上大模型。

实际工程中常用“路由”策略：简单请求走小模型，复杂请求走大模型，兼顾成本和效果。下面是一个极简的模型路由示例：

def route_model(query: str) -> str:
    """根据问题复杂度选择模型"""
    complex_keywords = ["推理", "证明", "代码", "分析", "为什么"]
    if any(kw in query for kw in complex_keywords) or len(query) > 100:
        return "gpt-4o"          # 复杂任务用大模型
    return "qwen2.5-7b"          # 简单任务用小模型

queries = ["今天天气怎么样", "请证明勾股定理并给出代码实现"]
for q in queries:
    print(f"问题: {q} -> 路由到: {route_model(q)}")

核心原则：不要用大炮打蚊子，也不要用弹弓打坦克。

1.4 典型应用场景：对话、编程、RAG、Agent

LLM 落地主要有四大场景，难度和工程复杂度依次递增：

  • 对话（Chat）：最基础，客服、助手、陪聊。核心是提示词设计和多轮上下文管理。
  • 编程（Coding）：代码补全、生成、审查、单测。代表产品 GitHub Copilot、Cursor。
  • RAG（检索增强生成）：先检索知识库，再让 LLM 基于检索结果回答。解决“模型不知道私有知识”和“幻觉”问题，是企业落地最火的方案。
  • Agent（智能体）：让 LLM 自主规划、调用工具、多步执行。比如“帮我订机票并安排行程”，需要 LLM + 工具 + 记忆 + 规划。

这四者不是互斥的，而是层层叠加：对话是交互层，RAG 是知识层，Agent 是行动层，编程是垂直应用。一个成熟的 AI 产品往往是“Agent 调度 + RAG 供知识 + 对话做交互”。

下面用 20 行代码实现一个最小 RAG 流程，感受“检索 + 生成”的威力：

from sklearn.feature_extraction.text import TfidfVectorizer
from sklearn.metrics.pairwise import cosine_similarity

# 模拟知识库
knowledge = [
    "LLM 全链路包括预训练、微调、部署和运维。",
    "RAG 通过检索外部知识来增强生成，减少幻觉。",
    "Agent 能调用工具并自主规划任务步骤。",
]

# 1. 检索：用 TF-IDF 找最相关的知识
def retrieve(query, docs, top_k=1):
    vectorizer = TfidfVectorizer()
    tfidf = vectorizer.fit_transform(docs + [query])
    sims = cosine_similarity(tfidf[-1], tfidf[:-1])[0]
    top_idx = sims.argsort()[::-1][:top_k]
    return [docs[i] for i in top_idx]

# 2. 生成：把检索结果拼进提示词（这里用模拟输出）
query = "RAG 是怎么减少幻觉的？"
context = retrieve(query, knowledge)
prompt = f"基于以下资料回答问题：\n{context[0]}\n\n问题：{query}\n回答："
print(prompt)
# 实际项目中把 prompt 发给 LLM 即可

这个例子虽然简单，但已经包含了 RAG 的核心思想：先检索、后生成，让模型“有据可依”。后续章节会深入向量数据库、Embedding、重排序等工程细节。

常见误区

  • 误区：LLM 真的“理解”了语言。实际上模型是在做概率预测，它的“理解”是统计规律的高维表示，并不具备人类意义上的意识和常识，所以会出现幻觉。
  • 误区：参数越大模型一定越好。模型效果还取决于数据质量、训练方法、对齐策略和推理优化；小模型在特定领域微调后完全可以超过通用大模型。
  • 误区：开源模型等于免费。开源模型省的是授权费，但 GPU 推理成本、部署运维、微调人力都是真金白银，规模大时可能比 API 更贵。

自测

LLM 的三大核心能力是什么？它们和“预测下一个词”有什么关系？

答案：三大核心能力是生成、理解、推理。它们都建立在“预测下一个词”的自监督训练目标之上：生成是直接续写；理解是通过预测任务学到的语义表示；推理是模型规模增大后从预测任务中涌现出的多步能力。

什么场景下你会优先选择开源模型而不是闭源 API？请至少说出两个理由。

第2章 · 数据工程与预处理

本章目标：掌握LLM训练数据的收集、清洗、去重与格式化方法

数据来源与采集：网页、书籍、代码、对话

大家好，欢迎来到第2章。上一章我们聊了LLM的整体链路，这一章我们钻进最脏最累但也最重要的环节——数据工程。模型再牛，数据不行，出来的东西就是“垃圾进，垃圾出”。

先看数据从哪来。LLM训练数据主要有四大来源：

  • 网页：Common Crawl是典型代表，体量巨大但噪声也巨大。需要做正文提取、语言过滤、质量打分。
  • 书籍：长文本、高质量、逻辑连贯，但版权和获取难度是问题。常用Books3、Project Gutenberg等。
  • 代码：GitHub、Stack Overflow等，对代码生成和推理能力至关重要。需要按许可证过滤、去重、解析AST。
  • 对话：论坛、客服记录、多轮对话数据，用于指令微调和对话能力。格式多样，需要统一成对话模板。

采集时要注意：数据来源的多样性直接决定模型能力的广度。只喂网页，模型可能不会写代码；只喂代码，模型可能不会聊天。所以数据配比是后面要讲的重点。

下面是一个最小示例，演示如何从本地文件加载不同来源的数据并统一成字典格式：

import json
from pathlib import Path

def load_jsonl(path):
    with open(path, 'r', encoding='utf-8') as f:
        return [json.loads(line) for line in f]

# 假设有三个文件：web.jsonl, books.jsonl, code.jsonl
web_data = load_jsonl('web.jsonl')
book_data = load_jsonl('books.jsonl')
code_data = load_jsonl('code.jsonl')

# 统一格式：每条数据包含 source, text, meta
def normalize(item, source):
    return {
        'source': source,
        'text': item.get('text', ''),
        'meta': {k: v for k, v in item.items() if k != 'text'}
    }

all_data = []
for item in web_data:
    all_data.append(normalize(item, 'web'))
for item in book_data:
    all_data.append(normalize(item, 'book'))
for item in code_data:
    all_data.append(normalize(item, 'code'))

print(f'Total samples: {len(all_data)}')
print(all_data[0])

这个例子很简单，但体现了数据工程的第一步：统一数据格式，方便后续处理。

数据清洗：去噪、去重与质量过滤

原始数据里全是“脏东西”：HTML标签、乱码、广告、重复段落、低质量内容。清洗的目标是保留高质量、多样化的文本，去掉噪声和冗余。

去噪：常见操作包括去除HTML标签、特殊字符、多余空白、页眉页脚。可以用正则或专门的库如trafilatura提取正文。

去重：重复数据会让模型记住特定样本，降低泛化。去重分三个层次：

  • 精确去重：完全相同的文本，用哈希即可。
  • 近似去重：相似但不完全相同的文本，常用MinHash+LSH或SimHash。
  • 子串去重：长文档中重复的段落，可以用后缀数组或n-gram重叠检测。

质量过滤：用规则或模型打分。规则包括：文本长度、平均词长、符号与词的比例、是否包含禁用词。模型方法如用fastText分类器判断是否像维基百科文本。

下面是一个综合示例，展示去噪、精确去重和简单质量过滤：

import re
import hashlib
from collections import defaultdict

def clean_text(text):
    # 去除HTML标签
    text = re.sub(r'<[^>]+>', '', text)
    # 去除多余空白
    text = re.sub(r'\s+', ' ', text).strip()
    # 去除特殊控制字符
    text = re.sub(r'[\x00-\x1f\x7f]', '', text)
    return text

def quality_filter(text, min_len=50, max_symbol_ratio=0.1):
    if len(text) < min_len:
        return False
    # 符号比例
    symbol_count = sum(1 for c in text if not c.isalnum() and not c.isspace())
    if symbol_count / len(text) > max_symbol_ratio:
        return False
    return True

def deduplicate(texts):
    seen = set()
    unique = []
    for t in texts:
        h = hashlib.md5(t.encode('utf-8')).hexdigest()
        if h not in seen:
            seen.add(h)
            unique.append(t)
    return unique

# 模拟原始数据
raw_texts = [
    '
Hello   world!
',
    'Hello world!',
    'This is a much longer text that should pass the quality filter because it has enough characters and not too many symbols.',
    'Short',
    '!!!!!@@@@@#####$$$$$%%%%%^^^^^&&&&&*****((((()))))',
]

cleaned = [clean_text(t) for t in raw_texts]
filtered = [t for t in cleaned if quality_filter(t)]
unique = deduplicate(filtered)

print('Cleaned:', cleaned)
print('Filtered:', filtered)
print('Unique:', unique)

注意：去重时，精确去重只能去掉完全一样的文本，近似去重才能解决“换几个词”的重复。工业级流水线通常用MinHash+LSH做大规模近似去重。

数据格式化：指令微调与对话模板

预训练数据是纯文本，但指令微调和对话模型需要结构化格式。这一步就是把数据整理成模型能理解的“模板”。

指令微调数据通常包含三部分：instruction（指令）、input（可选输入）、output（期望输出）。例如：

{
  "instruction": "将以下句子翻译成英文",
  "input": "今天天气真好",
  "output": "The weather is really nice today."
}

对话模板则把多轮对话组织成角色标记的序列。常见格式有Alpaca、ShareGPT、ChatML等。以ChatML为例：

&lt;|im_start|&gt;system
You are a helpful assistant.&lt;|im_end|&gt;
&lt;|im_start|&gt;user
你好&lt;|im_end|&gt;
&lt;|im_start|&gt;assistant
你好！有什么可以帮你的？&lt;|im_end|&gt;

格式化时要注意：训练和推理必须使用完全相同的模板，否则模型会“精神分裂”。另外，要正确处理padding和attention mask，把padding token的loss忽略掉。

下面是一个把Alpaca格式转成ChatML格式的示例：

def alpaca_to_chatml(example):
    instruction = example.get('instruction', '')
    input_text = example.get('input', '')
    output = example.get('output', '')
    if input_text:
        user_content = f"{instruction}\n\n{input_text}"
    else:
        user_content = instruction
    chatml = (
        "<|im_start|>system\nYou are a helpful assistant.<|im_end|>\n"
        f"<|im_start|>user\n{user_content}<|im_end|>\n"
        f"<|im_start|>assistant\n{output}<|im_end|>\n"
    )
    return {'text': chatml}

example = {
    'instruction': '将以下句子翻译成英文',
    'input': '今天天气真好',
    'output': 'The weather is really nice today.'
}
print(alpaca_to_chatml(example)['text'])

实际训练时，我们通常只对assistant部分的token计算loss，system和user部分mask掉。这需要在tokenizer层面处理。

数据配比与课程学习策略

数据配比（Data Mixture）是指不同来源数据在训练集中的比例。它直接决定模型的能力偏向。比如：

  • 网页数据多 → 知识面广，但可能废话多。
  • 代码数据多 → 代码能力强，但可能不会聊天。
  • 书籍数据多 → 长文本理解好，但可能缺乏时效性。

常见配比策略：按经验设定初始比例，然后通过小规模实验调整。例如Llama 2的预训练数据中，代码占比约5%，网页占比约80%以上。指令微调数据则更注重质量而非数量，通常几万到几百万条。

课程学习（Curriculum Learning）是另一种策略：先喂简单数据，再喂难数据。比如先短文本后长文本，先通用后专业。但LLM预训练中课程学习的效果仍有争议，因为数据量太大，很难定义“简单”和“难”。更常见的做法是动态数据配比，在训练过程中调整不同来源的采样权重。

下面是一个按比例采样数据配比的示例：

import random
from collections import defaultdict

def sample_by_ratio(data, ratios, total_samples):
    """
    data: list of dict, each has 'source'
    ratios: dict, source -> ratio (sum to 1)
    total_samples: int
    """
    by_source = defaultdict(list)
    for item in data:
        by_source[item['source']].append(item)
    sampled = []
    for source, ratio in ratios.items():
        n = int(total_samples * ratio)
        pool = by_source[source]
        if len(pool) < n:
            print(f'Warning: {source} only has {len(pool)} samples, requested {n}')
            n = len(pool)
        sampled.extend(random.sample(pool, n))
    random.shuffle(sampled)
    return sampled

# 模拟数据
data = [{'source': 'web', 'text': f'web_{i}'} for i in range(1000)]
data += [{'source': 'book', 'text': f'book_{i}'} for i in range(500)]
data += [{'source': 'code', 'text': f'code_{i}'} for i in range(300)]

ratios = {'web': 0.7, 'book': 0.2, 'code': 0.1}

print(f'Sampled {len(sampled)} items')

记住：数据配比没有银弹，必须结合评测结果反复迭代。建议先跑小规模消融实验，再放大到全量训练。

常见误区

  • 数据去重只需要精确去重，近似去重没必要。实际上，近似重复（如换几个词、调整语序）在网页数据中非常普遍，不做近似去重会导致模型重复记忆，降低泛化能力。
  • 指令微调数据越多越好。实际上，指令微调更看重质量而非数量，低质量或重复的指令数据会损害模型性能，通常几万条高质量数据就能有不错的效果。
  • 训练和推理可以使用不同的对话模板。这是错误的，模板不一致会导致模型输出格式混乱，必须严格保持一致。

自测

数据去重通常分为哪几个层次？各自适用什么场景？

答案：分为精确去重、近似去重和子串去重。精确去重用哈希去除完全相同的文本，适合快速过滤；近似去重用MinHash+LSH或SimHash去除相似文本，适合大规模网页数据；子串去重针对长文档中重复段落，用后缀数组或n-gram重叠检测，适合书籍等长文本。

为什么数据配比很重要？调整配比时应该注意什么？

答案：数据配比决定模型的能力偏向，不同来源的数据影响模型在知识、代码、对话等方面的表现。调整配比时应注意：先设定初始比例，通过小规模实验和评测结果迭代调整；避免某一来源过多导致能力失衡；动态调整采样权重可能比固定配比更有效。

第3章 · 预训练与分布式训练

本章目标：理解预训练目标、分布式训练策略与优化技巧

预训练目标：自回归语言建模

预训练是LLM获得通用语言能力的基石，而自回归语言建模（Autoregressive Language Modeling）是其中最主流的目标。它的核心思想很简单：给定前文，预测下一个token。形式化地，对于序列 \(x_1, x_2, ..., x_T\)，模型最大化对数似然：

\[\sum_{t=1}^{T} \log P(x_t | x_1, ..., x_{t-1}; \theta)\]

训练时，我们通常使用教师强制（teacher forcing）：将真实的前缀作为输入，并行计算所有位置的预测，并与真实的下一个token计算交叉熵损失。这样，一次前向传播就能得到所有位置的损失，效率很高。

下面是一个最小示例，展示如何用PyTorch实现自回归语言建模的损失计算：

import torch
import torch.nn as nn

# 假设词表大小为1000，批次大小2，序列长度5
vocab_size = 1000
batch_size = 2
seq_len = 5

# 模拟模型输出logits: (batch, seq_len, vocab_size)
logits = torch.randn(batch_size, seq_len, vocab_size)
# 真实标签: (batch, seq_len)
targets = torch.randint(0, vocab_size, (batch_size, seq_len))

# 自回归语言建模损失：预测下一个token
# 将logits和targets展平，计算交叉熵
loss_fn = nn.CrossEntropyLoss()
loss = loss_fn(logits.view(-1, vocab_size), targets.view(-1))
print(f"Loss: {loss.item():.4f}")

# 注意：实际中，模型输出logits[:, :-1]对应targets[:, 1:]
# 这里简化演示，假设已经对齐

关键点：自回归建模天然适合生成任务，但训练时每个位置只能看到左侧上下文，因此需要因果掩码（causal mask）防止信息泄露。此外，这种目标也常用于零样本和少样本学习。

分布式训练：数据并行、模型并行与流水线并行

当模型参数量达到数十亿甚至千亿时，单卡显存无法容纳，训练时间也难以接受。分布式训练成为必选项。主要策略有三类：

  • 数据并行（Data Parallelism）：每张卡持有完整的模型副本，但处理不同的数据批次。梯度通过AllReduce同步。适合模型能单卡放下，但数据量大的场景。PyTorch的DistributedDataParallel（DDP）是标准实现。
  • 模型并行（Model Parallelism）：将模型的不同层或同一层的不同部分拆分到不同设备。例如，将Transformer的注意力头拆分到多卡（张量并行）。适合单层参数过大，单卡放不下的情况。
  • 流水线并行（Pipeline Parallelism）：将模型按层切分成多个阶段，每个阶段放在不同设备上，数据像流水线一样依次通过。为了减少气泡，通常采用微批次（micro-batch）和调度策略（如GPipe、PipeDream）。

实际训练中，常结合多种并行策略，如3D并行（数据+模型+流水线）。下面是一个使用PyTorch DDP的简单示例：

import torch
import torch.distributed as dist
import torch.nn as nn
import torch.optim as optim
from torch.nn.parallel import DistributedDataParallel as DDP

def setup(rank, world_size):
    dist.init_process_group("gloo", rank=rank, world_size=world_size)

def cleanup():
    dist.destroy_process_group()

def train(rank, world_size):
    setup(rank, world_size)
    model = nn.Linear(10, 10).to(rank)
    ddp_model = DDP(model, device_ids=[rank])
    loss_fn = nn.MSELoss()
    optimizer = optim.SGD(ddp_model.parameters(), lr=0.001)
    
    # 模拟数据
    inputs = torch.randn(20, 10).to(rank)
    outputs = torch.randn(20, 10).to(rank)
    
    optimizer.zero_grad()
    preds = ddp_model(inputs)
    loss = loss_fn(preds, outputs)
    loss.backward()
    optimizer.step()
    print(f"Rank {rank}, Loss: {loss.item()}")
    cleanup()

# 启动方式：torchrun --nproc_per_node=2 script.py
# 每个进程调用train(rank, world_size)

关键点：数据并行通信开销大，模型并行和流水线并行则更复杂但能突破单卡显存限制。选择策略需权衡模型大小、集群网络和开发成本。

混合精度训练与梯度累积

混合精度训练（Mixed Precision Training）通过结合FP16和FP32来加速训练并减少显存占用。核心思想：前向和反向传播使用FP16计算，但保留一份FP32的模型权重副本用于更新，避免舍入误差累积。同时，使用损失缩放（loss scaling）防止梯度下溢。

PyTorch提供了torch.cuda.amp自动混合精度：

import torch
from torch.cuda.amp import autocast, GradScaler

model = torch.nn.Linear(10, 10).cuda()
optimizer = torch.optim.SGD(model.parameters(), lr=0.001)
scaler = GradScaler()

for data, target in dataloader:
    optimizer.zero_grad()
    with autocast():
        output = model(data)
        loss = loss_fn(output, target)
    scaler.scale(loss).backward()
    scaler.step(optimizer)
    scaler.update()

梯度累积（Gradient Accumulation）是另一种节省显存的技巧：当显存不足以容纳大batch时，可以多次前向/反向传播，累积梯度，再一次性更新。这等价于增大batch size，但不会增加显存峰值。

accumulation_steps = 4
optimizer.zero_grad()
for i, (data, target) in enumerate(dataloader):
    output = model(data)
    loss = loss_fn(output, target) / accumulation_steps
    loss.backward()
    if (i+1) % accumulation_steps == 0:
        optimizer.step()
        optimizer.zero_grad()

关键点：混合精度和梯度累积常结合使用，能显著降低显存需求，但需注意数值稳定性（如梯度裁剪）和超参数调整。

训练稳定性：学习率调度与梯度裁剪

大模型训练容易不稳定，表现为损失尖峰或发散。两个关键技巧是学习率调度和梯度裁剪。

学习率调度：常用预热（warmup）和余弦衰减。预热让学习率从0线性增加到峰值，避免早期梯度噪声导致的不稳定；随后余弦衰减到接近0，帮助模型收敛到更平坦的极小值。

from torch.optim.lr_scheduler import LambdaLR
import math

def lr_lambda(step):
    warmup_steps = 1000
    total_steps = 10000
    if step < warmup_steps:
        return step / warmup_steps
    else:
        progress = (step - warmup_steps) / (total_steps - warmup_steps)
        return 0.5 * (1 + math.cos(math.pi * progress))

scheduler = LambdaLR(optimizer, lr_lambda)

梯度裁剪：将梯度向量的范数限制在一个阈值内，防止梯度爆炸。通常按全局范数裁剪：

torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)

关键点：预热步数通常为总步数的1%-10%，梯度裁剪阈值常设为1.0。这些技巧能显著提升训练稳定性，尤其对于大模型。

常见误区

  • 自回归语言建模训练时，每个位置可以同时看到左右上下文，因此不需要因果掩码。
  • 数据并行中，每张卡持有模型的一部分，因此可以训练任意大的模型。
  • 混合精度训练会降低模型精度，因此不能用于最终部署。

自测

自回归语言建模中，为什么需要因果掩码（causal mask）？

答案：因果掩码确保模型在预测第t个token时只能看到前t-1个token，防止信息泄露，使训练目标与生成时的自回归特性一致。

数据并行和模型并行的主要区别是什么？各自适用什么场景？

答案：数据并行中每张卡有完整模型副本，处理不同数据批次，通过AllReduce同步梯度，适合模型能单卡放下但数据量大的场景；模型并行将模型拆分到不同设备，适合单卡显存不足以容纳整个模型的情况。

第4章 · 微调与对齐技术

本章目标：掌握全量微调、LoRA、RLHF等微调与对齐方法

全量微调 vs 参数高效微调：LoRA 与 QLoRA

当我们拿到一个预训练好的大模型（比如 LLaMA、Qwen），想让它适应特定任务或领域，最直接的办法就是全量微调：用任务数据继续训练模型的所有参数。这就像把整栋房子重新装修一遍，效果可能最好，但代价极高——7B 模型全量微调通常需要多张 A100，显存动辄上百 GB，而且每个任务都要存一份完整权重，部署时切换成本巨大。

于是参数高效微调（PEFT）登场了。核心思想：冻结预训练模型的大部分参数，只训练一小部分新增或选定的参数。其中最有代表性的就是 LoRA（Low-Rank Adaptation）。

LoRA 的直觉来自一个观察：模型在适配新任务时，权重的变化量 ΔW 往往是低秩的。与其直接更新原始权重 W，不如把 ΔW 分解成两个小矩阵的乘积：ΔW = B·A，其中 A 是 r×d 矩阵，B 是 d×r 矩阵，r（秩）远小于 d。训练时只更新 A 和 B，原始 W 冻结。这样可训练参数量能降到原来的 0.1%~1%，显存和存储都大幅下降。

前向传播变成：h = Wx + BAx。初始化时 A 用高斯随机，B 置零，保证训练开始时 LoRA 分支输出为 0，不破坏原模型行为。

QLoRA 则更进一步：先把基座模型量化成 4-bit（NF4）加载，再在量化权重上挂 LoRA 适配器。这样 7B 模型可以在单张 24GB 甚至 16GB 显卡上微调，让个人开发者也能玩转大模型微调。

下面是一个用 Hugging Face peft 库给模型加 LoRA 的最小示例：

from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, get_peft_model

model_name = "Qwen/Qwen2.5-0.5B"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name)

# 配置 LoRA：只作用于注意力层的 q、v 投影
lora_config = LoraConfig(
    r=8,                      # 秩
    lora_alpha=16,            # 缩放系数，通常设为 2*r
    target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM",
)

model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
# 输出类似：trainable params: 540,672 || all params: 494,032,768 || trainable%: 0.1094

可以看到，可训练参数只有约 0.1%。训练完成后，你可以只保存 LoRA 权重（几 MB），推理时再合并回基座模型，或者用 merge_and_unload() 永久合并。

指令微调与对话模板设计

预训练模型只会“续写”，不会“听话”。指令微调（Instruction Tuning）就是用“指令-回答”格式的数据继续训练，让模型学会遵循人类指令。这一步是 ChatGPT 类模型的关键。

但这里有个容易被忽视的工程细节：对话模板（Chat Template）。不同模型在训练时使用了不同的特殊 token 和格式来区分 system、user、assistant 角色。比如 Qwen 用 &lt;|im_start|&gt;role\ncontent&lt;|im_end|&gt;，Llama 3 用 &lt;|start_header_id|&gt; 系列。如果你微调时用的模板和推理时不一致，模型表现会断崖式下跌。

正确做法是：始终使用 tokenizer 自带的 apply_chat_template，它封装了模型训练时的标准格式。下面演示如何构造一条训练样本：

from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B")

messages = [
    {"role": "system", "content": "你是一个专业的AI助教。"},
    {"role": "user", "content": "什么是LoRA？"},
    {"role": "assistant", "content": "LoRA是一种低秩适应方法，通过训练两个小矩阵来近似权重更新。"},
]

# 生成完整对话文本（含特殊token）
text = tokenizer.apply_chat_template(messages, tokenize=False)
print(text)

# 训练时通常只对 assistant 部分计算 loss
# 做法：先对 prompt 部分设置 label 为 -100（忽略）
input_ids = tokenizer.apply_chat_template(messages, tokenize=True, return_tensors="pt")

关键结论：只对 assistant 回复部分计算损失，prompt 部分的 label 设为 -100。否则模型会去学习“如何提问”，浪费容量还可能降低效果。Hugging Face 的 trl 库中 SFTTrainer 配合 DataCollatorForCompletionOnlyLM 可以自动完成这个掩码。

指令数据的质量比数量更重要。一条高质量、多样化的指令数据，胜过十条低质重复数据。常见来源包括：人工标注、强模型蒸馏（如用 GPT-4 生成）、开源数据集（Alpaca、ShareGPT）以及业务真实日志。

RLHF 与 DPO：让模型对齐人类偏好

指令微调让模型“会回答”，但回答是否有用、诚实、无害，还需要对齐（Alignment）。经典方案是 RLHF（基于人类反馈的强化学习），分三步：

  1. 监督微调（SFT）：用高质量指令数据微调，得到基础策略模型。
  2. 训练奖励模型（RM）：让人类对同一 prompt 的多个回答排序，训练一个模型去预测“人类有多喜欢这个回答”。
  3. PPO 强化学习：用奖励模型作为打分器，用 PPO 算法优化策略模型，同时加 KL 惩罚防止跑偏。

RLHF 效果好，但工程复杂：要同时加载策略模型、参考模型、奖励模型、价值模型，显存爆炸，训练极不稳定。于是 DPO（Direct Preference Optimization） 出现了。

DPO 的巧妙之处在于：它从数学上证明了，RLHF 的最优策略可以解析地表示成偏好数据的函数，从而把强化学习问题转化成一个简单的分类损失。你只需要准备 (prompt, chosen, rejected) 三元组，直接像做监督学习一样训练即可，不需要奖励模型，也不需要 PPO。

DPO 损失的核心是：让模型对 chosen 回答的 log 概率相对 rejected 回答更高，同时用参考模型约束不要偏离太远。下面是一个用 trl 的 DPOTrainer 的最小示例：

from datasets import Dataset
from transformers import AutoModelForCausalLM, AutoTokenizer
from trl import DPOTrainer, DPOConfig

model_name = "Qwen/Qwen2.5-0.5B"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name)
ref_model = AutoModelForCausalLM.from_pretrained(model_name)  # 参考模型，冻结

# 偏好数据：每条包含 prompt、chosen、rejected
data = {
    "prompt": ["解释一下什么是过拟合。"],
    "chosen": ["过拟合是指模型在训练集上表现很好，但在新数据上表现差，通常因为模型过于复杂记住了噪声。"],
    "rejected": ["过拟合就是模型训练得太好了。"],
}
dataset = Dataset.from_dict(data)

training_args = DPOConfig(
    output_dir="./dpo_out",
    per_device_train_batch_size=1,
    num_train_epochs=1,
    beta=0.1,          # KL 约束强度，越大越保守
    learning_rate=5e-5,
)

trainer = DPOTrainer(
    model=model,
    ref_model=ref_model,
    args=training_args,
    train_dataset=dataset,
    tokenizer=tokenizer,
)
trainer.train()

选型建议：资源充足、追求极致效果，用 RLHF/PPO；资源有限、想快速迭代，用 DPO 或其变体（IPO、KTO、ORPO）。实践中，DPO 已成为大多数团队的首选对齐方案。

微调数据构建与评估

微调的上限往往由数据决定。构建数据时，建议遵循以下原则：

  • 多样性：覆盖任务类型、领域、难度、语言风格，避免模型只会一种腔调。
  • 质量优先：人工审核或强模型过滤，剔除事实错误、格式混乱、重复样本。
  • 格式统一：严格使用目标模型的对话模板，保证训练/推理一致。
  • 规模适中：指令微调通常 1k~100k 条即可见效，LoRA 场景下几千条高质量数据就能有不错表现。

评估方面，不能只看训练 loss。建议分三层：

  1. 自动指标：困惑度（PPL）、ROUGE/BLEU（生成任务）、准确率（分类任务）。
  2. 模型评判：用 GPT-4 等强模型对回答打分或做 pairwise 比较（LLM-as-a-Judge）。
  3. 人工评估：抽样盲评，关注有用性、事实性、安全性。

特别提醒：一定要留出和训练集同分布的验证集，并监控是否过拟合。LoRA 虽然参数少，但数据重复多、epoch 大时同样会过拟合。

下面是一个用 PPL 快速评估微调前后模型的示例：

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

def compute_ppl(model, tokenizer, texts):
    model.eval()
    total_loss, total_tokens = 0.0, 0
    with torch.no_grad():
        for text in texts:
            enc = tokenizer(text, return_tensors="pt")
            out = model(**enc, labels=enc["input_ids"])
            n = enc["input_ids"].size(1)
            total_loss += out.loss.item() * n
            total_tokens += n
    return torch.exp(torch.tensor(total_loss / total_tokens)).item()

model_name = "Qwen/Qwen2.5-0.5B"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name)

test_texts = ["什么是机器学习？", "解释一下梯度下降。"]
print("PPL:", compute_ppl(model, tokenizer, test_texts))

把微调后的模型用同样脚本跑一遍，对比 PPL 变化，就能快速判断微调是否有效。当然，PPL 低不代表回答好，最终还是要结合人工和模型评判。

常见误区

  • LoRA 只能用于注意力层的 q、v 投影，实际上可以作用于任何线性层（如 k、o、FFN），target_modules 的选择需要实验调优。
  • DPO 完全不需要参考模型，实际上 DPO 损失中必须有一个冻结的参考模型来计算 KL 约束，否则训练容易崩溃。
  • 指令微调时对所有 token 计算 loss 效果更好，实际上应该只对 assistant 回复部分计算 loss，prompt 部分要 mask 掉。

自测

LoRA 中秩 r 和缩放系数 lora_alpha 分别起什么作用？增大 r 会带来什么影响？

答案：r 控制低秩矩阵的秩，决定适配器的容量；lora_alpha 是缩放系数，实际更新量为 (alpha/r)·BA，用于稳定训练。增大 r 会提升模型表达能力，但可训练参数和显存增加，且更容易过拟合，通常从 8 或 16 开始调。

相比 RLHF，DPO 的主要优势是什么？它为什么能省掉奖励模型和 PPO？

答案：DPO 把 RLHF 的两阶段（训练奖励模型 + PPO 强化学习）合并成一个直接的偏好分类损失。它从数学上推导出 RLHF 最优策略的解析形式，使得只需在 (prompt, chosen, rejected) 数据上做类似监督学习的训练即可，无需显式奖励模型和 PPO，训练更稳定、显存更省、实现更简单。

第5章 · 模型评估与优化

本章目标：学会设计评估方案，并进行量化、剪枝与蒸馏优化

评估指标：从困惑度到人工评估

模型训完了，怎么知道它好不好？最直接的指标是困惑度（Perplexity, PPL）。它衡量模型对文本的“惊讶程度”：PPL 越低，说明模型越能预测下一个词。数学上，PPL 是交叉熵损失的指数：PPL = exp(loss)。比如 loss=2.0，PPL≈7.39，可以粗略理解为模型在每一步平均在 7.39 个词里犹豫。

但 PPL 只反映语言建模能力，不直接对应任务效果。所以还需要准确率（Accuracy），比如分类任务、选择题、代码通过率等。对于生成式任务，准确率往往需要人工或模型辅助判断。

最后是人工评估：让标注员对流畅性、相关性、事实性、安全性打分。人工评估成本高，但最贴近真实体验。实践中常采用“自动指标粗筛 + 人工精评”的组合。

import torch
from transformers import GPT2LMHeadModel, GPT2Tokenizer

model = GPT2LMHeadModel.from_pretrained('gpt2')
tokenizer = GPT2Tokenizer.from_pretrained('gpt2')

text = "The quick brown fox jumps over the lazy dog."
inputs = tokenizer(text, return_tensors='pt')
with torch.no_grad():
    outputs = model(**inputs, labels=inputs['input_ids'])
loss = outputs.loss
ppl = torch.exp(loss)
print(f'Loss: {loss.item():.4f}, Perplexity: {ppl.item():.2f}')

运行这段代码，你会得到 GPT-2 在这句话上的困惑度。注意：PPL 必须在同一 tokenizer 和同一数据集上比较才有意义，不同分词器算出的 PPL 不可直接对比。

基准测试：MMLU、GSM8K、HumanEval

光看 PPL 不够，业界用基准测试（Benchmark）来横向对比模型能力。常见的有：

  • MMLU：57 个学科的多选题，考知识广度，用准确率衡量。
  • GSM8K：小学数学应用题，考多步推理，看最终答案是否正确。
  • HumanEval：Python 函数补全，用 pass@k 衡量，即生成 k 个答案至少一个通过测试的概率。

设计评估方案时要注意：数据污染（训练集混入测试题）会让分数虚高；提示词敏感（few-shot 示例数量、格式）会显著影响结果。所以报告结果时要写清楚评测配置。

# 以 GSM8K 为例，用 few-shot 提示评估准确率（简化版）
from datasets import load_dataset

dataset = load_dataset('gsm8k', 'main', split='test[:20]')

    return f"Q: {question}\nA: Let's think step by step."

correct = 0
for ex in dataset:
    prompt = build_prompt(ex['question'])
    # 这里替换成你的模型调用，返回生成文本
    generated = "..."  # model.generate(prompt)
    # GSM8K 答案在 '####' 后面

    if gold in generated:

实际评测中，GSM8K 常用 8-shot，HumanEval 用 pass@1 或 pass@10。不要只看一个 benchmark 的分数就下结论，要结合多个维度。

模型量化：GPTQ、AWQ、GGUF

模型太大跑不动？量化（Quantization）把 FP16 权重压成 INT8/INT4，显存直接减半甚至更多。主流方案：

  • GPTQ：逐层量化，用校准数据最小化重构误差，适合 GPU 推理。
  • AWQ：激活感知权重量化，保护重要通道，精度通常比 GPTQ 略好。
  • GGUF：llama.cpp 的格式，支持 CPU/GPU 混合推理，适合本地部署。

量化不是免费的午餐：4-bit 量化通常损失 1~3 个点，但换来的显存和速度提升很划算。选择时先看硬件：GPU 用 GPTQ/AWQ，Mac/CPU 用 GGUF。

剪枝与知识蒸馏

除了量化，还有两条压缩路线：剪枝（Pruning）和知识蒸馏（Knowledge Distillation）。

剪枝是去掉不重要的权重或结构。非结构化剪枝把小的权重置零，但稀疏矩阵在普通硬件上不一定加速；结构化剪枝直接删掉整个注意力头或 FFN 通道，能真正减小模型。剪枝后通常要微调恢复精度。

知识蒸馏是让小的“学生模型”模仿大的“教师模型”。核心是让学生输出的概率分布（软标签）接近教师，而不是只拟合硬标签。损失函数通常是：L = α * CE(student, hard_label) + (1-α) * KL(student_soft, teacher_soft)，其中 soft 是带温度 T 的 softmax。

import torch
import torch.nn.functional as F

def distillation_loss(student_logits, teacher_logits, labels, T=2.0, alpha=0.7):
    # 软标签损失：KL 散度，注意 log_softmax 和 softmax 的配合
    soft_student = F.log_softmax(student_logits / T, dim=-1)
    soft_teacher = F.softmax(teacher_logits / T, dim=-1)
    kd_loss = F.kl_div(soft_student, soft_teacher, reduction='batchmean') * (T * T)
    # 硬标签损失
    ce_loss = F.cross_entropy(student_logits, labels)
    return alpha * ce_loss + (1 - alpha) * kd_loss

# 假设 batch_size=4, num_classes=10
student_logits = torch.randn(4, 10)
teacher_logits = torch.randn(4, 10)
labels = torch.tensor([1, 2, 3, 4])
loss = distillation_loss(student_logits, teacher_logits, labels)
print(f'Distillation loss: {loss.item():.4f}')

实践中，蒸馏常和量化、剪枝组合使用：先蒸馏得到小模型，再量化部署。温度 T 一般取 2~5，alpha 取 0.5~0.9，需要根据任务调。

常见误区

  • 困惑度越低模型效果一定越好——PPL 只反映语言建模能力，不直接对应下游任务准确率，且不同 tokenizer 的 PPL 不可比。
  • 量化一定会大幅掉点——4-bit 量化在多数任务上只损失 1~3 个点，配合 AWQ/GPTQ 校准可以做到几乎无损。
  • 知识蒸馏只是让学生拟合教师的硬标签——核心是软标签（概率分布）提供的暗知识，温度 T 和 alpha 的调节很关键。

自测

为什么不同 tokenizer 的模型困惑度不能直接比较？

答案：因为困惑度是交叉熵的指数，而交叉熵基于 token 级别的概率。不同 tokenizer 把同一段文本切成的 token 数量和粒度不同，导致每步预测的难度和损失尺度不同，因此 PPL 不可直接对比。

GPTQ、AWQ、GGUF 三种量化方案分别适合什么场景？

答案：GPTQ 适合 GPU 推理，精度较好；AWQ 也是 GPU 推理，激活感知，通常精度略优于 GPTQ；GGUF 适合 CPU/GPU 混合或本地部署（llama.cpp），对硬件要求低。

参考代码： ```python import torch from transformers import AutoModelForCausalLM, AutoTokenizer from datasets import load_dataset model_name = 'distilgpt2' tokenizer = AutoTokenizer.from_pretrained(model_name) # 加载 wikitext-2 测试集 dataset = load_dataset('wikitext', 'wikitext-2-raw-v1', split='test') text = '\n\n'.join(dataset['text']) encodings = tokenizer(text, return_tensors='pt') max_length = 1024 stride = 512 # 计算 PPL 的函数 def compute_ppl(model, encodings): model.eval() nlls = [] for i in range(0, encodings.input_ids.size(1), stride): begin_loc = max(i + stride - max_length, 0) end_loc = min(i + stride, encodings.input_ids.size(1)) trg_len = end_loc - i input_ids = encodings.input_ids[:, begin_loc:end_loc] target_ids = input_ids.clone() target_ids[:, :-trg_len] = -100 with torch.no_grad(): outputs = model(input_ids, labels=target_ids) neg_log_likelihood = outputs.loss * trg_len nlls.append(neg_log_likelihood) ppl = torch.exp(torch.stack(nlls).sum() / end_loc) return ppl.item() # FP32 模型 model_fp32 = AutoModelForCausalLM.from_pretrained(model_name) ppl_fp32 = compute_ppl(model_fp32, encodings) print(f'FP32 PPL: {ppl_fp32:.2f}') # 8-bit 量化模型 model_8bit = AutoModelForCausalLM.from_pretrained(model_name, load_in_8bit=True, device_map='auto') ppl_8bit = compute_ppl(model_8bit, encodings) print(f'8-bit PPL: {ppl_8bit:.2f}') # 显存对比（需在 GPU 上运行） if torch.cuda.is_available(): print(f'FP32 显存: {torch.cuda.max_memory_allocated() / 1024**2:.1f} MB') ``` 预期结果：8-bit 量化的 PPL 略高于 FP32（通常差距 <0.5），但显存占用减少约一半。注意：bitsandbytes 需要 GPU 环境，CPU 上可用 GGUF 替代。

第6章 · 推理优化与服务化

本章目标：掌握推理加速技术，并部署高性能推理服务

推理优化核心技术：KV缓存、连续批处理与PagedAttention

大模型推理的性能瓶颈往往不在计算，而在显存和调度。我们先从最基础的KV缓存说起。

KV缓存（KV Cache）：自回归生成时，每生成一个token都需要重新计算之前所有token的Key和Value，这会造成大量重复计算。KV缓存将历史token的K、V矩阵保存下来，生成新token时只需计算当前token的K、V，然后与缓存拼接。这样将每步计算复杂度从O(n²)降到O(n)，但代价是显存占用随序列长度线性增长。

连续批处理（Continuous Batching）：传统静态批处理要求所有请求同时开始、同时结束，短请求要等长请求，GPU利用率低。连续批处理在每次迭代时动态加入新请求、移除已完成请求，让GPU始终处理尽可能多的token。这就像餐厅翻台，而不是等一桌客人吃完才接待下一桌。

PagedAttention：KV缓存通常需要连续显存，导致碎片化和浪费。PagedAttention借鉴操作系统虚拟内存分页思想，将KV缓存分成固定大小的块（block），非连续存储，按需分配。这样显存利用率可提升数倍，并支持高效的内存共享（如并行采样、beam search）。

下面是一个极简的KV缓存示例，展示其工作原理：

import torch
import torch.nn as nn

class SimpleAttention(nn.Module):
    def __init__(self, dim):
        super().__init__()
        self.q_proj = nn.Linear(dim, dim)
        self.k_proj = nn.Linear(dim, dim)
        self.v_proj = nn.Linear(dim, dim)

    def forward(self, x, kv_cache=None):
        # x: [batch, seq_len, dim]
        q = self.q_proj(x)
        k = self.k_proj(x)
        v = self.v_proj(x)
        if kv_cache is not None:
            past_k, past_v = kv_cache
            k = torch.cat([past_k, k], dim=1)
            v = torch.cat([past_v, v], dim=1)
        # 缩放点积注意力
        attn = torch.softmax(q @ k.transpose(-2, -1) / (q.size(-1) ** 0.5), dim=-1)
        out = attn @ v
        return out, (k, v)

# 模拟生成过程
dim = 64
model = SimpleAttention(dim)
x = torch.randn(1, 1, dim)  # 初始输入
cache = None
for step in range(5):
    out, cache = model(x, cache)
    print(f"Step {step}, cache K shape: {cache[0].shape}")
    x = torch.randn(1, 1, dim)  # 模拟下一个token

运行后你会看到缓存K的形状从[1,1,64]逐步增长到[1,5,64]，这就是KV缓存累积的过程。

主流推理引擎：vLLM、TensorRT-LLM与TGI

自己实现优化太复杂，生产环境通常直接使用推理引擎。目前三大主流选择：

  • vLLM：开源社区最活跃，核心创新是PagedAttention和连续批处理。支持HuggingFace模型无缝加载，吞吐量比原生PyTorch高数倍。适合快速部署和大多数场景。
  • TensorRT-LLM：NVIDIA官方出品，基于TensorRT深度优化，支持量化、内核融合等，在NVIDIA GPU上延迟最低、吞吐最高。但编译流程复杂，模型转换需要额外步骤。

服务化框架：FastAPI与Triton Inference Server

推理引擎负责算得快，服务化框架负责接得住。常见方案：

  • FastAPI：轻量级Python Web框架，异步支持好，适合快速构建RESTful API。可以配合vLLM的AsyncLLMEngine实现流式输出。
  • Triton Inference Server：NVIDIA推出的企业级推理服务框架，支持多模型、多框架（TensorRT、PyTorch、ONNX等），提供动态批处理、模型版本管理、监控指标。适合大规模生产环境。

FastAPI示例：用vLLM的异步引擎提供流式接口。

from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from vllm import AsyncLLMEngine, AsyncEngineArgs, SamplingParams
import asyncio

app = FastAPI()
engine_args = AsyncEngineArgs(model="facebook/opt-125m")
engine = AsyncLLMEngine.from_engine_args(engine_args)

async def generate_stream(prompt: str):
    sampling_params = SamplingParams(temperature=0.8, max_tokens=50)
    request_id = "req-1"
    results_generator = engine.generate(prompt, sampling_params, request_id)
    async for request_output in results_generator:
        text = request_output.outputs[0].text
        yield f"data: {text}\n\n"

@app.get("/generate")
async def generate(prompt: str):
    return StreamingResponse(generate_stream(prompt), media_type="text/event-stream")

# 运行: uvicorn main:app --host 0.0.0.0 --port 8000

API设计与并发处理

设计LLM服务API时，需考虑以下要点：

  • 请求格式：通常包含prompt、max_tokens、temperature、top_p、stream等参数。建议使用JSON Schema校验。
  • 流式响应：使用Server-Sent Events (SSE) 或WebSocket，提升用户体验。注意设置正确的Content-Type和心跳。
  • 并发控制：推理引擎本身支持连续批处理，但API层仍需限制最大并发数，避免过载。可以使用信号量或队列。
  • 超时与重试：为每个请求设置超时，客户端实现指数退避重试。
  • 监控：记录QPS、延迟、错误率、GPU利用率等指标。

一个简单的并发控制示例：

import asyncio
from fastapi import FastAPI, HTTPException

app = FastAPI()
semaphore = asyncio.Semaphore(10)  # 最大并发10

@app.post("/generate")
async def generate(prompt: str):
    if semaphore.locked():
        raise HTTPException(status_code=429, detail="Too many requests")
    async with semaphore:
        # 模拟推理耗时
        await asyncio.sleep(1)
        return {"result": f"Generated for: {prompt}"}

更完善的做法是使用队列和限流中间件，如slowapi。

常见误区

  • KV缓存会减少显存占用：实际上KV缓存增加了显存占用，但减少了计算量。它用空间换时间。
  • 连续批处理就是动态批处理：连续批处理在每次迭代时动态调整批次，而动态批处理通常指在请求到达时组批，但批次内请求仍需同时完成。
  • PagedAttention只能用于vLLM：PagedAttention是一种通用技术，其他引擎如TensorRT-LLM也借鉴了类似思想。

使用LoRA微调模型

LoRA（Low-Rank Adaptation）是一种参数高效微调方法，它冻结原模型参数，只在Transformer层的注意力模块中注入可训练的低秩矩阵。这样可训练参数减少到原来的0.1%~1%，显存需求大幅降低。

使用Hugging Face的peft库可以轻松实现LoRA微调。关键参数：

  • r：低秩矩阵的秩，通常8~32。
  • lora_alpha：缩放因子，一般设为r的2倍。
  • target_modules：要注入的模块，如["q_proj", "v_proj"]。

下面是一个完整的微调脚本（以Qwen2.5-7B为例）：

from transformers import AutoModelForCausalLM, AutoTokenizer, TrainingArguments
from peft import LoraConfig, get_peft_model
from trl import SFTTrainer
from datasets import load_dataset

model_name = "Qwen/Qwen2.5-7B"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, device_map="auto")

# 配置LoRA
lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM"
)
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()  # 查看可训练参数比例

# 加载数据集
dataset = load_dataset("yahma/alpaca-cleaned", split="train[:1000]")

# 训练参数
training_args = TrainingArguments(
    output_dir="./lora_output",
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,
    learning_rate=2e-4,
    num_train_epochs=3,
    logging_steps=10,
    save_strategy="epoch",
    fp16=True,
)

# 使用SFTTrainer
trainer = SFTTrainer(
    model=model,
    args=training_args,
    train_dataset=dataset,
    tokenizer=tokenizer,
    dataset_text_field="text",  # 需要将数据格式化为文本
    max_seq_length=512,
)
trainer.train()
model.save_pretrained("./lora_adapter")

注意：实际使用时需要将数据集格式化为包含instruction、input、output的文本，例如：### Instruction:\n{instruction}\n### Input:\n{input}\n### Response:\n{output}。

模型量化与导出

微调后，为了部署，通常需要将模型量化以减小显存占用和加速推理。常见的量化方法有：

  • GPTQ：训练后量化，4-bit，精度损失小。
  • AWQ：激活感知权重量化，适合LLM。
  • GGUF：llama.cpp使用的格式，适合CPU推理。

这里以GPTQ为例，使用auto-gptq库进行量化：

from transformers import AutoModelForCausalLM, AutoTokenizer
from auto_gptq import AutoGPTQForCausalLM, BaseQuantizeConfig

model_name = "Qwen/Qwen2.5-7B"
tokenizer = AutoTokenizer.from_pretrained(model_name)

# 量化配置
quantize_config = BaseQuantizeConfig(
    bits=4,
    group_size=128,
    desc_act=False,
)

# 加载模型并量化
model = AutoGPTQForCausalLM.from_pretrained(model_name, quantize_config)

# 准备校准数据（少量样本）
calibration_dataset = ["示例文本1", "示例文本2"]  # 实际需更多

# 执行量化
model.quantize(calibration_dataset)
model.save_quantized("./qwen2.5-7b-gptq")
tokenizer.save_pretrained("./qwen2.5-7b-gptq")

量化后模型大小约为原模型的1/4，显存需求从~14GB降至~4GB。

如果使用LoRA微调，也可以将LoRA权重合并到基座模型后再量化：

from peft import PeftModel

merged_model.save_pretrained("./merged_model")

监控与日志：让LLM服务“看得见”

LLM服务上线后，最怕的就是“黑盒”运行——你不知道它是否健康、响应是否变慢、有没有报错。监控（Monitoring）就是给服务装上眼睛和耳朵。对于LLM服务，除了常规的CPU、内存、网络指标，还要关注推理延迟（P99）、每秒查询数（QPS）、Token吞吐量、错误率等业务指标。

# 定义指标
REQUEST_COUNT = Counter('llm_requests_total', 'Total LLM requests', ['method', 'endpoint', 'status'])
REQUEST_LATENCY = Histogram('llm_request_latency_seconds', 'LLM request latency', ['endpoint'])
TOKEN_COUNT = Counter('llm_tokens_total', 'Total tokens generated')

@app.middleware("http")
async def monitor_requests(request: Request, call_next):
    start_time = time.time()
    response = await call_next(request)
    latency = time.time() - start_time
    REQUEST_COUNT.labels(method=request.method, endpoint=request.url.path, status=response.status_code).inc()
    REQUEST_LATENCY.labels(endpoint=request.url.path).observe(latency)
    return response

@app.post("/generate")
async def generate(prompt: str):
    # 模拟LLM推理
    time.sleep(random.uniform(0.1, 0.5))
    tokens = random.randint(10, 100)
    TOKEN_COUNT.inc(tokens)
    return {"response": f"Generated {tokens} tokens for prompt: {prompt}"}

@app.get("/metrics")
async def metrics():
    return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)

自动扩缩容与负载均衡：应对流量洪峰

LLM推理通常很耗资源，流量波动大。如果一直保持高配，成本会爆炸；如果配置不足，高峰期又会超时。自动扩缩容（Auto Scaling）根据指标动态调整实例数量，是平衡成本与性能的关键。

在Kubernetes中，可以使用 Horizontal Pod Autoscaler (HPA)，基于CPU、内存或自定义指标（如QPS、延迟）来扩缩Pod。对于LLM服务，更推荐基于请求队列长度或GPU利用率来扩缩。同时，负载均衡将请求分发到多个实例，常用方案有Nginx、HAProxy或云厂商的LB。

下面是一个Kubernetes HPA配置示例，基于CPU利用率扩缩：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: llm-inference-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: llm-inference
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

如果使用云服务，AWS的ALB+ECS、GCP的Cloud Run等也支持自动扩缩。注意：LLM实例启动可能较慢（加载模型），需要设置合理的冷却时间，避免频繁扩缩。

安全与合规：内容过滤与隐私保护

LLM可能生成有害内容或泄露隐私，生产环境必须考虑内容过滤（Content Filtering）和隐私保护。内容过滤可以在输入和输出两个阶段进行：输入过滤防止恶意提示，输出过滤防止不当内容。常用方法包括关键词黑名单、分类模型（如毒性检测）和基于规则的后处理。

隐私保护方面，要避免训练数据中的个人身份信息（PII）被模型记忆并泄露。可以在预处理阶段脱敏，或在推理时使用差分隐私技术。此外，传输层加密（HTTPS）、访问控制、审计日志也是必备。

下面是一个简单的内容过滤示例，使用关键词和正则表达式：

import re

# 敏感词列表（实际应更全面）
BANNED_WORDS = ["暴力", "色情", "政治敏感"]

def contains_banned_content(text: str) -> bool:
    for word in BANNED_WORDS:
        if word in text:
            return True
    # 检测邮箱、电话等PII
    if re.search(r'[\w\.-]+@[\w\.-]+\.\w+', text):
        return True
    if re.search(r'\d{11}', text):
        return True
    return False

def filter_response(prompt: str, response: str) -> str:
    if contains_banned_content(prompt):
        return "您的输入包含不当内容，请修改后重试。"
    if contains_banned_content(response):
        return "抱歉，我无法回答该问题。"
    return response

# 测试
print(filter_response("你好", "你好，有什么可以帮助你？"))
print(filter_response("如何制作炸弹", "..."))

对于更高级的过滤，可以集成开源模型如 openai/moderation 或 unitary/toxic-bert。合规方面，需遵循GDPR、CCPA等法规，提供数据删除接口。

成本优化与缓存策略：省钱又提速

LLM推理成本高昂，成本优化（Cost Optimization）是生产运维的核心任务之一。主要手段包括：模型量化、蒸馏、使用更小的模型、批处理（batching）、以及缓存。

缓存策略尤其有效：对于相同或相似的请求，直接返回缓存结果，避免重复计算。常见方案有：精确缓存（键为完整输入）和语义缓存（键为输入嵌入向量，相似则命中）。精确缓存实现简单，适合FAQ场景；语义缓存需要向量数据库，但命中率更高。

下面是一个基于Redis的精确缓存示例：

import redis
import hashlib
import json

r = redis.Redis(host='localhost', port=6379, db=0)

def get_cache_key(prompt: str, model: str) -> str:
    content = f"{model}:{prompt}"
    return hashlib.sha256(content.encode()).hexdigest()

def cached_generate(prompt: str, model: str = "gpt-3.5"):
    key = get_cache_key(prompt, model)
    cached = r.get(key)
    if cached:
        return json.loads(cached)
    # 模拟调用LLM
    response = f"LLM response for: {prompt}"
    r.setex(key, 3600, json.dumps(response))  # 缓存1小时
    return response

# 第一次调用，缓存未命中
print(cached_generate("什么是LLM？"))
# 第二次调用，命中缓存
print(cached_generate("什么是LLM？"))

此外，还可以使用请求批处理：将多个请求合并成一个批次送给模型，提高GPU利用率。但要注意延迟与吞吐的权衡。监控缓存命中率，持续优化缓存策略。

常见误区

  • 监控只需要关注CPU和内存，LLM服务的业务指标（如Token吞吐、延迟）不重要。
  • 自动扩缩容可以立即响应流量变化，无需考虑冷启动时间。
  • 内容过滤只需在输出端进行，输入端不需要过滤。

自测

在LLM服务监控中，为什么需要特别关注P99延迟而不是平均延迟？

答案：P99延迟表示99%的请求在多少时间内完成，能反映长尾请求的体验。平均延迟可能被大量快速请求拉低，掩盖少数慢请求的问题，而慢请求往往导致用户不满。

语义缓存和精确缓存的主要区别是什么？各自适用什么场景？

答案：精确缓存基于完整输入字符串的哈希，只有完全相同的请求才命中；语义缓存基于输入嵌入向量的相似度，相似但不完全相同的请求也能命中。精确缓存实现简单，适合FAQ等重复率高的场景；语义缓存命中率更高，但需要向量数据库和相似度计算，适合用户问法多样的场景。
