监控与日志：让LLM服务“看得见”

LLM服务上线后，最怕的就是“黑盒”运行——你不知道它是否健康、响应是否变慢、有没有报错。监控（Monitoring）就是给服务装上眼睛和耳朵。对于LLM服务，除了常规的CPU、内存、网络指标，还要关注推理延迟（P99）、每秒查询数（QPS）、Token吞吐量、错误率等业务指标。

业界标准方案是 Prometheus + Grafana：Prometheus负责采集和存储时序数据，Grafana负责可视化。你需要在服务中暴露一个 /metrics 端点，Prometheus定期拉取（pull）数据。Python生态中，prometheus_client 库可以轻松实现。

下面是一个最小示例：用FastAPI启动一个LLM推理服务，并暴露Prometheus指标。

python
from fastapi import FastAPI, Request
from prometheus_client import Counter, Histogram, generate_latest, CONTENT_TYPE_LATEST
from starlette.responses import Response
import time
import random

app = FastAPI()

# 定义指标
REQUEST_COUNT = Counter('llm_requests_total', 'Total LLM requests', ['method', 'endpoint', 'status'])
REQUEST_LATENCY = Histogram('llm_request_latency_seconds', 'LLM request latency', ['endpoint'])
TOKEN_COUNT = Counter('llm_tokens_total', 'Total tokens generated')

@app.middleware("http")
async def monitor_requests(request: Request, call_next):
    start_time = time.time()
    response = await call_next(request)
    latency = time.time() - start_time
    REQUEST_COUNT.labels(method=request.method, endpoint=request.url.path, status=response.status_code).inc()
    REQUEST_LATENCY.labels(endpoint=request.url.path).observe(latency)
    return response

@app.post("/generate")
async def generate(prompt: str):
    # 模拟LLM推理
    time.sleep(random.uniform(0.1, 0.5))
    tokens = random.randint(10, 100)
    TOKEN_COUNT.inc(tokens)
    return {"response": f"Generated {tokens} tokens for prompt: {prompt}"}

@app.get("/metrics")
async def metrics():
    return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)

运行后，访问 http://localhost:8000/metrics 就能看到指标。然后在Prometheus配置中抓取该端点，Grafana中导入仪表盘即可。日志方面，建议使用结构化日志（如JSON格式），并集中收集到ELK或Loki中，方便排查问题。

自动扩缩容与负载均衡：应对流量洪峰

LLM推理通常很耗资源，流量波动大。如果一直保持高配，成本会爆炸；如果配置不足，高峰期又会超时。自动扩缩容（Auto Scaling）根据指标动态调整实例数量，是平衡成本与性能的关键。

在Kubernetes中，可以使用 Horizontal Pod Autoscaler (HPA)，基于CPU、内存或自定义指标（如QPS、延迟）来扩缩Pod。对于LLM服务，更推荐基于请求队列长度或GPU利用率来扩缩。同时，负载均衡将请求分发到多个实例，常用方案有Nginx、HAProxy或云厂商的LB。

下面是一个Kubernetes HPA配置示例，基于CPU利用率扩缩：

yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: llm-inference-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: llm-inference
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

如果使用云服务，AWS的ALB+ECS、GCP的Cloud Run等也支持自动扩缩。注意：LLM实例启动可能较慢（加载模型），需要设置合理的冷却时间，避免频繁扩缩。

安全与合规：内容过滤与隐私保护

LLM可能生成有害内容或泄露隐私，生产环境必须考虑内容过滤（Content Filtering）和隐私保护。内容过滤可以在输入和输出两个阶段进行：输入过滤防止恶意提示，输出过滤防止不当内容。常用方法包括关键词黑名单、分类模型（如毒性检测）和基于规则的后处理。

隐私保护方面，要避免训练数据中的个人身份信息（PII）被模型记忆并泄露。可以在预处理阶段脱敏，或在推理时使用差分隐私技术。此外，传输层加密（HTTPS）、访问控制、审计日志也是必备。

下面是一个简单的内容过滤示例，使用关键词和正则表达式：

python
import re

# 敏感词列表（实际应更全面）
BANNED_WORDS = ["暴力", "色情", "政治敏感"]

def contains_banned_content(text: str) -> bool:
    for word in BANNED_WORDS:
        if word in text:
            return True
    # 检测邮箱、电话等PII
    if re.search(r'[\w\.-]+@[\w\.-]+\.\w+', text):
        return True
    if re.search(r'\d{11}', text):
        return True
    return False

def filter_response(prompt: str, response: str) -> str:
    if contains_banned_content(prompt):
        return "您的输入包含不当内容，请修改后重试。"
    if contains_banned_content(response):
        return "抱歉，我无法回答该问题。"
    return response

# 测试
print(filter_response("你好", "你好，有什么可以帮助你？"))
print(filter_response("如何制作炸弹", "..."))

对于更高级的过滤，可以集成开源模型如 openai/moderation 或 unitary/toxic-bert。合规方面，需遵循GDPR、CCPA等法规，提供数据删除接口。

成本优化与缓存策略：省钱又提速

LLM推理成本高昂，成本优化（Cost Optimization）是生产运维的核心任务之一。主要手段包括：模型量化、蒸馏、使用更小的模型、批处理（batching）、以及缓存。

缓存策略尤其有效：对于相同或相似的请求，直接返回缓存结果，避免重复计算。常见方案有：精确缓存（键为完整输入）和语义缓存（键为输入嵌入向量，相似则命中）。精确缓存实现简单，适合FAQ场景；语义缓存需要向量数据库，但命中率更高。

下面是一个基于Redis的精确缓存示例：

python
import redis
import hashlib
import json

r = redis.Redis(host='localhost', port=6379, db=0)

def get_cache_key(prompt: str, model: str) -> str:
    content = f"{model}:{prompt}"
    return hashlib.sha256(content.encode()).hexdigest()

def cached_generate(prompt: str, model: str = "gpt-3.5"):
    key = get_cache_key(prompt, model)
    cached = r.get(key)
    if cached:
        return json.loads(cached)
    # 模拟调用LLM
    response = f"LLM response for: {prompt}"
    r.setex(key, 3600, json.dumps(response))  # 缓存1小时
    return response

# 第一次调用，缓存未命中
print(cached_generate("什么是LLM？"))
# 第二次调用，命中缓存
print(cached_generate("什么是LLM？"))

此外，还可以使用请求批处理：将多个请求合并成一个批次送给模型，提高GPU利用率。但要注意延迟与吞吐的权衡。监控缓存命中率，持续优化缓存策略。

常见误区

  • 监控只需要关注CPU和内存，LLM服务的业务指标（如Token吞吐、延迟）不重要。
  • 自动扩缩容可以立即响应流量变化，无需考虑冷启动时间。
  • 内容过滤只需在输出端进行，输入端不需要过滤。

自测

在LLM服务监控中，为什么需要特别关注P99延迟而不是平均延迟？

答案：P99延迟表示99%的请求在多少时间内完成，能反映长尾请求的体验。平均延迟可能被大量快速请求拉低，掩盖少数慢请求的问题，而慢请求往往导致用户不满。

语义缓存和精确缓存的主要区别是什么？各自适用什么场景？

答案：精确缓存基于完整输入字符串的哈希，只有完全相同的请求才命中；语义缓存基于输入嵌入向量的相似度，相似但不完全相同的请求也能命中。精确缓存实现简单，适合FAQ等重复率高的场景；语义缓存命中率更高，但需要向量数据库和相似度计算，适合用户问法多样的场景。
