部署与优化实战

本章目标：动手部署LLM并优化推理性能

环境准备配好硬件与依赖，跑通基线→模型部署选推理框架，服务化上线→性能压测测延迟吞吐，找瓶颈→推理优化量化缓存并行，逐项提速→回归验证对比效果成本，固化配置
部署不是终点：压测找瓶颈、优化再验证，形成性能闭环。

部署环境搭建：CUDA、PyTorch、Transformers库

把部署 LLM 想象成开一家餐厅：CUDA 是厨房里的燃气管道，PyTorch 是灶台和锅具，Transformers 则是已经备好食材的半成品料理包。没有燃气，灶台点不着；没有灶台，料理包也做不成菜。所以环境搭建的顺序是：先确认燃气（驱动与 CUDA 运行时）可用，再装灶台（PyTorch），最后引入料理包（Transformers）。

技术细节上，CUDA 是 NVIDIA 的并行计算平台，它让 PyTorch 能把矩阵运算下发给 GPU 执行。你并不一定需要单独安装完整的 CUDA Toolkit——直接安装 PyTorch 的 CUDA 版本时，它会自带所需的 CUDA 运行时库，这能避开大部分版本冲突。真正需要你单独装的是显卡驱动，驱动版本决定了它能支持的最高 CUDA 版本。例如驱动支持 CUDA 12.1，就选 cu121 的 PyTorch 安装包；选错版本，torch.cuda.is_available() 就会返回 False。

PyTorch 是深度学习框架，LLM 的推理与训练都依赖它；Transformers 是 Hugging Face 的库，封装了大量预训练模型和统一 API，几行代码就能完成加载、分词和生成。下面是最小可运行示例：先安装依赖，再验证 GPU 是否可用。预期输出第一行是类似 2.x.x+cu121 的版本号，第二行是 True。

python
# 安装 PyTorch（CUDA 12.1 版本）与 Transformers
# pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu121
# pip install transformers accelerate

import torch
print(torch.__version__)          # 预期：2.x.x+cu121
print(torch.cuda.is_available())  # 预期：True
print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else "no gpu")

如果第二行输出 False，按「驱动 → CUDA 版本 → PyTorch 安装包」的顺序排查：先用 nvidia-smi 看驱动支持的 CUDA 版本，再确认安装的 PyTorch 是否匹配。环境搭好，后面的量化与推理优化才有稳定的地基。

模型量化与剪枝：减少显存占用与加速推理

模型权重就像一本用极细字体印刷的百科全书：信息完整，但占地方、翻得慢。量化相当于把字体换成更粗的版本——大部分内容仍然读得懂，但书变薄了、翻页更快了；剪枝则相当于直接撕掉那些几乎没人查阅的页，书更薄，但撕多了可能丢掉关键内容。两者目标一致：用更少的资源跑同样的任务。

量化 (Quantization) 把权重从高精度（如 FP32、FP16）转换为低精度（如 INT8、INT4）。精度越低，显存占用越小、推理通常越快，但可能损失一点准确率。常见路线有训练后量化（PTQ）和量化感知训练（QAT）。Hugging Face 生态里，bitsandbytes 支持 8-bit 和 4-bit 加载，基本是一行参数的事。以 7B 模型为例，FP16 权重约需 14 GB 显存，INT8 约 7 GB，INT4 约 3.5 GB——这就是「显存减少 50%~75%」说法的来源（具体数值随模型与实现略有差异，待核实）。

剪枝 (Pruning) 移除不重要的权重（置零或删除），分为非结构化剪枝（单个权重）和结构化剪枝（整个神经元或注意力头）。结构化剪枝对硬件更友好，但剪枝后通常需要微调来恢复性能。下面是最小示例：用 4-bit 量化加载模型并查看设备分配。预期输出会打印模型所在设备（如 cuda:0），且显存占用明显低于 FP16 加载。

python
# pip install bitsandbytes
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

model_name = "gpt2"  # 演示用小模型；换成 Llama 等需申请权限
# 注意：gpt2 的 4-bit 加载在部分 bitsandbytes 版本上可能报错，可改用支持量化的模型（待核实）
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    load_in_4bit=True,        # 4-bit 量化
    device_map="auto",        # 自动分配设备
    torch_dtype=torch.float16
)
print(model.device)  # 预期：cuda:0 或 auto 分配到的设备

需要提醒的是，量化不是「越狠越好」：4-bit 对多数生成任务影响较小，但在数学推理、代码生成等对数值敏感的任务上，精度损失可能被放大。实践中的做法是先用 4-bit 跑通并测质量，若不达标再退回 8-bit 或 FP16。

推理优化：批处理、KV缓存、Flash Attention

模型能跑起来只是及格线，跑得快才是部署的目标。可以把自回归生成想象成写作文：每写一个字，都要回头把前面写过的内容重新读一遍。如果每次都从头读，写 100 个字就要读约 5000 次；如果手边有一份「前文摘要」，每次只读摘要，速度就快得多。KV 缓存就是这份摘要，批处理是同时写多篇作文，Flash Attention 则是更高效的阅读方式。

批处理 (Batching) 一次处理多个输入，提高 GPU 利用率。但简单批处理需要把序列 padding 到同一长度，短序列会浪费算力；动态批处理（如 vLLM 的 continuous batching）能在请求级别动态拼批，显著提升吞吐。KV 缓存 (KV Cache) 把自回归生成中历史 token 的 Key/Value 矩阵存下来，避免重复计算——没有 KV 缓存，生成速度会慢几倍，代价是缓存本身占用显存，序列越长占用越大。Flash Attention 通过分块计算减少显存读写，PyTorch 2.0+ 已内置支持，加载模型时设置 attn_implementation="flash_attention_2" 即可（需安装 flash-attn，且需要 Ampere 架构以上 GPU，如 RTX 30 系、A100）。

下面的最小示例演示启用 Flash Attention 并生成文本。预期输出是一段以 “The future of AI is” 开头的续写文本；若你的 GPU 不支持，把 attn_implementation 去掉即可回退到默认注意力实现。

python
# pip install flash-attn --no-build-isolation  # 需要 Ampere 以上 GPU
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

model_name = "gpt2"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.float16,
    attn_implementation="flash_attention_2"  # 不支持时删掉此行
).to("cuda")

inputs = tokenizer("The future of AI is", return_tensors="pt").to("cuda")
outputs = model.generate(**inputs, max_new_tokens=50, use_cache=True)  # KV 缓存默认开启
print(tokenizer.decode(outputs[0], skip_special_tokens=True))

三项技术并不互斥：批处理提升吞吐，KV 缓存降低单请求延迟，Flash Attention 降低注意力层的显存访问。实际部署中，它们常常叠加使用，再配合 vLLM 或 text-generation-inference 这类推理服务框架，才能同时扛住高并发与低延迟。

实战：使用 Hugging Face 部署一个 LLM 并评测

前面三节分别解决了「能跑」「省显存」「跑得快」，这一节把它们串成一条可验收的流水线：加载模型 → 编写推理函数 → 用多个 prompt 测质量 → 测延迟与吞吐。评测就像给餐厅出餐计时：不仅要看一道菜做多久（延迟），还要看一小时能出多少道菜（吞吐）。

技术细节上，延迟 (Latency) 指生成一个回复的总耗时；吞吐量 (Throughput) 指每秒生成的 token 数，可用「生成 token 数 ÷ 耗时」估算。注意 model.generate 返回的序列包含输入 token，统计新生成 token 数时要减去输入长度，否则吞吐会被高估。下面是一个完整可独立运行的示例，使用 gpt2 避免权限问题，可替换为其他模型。预期输出会为每个 prompt 打印生成文本与延迟，例如 Latency: 0.8s 量级（具体数值取决于硬件）。

python
from transformers import AutoModelForCausalLM, AutoTokenizer
import torch, time

model_name = "gpt2"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name, torch_dtype=torch.float16, device_map="auto"
)

def generate(prompt, max_new_tokens=50):
    inputs = tokenizer(prompt, return_tensors="pt").to(model.device)
    start = time.time()
    outputs = model.generate(
        **inputs, max_new_tokens=max_new_tokens,
        do_sample=True, temperature=0.7, use_cache=True
    )
    latency = time.time() - start
    new_tokens = outputs.shape[1] - inputs["input_ids"].shape[1]
    text = tokenizer.decode(outputs[0], skip_special_tokens=True)
    return text, latency, new_tokens / latency  # 文本、延迟、吞吐(token/s)

for p in ["The capital of France is", "Explain quantum computing in simple terms:"]:
    text, latency, tps = generate(p)
    print(f"Prompt: {p}\nOutput: {text}\nLatency: {latency:.2f}s  Throughput: {tps:.1f} tok/s\n")

拿到基线数据后，就可以做对照实验：把 use_cache 设为 False 看延迟变化，把 max_new_tokens 调大看吞吐趋势，或换用量化模型看显存与速度的权衡。如果显存不足，优先尝试量化或换更小模型；如果要面向生产环境提供 API，可进一步使用 vLLM 或 text-generation-inference 部署，它们内置了动态批处理和分页 KV 缓存。

常见误区

  • 错误理解：量化一定会显著降低模型准确率。→ 后果：因为担心质量而不敢用量化，白白浪费显存和成本，或者在必须量化的场景下过度保守、选了不必要的 8-bit 而非 4-bit。→ 正确做法：4-bit 量化对多数生成任务影响较小，应先用目标任务的评测集实测质量，再决定精度档位；对数值敏感的任务（数学、代码）才需要更谨慎。
  • 错误理解：KV 缓存会一直占用显存、无法释放。→ 后果：长序列或多并发场景下显存持续膨胀，最终 OOM，或者误以为只能重启进程解决。→ 正确做法：KV 缓存的生命周期与一次生成请求绑定，请求结束即可释放；也可设置 use_cache=False 关闭，生产环境可用 vLLM 的分页注意力动态管理缓存。
  • 错误理解：Flash Attention 在所有 GPU 上都能用。→ 后果：在旧卡上强行设置 attn_implementation="flash_attention_2" 导致加载报错，误以为环境装坏了。→ 正确做法：它需要 Ampere 架构以上 GPU（如 RTX 30 系、A100），旧卡应去掉该参数回退到默认注意力实现。

自测

KV 缓存的作用是什么？为什么它能加速推理？请结合自回归生成的步骤说明。

答案：自回归生成每产生一个新 token，都要对之前所有 token 做注意力计算，其中会反复用到历史 token 的 Key 和 Value 矩阵。若不缓存，生成第 n 个 token 时就要重算前 n-1 个 token 的 K/V，总计算量随序列长度呈平方级增长。KV 缓存把这些 K/V 存下来，新 token 只需计算自己的 K/V 并与缓存拼接，历史部分直接复用。因此它把「重复计算」变成「一次计算、多次读取」，显著降低计算量、加速推理；代价是缓存占用显存，序列越长占用越大。

模型量化有哪些常见精度？各有什么优缺点？为什么 4-bit 量化对显存的影响大约是 FP16 的四分之一？

答案：常见精度有 FP32（全精度，显存大、速度慢）、FP16/BF16（半精度，精度与显存较平衡）、INT8（8 位整数，显存约为 FP16 的一半，速度提升，精度略降）、INT4（4 位整数，显存约为 FP16 的四分之一，速度更快，精度损失稍大）。显存比例来自每个权重占用的比特数：FP16 是 16 bit，INT4 是 4 bit，理论上权重显存就是 1/4；实际还会叠加量化缩放因子等少量开销，所以是「大约」。选择取决于硬件和任务对精度的要求。

在评测推理性能时，为什么统计吞吐量要减去输入 token 数？如果直接用输出序列总长度除以耗时，会得到什么错误结论？

答案：model.generate 返回的序列包含输入 prompt 的 token 和新生成的 token，而吞吐量衡量的是「每秒生成多少新 token」。若直接用总长度除以耗时，输入越长，被高估得越厉害。例如输入 100 token、生成 50 token、耗时 1 秒，真实吞吐是 50 tok/s，但用总长度算会得到 150 tok/s，虚高 3 倍。这会导致不同 prompt 长度下的对比失真，甚至误判优化是否有效。正确做法是用 outputs.shape[1] 减去输入长度得到新生成 token 数，再除以耗时。

动手练习（带参考方案）

练习 · 使用 Hugging Face Transformers 加载一个预训练语言模型（如 gpt2 或 distilgpt2…

任务：使用 Hugging Face Transformers 加载一个预训练语言模型（如 gpt2 或 distilgpt2），分别以 FP16 和 8-bit 量化方式加载，在相同输入下测量并比较两者的显存占用与生成速度。要求：记录每种方式的峰值显存（GB）和延迟（秒），并写一段分析说明差异来源。验收标准：代码可独立运行，输出包含两种方式的显存与延迟数值。

参考方案：

python
# pip install torch transformers bitsandbytes accelerate
import torch, time
from transformers import AutoModelForCausalLM, AutoTokenizer

model_name = "gpt2"
tokenizer = AutoTokenizer.from_pretrained(model_name)
prompt = "The future of AI is"
inputs = tokenizer(prompt, return_tensors="pt").to("cuda")

def measure(load_kwargs, label):
    torch.cuda.empty_cache()
    torch.cuda.reset_peak_memory_stats()
    model = AutoModelForCausalLM.from_pretrained(model_name, device_map="auto", **load_kwargs)
    start = time.time()
    with torch.no_grad():
        model.generate(**inputs, max_new_tokens=50, use_cache=True)
    latency = time.time() - start
    peak = torch.cuda.max_memory_allocated() / 1e9
    print(f"{label}: latency={latency:.2f}s, peak_memory={peak:.2f}GB")
    del model
    torch.cuda.empty_cache()

measure({"torch_dtype": torch.float16}, "FP16")
measure({"load_in_8bit": True}, "8-bit")

# 分析：8-bit 每个权重占 8 bit，FP16 占 16 bit，权重显存理论上减半；
# 延迟差异取决于硬件与 kernel 实现，8-bit 可能略快或相近；
# 生成质量可能轻微下降，需用任务评测集确认。
