深入理解 Ontology（本体）

Ontology 是一个有两千多年历史、被两次「发明」的概念：一次在古希腊的哲学课堂，一次在 1990 年代的知识工程实验室。 本章带你看清它的全貌——它是什么、怎么建模、怎么查询，以及它为什么恰好是 Agent 时代最被低估的基础设施。

目标：真正理解而非背名词 交互实验：Ontology 实验室 与第 4、7、9 章强关联 rdflib 实战 + LLM 抽取管线 练习：3 题（带参考答案）

6.1 两次发明：从哲学到计算机

哲学中的 ontology（本体论）是形而上学的核心分支，研究「存在本身」：世界上有哪些东西？它们分属哪些基本范畴？如何组织？ 亚里士多德在《范畴篇》里给出了最早的「顶层分类」——十范畴：实体、数量、性质、关系、地点、时间、姿态、状况、主动、被动。 这其实就是一次「顶层本体建模」的尝试。

1990 年代，知识工程界把这个词借了过去，含义从「研究存在」变成「把某个领域的存在方式明确地写下来」。 最重要的定义来自 Thomas Gruber（1993）：

经典定义（Gruber 1993）

"An ontology is an explicit specification of a conceptualization."
（本体是对概念化的明确说明。）
Studer 等人后来补全为："formal, explicit specification of a shared conceptualization"——共享概念化的形式化、明确的规范说明。四个词各有分量：

• 概念化（conceptualization）：我们对领域「有哪些概念、它们如何关联」的抽象认识
• 明确（explicit）：概念的类型与使用约束被显式写出，不靠心照不宣
• 形式化（formal）：机器可读、可推理（而不是一篇散文）
• 共享（shared）：被一个群体共同认可——这是它与个人笔记的本质区别

经典文献入口

本节定义的两份原始文献：Gruber (1993)（Ontology 定义的出处）与 Ontology Development 101（6.6 节七步法的原型教程）——导读见 论文精读页。

6.2 Palantir Ontology：本体如何变成企业操作系统

如果说语义网本体回答的是「世界有哪些概念」，那么 Palantir Foundry 的 Ontology 回答的是另一个更锋利的问题： 一家企业的业务如何运转，以及如何被安全地操作。它是 Agent 时代最成功的工业级本体实现——理解它，你就理解了「本体」这个词为什么突然变得如此值钱， 也理解了「知识库 / 记忆 / 工具」这三样东西在企业里最终要汇合成什么。

核心三件套：对象 · 链接 · 动作

Palantir 的本体由三种一等公民构成（官方术语 Object Types / Link Types / Action Types）。注意它们与第 6.3 节纯描述性要素的微妙差异——多了一种「动作」：

组件是什么工单域的例子关键性质
Object Type 对象类型业务实体的数字化身：类型化属性 + 主键，底层由数据集 / 流数据实时同步Customer、Ticket、SupportAgent对象是「活的」：带着权限、血缘、版本——不是一张死表
Link Type 链接类型对象之间的关系本体（可多对多、可携带属性）Ticket —submitted_by→ Customer；Ticket —assigned_to→ SupportAgent关系不再藏在某张表的字段里，而是一等公民，可被检索、可被治理
Action Type 动作类型对对象状态的唯一合法写入口：声明式校验 + 权限检查 + 副作用编排escalateTicket(升级工单)、issueRefund(退款)业务流程本体化：谁、在什么条件下、能把世界改成什么样

第四个角色是 Function：挂在对象上的纯计算逻辑（如 calcSLA(ticket) → 剩余响应时长）——可测试、可复用，并且和 Action 一样能被 AI 直接调用。

AIP：当 Agent 走进本体

Palantir 的 AI 层（AIP）让大模型直接「活」在本体上，接线方式出奇地眼熟——正是你在第 1–7 章亲手搭过的那套结构：

  • 工具 = Action Types + Functions：模型不再面对一堆裸 API，而是面对一排经过校验与授权的本体动作——每次调用天然带校验、权限与审计；
  • 上下文 = 对象与链接：模型的"知识"不是文档碎片，而是当前业务对象及其关系图（通过 MCP 工具集 / OSDK 把本体暴露给模型）；
  • 权限继承：Agent 以用户的身份行动——用户在本体里看不见的工单，Agent 也碰不到。
Action Type = Agent 的高危工具闸门

第 7 章的权限分级（auto / confirm / deny）在 Palantir 体系里是原生能力：Action 的校验与审批规则定义在本体上，任何调用者（人类或 Agent）都走同一道闸门。这就是「本体 + Agent」组合真正的卖点：LLM 提供灵活性，本体提供确定性，二者各自负责自己擅长的部分——与第 3 章结构化输出闭环、第 6 章抽取校验管线是同一条工程哲学。

建模实例：客服工单域（可直接映射到你的项目）

yaml · 客服工单域的 Ontology 定义（示意）
objectTypes:
  - Customer: { primaryKey: id, properties: [name, tier, since] }
  - Ticket:   { primaryKey: id, properties: [title, status, priority, createdAt] }
linkTypes:
  - submitted_by: Customer 1..n Ticket
  - assigned_to:  SupportAgent 1..n Ticket
functions:
  - calcSLA(ticket) → 剩余响应时长（纯计算）
actionTypes:
  - escalateTicket(ticketId, reason):
      校验: ticket.status in [open, pending]；reason 非空
      副作用: status → escalated；通知值班经理；写审计日志
      权限: 仅当班组长及以上
  - issueRefund(ticketId, amount):
      校验: amount <= 500（超过需人工审批——即 confirm 级）
      权限: 客服主管

映射到 Agent 的工具清单时，每一行都是你在第 2 章已经写过的 JSON Schema——区别只在于：这里的工具背后站着校验、权限与审计：

模型可能要做的事对应本体组件对应你的 Harness
「查一下这个客户的历史工单」Object 检索 + Link 遍历只读工具（auto）
「这单还剩多久超时」Function: calcSLA只读工具（auto）
「把这单升级给经理」Action: escalateTicket写入工具（校验 + 审计）
「给客户退 300 块」Action: issueRefund写入工具（confirm 级，人工审批）

两条路线的对比：语义网本体 vs Palantir 本体

现在回答一个必然的困惑：第 6.5 节的 RDF/OWL 和 Palantir 的对象-链接-动作，到底是不是一回事？——同一门学科的两条路线，服务两种目标：

语义网路线（RDF / OWL）Palantir 路线（对象 · 链接 · 动作）
建模单位类 / 实例 / 三元组 / 公理对象 / 链接 / 动作 / 函数
主要目的描述世界、支持自动推理运营业务、支持安全写回
语义表达强逻辑（等价、传递、基数……）业务规则（校验、审批流、SLA）
「推理」OWL 推理机算出隐含事实计算引擎跑 Function 与规则
写操作无——RDF 是纯描述性的Action 类型是一等公民
治理无原生概念权限 / 血缘 / 审计原生内置
给 Agent 的接口自己包一层工具 SchemaOSDK / MCP 原生把本体暴露为工具
典型问题「X 和 Y 在逻辑上是什么关系？」「这单还能不能升级？升级了会发生什么？」
两条路线的共同底座

别被表格吓到——你在毕业项目里写的"轻量本体"（类目 + 关系 + 定义域值域校验）正是两条路线的公分母：它同时满足语义网的"形式化明确"与 Palantir 的"受治理写入"。Palantir 给本课程最大的启示是：本体要想对 Agent 有用，必须带上「动作」与「治理」——纯描述性的本体只是地图，带 Action 的本体才是控制台。

6.3 本体的构成要素

一个本体由五类「零件」组成。用一个「智能体领域」的例子贯穿：

要素含义本站例子
类（Class / Concept）一类事物的抽象Agent、Tool、Task、Human
实例（Instance / Individual）具体的个体ClaudeCode 是 Agent 的实例；WebSearch 是 Tool 的实例
属性（Property / Attribute）个体自身的特征工具的 version、任务的 deadline
关系（Relation）个体之间的连接uses(Agent → Tool)、executes(Agent → Task)
公理（Axiom / Constraint）必须成立的逻辑陈述「uses 的主语必须是 Agent，宾语必须是 Tool」；「CodingAgent 是 Agent 的子类」

描述逻辑传统里还有一对重要术语：TBox（Terminological Box，术语层——类与关系的定义，即 schema） 和 ABox（Assertional Box，断言层——具体实例的陈述）。 「知识图谱 = 本体（TBox）+ 实例数据（ABox）」，这句话能帮你定位市面上 90% 的相关讨论。

6.4 概念辨析：四个长得很像的东西

表达力一句话区分例子

6.5 语义网技术栈：RDF → RDFS → OWL → SPARQL

「形式化」意味着要有机器能懂的表示语言。W3C 语义网栈从下到上一层层加表达力：

① RDF：万物皆三元组

RDF（Resource Description Framework）把一切知识拆成 主语–谓语–宾语 三元组：

turtle · RDF 三元组示例
@prefix : <http://example.org/agent#> .

:ClaudeCode  :is-a  :CodingAgent .        # 类属关系
:ClaudeCode  :uses   :WebSearch .         # 关系断言
:WebSearch   :version "2.1" .             # 属性值
# 这三行读作：ClaudeCode 是一个编码智能体，
# 它使用 WebSearch 工具；WebSearch 的版本是 2.1。

三元组的天才之处在于同构：类属、关系、属性全部统一成「主谓宾」，于是整个知识库就是一张巨大的图，查询与合并都变成图操作。

② RDFS：给 RDF 加上类与继承

RDFS 引入 rdfs:subClassOf（子类）、rdfs:domain（定义域）、rdfs:range（值域）——本体开始能「推理」：知道 CodingAgent 是 Agent 的子类，就能自动推出「ClaudeCode 是 Agent」。

③ OWL：真正的本体语言

OWL（Web Ontology Language）把表达力拉满：

  • 属性特征：可声明属性是传递的（在……之上）、对称的（是……的配偶）、函数型的（每人只有一个生日）
  • 等价与互斥：Agent ≡ IntelligentSystem；「工具」与「人类」互斥
  • 基数约束：每个任务恰好有一个负责人
  • 开放世界假设（见下方要点）
关键认知：开放世界假设（OWA）

数据库世界是「封闭世界」：没查到的就是不存在。OWL 是开放世界：没写的事实只是「未知」，不能断定「假」——因为本体可能被分布式的各方不断补充。 这让 OWL 适合开放共享的场景，但也意味着推理结果与直觉时常不同（「没报错」可能只是「缺少信息」）。做企业内封闭系统时，常常要主动选择封闭世界语义（如 SHACL 校验）。

④ SPARQL：查询语义图

sparql · 查出所有 Agent 使用的工具
PREFIX : <http://example.org/agent#>
SELECT ?agent ?tool WHERE {
  ?agent a :Agent .          # ？agent 是一个 Agent（含子类，靠推理）
  ?agent :uses ?tool .       # ？agent 使用 ？tool
}
# 想象一下：这相当于「关系数据库的 JOIN + 面向对象的多态」，但全部自动完成

栈顶还有 SHACL（用 Shape 约束校验数据质量）与规则语言（SWRL 等），至此：RDF 存事实、RDFS/OWL 定语义、SPARQL 查、SHACL 验。

代码实战：用 rdflib 建图与查询（可运行）

概念讲完，亲手跑一次完整的语义栈。安装：

bash
pip install rdflib owlrl   # rdflib：RDF 库与 SPARQL；owlrl：RDFS/OWL 推理机

第一步，用 Turtle 格式写下本体与数据（这就是「形式化」——一个文本文件就是一份机器可读的本体）：

turtle · kg.ttl
@prefix : <http://example.org/agent#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

### TBox：类层级
:CodingAgent  rdfs:subClassOf :Agent .
:SearchTool   rdfs:subClassOf :Tool .
:Agent        rdfs:subClassOf :Thing .
:Tool         rdfs:subClassOf :Thing .

### ABox：实例与断言
:ClaudeCode a :CodingAgent ;
    :uses :WebSearch, :CodeRunner ;
    :executes :Task101 .
:R1 a :CodingAgent ;
    :uses :WebSearch .
:Task101 a :Task ; :assignedTo :Alice .

第二步，加载并查询——注意 :R1 a :Agent 这条断言我们从没写过，看推理机能不能把它「算」出来：

python · query_kg.py
from rdflib import Graph
from owlrl import DeductiveClosure, RDFS_Semantics

g = Graph()
g.parse("kg.ttl", format="turtle")
print(f"加载后：{len(g)} 条三元组")

# ── 运行 RDFS 推理：把 subClassOf / domain / range 的全部推论补进图里 ──
DeductiveClosure(RDFS_Semantics).expand(g)
print(f"推理后：{len(g)} 条三元组")   # 变多了！隐含事实被显式化了

# 查询 1：谁使用了工具？（继承推理后，CodingAgent 的实例也算 Agent）
q1 = """
PREFIX : <http://example.org/agent#>
SELECT ?agent ?tool WHERE {
  ?agent a :Agent ;
         :uses ?tool .
} ORDER BY ?agent"""
for row in g.query(q1):
    print(f"  {row.agent.split('#')[-1]} → {row.tool.split('#')[-1]}")
# 输出包含 ClaudeCode 和 R1 —— 它们只是 CodingAgent，:Agent 是推出来的

# 查询 2：每个智能体用几个工具？（SPARQL 聚合）
q2 = """
PREFIX : <http://example.org/agent#>
SELECT ?agent (COUNT(?tool) AS ?n) WHERE { ?agent :uses ?tool }
GROUP BY ?agent"""
for row in g.query(q2):
    print(f"  {row.agent.split('#')[-1]}: {row.n} 个工具")
你刚刚见证了什么

推理前 11 条三元组，推理后多了几十条——全是「买数据送知识」送出来的隐含事实（is-a 传递、domain/range 反推类型等）。查询 1 不需要任何人改写数据，就自动把 CodingAgent 的实例纳入 Agent。这就是本体相对「普通数据库表」的本质优势：把推理从应用代码下沉到数据层。

6.7 怎么建一个本体：七步法

斯坦福经典教程《Ontology Development 101》（Noy & McGuinness）给出七步流程。我们直接用它来建一个「智能体领域本体」：

  1. 确定领域与范围

    领域：智能体系统。范围问题（用一组问题定义边界）：「这个本体要回答什么？」——例如：某个工具属于哪个类目？某条记忆涉及哪些实体？某个任务由谁执行？

  2. 考虑复用现有本体

    通用实体可复用 schema.org 的 Person / Organization；能复用就复用，互联的价值大于自建的快感。

  3. 枚举重要术语

    Agent、Tool、Task、Human、Memory、uses、executes、delegates_to……先不管层级，全部列出来。

  4. 定义类层级

    自顶向下（从大类细分）或自底向上（从实例归纳）都行。得到：Thing ▸ Agent ▸ CodingAgent；Thing ▸ Tool ▸ SearchTool ……

  5. 定义属性与关系

    为每个类挂属性；定义关系并标注定义域 / 值域：uses(Agent, Tool)、executes(Agent, Task)。

  6. 定义分面

    约束细节：version 只能是字符串；status 只能取 {pending, running, done, failed}。

  7. 创建实例

    ClaudeCode ∈ CodingAgent、WebSearch ∈ SearchTool……实例随应用增长。

6.8 本体 × Agent：两个主题的交汇点

现在回答本站的核心问题之一：为什么 Agent 开发者要懂本体？三大用途，价值递增：

用途一：给工具目录建立「分类学骨架」

Agent 的工具超过一二十个后，全部塞进上下文既贵又乱（模型选错工具的概率上升）。 用本体把工具组织成类目树（搜索类 / 文件类 / 计算类 / 通信类……），运行时先按任务语义检索「相关类目」，再把该类目下的少数工具注入上下文—— 工具从平铺清单变成可索引的语义空间。第 9 章的综合项目会实现这一招。

用途二：让长期记忆长出「骨骼」

第 4 章说过向量记忆的盲区：相似 ≠ 相关。给记忆装上本体后，记忆变成实体–关系网络： 「用户 Alice — 负责 → 项目 X — 依赖 → Redis」「项目 X — 使用 → deepseek-chat」。 好处立竿见影：

  • 多跳查询：「A 的导师合作过的公司」这类问题，图上两跳就到，向量检索无能为力；
  • 一致性校验：写入前校验定义域 / 值域，脏数据进不来；
  • 幻觉检测：模型说出的实体在图里查无此人 → 触发怀疑与复核。业界的 GraphRAG、时序知识图谱记忆（如 Graphiti / Zep 一类方案）都在这个方向上。

用途三：LLM 与本体互相成就

LLM 帮本体

本体最贵的是人工建模。LLM 能从自然语言文本中抽取实体与关系、自动填充实例（ontology population），甚至起草类层级——建模成本骤降一个数量级。

本体帮 LLM

本体是 LLM 输出的校验器与接地桩：枚举约束让分类输出永远合法；关系校验抓出张冠李戴；生成 SPARQL 查图，让回答有据可查。幻觉从「治理问题」变成「工程问题」。

一个历史注脚 + 一个当代注脚

历史：早在 2000 年代的多智能体标准 FIPA ACL 中，智能体间通信消息就要求引用一个共享本体来解释消息内容——「没有共同语言就无法协作」是老问题。
当代：MCP（Model Context Protocol）把工具接口标准化了（JSON Schema 描述的工具 / 资源 / 提示），而本体解决的是工具语义的标准化——两者互补：MCP 管「怎么连」，本体管「连来的东西是什么意思」。

代码落地：LLM 抽取管线（本体 × LLM 的组合拳）

本体最贵的是人工建模，LLM 恰好是最便宜的建模工人。把第 3 章的「生成→校验」闭环用在这里：

python · extract.py
import json

EXTRACT_PROMPT = """从下面的文本中抽取 (主体, 关系, 客体) 三元组。
关系只能取：leads / belongs_to / uses / cites / supports / implemented_by
主体、客体用简短名词（≤10字）。输出 JSON：{"triples": [{"s":..., "r":..., "o":...}]}
文本中没有把握的不要输出。

文本：{text}"""

def extract_triples(text: str, onto) -> list:
    resp = client.chat.completions.create(
        model="deepseek-chat", temperature=0,
        response_format={"type": "json_object"},
        messages=[{"role": "user",
                   "content": EXTRACT_PROMPT.format(text=text)}])
    items = json.loads(resp.choices[0].message.content).get("triples", [])

    valid = []
    for it in items:
        err = onto.check(it.get("r"), it.get("s"), it.get("o"))
        if err is True:
            valid.append((it["s"], it["r"], it["o"]))
        else:
            print(f"✂️ 丢弃非法三元组 {it} → {err}")   # 模型的越界输出在这里被拦下
    return valid

store = TripleStore()
for t in extract_triples(
        "Alice 负责的 GraphRAG 对比实验用到了重排序技术，"
        "arXiv 2404.02765 这篇论文支持该方法。", onto):
    store.add(*t)
# ✂️ 若模型输出 {"s":"Alice","r":"uses","o":"重排序技术"}，
# 会被校验拦下：uses 的宾语必须是 Tool，"重排序技术" 是 Technique —— 换 uses 才对？不，
# 正确关系是 Project uses Technique，模型必须自己选对关系；选错了就丢弃
分工的艺术

模型负责它擅长的：从口语化文本里理解语义、识别实体与关系；本体负责它擅长的：用枚举和定义域值域把模型的输出硬约束在合法空间里。这个组合让「自动填充知识图谱」从研究课题变成了一个下午能写完的管线。两个已知的坑：① 同一实体的不同写法（DeepSeek / 深度求索）需要实体对齐，简单做法是让模型在抽取时输出规范名，进阶做法是嵌入聚类；② 抽取置信度低的条目可以标记 pending_review 留给人工，而不是硬丢弃。

6.9 实用主义建议与反模式

  • 从任务出发倒推建模：先写下本体要回答的 10 个问题（competency questions），建模只为它们服务。
  • 轻量优先：90% 的 Agent 场景，「类目 + 关系 + 定义域值域」这一层（RDFS 级）就够，不必上 OWL 全家桶与专业推理机。
  • 反模式：大而全：试图一次建成「企业万物本体」的项目几乎必死。本体是长出来的，不是一次规划出来的。
  • 反模式：为了本体而本体：如果三个字典对象就能解决当前问题，先解决，再谈语义。
  • 让 LLM 参与建模与填充：你负责审校公理与核心层级，批量实例交给抽取管线。

自测

用 TBox / ABox 的语言说清「本体」和「知识图谱」的关系。

答案：本体 ≈ TBox（术语层：类、关系、公理的定义），知识图谱 = TBox + ABox（术语层之上填充了大量实例断言）。所以「知识图谱里包含一个本体作为它的 schema 骨架」是准确的说法，而「本体就是知识图谱」丢掉了实例层。

OWL 的开放世界假设与数据库的封闭世界假设，各适合什么场景？

答案：开放世界适合开放、分布式、持续补充的知识（语义网、跨机构共享）——没写不代表假。封闭世界适合封闭、自治、要求校验严格的系统（企业数据库、表单校验）——没写就是假，可以做完整性检查。工程上常用 SHACL 在开放世界模型上叠加封闭式校验，兼得两者。

说出本体在 Agent 中的至少三个用途，并指出哪一个对你当前的项目最有价值。

答案：① 工具目录的语义组织与按需注入；② 结构化长期记忆（实体–关系图），支持多跳查询、一致性校验与幻觉检测；③ 作为 LLM 输出的校验器 / 接地桩，以及用 LLM 反向抽取填充本体。第三问没有标准答案——但如果你认真想了，说明这章学进去了。

动手练习（带参考答案）

练习 1 · 用七步法为「个人阅读清单」建迷你本体

任务：你想做一个管理自己读书生活的小 Agent。用七步法的前五步（确定范围、复用、列术语、类层级、属性与关系）建一个迷你本体，写出 3 个「本体能回答的问题」。

参考答案：

① 范围问题（competency questions）：「我读过哪些讲 X 主题的书？」「《A》的作者还写过什么？」「哪本书引用/推荐了《B》？」「我标记为「想读」但拖了半年的有哪些？」

② 复用：书籍条目复用 schema.org 的 Book（isbn、author 字段现成），人物复用 Person——不重复造轮子。

③ 类层级：Thing ▸ Work（著作）▸ Book / Paper；Thing ▸ Agent ▸ Person（作者）| Me；Thing ▸ Topic（主题）；Thing ▸ Note（批注）。

④ 关系与定义域值域：written_by(Work, Person)、about(Work, Topic)、cites(Work, Work)、my_status(Work, 状态枚举)（枚举：want / reading / done / abandoned）、recommended(Work, Work)。

⑤ 自查：每一个 competency question 都能被 1~2 跳查询回答吗？「拖了半年的想读」需要 status + 时间戳属性（status_since）——发现缺口就回炉补属性，这正是七步法的迭代本质。

练习 2 · 写一条 SPARQL：找出被两个以上智能体使用的工具
sparql · 参考答案
PREFIX : <http://example.org/agent#>
SELECT ?tool (COUNT(DISTINCT ?agent) AS ?users) WHERE {
  ?agent :uses ?tool .
}
GROUP BY ?tool
HAVING (COUNT(DISTINCT ?agent) > 1)
ORDER BY DESC(?users)

要点：DISTINCT 防止同一 agent 的多条 uses 边重复计数；HAVING 过滤聚合结果。这条查询在关系数据库里要写 JOIN + GROUP BY，在图上只是一次「按邻居数排序」——数据越关联，图查询的优势越明显。

练习 3 · 本体校验判定题：哪条三元组能入库？

任务：沿用第 9 章要用的本体（leads: Human→Project；belongs_to: Project→Project；uses: Project→Technique；implemented_by: Technique→Tool）。判断下列模型抽出的三元组哪些合法、哪些被拦、为什么：
① (Alice, leads, GraphRAG对比实验)　② (GraphRAG对比实验, uses, 重排序技术)　③ (重排序技术, uses, BM25工具)　④ (重排序技术, implemented_by, BM25工具)　⑤ (Alice, uses, 重排序技术)

参考答案：

  • ① 合法：Human leads Project ✓
  • ② 合法：Project uses Technique ✓
  • ③ 拦截：uses 的定义域是 Project，「重排序技术」是 Technique —— 定义域不符。模型大概率把关系选错了。
  • ④ 合法：Technique implemented_by Tool ✓（BM25 是检索工具）
  • ⑤ 拦截：uses 的定义域是 Project，Alice 是 Human —— 但注意！这条错误很有价值：它暴露了本体缺一条关系（人也可以采用某技术）。被拦下的三元组里有需求信号——校验失败日志就是本体迭代的路线图。
练习 4 · 为你的业务设计 Palantir 三件套

任务：选一个你熟悉的业务域（外卖配送 / 图书馆 / 健身房预约均可），写出 3 个 Object Type、2 个 Link Type、2 个 Action Type（每个 Action 给出校验规则与权限），并标注每个组件会映射成 Agent 工具清单里的什么。

参考答案（健身房预约域）：

  • Objects：Member（会员：等级、剩余课时）、Trainer（教练：专长、档期）、Session（课程：时间、容量、状态）
  • Links：books(Member → Session)、teaches(Trainer → Session)
  • Actions：bookSession(memberId, sessionId)——校验：容量未满、会员剩余课时 > 0、无时间冲突；权限：本人或前台。cancelSession(sessionId, reason)——校验：开课前 2 小时；副作用：退还课时、通知候补队列。
  • Agent 映射：查询档期 → Object+Link（auto）；bookSession → 写入 Action（校验兜底，auto）；cancelSession → confirm 级（不可逆）。

自查要点：每个 Action 是否都有「校验 + 权限 + 副作用」三要素？高危写操作是否进了 confirm 级？——这三问就是 Palantir 方法论对你 Harness 的直接迁移。
