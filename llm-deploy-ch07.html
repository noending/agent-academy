实战：微调与部署LLM

本章目标：完成一个LLM微调、量化并部署为API的完整项目

选基座模型按任务与算力挑开源LLM→数据准备清洗并构造指令微调集→LoRA微调低成本训练适配下游任务→量化压缩降精度减显存提速推理→部署API封装服务对外提供接口
从选模型到上线API，走通微调、量化、部署一条完整链路。

项目规划：选择基座模型与数据集

做任何LLM项目，第一步永远是明确目标：你要解决什么任务？是让模型学会特定领域的问答，还是遵循某种输出格式？目标决定了基座模型和数据集的选择。可以把选型想象成装修前量房：先知道房间多大（显存）、要住几个人（任务复杂度）、预算多少（训练成本），再决定买什么家具（模型规模）。如果跳过这一步直接下载最大的模型，往往会卡在显存不足或训练时间过长上。

基座模型选择：对于中文场景，推荐从以下模型入手：

  • Qwen2.5-7B：中文能力强，社区活跃，LoRA微调资料多。
  • Llama-3.1-8B：英文生态好，工具链成熟。
  • ChatGLM3-6B：轻量，适合消费级显卡。

选择时考虑三个硬指标：参数量（7B模型LoRA微调需约16GB显存，1.5B模型约6GB即可起步）、许可证（商用是否允许，务必读原始协议而非二手博客）、社区支持（是否有现成的微调脚本和issue讨论）。一个实用的判断法是：先用1.5B~3B的小模型跑通全链路，确认数据格式和训练脚本无误后，再换7B模型放大效果，这样试错成本从数小时降到数十分钟。

数据集准备：微调数据通常为指令格式，例如：

json
{
  "instruction": "将以下文本翻译成英文",
  "input": "今天天气真好",
  "output": "The weather is nice today."
}

数据量建议至少1000条，质量比数量更重要。可以使用开源数据集（如Alpaca、Firefly）或自己标注。这里有一个容易被忽略的细节：训练数据的格式必须与推理时的prompt模板一致。如果训练时用### Instruction:分隔，推理时却直接拼接用户输入，模型会因分布偏移而输出混乱。因此规划阶段就要把模板固定下来，写进配置而不是散落在脚本里。

下面是一个最小示例，展示如何加载数据集并查看格式。输入是一个公开指令数据集名称，预期输出是第一条样本的字段结构，用来确认字段名与后续格式化函数匹配：

python
from datasets import load_dataset

# 加载一个开源指令数据集
dataset = load_dataset("yahma/alpaca-cleaned", split="train")
print(dataset[0])
# 输出: {'instruction': '...', 'input': '...', 'output': '...'}

使用LoRA微调模型

LoRA（Low-Rank Adaptation）是一种参数高效微调方法，它冻结原模型参数，只在Transformer层的注意力模块中注入可训练的低秩矩阵。直觉上，全量微调像是把整栋楼重新装修，而LoRA只是在关键房间加装可拆卸的隔断——原结构不动，改动量极小却足以改变功能分区。数学上，它把权重更新 ΔW 分解为两个小矩阵的乘积 B·A，其中 B 是 d×r、A 是 r×k，r 远小于 d 和 k，因此可训练参数减少到原来的0.1%~1%，显存需求大幅降低。

使用Hugging Face的peft库可以轻松实现LoRA微调。关键参数：

  • r：低秩矩阵的秩，通常8~32。r=8 时一个7B模型的可训练参数约几百万量级，r=32 则翻数倍，表达能力更强但更易过拟合小数据集。
  • lora_alpha：缩放因子，一般设为r的2倍。实际生效的缩放是 alpha/r，所以 r 和 alpha 同步放大时等效强度不变。
  • target_modules：要注入的模块，如["q_proj", "v_proj"]。只挂 q/v 是最省参数的起点，效果不足时再扩展到 k_proj、o_proj 和 MLP 层。

下面是一个完整的微调脚本（以Qwen2.5-7B为例）。输入是基座模型名和1000条Alpaca格式数据，预期输出是保存到./lora_adapter的适配器权重，训练日志中可看到可训练参数占比（通常在1%以下）：

python
from transformers import AutoModelForCausalLM, AutoTokenizer, TrainingArguments
from peft import LoraConfig, get_peft_model
from trl import SFTTrainer
from datasets import load_dataset

model_name = "Qwen/Qwen2.5-7B"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, device_map="auto")

# 配置LoRA
lora_config = LoraConfig(
    r=16,
    lora_alpha=32,
    target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM"
)
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()  # 查看可训练参数比例

# 加载数据集
dataset = load_dataset("yahma/alpaca-cleaned", split="train[:1000]")

# 训练参数
training_args = TrainingArguments(
    output_dir="./lora_output",
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,
    learning_rate=2e-4,
    num_train_epochs=3,
    logging_steps=10,
    save_strategy="epoch",
    fp16=True,
)

# 使用SFTTrainer
trainer = SFTTrainer(
    model=model,
    args=training_args,
    train_dataset=dataset,
    tokenizer=tokenizer,
    dataset_text_field="text",  # 需要将数据格式化为文本
    max_seq_length=512,
)
trainer.train()
model.save_pretrained("./lora_adapter")

注意：实际使用时需要将数据集格式化为包含instruction、input、output的文本，例如：### Instruction:\n{instruction}\n### Input:\n{input}\n### Response:\n{output}。上面脚本里 dataset_text_field="text" 要求数据集中已存在 text 字段，而 Alpaca 原始数据只有 instruction/input/output 三列，直接运行会报字段缺失——这正是下一节动手练习要补上的格式化步骤。另外，fp16=True 在部分新显卡上可能不稳定，可改用 bf16=True（待核实具体硬件兼容性）。

模型量化与导出

微调后，为了部署，通常需要将模型量化以减小显存占用和加速推理。量化的直觉是：模型权重原本用16位浮点存储，每个数占2字节；改成4位整数后每个数只占0.5字节，7B模型的文件体积从约14GB降到约4GB，显存门槛随之下降。代价是数值精度损失，但LLM的权重分布通常冗余度较高，所以4-bit量化在多数任务上仍可用。常见的量化方法有：

  • GPTQ：训练后量化，4-bit，精度损失小。
  • AWQ：激活感知权重量化，适合LLM。
  • GGUF：llama.cpp使用的格式，适合CPU推理。

这里以GPTQ为例，使用auto-gptq库进行量化。输入是基座模型名和一小批校准文本，预期输出是./qwen2.5-7b-gptq目录下的4-bit权重与tokenizer。注意校准数据不是随便两句话就行：校准集应来自目标任务分布，通常几十到上百条，否则量化误差会偏大。

python
from transformers import AutoModelForCausalLM, AutoTokenizer
from auto_gptq import AutoGPTQForCausalLM, BaseQuantizeConfig

model_name = "Qwen/Qwen2.5-7B"
tokenizer = AutoTokenizer.from_pretrained(model_name)

# 量化配置
quantize_config = BaseQuantizeConfig(
    bits=4,
    group_size=128,
    desc_act=False,
)

# 加载模型并量化
model = AutoGPTQForCausalLM.from_pretrained(model_name, quantize_config)

# 准备校准数据（少量样本）
calibration_dataset = ["示例文本1", "示例文本2"]  # 实际需更多

# 执行量化
model.quantize(calibration_dataset)
model.save_quantized("./qwen2.5-7b-gptq")
tokenizer.save_pretrained("./qwen2.5-7b-gptq")

量化后模型大小约为原模型的1/4，显存需求从~14GB降至~4GB。这个数字是估算值，实际取决于是否加载KV Cache、batch size和序列长度，长上下文推理时KV Cache本身可能占用数GB。

如果使用LoRA微调，也可以将LoRA权重合并到基座模型后再量化。合并的意义在于把 B·A 加回原权重，得到一个普通模型，从而兼容不支持动态加载LoRA的推理栈。输入是基座模型和适配器目录，预期输出是./merged_model下的完整权重：

python
from peft import PeftModel

base_model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-7B")
lora_model = PeftModel.from_pretrained(base_model, "./lora_adapter")
merged_model = lora_model.merge_and_unload()
merged_model.save_pretrained("./merged_model")

使用vLLM部署并测试API

vLLM是一个高效推理引擎，支持PagedAttention，吞吐量比Hugging Face高数倍。PagedAttention的直觉来自操作系统的虚拟内存分页：把KV Cache切成固定大小的块按需分配，避免为每条请求预留最大长度的连续显存，从而显著减少浪费、提升并发。部署API只需几行命令：

bash
# 启动OpenAI兼容的API服务
python -m vllm.entrypoints.openai.api_server \
    --model ./qwen2.5-7b-gptq \
    --quantization gptq \
    --port 8000 \
    --host 0.0.0.0

然后就可以像调用OpenAI API一样调用。输入是一条用户消息，预期输出是模型回复的文本，打印在终端：

python
import openai

client = openai.OpenAI(base_url="http://localhost:8000/v1", api_key="token-abc123")

response = client.chat.completions.create(
    model="qwen2.5-7b-gptq",
    messages=[{"role": "user", "content": "你好，介绍一下你自己"}],
    temperature=0.7,
    max_tokens=100
)
print(response.choices[0].message.content)

测试时注意：并发测试可以使用locust或wrk；监控可以查看vLLM的日志和GPU利用率。一个常见的验收标准是：单请求首token延迟低于1秒、并发10路时吞吐明显高于逐条串行调用，否则说明批处理没有生效。

如果使用LoRA适配器，vLLM也支持动态加载。这样同一个基座可以挂多个适配器，按请求切换，省去为每个任务各存一份完整模型：

bash
python -m vllm.entrypoints.openai.api_server \
    --model Qwen/Qwen2.5-7B \
    --enable-lora \
    --lora-modules my-lora=./lora_adapter

调用时指定model="my-lora"即可。注意此时 --model 必须是未量化的基座模型路径，LoRA 与 GPTQ 量化权重同时启用时的兼容性需以所用 vLLM 版本文档为准（待核实）。

常见误区

  • 错误理解：LoRA微调后必须合并权重才能部署。→ 后果：多存一份完整模型、多花一次合并时间，且无法在同一基座上按请求切换多个任务适配器。→ 正确做法：vLLM等框架支持通过 --enable-lora 直接加载适配器，只有推理栈不支持动态LoRA或需要再量化时才合并。
  • 错误理解：量化一定会显著降低模型精度。→ 后果：因担心精度而放弃量化，继续用16位权重部署，显存和成本翻数倍。→ 正确做法：4-bit GPTQ/AWQ在多数任务上精度损失很小（<1%），但必须用目标任务样本做量化前后对比评测，而不是只看通用榜单。
  • 错误理解：微调数据越多越好。→ 后果：收集大量低质量或格式不一致的数据，训练更久却学到噪声和错误模板。→ 正确做法：优先保证格式统一、答案正确，1000条高质量数据可能胜过10万条低质量数据；扩充数据前先做小规模消融对比。

自测

LoRA微调中，参数r和lora_alpha分别代表什么？它们如何影响微调效果？

答案：推理过程：先看r，它是低秩分解B·A中的中间维度，直接决定新增可训练参数的数量——r从8增到32，参数量约翻4倍，表达能力增强但小数据集上过拟合风险上升。再看lora_alpha，它是缩放因子，实际注入强度约为alpha/r；若只调大alpha而不动r，等效于放大LoRA分支的输出。因此调参时应把alpha与r成比例设置（如r=16、alpha=32），单独改一个会同时改变强度和容量，难以归因。结论：r控容量，alpha控强度，二者需配合调整。

使用vLLM部署模型时，如何支持多个LoRA适配器？

答案：推理过程：第一步，启动服务时加--enable-lora开启动态加载能力；第二步，用--lora-modules以name=path形式注册一个或多个适配器，例如my-lora=./lora_adapter；第三步，客户端请求时把model字段设为注册名my-lora而非基座名，vLLM据此路由到对应适配器。需要注意--model指向的是基座权重，适配器只是叠加层，所以多个任务共享同一份基座显存。

为什么训练数据的prompt模板必须与推理时一致？不一致会发生什么？

答案：推理过程：模型在微调时学到的是「看到某种前缀→输出某种格式」的条件分布。若训练用### Instruction:分隔，推理时直接拼接用户输入，模型看到的输入分布与训练时不同，相当于在没见过的格式上做外推，常见表现是复读、答非所问或输出训练模板残留。验证方法：用训练集里的一条样本原样喂给部署后的API，若输出正常而换格式后变差，即可确认是模板不一致。正确做法是把模板写成配置，训练和推理共用同一份。

动手练习（带参考方案）

练习 · 选择一个基座模型（如Qwen2.5-1.5B），使用LoRA微调一个简单的指令跟随任务（例如将中文翻译成英文），然后量化…

任务：选择一个基座模型（如Qwen2.5-1.5B），使用LoRA微调一个简单的指令跟随任务（例如将中文翻译成英文），然后量化并部署为API，最后用Python脚本测试API。验收标准：① 训练脚本能跑通并保存适配器；② 部署后API对至少3条测试句返回英文翻译；③ 提交训练日志中的可训练参数占比和一条API返回结果。

参考方案：

python
# ========== 步骤1：数据准备 ==========
# 创建 translation_data.jsonl，每行一条，字段为 instruction/input/output
# 示例行：{"instruction": "将以下中文翻译成英文", "input": "你好", "output": "Hello"}

# ========== 步骤2：微调脚本（保存为 train.py） ==========
from transformers import AutoModelForCausalLM, AutoTokenizer, TrainingArguments
from peft import LoraConfig, get_peft_model
from trl import SFTTrainer
from datasets import load_dataset

model_name = "Qwen/Qwen2.5-1.5B"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name, device_map="auto")

lora_config = LoraConfig(r=8, lora_alpha=16,
                         target_modules=["q_proj", "v_proj"],
                         task_type="CAUSAL_LM")
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()  # 记录可训练参数占比

# 关键：把 instruction/input/output 拼成 text 字段，与推理模板保持一致
def format_sample(example):
    text = (f"### Instruction:\n{example['instruction']}\n"
            f"### Input:\n{example['input']}\n"
            f"### Response:\n{example['output']}")
    return {"text": text}

dataset = load_dataset("json", data_files="translation_data.jsonl", split="train")
dataset = dataset.map(format_sample)

training_args = TrainingArguments(
    output_dir="./lora_output",
    per_device_train_batch_size=4,
    num_train_epochs=3,
    learning_rate=2e-4,
    fp16=True,
    logging_steps=10,
)
trainer = SFTTrainer(model=model, args=training_args,
                     train_dataset=dataset, tokenizer=tokenizer,
                     dataset_text_field="text", max_seq_length=256)
trainer.train()
model.save_pretrained("./lora_adapter")
tokenizer.save_pretrained("./lora_adapter")

# ========== 步骤3：部署（命令行执行，二选一） ==========
# 方式A：直接加载LoRA适配器（无需合并、无需量化）
# python -m vllm.entrypoints.openai.api_server \
#     --model Qwen/Qwen2.5-1.5B --enable-lora \
#     --lora-modules my-lora=./lora_adapter --port 8000
#
# 方式B：先合并再量化（参考章节「模型量化与导出」），然后
# python -m vllm.entrypoints.openai.api_server \
#     --model ./qwen-1.5b-gptq --quantization gptq --port 8000

# ========== 步骤4：测试脚本（保存为 test_api.py） ==========
import openai

client = openai.OpenAI(base_url="http://localhost:8000/v1", api_key="token-abc123")

# 与训练时完全一致的模板
PROMPT = "### Instruction:\n将以下中文翻译成英文\n### Input:\n{}\n### Response:\n"

for zh in ["你好", "今天天气真好", "我喜欢学习人工智能"]:
    resp = client.chat.completions.create(
        model="my-lora",  # 方式B部署时改为 qwen-1.5b-gptq
        messages=[{"role": "user", "content": PROMPT.format(zh)}],
        temperature=0.0,
        max_tokens=50,
    )
    print(zh, "->", resp.choices[0].message.content.strip())

# 预期输出示例：
# 你好 -> Hello
# 今天天气真好 -> The weather is really nice today.
# 我喜欢学习人工智能 -> I like learning artificial intelligence.
