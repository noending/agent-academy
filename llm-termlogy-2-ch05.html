显存估算与部署选型

本章目标：能估算模型推理显存，区分装得下、跑得快、满足并发。

算显存权重加KV缓存逐项估算→装得下显存总量不超上限→跑得快带宽算力决定时延→扛并发批量与KV缓存权衡→定选型按目标反推硬件配置
显存估算只是起点，装得下、跑得快、扛并发三层依次校验，才能定部署选型。

显存都去哪儿了？拆解推理时的显存组成

想象你要开一家餐厅：厨房（GPU）里要放食材（模型权重）、备菜台（KV Cache）、临时切菜板（激活与临时缓冲）、还有收银机、冰箱等固定设备（框架开销），最后还得留点空间给客人走动（必要余量）。显存就是厨房面积，任何一样放不下，餐厅就开不了张。这个类比的关键在于：显存不是被单一项目吃掉的，而是被多个部分共同瓜分，且其中一部分会随使用方式动态膨胀。

具体来说，推理时显存主要被以下部分占用：

  • 模型权重：模型参数本身，比如 FP16 下每个参数占 2 字节。一个 8B 模型在 FP16 下权重约 14.9 GB，这是显存的“地基”。
  • 量化元数据：如果用了量化（如 GPTQ、AWQ），除了权重还会存缩放因子、零点等，通常额外占 5%~15%。所以 INT4 并非严格等于 FP16 的四分之一。
  • KV Cache：自回归生成时缓存历史 Key/Value，避免重复计算。它随上下文长度和并发数线性增长，是“动态膨胀”的主要来源。
  • 激活与临时缓冲：前向传播中的中间结果，通常不大，但长上下文或大 batch 时会显著增加。
  • 框架开销：CUDA context、cuDNN 工作区、通信缓冲等，一般 0.5~2 GB。
  • 必要余量：防止 OOM，建议留 10%~20%。

为什么 KV Cache 值得单独强调？举个前后对比：同样是 8B FP16 模型，上下文 4096、并发 1 时 KV Cache 只有约 0.5 GB，几乎可以忽略；但把并发提到 32，KV Cache 就涨到约 16 GB，直接超过模型权重本身。这就是为什么很多“单条测试很流畅”的部署，一上并发就 OOM。

下面是一个最小估算函数，帮你快速算个大概。输入是模型参数量、精度、上下文长度、并发数等，输出是各部分显存和加余量后的总需求：

python
def estimate_memory_gb(params_b, precision_bytes, context_len, batch_size, n_layers, n_kv_heads, head_dim, overhead_gb=1.5, reserve_ratio=0.15):
    # 模型权重
    weights = params_b * 1e9 * precision_bytes / (1024**3)
    # KV Cache: 2 (K和V) * layers * batch * seq_len * kv_heads * head_dim * precision_bytes
    kv_cache = 2 * n_layers * batch_size * context_len * n_kv_heads * head_dim * precision_bytes / (1024**3)
    # 激活与临时缓冲粗略估计为权重的 5%
    activations = weights * 0.05
    total = weights + kv_cache + activations + overhead_gb
    total_with_reserve = total * (1 + reserve_ratio)
    return weights, kv_cache, activations, overhead_gb, total_with_reserve

# 示例：8B 模型，FP16，上下文 4096，batch 1，32 层，8 个 KV 头，头维度 128
w, kv, act, ov, total = estimate_memory_gb(8, 2, 4096, 1, 32, 8, 128)
print(f"权重: {w:.2f} GB, KV Cache: {kv:.2f} GB, 激活: {act:.2f} GB, 总需求: {total:.2f} GB")

运行结果会告诉你，8B FP16 模型在 4K 上下文下单并发大约需要 18~19 GB 显存。把 batch_size 改成 32 再跑一次，你会看到总需求跳到 35 GB 以上。记住：显存估算不是精确科学，而是快速判断“装不装得下”的工程近似。

手把手估算：8B、32B、70B 在不同精度与并发下的显存

上一节我们拆开了显存的各个组成部分，这一节把它们组装成一个可复用的估算流程。先记住统一公式：总显存 ≈ 权重 + KV Cache + 激活 + 框架开销 + 余量。这个公式的价值不在于精确到小数点，而在于让你在选卡之前就能排除明显不可行的方案。

其中各部分的算法是：

  • 权重 = 参数量 × 每参数字节数（FP32=4、FP16=2、INT8=1、INT4=0.5）
  • KV Cache = 2 × 层数 × 并发数 × 上下文长度 × KV头数 × 头维度 × 每元素字节数
  • 激活 ≈ 权重的 5%~10%
  • 框架开销 ≈ 1~2 GB
  • 余量 ≈ 总和的 10%~20%

为了让脚本可运行，我们需要对模型结构做假设：层数 = 参数量(B) × 4，KV头数 = 8，头维度 = 128。这些是粗略经验值，真实模型请查 config.json。下面脚本对比四种典型配置，输入是参数量、精度、上下文和并发，输出权重、KV Cache 和总需求：

python
def estimate(params_b, precision, context_len, batch_size):
    bytes_per_param = {'fp32':4, 'fp16':2, 'int8':1, 'int4':0.5}[precision]
    n_layers = int(params_b * 4)
    n_kv_heads = 8
    head_dim = 128
    weights = params_b * 1e9 * bytes_per_param / (1024**3)
    kv = 2 * n_layers * batch_size * context_len * n_kv_heads * head_dim * bytes_per_param / (1024**3)
    act = weights * 0.05
    overhead = 1.5
    total = (weights + kv + act + overhead) * 1.15
    return weights, kv, total

configs = [
    (8, 'fp16', 4096, 1),
    (8, 'int4', 4096, 1),
    (32, 'fp16', 8192, 4),
    (70, 'int4', 4096, 8),
]
for p, prec, ctx, bs in configs:
    w, kv, total = estimate(p, prec, ctx, bs)
    print(f"{p}B {prec} ctx={ctx} bs={bs}: 权重 {w:.1f}GB, KV {kv:.1f}GB, 总需 {total:.1f}GB")

输出示例（数字为近似值，随假设变化）：

python
8B fp16 ctx=4096 bs=1: 权重 14.9GB, KV 0.5GB, 总需 19.5GB
8B int4 ctx=4096 bs=1: 权重 3.7GB, KV 0.5GB, 总需 6.6GB
32B fp16 ctx=8192 bs=4: 权重 59.6GB, KV 8.0GB, 总需 79.5GB
70B int4 ctx=4096 bs=8: 权重 32.6GB, KV 4.0GB, 总需 43.9GB

关键结论：

  • 8B FP16 单并发 4K 上下文，一张 24GB 卡（如 4090）刚好装下，但并发一高就爆。
  • 8B INT4 可以轻松跑在 8GB 显存上，适合边缘设备。
  • 32B FP16 需要至少 80GB 显存，单卡 A100/H100 可行，但并发 4 时已接近极限。
  • 70B INT4 在 48GB 卡（如 A6000）上可跑，但并发 8 时 KV Cache 会吃掉不少显存。

注意：这里假设 KV 头数为 8，实际模型可能不同（如 GQA 会减少 KV 头数），需要查模型配置。另外，“装得下”只是第一关，装下之后还要看吞吐和延迟是否达标，这会在部署选型一节展开。

MoE 模型：总参数与激活参数，别被名字骗了

MoE（混合专家）模型像一家大公司：公司有 1000 名员工（总参数），但每个任务只叫 10 个人干活（激活参数）。如果你只按 10 个人算工资（显存），那就大错特错了——因为公司得给所有 1000 人发工资（权重都得存着）。这个类比的要点是：显存是“养人”的成本，算力是“干活”的成本，两者在 MoE 里被刻意解耦了。

MoE 模型有两个关键数字：

  • 总参数：所有专家加起来的参数量，决定权重显存。
  • 激活参数：每次前向实际用到的参数量，决定计算量（FLOPs）和部分激活显存。

例如，Mixtral 8x7B 总参数约 46.7B，但激活参数只有约 12.9B。如果你按 12.9B 估算权重显存，会严重低估。具体差多少？46.7B 在 INT4 下权重约 21.8 GB，而 12.9B 在 INT4 下只有约 6 GB，差了 3 倍多——这个差距足以让一张 24GB 卡从“能跑”变成“跑不起来”。

估算 MoE 显存时，权重部分必须用总参数，KV Cache 和激活则与激活参数、层数、注意力头数相关。下面是一个简化示例，输入总参数、激活参数、精度、上下文和并发，输出权重、KV 和总需求：

python
def estimate_moe(total_params_b, active_params_b, precision, context_len, batch_size, n_layers, n_kv_heads, head_dim):
    bytes_per_param = {'fp16':2, 'int8':1, 'int4':0.5}[precision]
    weights = total_params_b * 1e9 * bytes_per_param / (1024**3)
    kv = 2 * n_layers * batch_size * context_len * n_kv_heads * head_dim * bytes_per_param / (1024**3)
    # 激活与激活参数相关，粗略按激活参数的 10% 估算
    act = active_params_b * 1e9 * bytes_per_param / (1024**3) * 0.1
    overhead = 1.5
    total = (weights + kv + act + overhead) * 1.15
    return weights, kv, total

# Mixtral 8x7B: 总参数 46.7B, 激活 12.9B, 32 层, 8 KV 头, 头维度 128
w, kv, total = estimate_moe(46.7, 12.9, 'int4', 4096, 1, 32, 8, 128)
print(f"权重: {w:.1f}GB, KV: {kv:.1f}GB, 总需: {total:.1f}GB")

输出：权重约 21.8GB，总需约 27GB。如果误用激活参数 12.9B 算权重，会得到约 6GB，差了三倍多。记住：MoE 的权重显存看总参数，计算量看激活参数。部署时，显存按总参数准备，算力按激活参数评估。这也解释了为什么 MoE 模型常被形容为“用更少的算力跑更大的模型”——省的是算力，不是显存。

部署选型：API、云 GPU、本地工作站、多卡服务器怎么选？

选部署方式就像选交通工具：API 是打车，云 GPU 是租车，本地工作站是买私家车，多卡服务器是买大巴。没有绝对好坏，只有合不合适。这个类比背后其实是一个经典权衡：你把“固定成本”换成“可变成本”的程度，决定了哪种方式更划算。

我们从几个维度比较：

维度API云 GPU本地工作站多卡服务器
质量取决于提供商，通常最强自选模型，灵活自选模型，受硬件限制可跑最大模型
延迟网络延迟，通常 100ms~2s取决于网络和实例极低，本地推理低，但需内部网络
并发按量付费，弹性好弹性伸缩受单卡显存限制高并发，需负载均衡
使用率按 token 计费，无闲置成本按小时计费，闲置也花钱一次性投入，闲置浪费高投入，需高使用率摊薄
隐私数据出域，风险高数据在云，需信任提供商数据完全本地数据完全本地
兼容无需操心需自己配环境需自己配环境需自己配环境，多卡通信复杂
运维无中等低高
TCO按量，短期低，长期可能高灵活，适合波动负载前期高，长期低前期很高，适合稳定高负载

如何决策？问自己几个问题：

  • 数据敏感吗？敏感选本地或多卡服务器。
  • 负载稳定吗？稳定且高选本地/多卡，波动大选 API/云。
  • 有运维团队吗？没有就选 API 或托管云。
  • 预算多少？算一下 3 年 TCO：本地 = 硬件 + 电费 + 运维；云 = 每小时费用 × 使用小时；API = token 单价 × 用量。

举个具体对比：假设某业务每天稳定跑 8 小时、并发 8，用 32B 模型。API 按 token 计费，短期最省心；云 GPU 按小时计费，8 小时/天意味着 2/3 时间在闲置付费；本地工作站一次性投入后边际成本低，但需要人维护。没有银弹，只有权衡。建议先用 API 验证需求，再根据使用率和隐私要求逐步迁移到云 GPU 或本地。注意：具体价格和性能数字随供应商与时间变化，选型时应以当期报价为准（待核实）。

常见误区

  • 错误理解：MoE 模型每次只激活部分专家，所以按激活参数估算权重显存就够了。→ 后果：严重低估显存，例如把 Mixtral 8x7B 按 12.9B 估算，INT4 下只算约 6 GB，实际需要约 21.8 GB，部署时直接 OOM。→ 正确做法：权重显存一律按总参数计算，激活参数只用于估算计算量和部分激活显存。
  • 错误理解：KV Cache 很小，可以忽略，显存主要看模型权重。→ 后果：单条测试正常，一上并发或长上下文就 OOM；例如 8B FP16 在 4K 上下文下并发 1 时 KV 仅约 0.5 GB，并发 32 时涨到约 16 GB，超过权重本身。→ 正确做法：把 KV Cache 作为独立项纳入估算，公式为 2 × 层数 × 并发 × 上下文 × KV头数 × 头维度 × 字节数，并随并发和上下文动态评估。
  • 错误理解：量化后显存按比例线性减少，INT4 就是 FP16 的四分之一。→ 后果：低估实际占用，因为量化元数据额外占 5%~15%，激活和框架开销不随量化同比缩小，且低精度可能影响质量。→ 正确做法：权重按量化字节数估算后，额外预留量化元数据，并单独计算激活、框架开销和余量，同时验证量化后的质量是否达标。

自测

一个 70B 模型，使用 INT4 量化，上下文长度 8192，并发数 4，假设 80 层，8 个 KV 头，头维度 128。请估算总显存需求（GB），并说明计算过程。

答案：推理过程：第一步算权重，70e9 × 0.5 字节 / (1024^3) ≈ 32.6 GB，这是显存的地基。第二步算 KV Cache，公式为 2 × 层数 × 并发 × 上下文 × KV头数 × 头维度 × 字节数，代入 2 × 80 × 4 × 8192 × 8 × 128 × 0.5 / (1024^3) ≈ 2.5 GB；注意这里并发 4 和上下文 8192 都乘进去了，所以比单并发 4K 时大 8 倍。第三步算激活，按权重的 5% 约 1.6 GB。第四步加框架开销 1.5 GB。总和 = 32.6 + 2.5 + 1.6 + 1.5 = 38.2 GB。最后加 15% 余量，38.2 × 1.15 ≈ 43.9 GB。因此需要至少 48GB 显存的 GPU，24GB 和 40GB 卡都不够。

MoE 模型的总参数和激活参数分别影响显存估算的哪一部分？为什么不能只用激活参数估算权重显存？

答案：推理过程：先明确两个数字的含义——总参数是所有专家参数之和，激活参数是每次前向实际参与计算的参数。权重显存取决于“需要加载到显存里的参数总量”，而所有专家都必须常驻显存以便随时切换，所以权重显存由总参数决定。激活参数决定的是计算量（FLOPs）以及部分激活缓冲的大小。如果只用激活参数估算权重，相当于假设未激活的专家不需要存储，但推理时路由是动态的，任何专家都可能被选中，不加载就会缺参数。以 Mixtral 8x7B 为例，总参数 46.7B 在 INT4 下权重约 21.8 GB，而激活参数 12.9B 只有约 6 GB，低估三倍多，足以导致选卡错误和 OOM。

某团队用 8B FP16 模型在 24GB 显卡上单条测试流畅，但上线后并发 16、上下文 4096 时频繁 OOM。请分析原因并给出至少两种解决方向。

答案：推理过程：先按公式定位瓶颈。权重约 14.9 GB，框架开销约 1.5 GB，激活约 0.7 GB，这些是固定项，合计约 17 GB。KV Cache 在并发 16、上下文 4096、32 层、8 KV 头、头维度 128、FP16 下约为 2 × 32 × 16 × 4096 × 8 × 128 × 2 / (1024^3) ≈ 8 GB。固定项加 KV 约 25 GB，再加 15% 余量约 28.8 GB，超过 24GB。单条测试时并发 1，KV 仅约 0.5 GB，所以流畅。解决方向：一是降低 KV Cache，例如启用量化 KV Cache、缩短上下文或减少并发；二是降低权重占用，例如改用 INT8/INT4 量化，把权重从约 14.9 GB 降到约 7.5 GB 或 3.7 GB；三是换更大显存的卡或做多卡切分。选择哪种取决于质量要求和成本约束。
