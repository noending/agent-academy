显存估算与部署选型

本章目标：能估算模型推理显存，区分装得下、跑得快、满足并发。

显存都去哪儿了？拆解推理时的显存组成

想象你要开一家餐厅：厨房（GPU）里要放食材（模型权重）、备菜台（KV Cache）、临时切菜板（激活与临时缓冲）、还有收银机、冰箱等固定设备（框架开销），最后还得留点空间给客人走动（必要余量）。显存就是厨房面积，任何一样放不下，餐厅就开不了张。

具体来说，推理时显存主要被以下部分占用：

  • 模型权重：模型参数本身，比如 FP16 下每个参数占 2 字节。
  • 量化元数据：如果用了量化（如 GPTQ、AWQ），除了权重还会存缩放因子、零点等，通常额外占 5%~15%。
  • KV Cache：自回归生成时缓存历史 Key/Value，避免重复计算。它随上下文长度和并发数线性增长。
  • 激活与临时缓冲：前向传播中的中间结果，通常不大，但长上下文或大 batch 时会显著增加。
  • 框架开销：CUDA context、cuDNN 工作区、通信缓冲等，一般 0.5~2 GB。
  • 必要余量：防止 OOM，建议留 10%~20%。

下面是一个最小估算函数，帮你快速算个大概：

def estimate_memory_gb(params_b, precision_bytes, context_len, batch_size, n_layers, n_kv_heads, head_dim, overhead_gb=1.5, reserve_ratio=0.15):
    # 模型权重
    weights = params_b * 1e9 * precision_bytes / (1024**3)
    # KV Cache: 2 (K和V) * layers * batch * seq_len * kv_heads * head_dim * precision_bytes
    kv_cache = 2 * n_layers * batch_size * context_len * n_kv_heads * head_dim * precision_bytes / (1024**3)
    # 激活与临时缓冲粗略估计为权重的 5%
    activations = weights * 0.05
    total = weights + kv_cache + activations + overhead_gb
    total_with_reserve = total * (1 + reserve_ratio)
    return weights, kv_cache, activations, overhead_gb, total_with_reserve

# 示例：8B 模型，FP16，上下文 4096，batch 1，32 层，8 个 KV 头，头维度 128
w, kv, act, ov, total = estimate_memory_gb(8, 2, 4096, 1, 32, 8, 128)
print(f"权重: {w:.2f} GB, KV Cache: {kv:.2f} GB, 激活: {act:.2f} GB, 总需求: {total:.2f} GB")

运行结果会告诉你，8B FP16 模型在 4K 上下文下单并发大约需要 18~19 GB 显存。记住：显存估算不是精确科学，而是快速判断“装不装得下”的工程近似。

手把手估算：8B、32B、70B 在不同精度与并发下的显存

我们用一个统一公式来估算：

总显存 ≈ 权重 + KV Cache + 激活 + 框架开销 + 余量

其中：

  • 权重 = 参数量 × 每参数字节数
  • KV Cache = 2 × 层数 × 并发数 × 上下文长度 × KV头数 × 头维度 × 每元素字节数
  • 激活 ≈ 权重的 5%~10%
  • 框架开销 ≈ 1~2 GB
  • 余量 ≈ 总和的 10%~20%

假设模型结构：层数 = 参数量(B) × 4，KV头数 = 8，头维度 = 128。我们写个脚本对比不同配置：

def estimate(params_b, precision, context_len, batch_size):
    bytes_per_param = {'fp32':4, 'fp16':2, 'int8':1, 'int4':0.5}[precision]
    n_layers = int(params_b * 4)
    n_kv_heads = 8
    head_dim = 128
    weights = params_b * 1e9 * bytes_per_param / (1024**3)
    kv = 2 * n_layers * batch_size * context_len * n_kv_heads * head_dim * bytes_per_param / (1024**3)
    act = weights * 0.05
    overhead = 1.5
    total = (weights + kv + act + overhead) * 1.15
    return weights, kv, total

configs = [
    (8, 'fp16', 4096, 1),
    (8, 'int4', 4096, 1),
    (32, 'fp16', 8192, 4),
    (70, 'int4', 4096, 8),
]
for p, prec, ctx, bs in configs:
    w, kv, total = estimate(p, prec, ctx, bs)
    print(f"{p}B {prec} ctx={ctx} bs={bs}: 权重 {w:.1f}GB, KV {kv:.1f}GB, 总需 {total:.1f}GB")

输出示例：

8B fp16 ctx=4096 bs=1: 权重 14.9GB, KV 0.5GB, 总需 19.5GB
8B int4 ctx=4096 bs=1: 权重 3.7GB, KV 0.5GB, 总需 6.6GB
32B fp16 ctx=8192 bs=4: 权重 59.6GB, KV 8.0GB, 总需 79.5GB
70B int4 ctx=4096 bs=8: 权重 32.6GB, KV 4.0GB, 总需 43.9GB

关键结论：

  • 8B FP16 单并发 4K 上下文，一张 24GB 卡（如 4090）刚好装下，但并发一高就爆。
  • 8B INT4 可以轻松跑在 8GB 显存上，适合边缘设备。
  • 32B FP16 需要至少 80GB 显存，单卡 A100/H100 可行，但并发 4 时已接近极限。
  • 70B INT4 在 48GB 卡（如 A6000）上可跑，但并发 8 时 KV Cache 会吃掉不少显存。

注意：这里假设 KV 头数为 8，实际模型可能不同（如 GQA 会减少 KV 头数），需要查模型配置。

MoE 模型：总参数与激活参数，别被名字骗了

MoE（混合专家）模型像一家大公司：公司有 1000 名员工（总参数），但每个任务只叫 10 个人干活（激活参数）。如果你只按 10 个人算工资（显存），那就大错特错了——因为公司得给所有 1000 人发工资（权重都得存着）。

MoE 模型有两个关键数字：

  • 总参数：所有专家加起来的参数量，决定权重显存。
  • 激活参数：每次前向实际用到的参数量，决定计算量（FLOPs）和部分激活显存。

例如，Mixtral 8x7B 总参数约 46.7B，但激活参数只有约 12.9B。如果你按 12.9B 估算权重显存，会严重低估。

估算 MoE 显存时，权重部分必须用总参数，KV Cache 和激活则与激活参数、层数、注意力头数相关。下面是一个简化示例：

def estimate_moe(total_params_b, active_params_b, precision, context_len, batch_size, n_layers, n_kv_heads, head_dim):
    bytes_per_param = {'fp16':2, 'int8':1, 'int4':0.5}[precision]
    weights = total_params_b * 1e9 * bytes_per_param / (1024**3)
    kv = 2 * n_layers * batch_size * context_len * n_kv_heads * head_dim * bytes_per_param / (1024**3)
    # 激活与激活参数相关，粗略按激活参数的 10% 估算
    act = active_params_b * 1e9 * bytes_per_param / (1024**3) * 0.1
    overhead = 1.5
    total = (weights + kv + act + overhead) * 1.15
    return weights, kv, total

# Mixtral 8x7B: 总参数 46.7B, 激活 12.9B, 32 层, 8 KV 头, 头维度 128
w, kv, total = estimate_moe(46.7, 12.9, 'int4', 4096, 1, 32, 8, 128)
print(f"权重: {w:.1f}GB, KV: {kv:.1f}GB, 总需: {total:.1f}GB")

输出：权重约 21.8GB，总需约 27GB。如果误用激活参数 12.9B 算权重，会得到约 6GB，差了三倍多。

记住：MoE 的权重显存看总参数，计算量看激活参数。部署时，显存按总参数准备，算力按激活参数评估。

部署选型：API、云 GPU、本地工作站、多卡服务器怎么选？

选部署方式就像选交通工具：API 是打车，云 GPU 是租车，本地工作站是买私家车，多卡服务器是买大巴。没有绝对好坏，只有合不合适。

我们从几个维度比较：

维度API云 GPU本地工作站多卡服务器
质量取决于提供商，通常最强自选模型，灵活自选模型，受硬件限制可跑最大模型
延迟网络延迟，通常 100ms~2s取决于网络和实例极低，本地推理低，但需内部网络
并发按量付费，弹性好弹性伸缩受单卡显存限制高并发，需负载均衡
使用率按 token 计费，无闲置成本按小时计费，闲置也花钱一次性投入，闲置浪费高投入，需高使用率摊薄
隐私数据出域，风险高数据在云，需信任提供商数据完全本地数据完全本地
兼容无需操心需自己配环境需自己配环境需自己配环境，多卡通信复杂
运维无中等低高
TCO按量，短期低，长期可能高灵活，适合波动负载前期高，长期低前期很高，适合稳定高负载

如何决策？问自己几个问题：

  • 数据敏感吗？敏感选本地或多卡服务器。
  • 负载稳定吗？稳定且高选本地/多卡，波动大选 API/云。
  • 有运维团队吗？没有就选 API 或托管云。
  • 预算多少？算一下 3 年 TCO：本地 = 硬件 + 电费 + 运维；云 = 每小时费用 × 使用小时；API = token 单价 × 用量。

没有银弹，只有权衡。建议先用 API 验证需求，再根据使用率和隐私要求逐步迁移到云 GPU 或本地。

常见误区

  • 只按激活参数估算 MoE 模型的权重显存，导致严重低估，实际部署时 OOM。
  • 忽略 KV Cache 的显存占用，尤其是在长上下文和高并发场景下，KV Cache 可能超过模型权重。
  • 认为量化后显存按比例线性减少，实际上量化元数据、激活和框架开销不会同比减少，且低精度可能影响质量。

自测

一个 70B 模型，使用 INT4 量化，上下文长度 8192，并发数 4，假设 80 层，8 个 KV 头，头维度 128。请估算总显存需求（GB），并说明计算过程。

答案：权重：70e9 * 0.5 / (1024^3) ≈ 32.6 GB；KV Cache：2 * 80 * 4 * 8192 * 8 * 128 * 0.5 / (1024^3) ≈ 2.5 GB；激活：约 32.6 * 0.05 ≈ 1.6 GB；框架开销：1.5 GB；总和 = 32.6+2.5+1.6+1.5 = 38.2 GB；加 15% 余量 ≈ 43.9 GB。因此需要至少 48GB 显存的 GPU。

MoE 模型的总参数和激活参数分别影响显存估算的哪一部分？为什么不能只用激活参数估算权重显存？

答案：总参数决定权重显存，因为所有专家参数都需要加载到显存中；激活参数决定计算量和部分激活显存。不能只用激活参数估算权重显存，因为虽然每次前向只激活部分专家，但所有专家的权重都必须存储在显存中，否则无法在需要时切换。

参考方案：

使用估算函数： Dense 32B FP16： - 权重：32e9 * 2 / (1024^3) ≈ 59.6 GB - 层数假设 32*4=128，KV 头 8，头维度 128 - KV Cache：2 * 128 * 8 * 4096 * 8 * 128 * 2 / (1024^3) ≈ 16.0 GB - 激活：59.6 * 0.05 ≈ 3.0 GB - 框架开销：1.5 GB - 总和：59.6+16+3+1.5=80.1 GB，加 15% 余量 ≈ 92.1 GB - 需要至少 96GB 显存，单卡 80GB 不够，需 2 张 48GB 或 2 张 80GB。 MoE 46.7B 总参 INT4： - 权重：46.7e9 * 0.5 / (1024^3) ≈ 21.8 GB - 层数假设 32 层（Mixtral 实际 32 层），KV 头 8，头维度 128 - KV Cache：2 * 32 * 8 * 4096 * 8 * 128 * 0.5 / (1024^3) ≈ 4.0 GB - 激活：12.9e9 * 0.5 / (1024^3) * 0.1 ≈ 0.6 GB - 框架开销：1.5 GB - 总和：21.8+4+0.6+1.5=27.9 GB，加 15% 余量 ≈ 32.1 GB - 单卡 48GB 可以轻松装下，甚至 24GB 卡可能勉强（但余量不足，不推荐）。 部署建议： - 如果追求质量且预算充足，选 Dense 32B FP16，需要 2 张 48GB 或 2 张 80GB 卡。 - 如果希望单卡部署且成本可控，选 MoE INT4，一张 48GB 卡（如 A6000）即可，并发 8 无压力。 - 综合考虑，MoE INT4 在显存和成本上更有优势，但需验证质量是否满足业务需求。
