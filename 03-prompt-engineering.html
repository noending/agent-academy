Prompt 工程与上下文设计

第 2 章的系统提示只有两句话，Agent 就能跑——但「能跑」和「稳定可用」之间隔着一门手艺。 模型的所有行为都由上下文决定，而上下文里你能直接写的那一部分，就是提示词。它是你写下的第一段 Harness 代码，也是性价比最高的优化点。

3.1 为什么提示词是「第一段 Harness 代码」

先建立一个认知转换：很多人把提示词当成「和 AI 聊天的说话技巧」，但在 Agent 开发里，它是系统的一部分，和函数、配置一样需要设计与版本管理。理由很直接：

  • 模型的行为 = f(上下文)。上下文里的系统提示、工具描述、历史消息，全都是你写进去的；
  • 同一个模型，提示词改几行，任务成功率可以从 40% 变 90%——杠杆率超过任何其他单点优化；
  • 提示词的缺陷不在运行时报错，而在悄悄劣化输出质量——所以它更需要工程方法（分区、版本、评估），而不是玄学口诀。
本章的核心心法

把「写提示词」重构成「设计上下文」：你不是在对模型说话，而是在定义一个函数的输入规格——输入有哪些区、每区放什么、以什么格式、边界情况怎么处理。第 5 章的「上下文工程」是这个心法的全面展开。

论文精读入口

本章方法的三个学术源头：Chain-of-Thought（先推理再作答的起点）、ReAct（推理与行动合流）、Toolformer（模型自学用工具）——按统一模板拆解见 论文精读页，逐段中译见 中文精读版。

3.2 系统提示的解剖学：五区结构

生产级系统提示几乎都能拆成五个区。不是每个任务都需要全部五区，但每区的职责要清晰、不要混写：

区职责写法要点
① 身份你是谁、为谁服务一两句即可。「你是一个电商客服」比「你是一个乐于助人的AI助手」有用——身份决定了大量隐含行为
② 能力与规则怎么做事、做事流程祈使句 + 编号列表；写「做什么」而不是「不要做什么」；每条规则只说一件事
③ 输出契约格式、长度、语言明确到「字段名 + 类型 + 枚举值」；有结构化需求直接给 schema 或示例
④ 边界与禁止什么不能做、不确定怎么办关键一条：「信息不足时如何表现」（说不知道 / 询问 / 写 null），这是抑制幻觉的主开关
⑤ 示例示范理想行为见 3.3 节，格式类任务几乎必备

好提示 vs 差提示：完整对比

任务：一个查询订单状态的智能体的系统提示。

text · ✗ 差提示（全网最常见的写法）
你是一个智能客服助手，请认真回答用户的问题，
要礼貌、专业、热情。如果用户问订单，请帮他查订单。
不要回答与订单无关的问题。
text · ✓ 好提示（五区结构）
【身份】你是「闪电电商」的订单客服，服务对象是消费者。

【能力与规则】
1. 查询订单状态时，必须先调用 query_order 工具，禁止凭记忆回答
2. 回答基于工具返回的信息，逐字段如实转述，不做延伸承诺
3. 用户问「多久到」时，用工具返回的预计送达时间回答，不自行估计

【输出契约】
- 中文回答，不超过 3 句话
- 涉及订单号时完整复述，避免用户抄错

【边界与禁止】
- 只处理订单相关咨询；其他请求回复：
  「我是订单客服，这个问题请转人工或联系对应部门」
- 工具查询失败时如实告知，并建议用户稍后再试，禁止编造订单状态
- 遇到投诉、退款纠纷，收集订单号后转人工，不要自行给出补偿方案

差异在哪？差提示全是形容词（认真/礼貌/专业/热情），模型无从执行；好提示全是可判定的行为规则——每一条都能在具体对话里打出「遵守了/没遵守」。这正是能用评估集（第 8 章）验证的前提。

五条写作军规

① 用祈使句写「做什么」，少写「不要」（负面指令模型遵守得差，且列表越长越互相稀释）；
② 每条规则独立成行、可单独判定；
③ 必须定义「不确定时怎么办」；
④ 输出格式明确到字段级；
⑤ 控制篇幅——系统提示本身也占上下文，300 字能说清的不要写 3000 字。

3.3 少样本示例（Few-shot）：给模型看作业范本

规则讲一万句，不如给一个标准答案。在提示里放 2~5 个「输入→理想输出」的示例，就是少样本提示。它解决三类问题：

  • 格式模仿：JSON 字段顺序、嵌套结构、标点习惯——用示例秒杀，用文字描述很难对齐；
  • 风格统一：客服语气、摘要详略、翻译腔调；
  • 边界判定：哪些算「订单相关」、哪个字段该写 null——示例是最自然的边界说明。
选例子的三条原则

① 覆盖典型 + 边界：一半普通样本，一半是容易出错的边界样本（缺失字段、歧义输入）；
② 示例之间多样化：别放三个只换名字的例子，模型会以为只有这一点点变化模式；
③ 数量克制：2~5 个足够，过多示例挤占上下文且收益递减。动态进阶：输入种类多时，可以按相似度检索最相关的几个示例动态拼进提示（第 4 章向量检索的直接应用）。

3.4 结构化输出与「生成 → 校验 → 重试」闭环

Agent 的输出经常要喂给程序（存数据库、触发动作），自由文本不可靠。三层防线，一层比一层强：

  1. JSON 模式

    请求里加 response_format={"type": "json_object"}（DeepSeek / OpenAI 兼容），并在提示词里包含 "json" 字样。保证输出是合法 JSON，但不保证字段和类型符合你的预期。

  2. Schema 校验

    拿到 JSON 后，用代码校验字段、类型、枚举值（生产环境用 pydantic，教学版手写也就十几行）。

  3. 校验失败 → 带着错误重试

    把校验错误信息连同原输出一起喂回模型重新生成，通常一次就能修好。重试 2 次仍失败就放弃并上报——这个闭环是 Harness 的职责，不是指望模型自觉。

python · structured_output.py —— 完整闭环
import json
from openai import OpenAI

client = OpenAI(api_key=os.environ["DEEPSEEK_API_KEY"],
                base_url="https://api.deepseek.com")

PROMPT = """从用户留言中抽取投诉信息，输出 JSON：
{"category": "物流|质量|服务|其他", "order_id": string|null, "urgent": boolean}
category 必须从四个枚举值中选一个；order_id 找不到写 null。

留言：{user_text}
只输出 JSON。"""

def extract_complaint(user_text: str, max_retries: int = 2) -> dict:
    messages = [{"role": "user",
                 "content": PROMPT.format(user_text=user_text)}]
    last_err = ""
    for _ in range(max_retries + 1):
        resp = client.chat.completions.create(
            model="deepseek-chat",
            messages=messages,
            response_format={"type": "json_object"},   # 第一层：JSON 模式
            temperature=0,
        )
        try:
            data = json.loads(resp.choices[0].message.content)
            data = validate(data)                      # 第二层：Schema 校验
            return data
        except (json.JSONDecodeError, ValueError) as e:
            last_err = str(e)
            # 第三层：把错误喂回去重试
            messages.append({"role": "assistant",
                             "content": resp.choices[0].message.content})
            messages.append({"role": "user",
                             "content": f"输出不合法：{last_err}。请修正后重新只输出 JSON。"})
    raise ValueError(f"结构化抽取失败: {last_err}")

def validate(d: dict) -> dict:
    if d.get("category") not in ("物流", "质量", "服务", "其他"):
        raise ValueError(f"category 非法: {d.get('category')!r}")
    if not isinstance(d.get("urgent"), bool):
        raise ValueError("urgent 必须是布尔值")
    oid = d.get("order_id")
    if oid is not None and not isinstance(oid, str):
        raise ValueError("order_id 必须是字符串或 null")
    return d
这个模式的价值

「生成→校验→带着错误重试」是 Agent 工程里最常用的可靠性模式之一，它把「模型偶尔出错」从致命问题变成了可测量的成本（多一次调用）。同样的模式会反复出现：工具参数校验（第 7 章）、本体写入校验（第 6 章）、评估打分（第 8 章）。

3.5 参数的工程含义：temperature、max_tokens、stop

参数作用Agent 场景建议
temperature采样随机性：0 ≈ 总选最高概率词，1+ 更发散工具调用 / 抽取 / 分类用 0~0.3（要稳定）；创意写作用 0.7+；同一个任务在不同温度下表现差异巨大，值得进评估集对比
max_tokens输出长度上限必须设。既是成本保险丝，也防止模型跑题写论文；注意 finish_reason="length" 表示被截断（第 2 章），要检测
stop遇到指定字符串就停止让模型只输出 JSON 时可设 stop=["\n\n"] 之类防跑偏；与结构化校验配合使用
seed尽量复现随机采样调试时固定 seed + temperature=0，让「同一个输入每次结果一样」，否则你改了一行提示词根本不知道效果变化是谁造成的

3.6 提示词的迭代方法：像改代码一样改提示词

  1. 先建评估集，再改提示词

    准备 20 个左右真实输入（含边界样本），在改动前后各跑一遍，对比通过率。没有评估的提示词调优 = 拍脑袋：你永远不知道这次「感觉变好了」是不是幻觉。评估集的做法第 8 章手把手教。

  2. 单变量修改

    一次只改一处（加一条规则 / 换一个示例 / 调一档温度），跑评估，记录结果。连续改五处再测，你永远不知道是哪处起效。

  3. 版本留痕

    提示词放独立文件（prompts/extract_v7.md）进 Git，commit message 写清「改了什么、评估结果如何」。三个月后你会感谢自己。

  4. 让模型帮你改，但你把关

    把「当前提示 + 失败案例 + 期望输出」喂给模型，让它提议修改——模型确实擅长此道。但每一条修改都要过评估集，模型和你一样会过度拟合单个案例。

反模式清单（每一条都真实高频）

  • 堆砌形容词：「认真、专业、热情、严谨」——不可判定，模型无法执行
  • 负面指令刷屏：十个「不要……」不如一条「应该……」+ 一个反例
  • 一大段散文无分区：身份、规则、格式混在一起，模型顾此失彼
  • 期望读心：「按我平时的风格写」——模型不知道你平时什么风格，给示例
  • 规则之间互相矛盾：「回答要简短」+「详细解释每个字段」——冲突时行为随机，合并成一条明确的
  • 所有任务共用一个巨型提示：为每个任务定制精简提示，按需拼装

3.7 全景：LLM 在智能体链路中的五种角色

学到这里可以回答一个根本问题了——「如何用 LLM 开发智能体？」 答案不是「调用一次 API」，而是：把同一个模型配置成不同角色，编排在 Harness 的循环里协同工作。 盘点前几章出现过的全部 LLM 用法，其实只有五种角色：

角色输入 → 输出温度在课程哪里出现
决策器上下文 + 工具声明 → 下一步行动或最终回答0~0.3第 1/2 章 Agent Loop 的每一步——Agent 的心脏
抽取器非结构化文本 → JSON（字段、三元组、查询改写）0本章校验闭环；第 6 章三元组抽取；第 4 章查询改写
分类/路由器输入 → 枚举标签0意图分类（本章练习 1）；第 7 章模型路由；第 6 章按类目选工具
裁判回答 + 评分标准 → 分数与理由0第 8 章 LLM-as-Judge，评估集的开放题判分器
生成器主题 + 约束 → 正文内容0.7+最终回答撰写、报告、摘要——面向用户的那一面
五个角色背后的统一规律

五个角色 = 同一个模型的五种「上下文配置」：每一种都是一套「系统提示（本章五区结构）+ 参数（本章 3.5）+ 校验方式（本章闭环）」的组合。

这就是入门与精通的分水岭：入门者把 LLM 当成「一个会被调用的接口」；精通者把 LLM 当成一组可配置、可编排、可各自评估的角色——第 6 章 Harness 负责编排，第 8 章评估集负责给每个角色的配置打分，第 9 章毕业项目把它们全部组装起来。从本章起，你写的每一个提示词都请标注：它在为哪个角色服务？

3.8 从提示词工程到上下文工程

最后做一次视角升级。模型每轮看到的上下文 = 系统提示 + 工具声明 + 对话历史 + 检索到的资料。系统提示只是其中一块，其余三块同样是「你写进去的信息」，同样遵循本章的所有原则：

  • 工具描述就是「给模型的迷你系统提示」（第 2 章的五原则）；
  • 历史消息的设计（留什么、裁什么、压缩什么）是第 5 章的主题；
  • 检索内容怎么排序、怎么标注来源，决定 RAG 质量（第 5 章）。
统一的判断标准

不管优化哪一块，都问同一个问题：「模型看到这段内容后，做对下一步决策所需的一切信息都在场吗？有没有会误导它的冗余或矛盾？」——这句话就是「上下文工程」的全部定义。

自测

「你是XXX，请认真、专业、热情地回答用户」为什么是一句无效提示？

答案：因为它由不可判定的形容词构成——没有任何方法判断一次输出是否「足够热情」，模型只能按训练数据的平均行为行事，这句提示约等于没写。有效提示由可判定的行为规则构成：「不超过 3 句话」「先查工具再回答」「查不到就说查不到」——每条都能打出遵守/不遵守，也才能进评估集被度量。

JSON 模式（response_format=json_object）保证了什么、没保证什么？

答案：保证了输出是语法合法的 JSON（能被 json.loads 解析）。没保证：字段齐全、类型正确、枚举值合法、语义符合预期——这些必须由你自己的 Schema 校验负责，校验失败走「带错误重试」闭环。两层防线各管一段，缺一不可。

什么任务该用 temperature=0，什么任务故意调高？同一个任务怎么确定最优温度？

答案：工具调用、信息抽取、分类、代码修改等「要稳定复现」的任务用 0~0.3；头脑风暴、文案创作、起名字等「要多样性」的任务调高。确定方法不是猜：把温度作为变量进评估集，跑 2~3 档对比通过率——第 8 章的评估管线让这种实验只要几分钟。

为什么说「把提示词放进 Git 做版本管理」而不是存在代码里的字符串常量？

答案：三个理由：① 提示词是被高频迭代的部分，独立文件 + commit 留痕，才能回溯「哪个版本的提示词配合哪个评估结果」；② 独立文件便于同一提示词被多处复用、便于做 A/B（加载不同版本对比）；③ 把提示词从代码逻辑里分离，改提示词不需要重新审查代码 diff——提示词的变更频率远高于代码。

动手练习（带参考答案）

练习 1 · 为「退换货意图分类」写一个工业级系统提示

任务：客服系统需要把用户留言分类到 return（退货）/ exchange（换货）/ repair（维修）/ other（其他），同时判断是否情绪激动（agitated: bool）。写出完整系统提示（输出 JSON）。

text · 参考答案
你是电商客服系统的意图分类模块。输入是一条用户留言，输出一个 JSON，
不要输出任何其他内容。

【字段定义】
- intent: "return" | "exchange" | "repair" | "other"
  - return：用户表达了退钱/退货意愿
  - exchange：用户想换货（换尺寸、换颜色、换货不退钱）
  - repair：商品故障，用户想要维修
  - other：咨询、投诉、闲聊等一切非上述意图
- agitated: boolean，出现明显愤怒、威胁投诉、连续感叹号时为 true

【规则】
1. 一条留言同时涉及退货和换货时，以用户最终诉求为准
   （例：「换个新的吧，不要这个了，太差了」→ 换货行为但意图是不要了 → return）
2. 只表达不满但没说要什么解决的，intent 为 "other"
3. 判断不准时，intent 取 "other"，不要猜

【示例】
输入：「手机屏幕摔碎了开不了机，我才买一个月！」
输出：{"intent": "repair", "agitated": true}

输入：「麻烦帮我退了，用了两天不喜欢」
输出：{"intent": "return", "agitated": false}

自查要点：枚举值全部显式列出 ✓；每条边界规则都对应一个具体案例 ✓；给了含边界情形的示例 ✓；「判断不准怎么办」有明确出口（other）而不是留给模型猜 ✓。把这个提示词接上第 2 章的 API 调用，就是一个能上线的分类模块。

练习 2 · 地址标准化：设计一组 few-shot 示例

任务：把用户随手写的地址转成 {"province","city","district","detail"}。请设计 3 个示例，覆盖最容易出错的边界。

参考答案（选例思路比答案本身更重要）：

text · 三个覆盖关键边界的示例
输入：上海市浦东新区张江高科纳贤路800弄10栋301
输出：{"province":"上海市","city":"上海市","district":"浦东新区",
       "detail":"张江高科纳贤路800弄10栋301"}
      （边界1：直辖市——province 和 city 相同，不能把 city 写成空）

输入：杭州西湖区文三路 100 号
输出：{"province":"浙江省","city":"杭州市","district":"西湖区",
       "detail":"文三路100号"}
      （边界2：用户省略省份——按城市补全省份，这是补全而不是编造）

输入：深圳南山那边有个科技园的，具体门牌我忘了
输出：{"province":"广东省","city":"深圳市","district":"南山区",

要点：三个示例分别教会模型「直辖市怎么填」「缺省份要补全」「缺失信息写 null」。这三类错误恰好是这类任务最高频的三种失败——示例的价值在于精准覆盖失败模式，而不是数量多。

练习 3 · 补全校验重试闭环中的 validate 函数

任务：为「日程抽取」输出实现校验：要求字段 title(str)、date("YYYY-MM-DD")、start_time("HH:MM")、attendees(list[str])，date 必须是合法日期且不早于今天，start_time 必须是合法时间。

python · 参考答案
from datetime import date, datetime

def validate(d: dict) -> dict:
    if not isinstance(d.get("title"), str) or not d["title"].strip():
        raise ValueError("title 必须是非空字符串")
    try:
        d_date = datetime.strptime(d["date"], "%Y-%m-%d").date()
    except (KeyError, ValueError):
        raise ValueError(f"date 缺失或不是 YYYY-MM-DD: {d.get('date')!r}")
    if d_date < date.today():
        raise ValueError(f"date {d['date']} 早于今天，日程不能创建在过去")
    try:
        datetime.strptime(d["start_time"], "%H:%M")
    except (KeyError, ValueError):
        raise ValueError(f"start_time 缺失或不是 HH:MM: {d.get('start_time')!r}")
    if not isinstance(d.get("attendees"), list) or \
       not all(isinstance(a, str) for a in d["attendees"]):
        raise ValueError("attendees 必须是字符串列表")
    return d

pydantic 对照版（生产推荐）：声明即校验，错误明细自动生成：

python · pydantic 版
from pydantic import BaseModel, Field, field_validator
from datetime import date

class Schedule(BaseModel):
    title: str = Field(min_length=1)
    date: date                                    # 类型不合法直接抛错
    start_time: str = Field(pattern=r"^\d{2}:\d{2}$")
    attendees: list[str] = Field(default_factory=list)

    @field_validator("date")
    @classmethod
    def not_past(cls, v: date) -> date:
        if v < date.today():
            raise ValueError("日程不能创建在过去")
        return v

# Schedule.model_validate(data) 失败时抛 ValidationError，
# str(e) 自带「哪个字段、什么原因」的明细——直接喂回模型走闭环

要点：错误信息必须具体到能指导修正（「date 非法」不如「date 早于今天」）——因为这段错误信息会被原样喂回模型。同时注意：校验代码跑在你这边，永远不要相信模型自称「我已按要求输出」，要用代码验证。
