前六章造出了能力，这一章解决三个「从 demo 到产品」的生死问题：坏了怎么查（调试）、好不好怎么知道（评估）、能不能给别人用（上线）。 这一章的方法不依赖任何框架，是你以后每天都会用的肌肉。

目标：具备独立调试与上线能力 交互实验：Trace 侦探 LLM-as-Judge · Gradio · 部署清单 练习：3 题（带参考答案）

8.1 Agent 调试为什么特别难

传统程序调试的三板斧（断点、单步、看变量）在 Agent 上几乎全失效，原因有四：

非确定性

同样的输入两次运行可能走完全不同的路径。复现 bug 需要固定 temperature=0 + seed，或从 Trace 完整回放。

错误延迟显形

第 4 步埋下的误判，第 9 步才表现为失败。出错的地方 ≠ 出问题的原因。

状态藏在上下文里

Agent 的全部「心理状态」就是那个 messages 数组，代码里没有变量可看——你只能看它每一步看到了什么。

没有报错栈

行为类失败（答非所问、悄悄降标准）不抛异常，只有结果不对。崩溃类 bug 反而是最简单的一类。

8.2 Trace 调试方法论：五步定位法

前提：你的 Harness 在记录全量 Trace（第 5 章的 JSONL + 第 7 章的 Trace 类）。没有 Trace，以下全部免谈。

  1. 复现

    固定变量：temperature=0、固定模型版本、原样重放用户输入。行为类 bug 若无法稳定复现，先跑 10 次统计出现率——「20% 出现」本身就是重要线索（说明模型在两个方案间摇摆，通常提示提示词有歧义）。

  2. 定位「首次偏离」

    从失败的最终输出倒着读 Trace，问每一步：「它的这个判断，依据的是上一步真实给到的信息吗？」找到第一处「依据不足却下了结论」的步骤——那里才是根因，而不是报错的那一步。

  3. 归类缺口

    根因通常落进三类之一：信息缺口（模型没看到本该看到的东西——工具没返回、结果被裁剪掉了）、规则缺口（提示词没约束到这种情况）、能力缺口（任务超出模型能力，需要换模型或拆任务）。三类对应三种修法。

  4. 单变量修复

    只改一处：补一个工具返回字段 / 加一条规则 / 换一档模型。禁止一次改三处——你将永远不知道是哪处起效（第 3 章的纪律在这里同样生效）。

  5. 回归验证

    跑评估集（7.3 节）。确认目标案例修复且没有打破别的案例——「修好一个坏三个」是提示词工程最常见的结局。

8.3 构建你自己的评估集

评估集（evals）是 Agent 工程里复利最高的资产：代码会重写、提示词会迭代，评估集会一直帮你守住质量底线。

用例从哪来？三层结构

层占比来源作用
能力层~60%产品要支持的核心任务，各写 3~5 个变体守住基本盘
边界层~25%输入残缺、字段缺失、恶意输入、超长输入守住下限——多数线上事故来自这层
回归层~15%每一个线上真实失败案例，修完就收进来保证同一个坑不摔第二次

三种自动评分器，由廉到贵

  1. 关键词断言

    第 5 章的 must_include / must_exclude。零成本，适合事实类答案。

  2. 规则断言

    用代码校验结构：JSON 可解析、字段合法、长度范围、必须引用了工具返回的某个数值。

  3. LLM-as-Judge

    开放性任务（写作、总结、建议质量）无法用规则断言，请另一个模型按评分标准打分。

python · judge.py —— LLM-as-Judge 最小实现
import json

JUDGE_PROMPT = """你是严格的质量评审。依据【评分标准】给【回答】打分。
评分标准（每条都要逐一核对）：
{rubric}

【任务输入】
{input}

【待评回答】
{answer}

输出 JSON：{{"score": 0到10的整数, "failed_rules": ["没满足的标准"], "reason": "一句话"}}
只输出 JSON。"""

def judge(input_text: str, answer: str, rubric: str) -> dict:
    resp = client.chat.completions.create(
        model="deepseek-chat",          # 有条件用更强的模型当裁判
        temperature=0,                  # 裁判必须稳定
        response_format={"type": "json_object"},
        messages=[{"role": "user", "content": JUDGE_PROMPT.format(
            rubric=rubric, input=input_text, answer=answer)}],
    )
    return json.loads(resp.choices[0].message.content)

# 用法：
# rubric = "1. 明确回答了汇率是多少（数字）；2. 说明了数据截至日期；3. 未编造来源"
# print(judge("现在换美元划算吗", "美元汇率约7.1，数据来自昨天银行牌价……", rubric))
# → {"score": 6, "failed_rules": ["未说明数据截至日期"], "reason": "..."}
Judge 的三个已知偏差（必须防）

① 偏爱长回答：在 rubric 里明确「长度本身不加分」或对超长扣分；
② 自我偏好：裁判模型与被评模型同源时打分偏高——评测分数只用于内部对比、不对外宣称绝对值；
③ 规则越含糊偏差越大：rubric 必须写成可核对的条目（第 3 章的「可判定规则」原则原样适用）。定期抽样 10% 人工复核 judge 的判定，发现漂移立即修 rubric。

评估的运行纪律

把 python eval_runner.py 变成你的肌肉记忆：任何改动（提示词、工具、模型、温度）之后必跑。每次运行存档结果（日期 + 通过率 + 改动说明），三个月后它就是整个项目的质量时间线。

形态三：FastAPI 服务化（给产品 / 前端调用）

python · server.py —— 骨架
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class Ask(BaseModel):
    session_id: str
    message: str

@app.post("/ask")
def ask(req: Ask):
    harness = get_or_create_session(req.session_id)   # 每会话一份状态
    try:
        answer = harness.run(req.message)
        return {"answer": answer, "session_id": req.session_id}
    except Exception as e:
        # 永远不要把原始异常堆栈直接抛给前端
        return {"answer": "处理出错，请稍后再试（已记录日志）",
                "error_id": log_and_get_id(e)}

# 部署：uvicorn server:app --host 0.0.0.0 --port 8000
# 流式版用 StreamingResponse + SSE，逐段推送第 7 章拼接出的 delta

上线检查清单（一条 5 分，低于 40 分别上线）

  • API Key 在环境变量 / 密钥管理服务里，代码与日志中不出现
  • 每次 LLM 调用有超时 + 重试（第 2 章 2.7 节）；工具执行有上限时长
  • 高危工具全部 confirm 级，Web 端有审批 UI

  • 评估集 ≥ 30 条且最近一次通过率已知；改动必跑
  • 失败对用户可见且体面（「我没查到」好过编一个）
  • 有用户反馈入口（👍/👎），坏例自动进回归层

8.6 Day-2 运维：上线之后才是 FDE 的日常

部署完成只是第一天。上线后的每一天，三类事故会轮流找上门——每一类都要有预先写好的剧本（runbook），事故发生时照着执行而不是临场发明：

事故类型典型症状剧本（按序执行）
① 质量劣化评估集通过率隔夜下跌、客诉上升确认评估集本身没变 → 检查供应商是否静默更新模型（比对响应元数据）→ diff 新增失败用例、按五步定位法找首次偏离 → 决策：锁定旧版本 / 适配提示词 / 回滚 → 失败用例进回归层
② 成本飙升CostMeter 日报异常、单任务成本 ×3定位：哪类任务哪一步膨胀（缓存失效 / 检索返回变大 / 循环失控）→ 熔断：日预算上限触发自动降级（小模型 / 拒新任务）→ 修复后压测 → 调整告警线
③ 供应商故障API 超时 / 限流 / 5xx 集中出现状态页确认范围 → 切换备用引擎（第 7 章：改 base_url 两行）→ 开启降级输出（「稍后重试」优于编造）→ 把切换演练固化为季度例行
模型版本迁移清单（供应商宣布旧模型退役时照做）

① 在评估集上同时跑新旧版本，产出指标对比表；② diff 失败用例，归类原因（格式偏好变了？安全策略收紧了？）；③ 单变量适配提示词 / 工具描述，逐项回归；④ 10% 流量灰度 48 小时；⑤ 全量切换，旧版本别名保留 30 天（第 7 章）。整个清单的目标：48 小时内完成迁移决策。

真实案例研究：三个公开可考的教训

案例一 · Air Canada 聊天机器人赔偿案（2024）
加拿大航空官网聊天机器人就 bereavement（丧亲）票价政策给出了错误答复（告诉乘客可以事后申请退款），乘客据此购票，事后航司拒绝认账，乘客 Moffatt 起诉——不列颠哥伦比亚民事仲裁庭裁定：公司须为其网站聊天机器人的错误陈述负责，赔偿约 650 加元。航司抗辩称「聊天机器人是独立法人、自负其责」，被法庭驳回。
FDE 视角复盘：这是「幻觉的法律后果」第一个标志性判例。三条交付前就能拦住它的动作：① 你的 Agent 承诺了什么，公司就要兑现什么——"那是 AI 说的"不是抗辩理由；② 政策类回答必须从受治理的知识库生成（第 4 章），而不是模型参数记忆；③ 免责声明要放在对话流内，而不是网站角落。
案例二 · 车行聊天机器人「1 美元卖车」事件（2023）
加州某雪佛兰经销商的 ChatGPT 驱动聊天机器人在与用户的玩笑式对话中同意以 1 美元出售一辆全新 Tahoe（"成交，法律上有效——不退不换"），用户截图为证，经销商只能公开认错取消订单。同类事件随后在多家公司的客服机器人上重演。
FDE 视角复盘：教训不是"别用大模型"，而是报价、承诺、协议类输出必须是 Action 类型（第 6 章）而非自由文本：受治理的写入口 + 校验规则（报价 ≥ 成本价）+ 人在环确认。第 7 章 confirm 级权限的存在理由，这个案例是最生动的注脚。
案例三 · 企业 RAG 项目的共性复盘（2024 起大量公开）
2024 年起大量团队公开复盘失败的 RAG 项目，失败原因高度收敛于四条：① PDF 解析被跳过（扫描件/表格成为检索黑洞——第 4 章 4.1 关卡）；② 没有评估集就上线（质量靠"感觉不错"支撑，首次演示即翻车）；③ 切块策略拍脑袋（从未跑过 hit@k 对比）；④ 用"更大的模型"救检索不足（方向性错误）。
解读：注意这个分布——四个高频死因里三个在数据/检索层、一个在流程层，没有一个在"模型不够好"上。这与第 4 章「先查检索层」的二分法、第 8 章「先磨接口再换模型」完全一致：企业级失败几乎从不发生在模型层，而发生在工程没做完的地方。

一个反直觉的结论

三个月后回看你的项目：代码可能已经重写了两遍，但评估集一条没废。它是你对「这个 Agent 应该怎样才算对」的全部理解的结晶——比任何一段实现都更接近项目的本质。

自测

为什么「报错的那一步」常常不是「根因所在的那一步」？定位根因的正确动作是什么？

答案：Agent 是链式推理：第 N 步的判断建立在第 N-1 步给到的信息与结论之上，一处「依据不足的推断」会传播到几步之后才显形为失败。所以定位要从最终失败倒着读 Trace，逐步审问「这个判断的依据真实存在吗」，找到首次偏离的那一步——它才是根因。

LLM-as-Judge 为什么必须 temperature=0？为什么 rubric 要写成可核对的条目？

答案：裁判的价值在于一致性——同一个回答今天 7 分明天 5 分，评估集就失去了回归意义，所以温度必须 0（必要时固定 seed）。rubric 写成可核对条目（「是否说明了数据截至日期」）而非形容词（「回答是否优秀」），一是让裁判有据可依、减少随机漂移，二是让你能人工复核裁判的判定、发现偏差立即修 rubric。

评估集三层结构（能力 / 边界 / 回归）各自防守什么？为什么说回归层最「值钱」？

答案：能力层守住核心功能的下限；边界层守住异常输入（残缺、恶意、超长）——多数线上事故来自这里；回归层守住「同一个坑不摔第二次」。回归层最值钱是因为每一条都是真实发生过的失败：它带有完整的复现信息和已验证的修复，是唯一随时间只增不减、且条条有用的资产。

动手练习（带参考答案）

练习 1 · 给 run_eval 加 LLM-as-Judge 分支

任务：扩展第 5 章的 run_eval：用例可以有 "judge_rubric" 字段，有则走 judge 评分（≥7 分算过），没有则走关键词断言。

python · 参考答案
def check_case(c: dict, answer: str) -> bool:
    if "judge_rubric" in c:                      # 开放题：裁判说了算
        verdict = judge(c["input"], answer, c["judge_rubric"])
        print(f"   judge: {verdict['score']}/10 - {verdict['reason']}")
        return verdict["score"] >= 7
    return (all(kw in answer for kw in c.get("must_include", []))
            and all(bad not in answer for bad in c.get("must_exclude", [])))

def run_eval(path="evals.jsonl", agent_fn=run_agent):
    cases = [json.loads(l) for l in open(path, encoding="utf-8") if l.strip()]
    passed = sum(check_case(c, agent_fn(c["input"])) for c in cases)
    print(f"\\n通过率 {passed}/{len(cases)} = {passed/len(cases):.0%}")

要点：judge 的分数阈值（≥7）也是评估集的一部分，改阈值同样要留痕。成本注意：judge 每条多一次调用，回归层用关键词、能力层才上 judge，是常见的省钱分层。

练习 2 · 文字版 Trace 侦查：根因在哪一步？

任务：旅行规划 Agent 的任务「查下周东京的天气并推荐穿搭」，最终回答「下周东京约 15~22°C，建议穿薄外套」被用户投诉「错得离谱——下周东京是雨季，几乎天天暴雨」。Trace 如下，定位首次偏离：

text · Trace 片段
① thought: 查东京天气 → weather_tool(city=东京, date=next_week)
② obs: {"forecast": "15~22°C", "note": "雨季降水概率高"}
③ thought: 温度区间拿到了，15~22°C 对应薄外套。
④ answer: 下周东京约 15~22°C，建议穿薄外套。

参考答案：首次偏离在 ③。观察里明确带着「雨季降水概率高」的 note，模型只取了温度字段、丢弃了天气现象信息——一次「选择性读取」。修法属信息缺口类：不是模型没收到（收到了！），而是工具返回结构让关键信息像个附带注释；把 weather_tool 的返回重构为显式字段 "condition": "rain"，或加规则「穿搭建议必须综合全部天气字段」。①②无错，④只是③的忠实执行。
