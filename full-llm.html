第1章 · LLM基础概念

本章目标：理解LLM核心概念与工作原理

从统计语言模型到神经网络语言模型

语言模型（Language Model）的核心任务很简单：计算一个词序列出现的概率。比如“今天天气真不错”这句话，语言模型会给出它作为一个合法句子的概率。早期我们用统计方法，比如 N-gram：假设每个词只依赖前面 N-1 个词。N=2 时，“不错”只依赖“真”。这种方法简单，但有两个致命问题：数据稀疏（很多词组合在语料里根本没出现过，概率为 0）和上下文窗口太短（无法捕捉长距离依赖）。

神经网络语言模型改变了游戏规则。它把词映射成稠密向量（词嵌入），然后用神经网络根据前面的词预测下一个词。这样即使没见过“真不错”这个组合，模型也能从“真好”“很棒”等相似语境中泛化。2017 年 Transformer 的出现，让模型可以并行处理整个序列，并且通过自注意力机制直接建模任意两个词之间的关系，这才有了今天的大语言模型（LLM）。

下面是一个用 PyTorch 实现的最简神经网络语言模型（Bigram 版），帮你直观感受“用神经网络预测下一个词”是怎么回事：

import torch
import torch.nn as nn
import torch.nn.functional as F

# 假设词表只有 5 个词：我, 爱, 学习, 人工智能, &lt;eos&gt;
vocab_size = 5
embed_dim = 8

class BigramLM(nn.Module):
    def __init__(self):
        super().__init__()
        # 输入词索引 -&gt; 嵌入向量
        self.embed = nn.Embedding(vocab_size, embed_dim)
        # 嵌入向量 -&gt; 下一个词的 logits
        self.linear = nn.Linear(embed_dim, vocab_size)

    def forward(self, x):
        # x: (batch, seq_len) 词索引
        emb = self.embed(x)          # (batch, seq_len, embed_dim)
        logits = self.linear(emb)    # (batch, seq_len, vocab_size)
        return logits

model = BigramLM()
# 输入序列：我 爱 学习
x = torch.tensor([[0, 1, 2]])
logits = model(x)
# 对最后一个位置的输出做 softmax，得到下一个词的概率分布
probs = F.softmax(logits[0, -1], dim=-1)
print(probs)  # 例如 tensor([0.1, 0.2, 0.3, 0.3, 0.1])

这个模型只根据当前词预测下一个词，非常简陋，但已经包含了现代 LLM 的基本要素：词嵌入 + 神经网络 + 概率输出。真正的 LLM 只是把这个结构堆叠得极深、极宽，并用海量文本训练。

Transformer 与自注意力机制

Transformer 是 LLM 的骨架。它的核心是自注意力（Self-Attention）：对于序列中的每个词，计算它与其他所有词的关联程度，然后加权求和，得到新的表示。这样，每个词都能“看到”整个句子，并动态决定关注哪些部分。

自注意力的计算可以概括为三步：

  1. 把每个词的向量分别投影成 Query（查询）、Key（键）、Value（值）三个向量。
  2. 用 Query 和所有 Key 做点积，得到注意力分数，再除以 √d 防止梯度消失，然后 softmax 归一化。
  3. 用归一化后的分数对 Value 加权求和，得到输出。

用公式表示就是：Attention(Q, K, V) = softmax(QK^T / √d) V。多头注意力（Multi-Head Attention）则是并行做多组这样的计算，让模型从不同子空间捕捉信息。

下面是一个可运行的单头自注意力最小实现：

import torch
import torch.nn as nn
import torch.nn.functional as F
import math

class SelfAttention(nn.Module):
    def __init__(self, embed_dim):
        super().__init__()
        self.embed_dim = embed_dim
        self.q_proj = nn.Linear(embed_dim, embed_dim)
        self.k_proj = nn.Linear(embed_dim, embed_dim)
        self.v_proj = nn.Linear(embed_dim, embed_dim)

    def forward(self, x):
        # x: (batch, seq_len, embed_dim)
        Q = self.q_proj(x)
        K = self.k_proj(x)
        V = self.v_proj(x)
        # 计算注意力分数
        scores = torch.matmul(Q, K.transpose(-2, -1)) / math.sqrt(self.embed_dim)
        attn = F.softmax(scores, dim=-1)
        out = torch.matmul(attn, V)
        return out, attn

# 模拟一个 batch=1, seq_len=3, embed_dim=4 的输入
x = torch.randn(1, 3, 4)
attn_layer = SelfAttention(embed_dim=4)
out, attn_weights = attn_layer(x)
print('输出形状:', out.shape)          # torch.Size([1, 3, 4])
print('注意力权重形状:', attn_weights.shape)  # torch.Size([1, 3, 3])
print('注意力权重（每行和为1）:\n', attn_weights)

运行后你会看到，每个位置对三个位置的注意力权重加起来是 1。这就是自注意力的直观含义：每个词都在问“我应该关注谁？”。Transformer 还包含前馈网络、残差连接、层归一化等组件，但自注意力是它区别于 RNN/CNN 的关键。

预训练与微调范式

现代 LLM 的训练分为两个阶段：预训练（Pre-training）和微调（Fine-tuning）。

预训练是在海量无标注文本上进行的自监督学习。最常见的任务是“预测下一个词”（自回归语言建模，如 GPT 系列）或“完形填空”（掩码语言建模，如 BERT）。模型通过反复预测被遮住或接下来的词，学会了语法、事实知识、推理能力等。这个阶段计算量极大，通常需要数千 GPU/TPU 训练数周，成本极高。

微调是在预训练模型的基础上，用少量标注数据（或指令数据）继续训练，让模型适应特定任务或领域。比如用医疗问答数据微调，模型就能更好地回答医学问题。微调需要的计算资源远小于预训练，是开发者最常接触的环节。

近年来还出现了参数高效微调（PEFT），如 LoRA、Prefix Tuning，只训练极少量参数就能达到接近全量微调的效果，大大降低了门槛。

下面用 Hugging Face Transformers 演示一个极简的微调流程（以文本分类为例）：

from transformers import AutoTokenizer, AutoModelForSequenceClassification, Trainer, TrainingArguments
import torch
from torch.utils.data import Dataset

# 加载预训练模型和分词器（这里用一个小模型演示）
model_name = 'distilbert-base-uncased'
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForSequenceClassification.from_pretrained(model_name, num_labels=2)

# 模拟一些训练数据
texts = ['I love this movie', 'This is terrible', 'Great film', 'Awful experience']
labels = [1, 0, 1, 0]

class SimpleDataset(Dataset):
    def __init__(self, texts, labels):
        self.encodings = tokenizer(texts, truncation=True, padding=True, return_tensors='pt')
        self.labels = labels
    def __len__(self):
        return len(self.labels)
    def __getitem__(self, idx):
        item = {key: val[idx] for key, val in self.encodings.items()}
        item['labels'] = torch.tensor(self.labels[idx])
        return item

dataset = SimpleDataset(texts, labels)

training_args = TrainingArguments(
    output_dir='./results',
    num_train_epochs=3,
    per_device_train_batch_size=2,
    logging_steps=1,
    save_steps=10,
)

trainer = Trainer(
    model=model,
    args=training_args,
    train_dataset=dataset,
)

trainer.train()
print('微调完成！')

这段代码展示了微调的标准流程：加载预训练模型 → 准备数据 → 配置训练参数 → 训练。实际项目中，你会用更大的模型和更多数据，但核心逻辑不变。

LLM 的能力与局限性

LLM 展现出了令人惊讶的能力：

  • 语言理解与生成：流畅地写文章、翻译、总结、问答。
  • 上下文学习（In-Context Learning）：给几个例子，模型就能学会新任务，无需更新参数。
  • 推理与代码：能进行一定程度的逻辑推理，并生成可运行的代码。
  • 知识存储：预训练过程中“记住”了大量事实知识。

但 LLM 也有明显的局限性：

  • 幻觉（Hallucination）：模型会自信地编造不存在的事实。这是因为它的目标是预测下一个词，而不是追求真理。
  • 上下文窗口有限：虽然现在有 128K 甚至更长的上下文，但依然无法处理无限长的输入，且长上下文中的信息检索能力会下降。
  • 知识截止：预训练数据有时间截止点，模型不知道之后发生的事情。
  • 推理能力不稳定：在复杂数学、多步逻辑上容易出错。
  • 计算成本高：训练和推理都需要大量算力，部署时需要考虑延迟和吞吐。

理解这些局限性，才能在后续章节中设计出更可靠的系统，比如用 RAG（检索增强生成）缓解幻觉，用缓存和量化优化推理速度。

常见误区

  • LLM 真的“理解”语言。实际上，LLM 是通过统计规律预测下一个词，它的“理解”与人类不同，缺乏真实世界的体验和常识。
  • 预训练和微调是一回事。预训练是在海量无标注数据上学习通用语言表示，微调是在特定任务数据上调整参数，两者目标、数据、成本都不同。
  • 自注意力机制中每个词只关注自己。实际上，自注意力让每个词关注序列中所有词（包括自己），权重由学习得到，并非固定。

自测

请简要解释自注意力机制中 Query、Key、Value 的作用。

答案：Query 代表当前词的查询需求，Key 代表其他词提供的索引信息，Value 代表其他词的实际内容。通过 Query 和 Key 的点积计算相关性权重，再用权重对 Value 加权求和，得到当前词的新表示。

预训练和微调的主要区别是什么？

答案：预训练是在海量无标注文本上通过自监督任务（如预测下一个词）学习通用语言表示，计算成本极高；微调是在预训练模型基础上，用少量标注数据针对特定任务继续训练，计算成本较低，目的是让模型适应下游任务。

import torch import torch.nn as nn import torch.nn.functional as F import math class MultiHeadSelfAttention(nn.Module): def __init__(self, embed_dim, num_heads): super().__init__() assert embed_dim % num_heads == 0, 'embed_dim 必须能被 num_heads 整除' self.embed_dim = embed_dim self.num_heads = num_heads self.head_dim = embed_dim // num_heads self.q_proj = nn.Linear(embed_dim, embed_dim) self.k_proj = nn.Linear(embed_dim, embed_dim) self.v_proj = nn.Linear(embed_dim, embed_dim) self.out_proj = nn.Linear(embed_dim, embed_dim) def forward(self, x): batch_size, seq_len, _ = x.shape # 线性投影 Q = self.q_proj(x) # (batch, seq_len, embed_dim) K = self.k_proj(x) V = self.v_proj(x) # 分头: (batch, seq_len, num_heads, head_dim) -> (batch, num_heads, seq_len, head_dim) Q = Q.view(batch_size, seq_len, self.num_heads, self.head_dim).transpose(1, 2) K = K.view(batch_size, seq_len, self.num_heads, self.head_dim).transpose(1, 2) V = V.view(batch_size, seq_len, self.num_heads, self.head_dim).transpose(1, 2) # 缩放点积注意力 scores = torch.matmul(Q, K.transpose(-2, -1)) / math.sqrt(self.head_dim) attn = F.softmax(scores, dim=-1) out = torch.matmul(attn, V) # (batch, num_heads, seq_len, head_dim) # 合并头 out = out.transpose(1, 2).contiguous().view(batch_size, seq_len, self.embed_dim) out = self.out_proj(out) return out # 测试 x = torch.randn(2, 5, 16) mha = MultiHeadSelfAttention(embed_dim=16, num_heads=4) out = mha(x) print(out.shape) # torch.Size([2, 5, 16])

本章目标：掌握构建高质量训练数据集的方法

数据收集：来源与版权考量

训练一个LLM，第一步不是写模型代码，而是找数据。数据质量直接决定模型的上限。常见的数据来源包括：公开网页（如Common Crawl）、书籍、学术论文、代码仓库、对话数据等。但收集数据时，版权和合规性是必须优先考虑的问题。

你需要关注：

  • 许可证：数据是否允许商用？例如CC-BY-NC禁止商用，而MIT、Apache 2.0则相对宽松。
  • 隐私：是否包含个人身份信息（PII）？如姓名、电话、地址，必须脱敏。
  • 偏见与毒性：数据中可能包含歧视性言论，需要过滤。
  • 来源可信度：低质量网站（如内容农场）会污染模型。

实际操作中，可以优先使用已清洗的开源数据集（如The Pile、C4、Wikipedia），或使用爬虫时遵守robots.txt并记录来源。一个简单的数据收集示例：从Hugging Face Datasets加载公开数据集。

from datasets import load_dataset

# 加载wikitext-2数据集作为示例
dataset = load_dataset('wikitext', 'wikitext-2-raw-v1', split='train')
print(dataset[0])
# 输出: {'text': '\n = Valkyria Chronicles III = \n'}

记住：数据收集不是越多越好，而是越相关、越干净越好。在训练前，务必确认数据集的许可证和隐私政策。

数据清洗：去重、过滤与格式化

原始数据往往包含重复、噪声、格式混乱等问题。清洗的目标是得到干净、一致、高质量的文本。主要步骤包括：

  • 去重：删除完全重复或近似重复的文档。重复数据会导致模型过拟合，降低泛化能力。常用方法：精确哈希（MD5）、SimHash、MinHash。
  • 过滤：移除低质量内容，如过短文本、乱码、HTML标签、广告等。可以基于规则（长度、特殊字符比例）或模型（质量分类器）。
  • 格式化：统一文本格式，如去除多余空格、换行，标准化Unicode字符。

下面是一个简单的清洗示例，使用Python进行去重和过滤：

import hashlib
from datasets import load_dataset

def clean_text(text):
    # 去除首尾空白，替换多个空格为单个
    text = ' '.join(text.split())
    return text

def is_quality(text, min_len=50):
    # 过滤过短文本
    return len(text) >= min_len

dataset = load_dataset('wikitext', 'wikitext-2-raw-v1', split='train')
seen_hashes = set()
cleaned = []
for example in dataset:
    text = clean_text(example['text'])
    if not is_quality(text):
        continue
    # 精确去重
    h = hashlib.md5(text.encode()).hexdigest()
    if h in seen_hashes:
        continue
    seen_hashes.add(h)
    cleaned.append(text)

print(f'原始样本数: {len(dataset)}, 清洗后: {len(cleaned)}')

去重和过滤是数据清洗的核心，能显著提升训练效率和模型质量。对于大规模数据，可以使用Spark或Dask进行分布式处理。

分词器原理与训练

分词器（Tokenizer）负责将文本转换为模型可处理的数字序列（token IDs）。分词器的选择直接影响模型效果和推理速度。主流的分词算法有BPE（Byte Pair Encoding）、WordPiece和SentencePiece。

以BPE为例，它从字符开始，反复合并出现频率最高的相邻字符对，直到达到预设的词表大小。这样既能处理未登录词，又能控制词表规模。

训练一个分词器通常使用Hugging Face的tokenizers库。下面是一个训练BPE分词器的最小示例：

from tokenizers import Tokenizer
from tokenizers.models import BPE
from tokenizers.trainers import BpeTrainer
from tokenizers.pre_tokenizers import Whitespace

# 初始化BPE分词器
tokenizer = Tokenizer(BPE(unk_token='[UNK]'))
tokenizer.pre_tokenizer = Whitespace()

# 训练器：词表大小1000，特殊token
trainer = BpeTrainer(special_tokens=['[UNK]', '[CLS]', '[SEP]', '[PAD]', '[MASK]'], vocab_size=1000)

# 使用清洗后的文本训练
tokenizer.train_from_iterator(cleaned, trainer=trainer)

# 测试编码
output = tokenizer.encode('Hello, world!')
print(output.tokens)  # ['Hello', ',', 'world', '!']
print(output.ids)     # [123, 45, 678, 90]

训练完成后，保存分词器供后续使用：tokenizer.save('tokenizer.json')。分词器必须与模型训练时使用的保持一致，否则会导致性能下降。

数据集划分与批处理

在训练前，需要将数据集划分为训练集、验证集和测试集。通常比例为80/10/10或90/5/5。验证集用于调参和早停，测试集用于最终评估。划分时要确保数据分布一致，避免泄漏。

批处理（Batching）是将数据分成小批次输入模型，以提高训练效率和内存利用率。对于变长文本，需要填充（padding）到相同长度，或使用动态批处理（按长度分组）。

使用Hugging Face Datasets的map和DataLoader可以方便地实现：

from datasets import Dataset
from transformers import DataCollatorWithPadding
from torch.utils.data import DataLoader

# 假设cleaned是清洗后的文本列表
dataset = Dataset.from_dict({'text': cleaned})

# 划分数据集
train_test = dataset.train_test_split(test_size=0.2, seed=42)
train_val = train_test['train'].train_test_split(test_size=0.1, seed=42)
train_dataset = train_val['train']
val_dataset = train_val['test']
test_dataset = train_test['test']

# 使用分词器编码
def tokenize_function(examples):
    return tokenizer(examples['text'], truncation=True, padding=False, max_length=128)

train_dataset = train_dataset.map(tokenize_function, batched=True)
val_dataset = val_dataset.map(tokenize_function, batched=True)

# 动态填充的collator
data_collator = DataCollatorWithPadding(tokenizer=tokenizer)

# 创建DataLoader
train_loader = DataLoader(train_dataset, batch_size=8, shuffle=True, collate_fn=data_collator)

# 查看一个批次
batch = next(iter(train_loader))
print(batch['input_ids'].shape)  # torch.Size([8, 128])

动态批处理能减少填充，提升训练速度。对于大规模数据，可以使用IterableDataset流式加载，避免内存不足。

常见误区

  • 数据越多越好：实际上，低质量或重复数据会损害模型性能，清洗和去重比单纯增加数据量更重要。
  • 分词器可以随意选择：分词器必须与模型预训练时使用的保持一致，否则token分布不匹配，导致模型效果大幅下降。
  • 验证集和测试集可以混用：测试集只能用于最终评估，如果用于调参会导致过拟合，失去客观性。

自测

为什么数据去重对LLM训练很重要？

答案：重复数据会导致模型在训练中多次看到相同样本，容易过拟合，降低泛化能力，同时浪费计算资源。去重可以提升数据多样性和训练效率。

训练分词器时，词表大小（vocab_size）设置过小或过大分别有什么问题？

答案：词表过小会导致很多词被拆分成多个子词，序列变长，增加计算负担；词表过大则会导致参数矩阵变大，模型复杂度增加，且低频词可能训练不充分。需要根据任务和语料规模权衡。

分布式训练常用数据并行（Data Parallelism），每个GPU持有完整模型副本，处理不同数据批次，梯度同步。PyTorch提供DistributedDataParallel（DDP）。启动方式：

损失函数与优化器选择

语言模型训练通常用交叉熵损失（CrossEntropyLoss），预测下一个token。PyTorch中：

import torch.nn as nn

优化器首选AdamW，它修正了权重衰减，适合Transformer。学习率常用预热+余弦衰减。

from transformers import AdamW, get_cosine_schedule_with_warmup
optimizer = AdamW(model.parameters(), lr=5e-5, weight_decay=0.01)
scheduler = get_cosine_schedule_with_warmup(optimizer, num_warmup_steps=1000, num_training_steps=10000)

关键结论：损失函数选交叉熵，优化器选AdamW，学习率要预热。

训练循环与检查点保存

训练循环是核心，包括前向传播、计算损失、反向传播、优化器更新。每若干步保存检查点（Checkpoint），防止训练中断丢失进度。

model.train()
for epoch in range(epochs):
    for step, batch in enumerate(dataloader):
        inputs = batch['input_ids'].to(device)
        labels = batch['labels'].to(device)
        outputs = model(inputs, labels=labels)
        loss = outputs.loss
        loss.backward()
        optimizer.step()
        scheduler.step()
        optimizer.zero_grad()
        if step % 100 == 0:
            torch.save({
                'epoch': epoch,
                'model_state_dict': model.state_dict(),
                'optimizer_state_dict': optimizer.state_dict(),
                'loss': loss.item()
            }, f'checkpoint-{step}.pt')

关键结论：定期保存检查点，包含模型、优化器状态和当前步数。

常见训练问题与调试

训练中常遇到损失不下降、梯度爆炸、显存不足。调试方法：

  • 损失不降：检查学习率、数据标签、模型初始化。
  • 梯度爆炸：使用梯度裁剪torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)。
  • 显存不足：减小批次大小、使用梯度累积、混合精度训练。

混合精度训练示例：

from torch.cuda.amp import autocast, GradScaler
scaler = GradScaler()
with autocast():
    outputs = model(inputs, labels=labels)
    loss = outputs.loss
scaler.scale(loss).backward()
scaler.step(optimizer)
scaler.update()

关键结论：梯度裁剪和混合精度是稳定训练的利器。

常见误区

  • 学习率越大训练越快：过大的学习率会导致损失震荡甚至发散，需要预热和衰减。
  • 检查点只保存模型权重就够了：恢复训练还需要优化器状态、学习率调度器状态和当前步数。
  • 分布式训练一定比单卡快：如果通信开销大或批次太小，加速比可能很低，甚至变慢。

第4章 · 微调与对齐

本章目标：使用微调技术适配下游任务

4.1 全参数微调 vs 参数高效微调：为什么需要 LoRA？

大家好，欢迎来到第4章。前面我们已经预训练或拿到了一个基础模型，但它可能只会“续写”，不会“听话”。微调就是让模型适配下游任务的关键一步。

最直接的方法是全参数微调（Full Fine-tuning）：拿预训练权重，在下游数据上继续用较小的学习率训练所有参数。效果通常最好，但代价也最大——一个 7B 模型全量微调，优化器状态 + 梯度 + 参数本身，显存轻松超过 80GB，而且每个任务都要存一份完整权重。

于是有了参数高效微调（PEFT），代表就是 LoRA（Low-Rank Adaptation）。它的核心思想非常优雅：冻结原模型权重，只在旁边插入一小对低秩矩阵，训练时只更新这对小矩阵。

具体来说，对于原权重 W ∈ R^{d×k}，LoRA 不直接改 W，而是学习一个增量 ΔW = B·A，其中 A ∈ R^{r×k}，B ∈ R^{d×r}，秩 r 远小于 d、k。前向变成：

h = Wx + (alpha / r) * B(Ax)

初始化时 A 用高斯随机，B 全零，所以训练开始时 ΔW=0，不破坏原模型。训练完只需要保存 A 和 B，一个 7B 模型的 LoRA 权重可能只有几十 MB。

下面是一个用 HuggingFace PEFT 库给模型加 LoRA 的最小示例：

from transformers import AutoModelForCausalLM
from peft import LoraConfig, get_peft_model

model = AutoModelForCausalLM.from_pretrained("gpt2")

lora_config = LoraConfig(
    r=8,                      # 低秩维度
    lora_alpha=16,            # 缩放系数
    target_modules=["c_attn"], # 对哪些层加 LoRA
    lora_dropout=0.05,
    bias="none",
    task_type="CAUSAL_LM"
)

model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
# 输出类似: trainable params: 294,912 || all params: 124,734,720 || trainable%: 0.24%

可以看到，可训练参数只有 0.24%。LoRA 用极小的训练成本，换来了接近全量微调的效果，这就是它成为当前微调事实标准的原因。

4.2 QLoRA：把大模型塞进单卡

LoRA 已经省了很多，但基座模型本身还是要占显存。一个 7B 模型用 fp16 加载就要约 14GB，加上激活值，单张 24GB 卡还是紧张。于是 QLoRA（Quantized LoRA） 登场了。

QLoRA 做了三件事：

  • 4-bit 量化基座模型：用 NF4（Normal Float 4）这种信息论上对正态分布权重最优的 4-bit 数据类型加载原模型，显存直接降到约 1/4。
  • 双重量化：对量化常数再量化一次，进一步省显存。
  • 分页优化器：用 NVIDIA 统一内存，避免显存尖峰导致 OOM。

关键点：基座是 4-bit 冻结的，只有 LoRA 适配器用 bf16 训练。所以梯度精度不受量化影响，效果几乎不掉。

用 bitsandbytes + PEFT 实现 QLoRA 的最小代码：

import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model

bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,
)

model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-2-7b-hf",
    quantization_config=bnb_config,
    device_map="auto",
)

lora_config = LoraConfig(
    r=16, lora_alpha=32,
    target_modules=["q_proj", "v_proj"],
    lora_dropout=0.05, bias="none", task_type="CAUSAL_LM"
)
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()

这样一张 24GB 的 4090 就能微调 7B 模型，甚至 33B 模型也能在 48GB 卡上跑起来。QLoRA 让“个人开发者微调大模型”从不可能变成了日常。

实践建议：r 一般取 8~64，任务越复杂取越大；target_modules 至少覆盖 q_proj 和 v_proj，追求效果可以加上 k_proj、o_proj 和 MLP 层。

4.3 指令微调与 RLHF：让模型“听懂人话”

光会续写的模型不是好助手。要让它遵循指令，需要 指令微调（Instruction Tuning）：用大量“指令-回答”对训练，格式通常长这样：

### Instruction:
把下面的句子翻译成英文。
### Input:
今天天气很好。
### Response:
The weather is nice today.

指令微调让模型学会“看到指令就执行”，这是 ChatGPT 类模型的第一阶段对齐。

第二阶段是 RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习），经典三步：

  1. 监督微调（SFT）：用高质量示范数据微调，就是上面的指令微调。
  2. 训练奖励模型（RM）：让人类对同一问题的多个回答排序，训练一个模型去预测“人类更喜欢哪个回答”。
  3. PPO 强化学习：用奖励模型当裁判，让语言模型生成更受偏好的回答，同时加 KL 惩罚防止跑偏。

RLHF 效果很好但工程复杂、不稳定。现在更流行 DPO（Direct Preference Optimization）：跳过奖励模型和 PPO，直接用偏好数据对优化策略，简单又稳定。很多开源模型（如 Zephyr、Llama-3-Instruct）都用 DPO 或类似方法。

一个用 TRL 做 DPO 的极简片段：

from trl import DPOTrainer, DPOConfig

config = DPOConfig(
    beta=0.1,               # KL 约束强度
    learning_rate=5e-5,
    per_device_train_batch_size=2,
    num_train_epochs=1,
)

trainer = DPOTrainer(
    model=model,
    ref_model=None,         # 用 PEFT 时可传 None
    args=config,
    train_dataset=preference_dataset,  # 含 prompt/chosen/rejected
    tokenizer=tokenizer,
)
trainer.train()

一句话总结：SFT 教模型“怎么做”，RLHF/DPO 教模型“做什么更好”。

4.4 如何评估微调效果？

训练完不是结束，评估才是决定能不能上线的关键。微调评估分三个层次：

  • 任务指标：分类任务看准确率/F1，生成任务看 ROUGE、BLEU、BERTScore，代码任务看 pass@k。
  • 通用能力：用 MMLU、GSM8K 等基准检查是否“灾难性遗忘”——微调后模型变笨了没有。
  • 人工/模型评估：用 GPT-4 或人工对回答打分，看有用性、安全性、格式遵循度。

一个常见的坑：只看训练 loss 下降就以为成功了。实际上小数据集上 loss 很快降到 0，但模型可能只是背下了答案，泛化很差。

推荐做法：

  1. 留出验证集，训练时监控验证 loss。
  2. 用 lm-evaluation-harness 跑标准基准，对比微调前后。
  3. 准备 20~50 条真实业务问题，人工盲评。
  4. 检查输出格式是否稳定（比如 JSON 是否总能解析）。

下面用 lm-eval 跑一个基准的例子：

# 命令行方式
# lm_eval --model hf \
#   --model_args pretrained=./my-lora-merged \
#   --tasks mmlu,gsm8k \
#   --batch_size 8

# Python 方式

    model="hf",

记住：没有评估的微调等于赌博。每次微调都要有基线对比，才能知道改动到底有没有用。

常见误区

  • LoRA 只能用于注意力层，其实也可以加到 MLP、LayerNorm 等模块，target_modules 的选择会显著影响效果。
  • QLoRA 的 4-bit 量化会严重损失效果，实际上 NF4 + 双重量化在多数任务上几乎无损，因为 LoRA 适配器仍以 bf16 训练。
  • RLHF 一定比 DPO 好，实际上 DPO 在很多场景下效果相当甚至更稳定，且实现简单得多，是当前主流选择。

自测

LoRA 为什么能大幅减少可训练参数量？它的前向计算是如何进行的？

答案：LoRA 冻结原权重 W，只训练两个低秩矩阵 A 和 B，用 ΔW = B·A 近似权重更新。前向为 h = Wx + (alpha/r)·B(Ax)。因为 r 远小于原维度，可训练参数从 d×k 降到 r×(d+k)，通常只有原模型的 0.1%~1%。

QLoRA 相比 LoRA 多了哪些关键技术？为什么它能在单卡上微调 7B 模型？

答案：QLoRA 在 LoRA 基础上增加了：4-bit NF4 量化基座模型、双重量化、分页优化器。基座以 4-bit 加载使显存降到约 1/4，而 LoRA 适配器仍用 bf16 训练保证精度，因此 24GB 单卡即可微调 7B 模型。

本章目标：优化模型推理速度与资源占用

量化：PTQ与QAT

量化是把模型参数和激活值从高精度（如FP32）转换为低精度（如INT8）的过程，能大幅减少内存占用和加速推理。训练后量化（PTQ）无需重新训练，直接对训练好的模型进行量化，简单快速但可能损失精度；量化感知训练（QAT）在训练过程中模拟量化误差，让模型适应低精度，通常精度更高但需要训练资源。

下面是一个使用PyTorch进行动态量化的最小示例，对线性层进行INT8量化：

import torch
import torch.quantization

# 定义一个简单模型
class SimpleModel(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = torch.nn.Linear(10, 5)
    def forward(self, x):
        return self.fc(x)

model = SimpleModel()
# 动态量化（仅量化权重，激活在运行时量化）
quantized_model = torch.quantization.quantize_dynamic(
    model, {torch.nn.Linear}, dtype=torch.qint8
)
print(quantized_model)
# 比较大小
print(f"原始模型大小: {sum(p.numel() for p in model.parameters()) * 4} bytes")
print(f"量化模型大小: {sum(p.numel() for p in quantized_model.parameters()) * 1} bytes")

运行后可以看到量化模型大小约为原始模型的1/4。PTQ适合快速部署，QAT适合对精度要求高的场景。

剪枝与知识蒸馏

剪枝通过移除模型中不重要的权重或神经元来减少参数量和计算量。常见方法有非结构化剪枝（移除单个权重）和结构化剪枝（移除整个通道或层）。知识蒸馏让一个小模型（学生）模仿大模型（教师）的输出分布，从而获得接近大模型的性能。

下面是一个简单的知识蒸馏训练示例，使用KL散度损失：

import torch
import torch.nn as nn
import torch.nn.functional as F

# 教师模型（大）和学生模型（小）
teacher = nn.Sequential(nn.Linear(10, 100), nn.ReLU(), nn.Linear(100, 5))
student = nn.Sequential(nn.Linear(10, 20), nn.ReLU(), nn.Linear(20, 5))

# 模拟数据
x = torch.randn(32, 10)

# 蒸馏损失：学生模仿教师的软输出
teacher.eval()
with torch.no_grad():
    teacher_logits = teacher(x)
    teacher_probs = F.softmax(teacher_logits / 2.0, dim=1)  # 温度T=2

student_logits = student(x)
student_log_probs = F.log_softmax(student_logits / 2.0, dim=1)
loss = F.kl_div(student_log_probs, teacher_probs, reduction='batchmean')
print(f"蒸馏损失: {loss.item():.4f}")

剪枝和蒸馏可以结合使用，先剪枝再蒸馏微调，能进一步压缩模型。

推理加速：ONNX与TensorRT

ONNX（Open Neural Network Exchange）是一种开放的模型格式，支持跨框架转换和优化。TensorRT是NVIDIA的高性能推理SDK，能对ONNX模型进一步优化，利用GPU加速。

将PyTorch模型导出为ONNX格式的示例：

import torch
import torch.onnx

# 定义一个简单模型
class Model(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = torch.nn.Linear(10, 5)
    def forward(self, x):
        return self.fc(x)

model = Model()
dummy_input = torch.randn(1, 10)

# 导出为ONNX
torch.onnx.export(
    model, dummy_input, "model.onnx",
    input_names=["input"], output_names=["output"],
    dynamic_axes={"input": {0: "batch"}, "output": {0: "batch"}}
)
print("ONNX模型已导出")

# 使用ONNX Runtime推理
import onnxruntime as ort
import numpy as np

ort_session = ort.InferenceSession("model.onnx")
input_data = np.random.randn(1, 10).astype(np.float32)
outputs = ort_session.run(None, {"input": input_data})
print("ONNX Runtime推理输出形状:", outputs[0].shape)

对于TensorRT，可以使用torch-tensorrt或trtexec工具将ONNX转换为TensorRT引擎，获得更低的延迟。ONNX提供跨平台兼容性，TensorRT则针对NVIDIA GPU极致优化。

内存优化与批处理策略

内存优化和批处理能显著提升推理吞吐量。梯度检查点用计算换内存，混合精度训练减少显存占用，动态批处理将多个请求合并处理以提高GPU利用率。

下面是一个使用PyTorch进行混合精度推理的示例：

import torch

model = torch.nn.Linear(1000, 1000).cuda()
input_data = torch.randn(32, 1000).cuda()

# 混合精度推理
with torch.cuda.amp.autocast():
    output = model(input_data)
print(f"输出类型: {output.dtype}")  # 应为float16

# 动态批处理模拟：将多个小批次合并
batch1 = torch.randn(4, 1000).cuda()
batch2 = torch.randn(4, 1000).cuda()
combined = torch.cat([batch1, batch2], dim=0)
with torch.no_grad():
    out = model(combined)
print(f"合并批次输出形状: {out.shape}")

合理设置批大小和采用动态批处理能最大化硬件利用率，但需注意延迟与吞吐的权衡。

常见误区

  • 量化一定会导致明显的精度下降，实际上PTQ在多数模型上精度损失很小，QAT可以几乎无损。
  • 剪枝后模型一定变小，非结构化剪枝需要特定硬件支持才能加速，否则只是稀疏存储。
  • 知识蒸馏只能用于分类任务，实际上蒸馏可用于各种任务，包括生成任务。

部署模式：本地、云、边缘

部署大语言模型时，首先要决定模型跑在哪里。常见模式有三种：本地部署、云部署和边缘部署。它们各有优劣，选择取决于你的业务需求、预算和延迟要求。

  • 本地部署：模型运行在自己的服务器或工作站上。优点：数据不出内网，隐私安全；无网络延迟；一次性硬件投入。缺点：需要维护硬件，扩展性差，前期成本高。适合对数据安全要求极高的场景，如金融、医疗。
  • 云部署：模型托管在云服务器（如 AWS、GCP、阿里云）上。优点：弹性伸缩，按需付费，免运维。缺点：数据需上传云端，有网络延迟，长期使用成本可能较高。适合大多数互联网应用。
  • 边缘部署：模型运行在终端设备（如手机、IoT 设备）上。优点：超低延迟，离线可用，隐私保护好。缺点：算力有限，只能跑小模型或量化模型。适合移动端 AI 助手、智能摄像头等。

实际生产中，常采用混合部署：核心模型在云上，轻量模型在边缘，敏感数据在本地处理。例如，一个智能客服系统可以在云端跑大模型，在手机端跑意图识别小模型。

下面是一个简单的 Python 脚本，用于检测当前环境适合哪种部署模式（根据可用内存和 GPU）。

import psutil
import torch

def suggest_deployment():
    mem_gb = psutil.virtual_memory().total / (1024**3)
    has_gpu = torch.cuda.is_available()
    if has_gpu and mem_gb >= 32:
        return "本地/云服务器（可跑大模型）"
    elif mem_gb >= 16:
        return "云服务器（中等模型）"
    else:
        return "边缘设备（需量化小模型）"

print(suggest_deployment())

运行前需安装 psutil 和 torch。这个例子帮你快速判断当前机器适合哪种部署模式。

RESTful API 与 gRPC 接口设计

模型部署后，需要对外提供接口。最常用的是 RESTful API 和 gRPC。RESTful API 基于 HTTP/1.1，使用 JSON 传输，简单通用，适合 Web 和移动端。gRPC 基于 HTTP/2，使用 Protocol Buffers 二进制传输，性能高，适合内部服务间通信。

RESTful API 设计要点：

  • 使用名词表示资源，如 /v1/completions。
  • 用 HTTP 方法表示操作：GET 获取，POST 创建，PUT 更新，DELETE 删除。
  • 状态码：200 成功，400 客户端错误，500 服务器错误。
  • 请求和响应使用 JSON。

gRPC 设计要点：

  • 定义 .proto 文件，声明服务和消息格式。
  • 支持四种流式：一元、服务器流、客户端流、双向流。
  • 适合低延迟、高吞吐场景，如模型推理。

下面是一个简单的 gRPC 服务定义示例（inference.proto）：

syntax = "proto3";

service Inference {
  rpc Predict (PredictRequest) returns (PredictResponse);
}

message PredictRequest {
  string prompt = 1;
  int32 max_tokens = 2;
}

message PredictResponse {
  string text = 1;
}

对应的 RESTful API 可能长这样：

POST /v1/predict
Content-Type: application/json

{
  "prompt": "你好",
  "max_tokens": 50
}

响应：
{
  "text": "你好！有什么可以帮你的吗？"
}

选择建议：对外公开 API 用 RESTful，内部微服务间用 gRPC。如果团队熟悉 HTTP，RESTful 更易上手；如果追求极致性能，选 gRPC。

使用 FastAPI 构建推理服务

FastAPI 是一个现代、高性能的 Python Web 框架，非常适合构建 LLM 推理服务。它支持异步、自动生成文档，并且与 Pydantic 集成良好。

下面是一个完整的 FastAPI 推理服务示例，使用 Hugging Face 的 transformers 加载一个小模型（如 GPT-2）进行文本生成。

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
from transformers import pipeline
import uvicorn

app = FastAPI(title="LLM Inference API")

# 加载模型（首次运行会下载）
generator = pipeline("text-generation", model="gpt2")

class GenerationRequest(BaseModel):
    prompt: str
    max_length: int = 50
    temperature: float = 0.7

class GenerationResponse(BaseModel):
    generated_text: str

@app.post("/v1/generate", response_model=GenerationResponse)
async def generate(request: GenerationRequest):
    try:
        result = generator(
            request.prompt,
            max_length=request.max_length,
            temperature=request.temperature,
            do_sample=True
        )
        return GenerationResponse(generated_text=result[0]["generated_text"])
    except Exception as e:
        raise HTTPException(status_code=500, detail=str(e))

if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=8000)

运行方式：python app.py，然后访问 http://localhost:8000/docs 查看自动生成的 API 文档。你可以用 curl 测试：

curl -X POST http://localhost:8000/v1/generate -H "Content-Type: application/json" -d '{"prompt": "Hello, world", "max_length": 30}'

关键点：使用 async def 定义异步端点，避免阻塞；用 Pydantic 模型校验请求和响应；通过 uvicorn 启动服务。对于生产环境，建议使用 Gunicorn 管理多个 Uvicorn worker。

负载均衡与自动扩缩容

当请求量增大时，单个服务实例可能扛不住。这时需要负载均衡和自动扩缩容。

负载均衡：将请求分发到多个服务实例。常见策略：轮询、最少连接、IP 哈希。工具：Nginx、HAProxy、云厂商的 LB（如 AWS ALB）。

自动扩缩容：根据指标（如 CPU、QPS）动态调整实例数量。Kubernetes 的 HPA（Horizontal Pod Autoscaler）是典型方案。它监控 Pod 的 CPU/内存使用率，自动增加或减少副本数。

下面是一个 Kubernetes HPA 配置示例，针对我们的 FastAPI 服务：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: llm-inference-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: llm-inference
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

这个 HPA 会在 CPU 平均利用率超过 70% 时增加 Pod，最多 10 个；低于时减少，最少 2 个。

对于 LLM 服务，由于模型加载慢，扩缩容需要预热。建议使用就绪探针确保模型加载完成后再接收流量。另外，可以结合队列（如 Redis）做请求缓冲，避免突发流量打垮服务。

总结：负载均衡提高可用性，自动扩缩容应对流量波动。两者结合，才能构建稳定的生产级 LLM 服务。

常见误区

  • 认为本地部署一定比云部署便宜：实际上，本地部署需要购买 GPU 服务器、支付电费和运维人力，长期看可能比云服务更贵，尤其对于波动负载。
  • 认为 gRPC 总是比 RESTful 好：gRPC 性能高但调试复杂，浏览器支持有限，对外 API 用 RESTful 更通用。
  • 忽略模型加载时间，直接做快速扩缩容：LLM 加载可能需几分钟，扩缩容必须配合就绪探针和预热，否则新实例无法及时处理请求。

本章目标：完成一个小型LLM的训练与微调

项目规划与数据准备

训练一个小型LLM，第一步不是写代码，而是想清楚要它做什么。比如，我们想训练一个能生成简单英文句子的模型，或者一个能回答简单问题的助手。明确目标后，再规划模型大小、数据来源和训练时间。

数据是模型的粮食。对于小型LLM，我们可以使用公开的小型文本数据集，比如莎士比亚作品、新闻文章或代码片段。数据需要经过清洗、分词，并转换为模型可以处理的格式。

下面是一个最小示例：下载一个小型文本数据集，进行简单的预处理，并构建一个字符级的分词器。

import torch
from torch.utils.data import Dataset, DataLoader

# 假设我们有一个文本文件 'input.txt'
with open('input.txt', 'r', encoding='utf-8') as f:
    text = f.read()

# 构建字符级词汇表
chars = sorted(list(set(text)))
vocab_size = len(chars)
stoi = {ch: i for i, ch in enumerate(chars)}
itos = {i: ch for i, ch in enumerate(chars)}

# 编码函数
def encode(s):
    return [stoi[c] for c in s]

def decode(l):
    return ''.join([itos[i] for i in l])

# 将文本转换为张量
data = torch.tensor(encode(text), dtype=torch.long)

# 划分训练集和验证集
n = int(0.9 * len(data))
train_data = data[:n]
val_data = data[n:]

# 定义数据集类
class TextDataset(Dataset):
    def __init__(self, data, block_size):
        self.data = data
        self.block_size = block_size
    def __len__(self):
        return len(self.data) - self.block_size
    def __getitem__(self, idx):
        x = self.data[idx:idx+self.block_size]
        y = self.data[idx+1:idx+self.block_size+1]
        return x, y

block_size = 128
train_dataset = TextDataset(train_data, block_size)
val_dataset = TextDataset(val_data, block_size)
train_loader = DataLoader(train_dataset, batch_size=32, shuffle=True)
val_loader = DataLoader(val_dataset, batch_size=32, shuffle=False)

print(f'词汇表大小: {vocab_size}, 训练样本数: {len(train_dataset)}')

这段代码展示了数据准备的核心步骤：读取文本、构建词汇表、编码、划分数据集，并创建PyTorch数据加载器。数据质量直接决定模型效果，所以务必确保文本干净、格式统一。

训练配置与启动

有了数据，接下来要定义模型结构和训练配置。对于小型LLM，我们可以使用一个简单的Transformer解码器，比如GPT的简化版。关键配置包括：层数、注意力头数、嵌入维度、学习率、批次大小等。

下面是一个极简的GPT模型定义和训练循环。我们使用PyTorch实现，并假设你已经安装了torch。

import torch.nn as nn
import torch.nn.functional as F

class Head(nn.Module):
    def __init__(self, head_size, n_embd, block_size, dropout=0.1):
        super().__init__()
        self.key = nn.Linear(n_embd, head_size, bias=False)
        self.query = nn.Linear(n_embd, head_size, bias=False)
        self.value = nn.Linear(n_embd, head_size, bias=False)
        self.register_buffer('tril', torch.tril(torch.ones(block_size, block_size)))
        self.dropout = nn.Dropout(dropout)
    def forward(self, x):
        B, T, C = x.shape
        k = self.key(x)
        q = self.query(x)
        wei = q @ k.transpose(-2, -1) * (C ** -0.5)
        wei = wei.masked_fill(self.tril[:T, :T] == 0, float('-inf'))
        wei = F.softmax(wei, dim=-1)
        wei = self.dropout(wei)
        v = self.value(x)
        out = wei @ v
        return out

class MultiHeadAttention(nn.Module):
    def __init__(self, num_heads, head_size, n_embd, block_size, dropout=0.1):
        super().__init__()
        self.heads = nn.ModuleList([Head(head_size, n_embd, block_size, dropout) for _ in range(num_heads)])
        self.proj = nn.Linear(n_embd, n_embd)
        self.dropout = nn.Dropout(dropout)
    def forward(self, x):
        out = torch.cat([h(x) for h in self.heads], dim=-1)
        out = self.dropout(self.proj(out))
        return out

class FeedForward(nn.Module):
    def __init__(self, n_embd, dropout=0.1):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(n_embd, 4 * n_embd),
            nn.ReLU(),
            nn.Linear(4 * n_embd, n_embd),
            nn.Dropout(dropout),
        )
    def forward(self, x):
        return self.net(x)

class Block(nn.Module):
    def __init__(self, n_embd, n_head, block_size, dropout=0.1):
        super().__init__()
        head_size = n_embd // n_head
        self.sa = MultiHeadAttention(n_head, head_size, n_embd, block_size, dropout)
        self.ffwd = FeedForward(n_embd, dropout)
        self.ln1 = nn.LayerNorm(n_embd)
        self.ln2 = nn.LayerNorm(n_embd)
    def forward(self, x):
        x = x + self.sa(self.ln1(x))
        x = x + self.ffwd(self.ln2(x))
        return x

class MiniGPT(nn.Module):
    def __init__(self, vocab_size, n_embd=128, n_head=4, n_layer=4, block_size=128, dropout=0.1):
        super().__init__()
        self.token_embedding = nn.Embedding(vocab_size, n_embd)
        self.position_embedding = nn.Embedding(block_size, n_embd)
        self.blocks = nn.Sequential(*[Block(n_embd, n_head, block_size, dropout) for _ in range(n_layer)])
        self.ln_f = nn.LayerNorm(n_embd)
        self.lm_head = nn.Linear(n_embd, vocab_size)
        self.block_size = block_size
    def forward(self, idx, targets=None):
        B, T = idx.shape
        tok_emb = self.token_embedding(idx)
        pos_emb = self.position_embedding(torch.arange(T, device=idx.device))
        x = tok_emb + pos_emb
        x = self.blocks(x)
        x = self.ln_f(x)
        logits = self.lm_head(x)
        if targets is None:
            loss = None
        else:
            B, T, C = logits.shape
            logits = logits.view(B*T, C)
            targets = targets.view(B*T)
            loss = F.cross_entropy(logits, targets)
        return logits, loss
    def generate(self, idx, max_new_tokens):
        for _ in range(max_new_tokens):
            idx_cond = idx[:, -self.block_size:]
            logits, _ = self(idx_cond)
            logits = logits[:, -1, :]
            probs = F.softmax(logits, dim=-1)
            idx_next = torch.multinomial(probs, num_samples=1)
            idx = torch.cat((idx, idx_next), dim=1)
        return idx

# 训练配置
device = 'cuda' if torch.cuda.is_available() else 'cpu'
model = MiniGPT(vocab_size=vocab_size, n_embd=128, n_head=4, n_layer=4, block_size=block_size).to(device)
optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4)

# 训练循环
epochs = 10
for epoch in range(epochs):
    model.train()
    for x, y in train_loader:
        x, y = x.to(device), y.to(device)
        logits, loss = model(x, y)
        optimizer.zero_grad()
        loss.backward()
        optimizer.step()
    print(f'Epoch {epoch+1}, Loss: {loss.item():.4f}')

# 保存模型
torch.save(model.state_dict(), 'mini_gpt.pth')

这段代码定义了一个4层、4头的MiniGPT，并在训练集上训练了10个epoch。训练配置需要根据硬件调整，如果显存不足，可以减小批次大小或模型维度。

微调与评估

训练完成后，模型可能已经能生成一些文本，但可能不符合我们的具体需求。这时可以进行微调，比如在特定领域数据上继续训练，或者使用指令微调让模型学会回答问题。

评估是检验模型效果的关键。对于语言模型，常用的评估指标是困惑度（Perplexity），它衡量模型对文本的预测能力。我们也可以在验证集上计算损失。

下面展示如何在验证集上评估模型，并计算困惑度。

import math

model.eval()
total_loss = 0
with torch.no_grad():
    for x, y in val_loader:
        x, y = x.to(device), y.to(device)
        logits, loss = model(x, y)
        total_loss += loss.item()

avg_loss = total_loss / len(val_loader)
perplexity = math.exp(avg_loss)
print(f'验证集损失: {avg_loss:.4f}, 困惑度: {perplexity:.2f}')

# 生成示例
context = torch.zeros((1, 1), dtype=torch.long, device=device)
generated = model.generate(context, max_new_tokens=100)
print(decode(generated[0].tolist()))

困惑度越低，说明模型对数据的预测越准确。通常困惑度在20以下表示模型表现不错，但具体取决于任务和数据集。

如果效果不理想，可以尝试：增加数据量、调整模型大小、改变学习率、或进行更长时间的训练。

模型导出与保存

训练完成后，我们需要保存模型以便后续部署。PyTorch提供了多种保存方式：保存整个模型、保存状态字典、或导出为ONNX格式以便在其他框架中使用。

推荐保存状态字典（state_dict），因为它更灵活，加载时需要重新实例化模型结构。

# 保存模型状态字典
torch.save(model.state_dict(), 'mini_gpt.pth')

# 加载模型
model_loaded = MiniGPT(vocab_size=vocab_size, n_embd=128, n_head=4, n_layer=4, block_size=block_size)
model_loaded.load_state_dict(torch.load('mini_gpt.pth'))
model_loaded.to(device)
model_loaded.eval()

# 导出为ONNX格式（可选）
dummy_input = torch.randint(0, vocab_size, (1, block_size), device=device)
torch.onnx.export(
    model_loaded,
    dummy_input,
    'mini_gpt.onnx',
    input_names=['input'],
    output_names=['output'],
    dynamic_axes={'input': {0: 'batch_size', 1: 'sequence'}, 'output': {0: 'batch_size', 1: 'sequence'}}
)
print('模型已保存为 mini_gpt.pth 和 mini_gpt.onnx')

保存后，你可以将模型文件部署到服务器，或集成到应用程序中。记得同时保存词汇表（stoi和itos），因为推理时需要它们来编码和解码文本。

至此，你已经完成了小型LLM的训练、微调、评估和导出全流程。接下来可以尝试更大的模型或更复杂的数据集。

常见误区

  • 训练LLM必须要有大量数据和强大算力，小型LLM无法产生有意义的结果。实际上，小型LLM可以在小数据集上训练，并用于特定任务，如文本生成或简单对话。
  • 模型保存只需要保存权重文件，不需要保存模型结构或词汇表。实际上，加载模型时需要相同的模型结构，并且推理时需要词汇表来编码和解码文本。
  • 困惑度越低模型越好，所以应该无限降低困惑度。实际上，过低的困惑度可能意味着过拟合，模型在验证集上表现好但在新数据上表现差。

自测

在训练小型LLM时，为什么需要划分训练集和验证集？

答案：训练集用于训练模型参数，验证集用于评估模型在未见过的数据上的表现，从而监控过拟合和调整超参数。

保存模型时，为什么推荐保存状态字典（state_dict）而不是整个模型？

答案：保存状态字典更灵活，因为它只包含参数，不包含模型结构。加载时需要重新实例化模型结构，这样可以避免因代码变更导致的兼容性问题，并且文件更小。

容器化与Kubernetes部署

把训练好的LLM部署到生产环境，第一步就是容器化。Docker能把模型、依赖、代码打包成一个镜像，保证在任何环境都能一致运行。对于LLM，镜像通常包含推理框架（如vLLM、TGI）、模型权重和启动脚本。

一个最小化的Dockerfile示例：

# 使用官方Python镜像作为基础
FROM python:3.10-slim

# 安装依赖
RUN pip install vllm fastapi uvicorn

# 复制模型权重（假设已下载到本地）
COPY ./model /app/model

# 复制启动脚本
COPY server.py /app/server.py

WORKDIR /app

# 暴露端口
EXPOSE 8000

# 启动服务
CMD ["python", "server.py"]

对应的server.py可以这样写：

from vllm import LLM, SamplingParams
from fastapi import FastAPI

app = FastAPI()
llm = LLM(model="/app/model")

@app.post("/generate")
async def generate(prompt: str):
    sampling_params = SamplingParams(temperature=0.7, max_tokens=100)
    outputs = llm.generate([prompt], sampling_params)
    return {"text": outputs[0].outputs[0].text}

构建并运行：

docker build -t llm-server .
docker run -p 8000:8000 --gpus all llm-server

当需要横向扩展时，Kubernetes（K8s）是首选。你需要定义Deployment和Service。Deployment管理Pod副本，Service提供稳定访问入口。对于GPU资源，需要在Pod中声明nvidia.com/gpu。

关键点：容器化保证环境一致性，K8s提供弹性伸缩和高可用。生产环境建议使用Helm管理复杂配置。

监控与日志收集

部署后，必须监控服务的健康状态和性能指标。常用的监控栈是Prometheus + Grafana。Prometheus负责采集指标，Grafana负责可视化。对于LLM服务，关键指标包括：请求延迟、吞吐量、GPU利用率、显存占用、错误率。

在FastAPI中暴露Prometheus指标：

from prometheus_fastapi_instrumentator import Instrumentator

app = FastAPI()
Instrumentator().instrument(app).expose(app)

这样/metrics端点就会输出指标，Prometheus可以定期抓取。

日志收集推荐使用ELK（Elasticsearch, Logstash, Kibana）或Loki + Grafana。结构化日志（JSON格式）便于查询。例如：

import logging
import json_log_formatter

formatter = json_log_formatter.JSONFormatter()
handler = logging.StreamHandler()
handler.setFormatter(formatter)
logger = logging.getLogger(__name__)
logger.addHandler(handler)
logger.setLevel(logging.INFO)

logger.info("Request processed", extra={"prompt_length": 10, "latency_ms": 150})

关键点：监控要覆盖基础设施（CPU/GPU/内存）和应用层（QPS、延迟、错误）。设置告警规则，如延迟超过阈值或错误率上升时通知。

性能测试与优化

性能测试是确保LLM服务满足SLA的关键。常用工具：Locust、wrk、JMeter。测试时关注吞吐量（tokens/s）、延迟（P50、P95、P99）和并发能力。

一个简单的Locust测试脚本：

from locust import HttpUser, task, between

class LLMUser(HttpUser):
    wait_time = between(1, 3)

    @task
    def generate(self):
        self.client.post("/generate", json={"prompt": "Hello, how are you?"})

运行：locust -f locustfile.py --host=http://localhost:8000

优化手段包括：

  • 批处理（Batching）：将多个请求合并成一个批次，提高GPU利用率。vLLM支持连续批处理。
  • 量化：使用FP16、INT8或4-bit量化减少显存占用，提升推理速度。
  • 缓存：对常见请求结果进行缓存，减少重复计算。
  • 模型编译：使用TensorRT、ONNX Runtime等加速推理。

例如，vLLM启动时开启量化：

llm = LLM(model="/app/model", quantization="awq")

关键点：性能优化需要权衡延迟和吞吐，根据业务场景调整批处理大小和量化级别。

安全与权限管理

生产环境必须考虑安全。主要方面：API认证、授权、输入验证、模型安全、网络安全。

API认证：使用API Key或JWT。FastAPI中可以通过依赖注入实现：

from fastapi import Depends, HTTPException, status
from fastapi.security import APIKeyHeader

api_key_header = APIKeyHeader(name="X-API-Key")

async def verify_api_key(api_key: str = Depends(api_key_header)):
    if api_key != "your-secret-key":
        raise HTTPException(status_code=status.HTTP_403_FORBIDDEN, detail="Invalid API Key")

@app.post("/generate", dependencies=[Depends(verify_api_key)])
async def generate(prompt: str):
    ...

授权：不同用户可能有不同配额。可以使用Redis记录使用量，并限制速率。

输入验证：防止提示注入和恶意输入。对输入长度、内容进行过滤。

模型安全：防止模型被窃取。可以通过加密模型文件、限制访问权限。

网络安全：使用HTTPS、网络策略（NetworkPolicy）限制Pod间通信。

关键点：安全要贯穿整个生命周期，从镜像构建到服务暴露，遵循最小权限原则。

常见误区

  • 容器化后就不需要管理依赖了：实际上，容器内仍需正确安装依赖，且镜像大小和构建时间需要优化。
  • 监控只需要看GPU利用率：应用层的延迟、错误率、吞吐量同样重要，否则无法定位性能瓶颈。
  • 性能测试一次就够了：随着模型更新、流量变化，需要持续进行性能测试和优化。
