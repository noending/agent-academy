硬件评测实战

本章目标：能看懂GPU等硬件评测指标并选型

明确评测目标先定用途与预算,再谈参数→读懂核心指标算力、显存、带宽逐项对照→跑分实测验证用基准测试检验纸面数据→横向对比选型同价位比性价比,锁定型号→复盘反馈按实际体验修正选型标准
从需求出发,用指标和实测交叉验证,最终落到性价比选型。

关键硬件指标：算力、显存、带宽、功耗

选GPU就像选车，不能只看马力（算力），还要看油箱大小（显存）、输油管粗细（带宽）和油耗（功耗）。但更关键的是，你要先搞清楚你的任务到底是“飙极速”还是“拉货”——LLM推理更像后者，它卡在数据搬运上，而不是计算上。这一节我们把四个核心指标拆开讲清楚，并告诉你哪个指标在什么场景下才是真正的瓶颈。

算力 (FLOPS)：每秒浮点运算次数，衡量GPU做数学计算的速度。常见单位有TFLOPS（万亿次/秒）和PFLOPS（千万亿次/秒）。注意：算力分精度，比如FP32、FP16、BF16、INT8。LLM训练和推理常用FP16/BF16，所以看算力时要确认精度。例如NVIDIA A100的FP16算力约312 TFLOPS（带稀疏），而FP32只有19.5 TFLOPS，差距巨大。但这里有个反直觉的事实：对于自回归生成（decoding）阶段，算力往往大量闲置，因为每生成一个token都要把整个模型权重从显存读一遍，计算量却很小。所以算力高不等于推理快，除非你在做大批量预填充（prefill）或训练。

显存 (VRAM)：GPU自带的内存，用来放模型权重、激活值、KV Cache、优化器状态等。显存不够，模型根本跑不起来。粗略估算：推理时，FP16模型每1B参数约需2GB显存；训练时，因为要存优化器状态和梯度，每1B参数约需16-20GB。所以7B模型推理至少14GB显存，训练则要100GB以上。但注意，这只是“权重”的账，实际还要加上KV Cache——它随序列长度和batch size线性增长，长上下文场景下可能比权重还大。比如7B模型FP16权重14GB，在batch size=8、序列长度4096时，KV Cache可能额外占用数GB（具体取决于层数和头数，待核实）。

内存带宽 (Memory Bandwidth)：GPU从显存读写数据的速度，单位GB/s。LLM推理是内存带宽瓶颈型任务：每生成一个token，都要把整个模型权重从显存读一遍。所以推理速度 ≈ 内存带宽 / 模型大小。例如A100带宽约2000GB/s，7B模型FP16约14GB，理论速度约143 token/s。这个公式解释了为什么大模型推理慢——不是算力不够，是数据搬运太慢。对比一下：同样14GB的模型，放在带宽1000GB/s的GPU上只能跑约71 token/s，直接腰斩。所以同价位选GPU，带宽往往比峰值算力更值得关注。

功耗 (TDP)：热设计功耗，单位瓦特。功耗决定散热和电费，也影响能否塞进机箱。数据中心GPU如H100功耗可达700W，消费级RTX 4090约450W。功耗还间接影响持续性能——如果散热跟不上，GPU会降频，实际算力和带宽都会打折。所以看评测时，要关注“持续性能”而不是“峰值性能”。

下面用Python快速估算一个模型需要多少显存和理论推理速度，你可以改参数直接跑：

python
def estimate_gpu_requirements(params_billion, precision_bytes=2, bandwidth_gbps=2000):
    """
    估算LLM推理的显存需求和理论速度
    params_billion: 模型参数量（十亿）
    precision_bytes: 每个参数的字节数，FP16=2, INT8=1, FP32=4
    bandwidth_gbps: GPU内存带宽（GB/s）
    """
    model_size_gb = params_billion * precision_bytes
    # 激活值、KV Cache等额外开销，粗略按20%算
    total_vram_gb = model_size_gb * 1.2
    print(f"模型大小: {model_size_gb:.1f} GB")
    print(f"建议显存: {total_vram_gb:.1f} GB")
    
    tokens_per_sec = bandwidth_gbps / model_size_gb
    print(f"理论推理速度: {tokens_per_sec:.1f} token/s")

# 测试7B模型，FP16精度，A100带宽
estimate_gpu_requirements(7, precision_bytes=2, bandwidth_gbps=2000)
# 输出：模型大小14.0GB，建议显存16.8GB，理论速度142.9 token/s

运行这段代码，你会看到7B FP16模型在A100上的理论速度约143 token/s。把带宽改成1000，速度立刻降到约71 token/s——这就是带宽的威力。记住这个公式：推理速度 ≈ 内存带宽 / 模型大小。它是你选型时最该先算的一笔账。

常见评测工具：MLPerf、DLBench、自定义基准

光看厂商给的峰值算力不靠谱，实际性能要看评测工具。这就像买车不能只看发动机参数，得看实测百公里加速和油耗。评测工具分三个层次：行业标准基准、国内/厂商基准、以及最贴近你真实场景的自定义基准。层次越往下，参考价值越高，但可比性越差。

MLPerf：由MLCommons组织维护的行业标准基准，相当于AI硬件界的“奥运会”。它分训练（Training）和推理（Inference）两套，覆盖图像分类、目标检测、语言模型（BERT、GPT-3）等任务。MLPerf的结果可横向对比不同厂商的GPU、TPU、CPU。看MLPerf报告时注意：看场景（Scenario），比如Offline（离线批处理）、Server（在线服务）、SingleStream（单流低延迟），不同场景排名可能完全不同。一个GPU可能在Offline场景吞吐第一，但在SingleStream场景延迟排到中游。所以先确定你的场景，再看对应榜单。

DLBench：国内一些机构推出的深度学习基准，更贴近中文场景和国产硬件。它通常包含ResNet、BERT等模型的训练和推理测试。相比MLPerf，DLBench的测试项更少，但部署更简单。不过要注意，DLBench的版本和测试集可能更新较慢，引用具体数字前最好确认最新版本（待核实）。

自定义基准：最实用的评测。因为你的模型、数据、框架和MLPerf不一定一样。自定义基准就是拿你自己的模型和真实数据，测延迟、吞吐、显存占用。关键指标：

  • 推理延迟 (Inference Latency)：从输入到输出的时间，单位ms。对在线服务至关重要。
  • 吞吐量 (Throughput)：每秒处理的请求数或token数。对离线批处理重要。
  • 首token延迟 (TTFT)：生成第一个token的时间，影响用户感知。用户等首token超过1秒就会觉得卡。

下面是一个自定义基准的简单示例，用PyTorch测推理延迟。注意代码里做了预热，并且同时报告平均延迟和P99延迟：

python
import torch
import time

# 一个简单的模型，模拟LLM中的一层变换
def create_model():
    return torch.nn.Sequential(
        torch.nn.Linear(768, 3072),
        torch.nn.ReLU(),
        torch.nn.Linear(3072, 768)
    )

model = create_model().cuda().half()  # 用FP16
input_tensor = torch.randn(1, 128, 768).cuda().half()

# 预热：GPU首次运行有初始化开销，必须跳过
for _ in range(10):
    _ = model(input_tensor)
torch.cuda.synchronize()

# 测延迟
latencies = []
for _ in range(100):
    start = time.perf_counter()
    _ = model(input_tensor)
    torch.cuda.synchronize()  # 等待GPU真正算完
    latencies.append(time.perf_counter() - start)

avg_latency = sum(latencies) / len(latencies) * 1000  # 转ms
print(f"平均延迟: {avg_latency:.2f} ms")
print(f"P99延迟: {sorted(latencies)[98]*1000:.2f} ms")

运行后你会得到类似“平均延迟: 0.5 ms，P99延迟: 0.8 ms”的输出（具体数字因GPU而异）。评测时一定要预热（warm-up），因为GPU首次运行会有初始化开销。另外要测P99延迟，而不只是平均延迟，因为用户体验由最慢的请求决定。平均延迟0.5ms但P99是5ms，意味着每100个请求就有1个让用户等5ms，这在在线服务里是不可接受的。

硬件与模型匹配：如何根据模型大小选择GPU

知道了指标和评测工具，现在来解决实际问题：给定一个模型，该选什么GPU？我们分推理和训练两种情况。核心思路是：先算显存底线，再看带宽决定速度，最后看互联决定能不能多卡扩展。

推理场景：主要看显存和带宽。步骤：

  1. 算模型大小：参数量 × 精度字节数。例如7B模型FP16约14GB，INT8约7GB。
  2. 加额外开销：激活值、KV Cache等。KV Cache随序列长度和batch size增长，长上下文时可能比模型还大。粗略加20%-50%。
  3. 选显存足够的GPU：7B FP16建议16GB以上，如RTX 4090（24GB）、A10（24GB）。13B FP16建议32GB以上，如A100 40GB。70B FP16需要140GB，单卡放不下，需多卡或量化。
  4. 看带宽：带宽越高，推理越快。同价位选带宽大的。

训练场景：显存需求暴增，因为要存优化器状态、梯度、激活值。粗略公式：训练显存 ≈ 参数量 × (2 + 2 + 4 + 4) 字节 = 参数量 × 12字节（FP16混合精度：权重2、梯度2、优化器动量4、方差4）。再加上激活值，实际约16-20字节/参数。所以7B模型训练需要约112-140GB显存，至少2张A100 80GB。全量微调13B模型需要8张A100 80GB是常见配置。这里的关键是：训练不仅吃显存，还吃卡间互联带宽。多卡训练时，梯度同步走NVLink比PCIe快数倍，所以训练选型要优先看互联能力。

下面用Python写一个选型助手，输入模型大小和模式，直接给出建议：

python
def recommend_gpu(params_billion, mode='inference', precision='fp16'):
    """
    根据模型大小推荐GPU配置
    mode: 'inference' 或 'training'
    precision: 'fp16', 'int8', 'fp32'
    """
    bytes_per_param = {'fp16': 2, 'int8': 1, 'fp32': 4}[precision]
    model_size = params_billion * bytes_per_param
    
    if mode == 'inference':
        vram_needed = model_size * 1.3  # 加30%开销
        print(f"推理模式：模型{model_size:.1f}GB，建议显存{vram_needed:.1f}GB")
        if vram_needed <= 24:
            print("推荐：RTX 4090 / A10 (24GB)")
        elif vram_needed <= 48:
            print("推荐：A6000 (48GB) / L40S (48GB)")
        elif vram_needed <= 80:
            print("推荐：A100 80GB / H100 80GB")
        else:
            print(f"需要多卡：至少{int(vram_needed//80)+1}张80GB GPU")
    else:
        # 训练：约16字节/参数（混合精度+激活值）
        vram_needed = params_billion * 16
        print(f"训练模式：建议显存{vram_needed:.1f}GB")
        num_gpus = int(vram_needed // 80) + 1
        print(f"推荐：{num_gpus}张A100 80GB或H100 80GB")

# 测试
recommend_gpu(7, 'inference', 'fp16')
recommend_gpu(7, 'training', 'fp16')
recommend_gpu(70, 'inference', 'int8')

运行结果会告诉你：7B推理建议16.8GB显存，推荐24GB卡；7B训练建议112GB，推荐2张80GB卡；70B INT8推理建议91GB，需要2张80GB卡。关键结论：推理选显存够用且带宽高的；训练选显存大且支持多卡互联的（如NVLink）。不要用消费级显卡做多卡训练，因为PCIe带宽和NVLink差距巨大，训练时间可能差出数倍。

成本与性能权衡：云GPU vs 本地GPU

最后我们来算账。云GPU和本地GPU各有优劣，选择取决于使用频率、预算和隐私要求。这就像租房和买房：短期灵活选租，长期稳定选买，但关键变量是你的“入住时长”。

云GPU：按需付费，灵活。优点：无需前期投入，随时升级到最新硬件，适合短期项目、实验、突发流量。缺点：长期使用成本高，数据隐私风险，网络延迟。主流云GPU价格（2024年参考，实际价格随厂商和区域波动，待核实）：

GPU型号显存按需价格（美元/小时）适合场景
T416GB0.35-0.5轻量推理
A10G24GB1.0-1.5中等推理
A100 40GB40GB2.5-4.0训练/大模型推理
H100 80GB80GB8.0-12.0大模型训练

本地GPU：一次性购买，长期使用成本低。优点：数据安全，无网络延迟，可深度定制。缺点：前期投入大，硬件贬值快，维护麻烦。参考价格：RTX 4090约1600美元，A100 80GB约15000美元，H100约30000美元（价格随市场波动，待核实）。

盈亏平衡点计算：假设云GPU每小时3美元，本地GPU购买价15000美元，电费和维护每月200美元。则回本时间 = 15000 / (3*24*30 - 200) ≈ 7.5个月。如果每天使用超过8小时，本地更划算；如果只是偶尔用，云更划算。注意这里还没算本地GPU的残值和折旧，实际回本时间会更长一些。

下面用Python算一下不同使用时长下的月成本对比：

python
def cost_comparison(cloud_price_per_hour, local_gpu_price, local_power_cost_per_month, hours_per_day):
    """
    比较云GPU和本地GPU的月成本
    """
    cloud_monthly = cloud_price_per_hour * hours_per_day * 30
    # 本地GPU折旧，按3年直线折旧
    depreciation = local_gpu_price / 36
    local_total = local_power_cost_per_month + depreciation
    
    print(f"每天使用{hours_per_day}小时：")
    print(f"云GPU月成本: ${cloud_monthly:.2f}")
    print(f"本地GPU月成本（含折旧）: ${local_total:.2f}")
    if cloud_monthly > local_total:
        print("结论：本地更划算")
    else:
        print("结论：云更划算")

# 测试不同使用时长
for hours in [2, 8, 24]:
    cost_comparison(3.0, 15000, 200, hours)
    print()

运行后你会看到：每天2小时，云月成本180美元，本地约617美元，云更划算；每天8小时，云720美元，本地仍约617美元，本地开始反超；每天24小时，云2160美元，本地617美元，本地大幅胜出。这就是盈亏平衡点的直观体现。混合策略：很多团队采用“本地推理+云训练”或“云突发+本地常驻”的混合模式。例如，用本地RTX 4090做日常推理，需要训练时租用云A100集群。这样兼顾成本和灵活性。

最终建议：初学者先用云GPU（如Colab、AutoDL）练手；团队有稳定需求且预算充足时，考虑本地GPU；对数据隐私要求高的场景，必须本地部署。选型没有绝对答案，只有匹配你使用模式的答案。

常见误区

  • 错误理解：算力（FLOPS）越高，LLM推理越快。→ 后果：可能花高价买了算力强但带宽低的卡，实际推理速度反而不如便宜卡。→ 正确做法：先确认你的任务是带宽瓶颈型（自回归生成）还是算力瓶颈型（大批量预填充/训练），推理场景优先看内存带宽和模型大小算出的理论token/s。
  • 错误理解：显存只要装下模型权重就够了。→ 后果：部署后频繁OOM（显存溢出），或者batch size只能设1，吞吐极低。→ 正确做法：在权重之外预留20%-50%余量给KV Cache、激活值和框架开销，长上下文场景要单独估算KV Cache并留更多余量。
  • 错误理解：云GPU一定比本地GPU便宜。→ 后果：长期高负载使用时持续付费，总成本远超一次性购买。→ 正确做法：按每天实际使用小时数计算月成本，把本地折旧（如3年直线折旧）和电费维护算进去，找到盈亏平衡点后再决策。

自测

一个13B参数的模型，使用FP16精度进行推理，至少需要多少显存？如果GPU内存带宽是1000GB/s，理论推理速度是多少token/s？请写出计算过程。

答案：第一步算权重：13B × 2字节 = 26GB。第二步加开销：推理还要放激活值和KV Cache，粗略加30%，26 × 1.3 ≈ 34GB，所以建议显存至少34GB。第三步算速度：自回归生成每token要把整个权重读一遍，理论速度 = 带宽 / 模型大小 = 1000GB/s / 26GB ≈ 38.5 token/s。注意这里用的是权重大小26GB而不是加开销后的34GB，因为带宽瓶颈主要来自读权重。

MLPerf推理基准中的Offline和Server场景有什么区别？分别适合评估什么类型的应用？

答案：Offline场景模拟离线批处理：所有查询一次性可用，系统可以攒大批量一起算，追求最大吞吐量，没有延迟约束。Server场景模拟在线服务：请求按泊松分布陆续到达，有延迟约束（如P99），系统要在吞吐和延迟之间平衡。所以评估批量推理任务（如夜间跑数据集）看Offline；评估在线API服务看Server。同一个GPU在两个场景的排名可能完全不同，选型时要先确定自己的场景再看对应榜单。

假设云GPU每小时3美元，本地GPU购买价15000美元，电费和维护每月200美元，按3年折旧。每天使用多少小时是云和本地的盈亏平衡点？请写出推导。

答案：设每天使用h小时。云月成本 = 3 × h × 30 = 90h 美元。本地月成本 = 电费维护200 + 折旧15000/36 ≈ 200 + 416.7 = 616.7美元。令90h = 616.7，解得h ≈ 6.85小时。所以每天使用约6.85小时是平衡点：低于这个时长云更划算，高于则本地更划算。这个计算还没考虑本地GPU的残值、网络延迟和隐私价值，实际决策时要把这些定性因素也纳入。

# 方案二：本地 2×A100 80GB，购买价 2×15000 = 30000 美元，月电费维护 300 美元
# 方案三（对比）：云 2×H100 80GB，每小时 2×10 = 20 美元

def compare_cost(name, cloud_price_per_hour, local_gpu_price, local_monthly_cost, hours_per_day=12):
    """比较云和本地的月成本，按3年折旧"""
    cloud_monthly = cloud_price_per_hour * hours_per_day * 30
    depreciation = local_gpu_price / 36
    local_total = local_monthly_cost + depreciation
    print(f"--- {name} ---")
    print(f"云GPU月成本: ${cloud_monthly:.2f}")
    print(f"本地GPU月成本（含折旧）: ${local_total:.2f}")
    if cloud_monthly > local_total:
        print("结论：本地更划算")
    else:
        print("结论：云更划算")
    print()

# 方案一：云 2×A100
compare_cost("云 2×A100 80GB", cloud_price_per_hour=6.0, local_gpu_price=0, local_monthly_cost=0)
# 方案二：本地 2×A100
compare_cost("本地 2×A100 80GB", cloud_price_per_hour=0, local_gpu_price=30000, local_monthly_cost=300)
# 方案三：云 2×H100
compare_cost("云 2×H100 80GB", cloud_price_per_hour=20.0, local_gpu_price=0, local_monthly_cost=0)

# 预期输出：
# 云 2×A100：月成本 6×12×30 = 2160 美元
# 本地 2×A100：月成本 300 + 30000/36 ≈ 1133.33 美元 → 本地更划算
# 云 2×H100：月成本 20×12×30 = 7200 美元
