本章目标：建立LLM知识地图，解释20+高频术语及其关系。

1.1 从一句话到Token：LLM的输入输出流水线

想象你对着一个博学但只会“接龙”的朋友说话：你给他前半句，他根据读过的海量文本，猜下一个词最可能是什么。LLM 本质上就是这样一个超级接龙机器，只不过它把“词”切成了更小的单位——Token（词元）。

当你输入“我爱吃苹果”，模型并不会直接看到汉字。它先经过 Tokenizer（分词器），把文本切成 Token 序列，比如 ['我', '爱', '吃', '苹果']，每个 Token 再映射成一个整数 ID。这些 ID 进入模型后，会被转换成 Embedding（嵌入）——一串高维浮点数向量，表示这个 Token 的语义。模型内部通过 Transformer（变换器） 和 Attention（注意力机制） 不断计算这些向量之间的关系，最终输出下一个 Token 的概率分布。

这里有两个关键数字：参数量（模型内部可学习的权重总数，比如 7B 表示 70 亿）和 上下文窗口（模型一次能“看到”的最大 Token 数，比如 8K、128K）。参数量决定模型的“脑容量”，上下文窗口决定它一次能读多长的文章。

下面是一个最小可运行示例，用 Hugging Face 的 tokenizer 观察分词和 Embedding 维度：

from transformers import AutoTokenizer, AutoModel
import torch

model_name = "bert-base-chinese"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModel.from_pretrained(model_name)

text = "我爱吃苹果"
inputs = tokenizer(text, return_tensors="pt")
print("Token IDs:", inputs["input_ids"].tolist())
print("Tokens:", tokenizer.convert_ids_to_tokens(inputs["input_ids"][0]))

with torch.no_grad():
    outputs = model(**inputs)
print("Embedding shape:", outputs.last_hidden_state.shape)  # [batch, seq_len, hidden_dim]

运行后你会看到类似 ['[CLS]', '我', '爱', '吃', '苹', '果', '[SEP]'] 的 Token 列表，以及形状为 [1, 7, 768] 的 Embedding。这 768 就是隐藏维度，是模型内部表示向量的宽度。

1.2 模型结构术语：Transformer、Attention、Dense与MoE

Transformer 是 LLM 的骨架。它由很多层堆叠而成，每一层包含一个 Attention 模块和一个前馈网络。Attention 让每个 Token 都能“看到”序列中其他 Token，并决定关注谁。比如在“苹果很好吃，因为它很甜”中，“它”会高度关注“苹果”。

传统 Transformer 的前馈网络是 Dense（稠密） 的：每个输入都会激活全部参数。而 MoE（Mixture of Experts，混合专家） 把前馈网络拆成多个“专家”，每次只激活其中一小部分。这样总参数量可以很大，但实际计算量只相当于一个小模型。例如 Mixtral 8x7B 总参数量约 47B，但每次推理只激活约 13B 参数。

另一个重要概念是位置编码。Attention 本身不知道顺序，所以需要给每个 Token 加上位置信息。早期用正弦函数，现在主流用 RoPE（旋转位置编码），它能让模型更好地外推到更长的上下文。

下面用 PyTorch 手写一个极简的单头 Attention，帮助理解其计算过程：

import torch
import torch.nn.functional as F

def attention(Q, K, V):
    # Q, K, V: [seq_len, d_k]
    scores = torch.matmul(Q, K.T) / (Q.size(-1) ** 0.5)
    weights = F.softmax(scores, dim=-1)
    return torch.matmul(weights, V)

seq_len, d_k = 4, 8
Q = torch.randn(seq_len, d_k)
K = torch.randn(seq_len, d_k)
V = torch.randn(seq_len, d_k)
out = attention(Q, K, V)
print("Attention output shape:", out.shape)  # [4, 8]

结论：Transformer 通过 Attention 捕捉上下文关系，通过层数堆叠增加表达能力，通过 MoE 在参数量和计算量之间做权衡。

1.3 训练与适配术语：从预训练到LoRA

LLM 的训练像培养一个学生：先大量阅读（预训练），再专项辅导（SFT），最后根据反馈调整（RLHF/DPO）。

  • 预训练：在海量文本上做“预测下一个 Token”的任务，让模型学会语言规律和世界知识。成本极高，通常只有大公司做。
  • SFT（Supervised Fine-Tuning，监督微调）：用人工标注的“问题-答案”对，教模型遵循指令。
  • RLHF（Reinforcement Learning from Human Feedback，人类反馈强化学习）：训练一个奖励模型来模拟人类偏好，再用强化学习优化 LLM。DPO 是它的简化替代，直接用偏好数据优化，不需要奖励模型。
  • 蒸馏：让一个小模型模仿大模型的输出，从而用更低成本获得接近的能力。
  • 微调：在预训练模型上继续训练，适配特定领域。
  • LoRA（Low-Rank Adaptation，低秩适应）：冻结原模型，只训练两个小矩阵，大幅减少可训练参数量。QLoRA 则在此基础上把原模型量化到 4-bit，进一步降低显存。
  • 量化：把模型权重从 FP16 压缩到 INT8/INT4，减少显存和加速推理，但可能损失精度。

下面用 PEFT 库演示如何给模型加上 LoRA：

from transformers import AutoModelForCausalLM
from peft import LoraConfig, get_peft_model

model = AutoModelForCausalLM.from_pretrained("gpt2")
config = LoraConfig(
    r=8,
    lora_alpha=32,
    target_modules=["c_attn"],
    lora_dropout=0.1,
    bias="none"
)
model = get_peft_model(model, config)
model.print_trainable_parameters()
# 输出类似：trainable params: 294,912 || all params: 124,734,720 || trainable%: 0.24%

关键结论：预训练赋予通用能力，SFT/RLHF 对齐人类偏好，LoRA/QLoRA/量化让适配和部署变得平民化。

1.4 应用与推理术语：Prompt、RAG、Agent与KV Cache

模型训练好后，怎么用？这涉及应用层和推理层术语。

  • Prompt（提示词）：你给模型的输入。好的 Prompt 能显著提升效果。
  • RAG（Retrieval-Augmented Generation，检索增强生成）：先从知识库检索相关文档，再把文档和问题一起交给模型生成答案。适合需要最新或私有知识的场景。
  • Agent（智能体）：让 LLM 自主规划、调用工具、多步执行任务。工具调用是 Agent 的核心能力，比如调用计算器、搜索 API。
  • Temperature：控制输出随机性。值越高越随机，越低越确定。Top-p 是另一种采样策略，只从累积概率达到 p 的 Token 中采样。
  • KV Cache（键值缓存）：自回归生成时，缓存之前 Token 的 Key 和 Value，避免重复计算，大幅加速推理。
  • Batching（批处理）：同时处理多个请求，提高 GPU 利用率。连续批处理（Continuous Batching）是 vLLM 等推理框架的关键技术。

  • Token 等于字或词：实际上 Token 是子词单元，不同 Tokenizer 切分方式不同，一个汉字可能对应一个或多个 Token。
  • 参数量越大模型一定越好：参数量只是潜力，训练数据质量、对齐程度、推理配置同样关键，MoE 模型总参数量大但激活参数少。

第2章 · 模型能力评测与可信度

本章目标：能设计小规模评测，识别不公平比较，给出有证据的选型结论。

公开基准：它们到底在测什么？

想象你要给一个学生写推荐信，你会怎么描述他的能力？你可能会说“数学不错，但语文一般”。LLM 也一样，没有一个单一分数能概括所有能力。公开基准就是给模型出的“标准化考卷”，每张考卷测不同的能力维度。

先看几个最常被引用的：

  • MMLU：像“高考综合卷”，覆盖57个学科（数学、历史、法律、医学等），全是四选一选择题。它测的是广博的知识面，但几乎不测推理深度和生成能力。
  • GPQA：像“研究生入学考试”，题目由领域专家编写，设计成“谷歌搜不到答案”。它测的是专家级推理，难度远高于 MMLU。
  • AIME：美国数学邀请赛，15道填空，答案都是0-999的整数。它测的是多步数学推理，对模型来说极难，近年才被突破。
  • HumanEval：给函数签名和文档字符串，让模型补全代码，用单元测试判分。它测的是短代码生成，但题目短、场景简单，和真实工程差距大。
  • SWE-bench：从真实 GitHub 仓库提取 issue 和对应修复，让模型生成补丁，跑测试验证。它测的是真实软件工程能力，难度高，更接近实际开发。

关键点：每个基准都有明确的“测什么”和“不能说明什么”。比如 MMLU 高分不代表会写代码，SWE-bench 高分也不代表能和你流畅对话。选型时，先问“我的业务场景最像哪个基准”，而不是只看排行榜。

下面是一个最小示例，用 Python 模拟计算 MMLU 准确率：

评测可信度：分数背后的陷阱

你看到两个模型在 MMLU 上分别是 85% 和 84%，能直接说第一个更好吗？不一定。评测结果可能被多种因素扭曲，就像考试作弊或泄题一样。

常见陷阱：

  • 数据污染：训练数据里混入了测试题。模型可能“背过答案”，分数虚高。检测方法：看模型在扰动题目（如改数字）上的表现是否骤降。
  • 测试集泄漏：测试集被用于调参或模型选择，导致过拟合。正确做法是严格划分开发集和测试集，测试集只在最后用一次。
  • 样本过少：只测 20 道题，随机波动可能让分数差 10%。一般建议至少几百个样本，并用置信区间报告。
  • 只报告最好结果：跑多次取最高分，忽略方差。应该报告平均值和标准差。
  • 提示词与推理预算不公平：给模型 A 精心设计的提示词和更多推理步数，模型 B 用默认设置，比较就不公平。必须控制变量。

举个例子：假设两个模型真实能力相同，但测试集只有 50 题，准确率都是 80%。由于随机性，一个可能考 86%，另一个 74%。用下面代码模拟：

import random

def eval_model(true_acc, n=50):
    return sum(random.random() < true_acc for _ in range(n)) / n

random.seed(0)
# 两个模型真实准确率都是 0.8
scores_a = [eval_model(0.8) for _ in range(5)]
scores_b = [eval_model(0.8) for _ in range(5)]
print("模型A 5次评测:", [f"{s:.0%}" for s in scores_a])
print("模型B 5次评测:", [f"{s:.0%}" for s in scores_b])
# 输出可能显示 A 最高 88%，B 最低 72%，但真实能力相同

结论：比较模型时，必须确保测试条件一致，并报告不确定性。否则你的选型结论可能只是噪声。

人工评测与 LLM-as-a-Judge：如何让评判更可靠

很多任务没有标准答案，比如“写一封友好的客户邮件”。这时需要人工评分，但人工贵且慢。于是有了 LLM-as-a-Judge：用另一个大模型当裁判，给回答打分或排序。

它像请了一个“助教”来批改作业，但助教也有偏见：可能偏爱长回答、偏爱自己家族的模型、对某些格式敏感。所以必须设计防偏机制：

  • 盲评：裁判不知道哪个回答来自哪个模型，避免品牌偏见。
  • 随机顺序：交换两个回答的呈现顺序，消除位置偏见。
  • 重复测试：同一对回答多次评判，看一致性。
  • 人工校验：抽样一部分让人类专家复核，校准裁判的可靠性。

下面是一个简化的 LLM-as-a-Judge 流程示例（用伪代码表示）：

# 模拟 LLM-as-a-Judge 盲评流程
import random

def judge(answer_a, answer_b, model_name):
    # 真实裁判会调用 LLM API，这里用随机模拟
    # 假设裁判有 60% 概率选更好的那个，但不知道模型名
    return random.choice(["A", "B"])

def blind_compare(model1_answers, model2_answers, n_trials=5):
    wins = {"model1": 0, "model2": 0}
    for i in range(len(model1_answers)):
        for _ in range(n_trials):
            # 随机交换顺序
            if random.random() < 0.5:
                a, b = model1_answers[i], model2_answers[i]
                mapping = {"A": "model1", "B": "model2"}
            else:
                a, b = model2_answers[i], model1_answers[i]
                mapping = {"A": "model2", "B": "model1"}
            winner = judge(a, b, "judge_model")
            wins[mapping[winner]] += 1
    return wins

# 模拟两个模型的回答
m1 = ["回答1-模型1", "回答2-模型1"]
m2 = ["回答1-模型2", "回答2-模型2"]
random.seed(1)
result = blind_compare(m1, m2)
print("盲评胜场:", result)

LLM-as-a-Judge 适合快速迭代和粗筛，但不能完全替代人工，尤其是高风险场景。最终选型报告里，最好同时给出自动指标和人工评估结果。

实操：设计一次小规模业务评测

现在把前面知识串起来。假设你要为“企业客服助手”选型，候选模型 A 和 B。你需要设计一个评测，用证据说话。

步骤：

  1. 定义能力维度：根据业务，确定关键维度，比如“回答准确性”、“语气友好度”、“拒绝不当请求”。
  2. 收集业务样本：从真实客服日志中抽取 100 条用户问题，覆盖常见和边缘情况。
  3. 划分开发集和测试集：用 50 条做开发集，用来调试提示词和评分标准；另外 50 条做测试集，只在最终比较时用。
  4. 设计评分标准：每个维度 1-5 分，并写清楚评分细则。例如准确性：5=完全正确，3=部分正确，1=错误。
  5. 运行评测：对两个模型使用相同的提示词和推理预算，生成回答。
  6. 评分：先用 LLM-as-a-Judge 盲评，再人工校验 20% 的样本。
  7. 分析失败类型：统计错误类别，比如“答非所问”、“信息过时”、“语气生硬”。
  8. 得出结论：基于测试集分数和失败分析，给出选型建议。

第3章 · 推理性能与成本评测

本章目标：能测量TTFT、TPOT、吞吐等指标，计算每次请求成本。

3.1 性能指标：从用户点击到最后一个字

想象你去餐厅点餐：TTFT 是“下单到第一道菜上桌”的时间，TPOT 是“吃完一道菜到下一道菜上桌”的平均间隔，端到端延迟 是“从下单到吃完最后一道菜”的总时间。对 LLM 推理来说，用户感知的“快”往往由 TTFT 决定，而“完成快”则由 TPOT 和输出长度共同决定。

具体定义：

  • TTFT (Time to First Token)：从发送请求到收到第一个输出 token 的时间，包含网络、排队、prefill 计算。
  • TPOT (Time per Output Token)：生成阶段每个输出 token 的平均耗时，通常等于 (端到端延迟 - TTFT) / (输出 token 数 - 1)。
  • ITL (Inter-Token Latency)：相邻两个输出 token 之间的时间间隔，TPOT 是 ITL 的平均值。
  • 吞吐量 (Throughput)：单位时间内系统处理的 token 总数或请求数，常用 tokens/s 表示。
  • 并发 (Concurrency)：同时处理的请求数量，直接影响吞吐和延迟。
  • P50/P95/P99：延迟的百分位数，P95 表示 95% 的请求延迟低于该值，比平均值更能反映尾部体验。
  • 成功率/错误率/超时率：成功完成的请求比例、返回错误的比例、超过设定时限的比例。

下面是一个最小可运行示例，用 Python 模拟测量这些指标（实际中需替换为真实 API 调用）：

import time
import random

def mock_llm_call(prompt, max_tokens=50):
    """模拟一次流式 LLM 调用，返回每个 token 的时间戳。"""
    # 模拟 prefill 和排队
    ttft = random.uniform(0.1, 0.5)
    time.sleep(ttft)
    timestamps = [time.time()]
    # 模拟生成 token
    for _ in range(max_tokens - 1):
        time.sleep(random.uniform(0.01, 0.05))
        timestamps.append(time.time())
    return timestamps

def measure(prompt):
    start = time.time()
    timestamps = mock_llm_call(prompt)
    end = time.time()
    ttft = timestamps[0] - start
    tpot = (end - timestamps[0]) / (len(timestamps) - 1) if len(timestamps) > 1 else 0
    e2e = end - start
    return {"ttft": ttft, "tpot": tpot, "e2e": e2e, "output_tokens": len(timestamps)}

# 模拟 10 次请求
results = [measure("你好") for _ in range(10)]
for i, r in enumerate(results):
    print(f"请求{i+1}: TTFT={r['ttft']:.3f}s, TPOT={r['tpot']:.3f}s, E2E={r['e2e']:.3f}s")

# 计算 P50/P95
import statistics
ttfts = sorted([r['ttft'] for r in results])
p50 = ttfts[len(ttfts)//2]
p95 = ttfts[int(len(ttfts)*0.95)]
print(f"TTFT P50={p50:.3f}s, P95={p95:.3f}s")

关键结论：首字快不等于完成快，单用户快不等于并发快。 评估时必须同时看 TTFT、TPOT 和吞吐，并在目标并发下测量。

3.2 评测条件记录：让结果可复现

性能数字脱离条件毫无意义。就像说“我跑得很快”，必须说明是百米还是马拉松、顺风还是逆风。LLM 推理评测必须记录以下条件：

  • 模型版本：具体到 commit 或日期，如 llama-3-8b-instruct-2024-04。
  • 硬件：GPU 型号、数量、显存、互联方式（NVLink/PCIe）。
  • 推理框架：vLLM、TensorRT-LLM、TGI 等及版本。
  • 精度：FP16、BF16、INT8、INT4 等。
  • 输入/输出长度：平均和分布，如输入 512 tokens、输出 128 tokens。
  • 并发与批处理：并发请求数、最大 batch size、是否启用 continuous batching。
  • 缓存：是否启用 KV Cache、prefix caching。
  • 预热：是否预热、预热次数，避免冷启动影响。
  • 测试次数：至少 100 次以上，报告 P50/P95/P99。

3.3 成本计算：从每百万 Token 到每个成功任务

云厂商常标“每百万 Token 价格”，但业务成本要看每个成功任务花了多少钱。类比：买菜看单价，但请客吃饭要看“一桌菜总价”，还要算上烧焦重做的成本。

成本计算步骤：

  1. 每百万 Token 价格：输入和输出通常不同价，如输入 $0.5/M，输出 $1.5/M。
  2. 每次请求成本 = (输入 tokens / 1e6) * 输入单价 + (输出 tokens / 1e6) * 输出单价。
  3. 考虑重试：如果失败率 5%，则平均请求次数 = 1 / (1 - 0.05) ≈ 1.053。
  4. 工具调用和额外推理：Agent 场景可能多次调用 LLM，需累加。
  5. 每个成功任务成本 = 总成本 / 成功任务数。

下面是一个计算示例：

def cost_per_request(input_tokens, output_tokens, price_in_per_m, price_out_per_m):
    return (input_tokens / 1e6) * price_in_per_m + (output_tokens / 1e6) * price_out_per_m

def cost_per_success(input_tokens, output_tokens, price_in, price_out, success_rate, retries_per_failure=1):
    base = cost_per_request(input_tokens, output_tokens, price_in, price_out)
    # 平均尝试次数 = 1 + (1 - success_rate) * retries_per_failure
    avg_attempts = 1 + (1 - success_rate) * retries_per_failure
    total_cost = base * avg_attempts
    return total_cost / success_rate  # 分摊到每个成功任务

# 示例：输入 500 tokens，输出 200 tokens，输入 $0.5/M，输出 $1.5/M，成功率 95%
base = cost_per_request(500, 200, 0.5, 1.5)
print(f"单次请求成本: ${base:.6f}")
per_success = cost_per_success(500, 200, 0.5, 1.5, 0.95)
print(f"每个成功任务成本: ${per_success:.6f}")

关键结论：最低单价不等于最低业务成本。 必须把重试、工具调用、超时和失败率纳入计算。

常见误区

  • 首字快（TTFT 低）不等于完成快，如果 TPOT 很高，长输出的端到端延迟仍然很大。
  • 单用户测试快不等于并发快，高并发下排队和批处理会导致延迟显著上升。
  • Tokens/s 不可直接比较，必须结合输入输出长度、并发数、硬件和精度等条件。
  • 最低单价不等于最低业务成本，需考虑重试、工具调用、超时和失败率。

自测

某模型 TTFT=0.2s，TPOT=0.05s，输出 100 个 token，端到端延迟大约是多少？如果 TPOT 变为 0.1s，端到端延迟变为多少？

答案：端到端延迟 ≈ TTFT + TPOT × (输出 token 数 - 1) = 0.2 + 0.05 × 99 = 5.15s。若 TPOT=0.1s，则 0.2 + 0.1 × 99 = 10.1s。说明 TPOT 对长输出影响巨大。

为什么报告 P95 延迟比平均延迟更有意义？

答案：平均延迟会被大量快请求拉低，掩盖尾部慢请求。P95 表示 95% 的请求延迟低于该值，能反映最差 5% 用户的体验，对 SLA 和容量规划更关键。

第4章 · 硬件参数与算力评估

本章目标：读懂硬件规格表，解释显存、带宽、算力对推理的影响。

硬件组成：GPU、CPU、内存、存储、互联与网络

把一台推理服务器想象成一家餐厅：GPU 是后厨的灶台，负责真正“炒菜”（矩阵乘法）；CPU 是前台和调度员，负责接单、拆解任务、启动 GPU；内存（RAM）是备菜台，存放还没下锅的食材（模型权重、中间数据）；显存（VRAM）是灶台旁边的操作台，离 GPU 最近，放正在炒的菜；存储（SSD/HDD）是仓库，放冷鲜食材（模型文件、日志）；互联（PCIe/NVLink）是传菜通道，决定食材从备菜台到灶台的速度；网络（以太网/InfiniBand）是外卖通道，决定多台机器之间怎么协作。

不同场景对硬件的需求不同：

  • 消费级 GPU（如 RTX 4090）：显存 24GB 左右，适合个人开发、小模型推理、微调。优点是便宜、功耗低；缺点是显存小、没有 NVLink、多卡通信走 PCIe。
  • 数据中心 GPU（如 A100/H100）：显存 40GB~80GB，支持 NVLink，带宽极高，适合大模型训练和推理。缺点是贵、功耗高、需要专业散热和供电。
  • Apple Silicon（M 系列）：统一内存架构，CPU 和 GPU 共享内存，内存可达 128GB 甚至 192GB，适合本地跑大模型。缺点是 GPU 算力相对弱，生态不如 CUDA 成熟。

关键结论：选硬件不是只看 GPU，而是看整个数据通路是否匹配你的任务。如果模型权重放不进显存，再强的算力也发挥不出来；如果互联带宽太低，多卡并行反而会拖慢速度。

关键参数：显存、带宽、算力、互联与功耗

读懂硬件规格表，核心看这几个参数：

参数含义对推理的影响

显存带宽（Memory Bandwidth）每秒能从显存读写多少数据，单位 GB/s决定 token 生成速度；带宽越高，解码越快

一个具体例子：RTX 4090 有 24GB 显存、约 1008 GB/s 带宽、FP16 算力约 330 TFLOPS。A100 80GB 有 80GB 显存、约 2039 GB/s 带宽、FP16 算力约 312 TFLOPS。虽然两者 FP16 峰值算力接近，但 A100 显存更大、带宽更高，所以能跑更大的模型，且解码速度更快。

关键结论：推理速度往往受显存带宽限制，而不是峰值算力。因为自回归生成时，每生成一个 token 都要把整个模型权重读一遍，这是典型的“内存带宽瓶颈”场景。

单位与口径：FLOPs、TFLOPS、TOPS、GB 与 GiB、精度

硬件规格表里单位很多，容易混淆。先记住几个核心换算：

  • FLOPs：浮点运算次数，是“工作量”。比如一次矩阵乘法做了多少 FLOPs。
  • FLOP/s：每秒浮点运算次数，是“速度”。TFLOPS = 10^12 FLOP/s，PFLOPS = 10^15 FLOP/s。
  • TOPS：每秒万亿次操作，通常用于整数运算（INT8/INT4）。TOPS 和 TFLOPS 不能直接比，因为操作类型和精度不同。
  • GB vs GiB：GB 是十进制（10^9 字节），GiB 是二进制（2^30 字节）。1 GiB ≈ 1.074 GB。厂商标注的“80GB”通常是十进制，系统里看到的是 GiB，所以会“缩水”。
  • GB/s vs Gb/s：GB/s 是字节，Gb/s 是比特。1 GB/s = 8 Gb/s。网络带宽常用 Gb/s，显存带宽常用 GB/s。

精度方面，不同精度占用的显存和算力不同：

精度每参数字节特点
FP324最精确，训练常用，推理慢
FP162推理常用，范围较小
BF162范围与 FP32 相同，训练/推理都常用
FP81新卡支持，速度快，精度损失可控
INT81量化推理常用，速度快
INT40.5极致压缩，精度损失较大

    bytes_total = num_params * bytes_per_param

常见误区与实战选型思路

这一节把最容易踩的坑集中讲清楚：

  • 只看显存选卡：显存大不代表推理快。如果带宽低，生成 token 会很慢。比如某些大显存但低带宽的卡，跑大模型时吞吐可能不如小显存高带宽的卡。
  • 峰值算力高不等于推理快：推理分预填充和解码两个阶段。预填充吃算力，解码吃带宽。很多场景解码是瓶颈，所以带宽比峰值算力更重要。
  • 不同精度 TOPS 不能直接比：INT8 的 TOPS 和 FP16 的 TFLOPS 不是一回事。比较时要看同一精度下的数据，或者看实际任务吞吐。
  • 多卡显存不能无条件合并：多卡不会自动把显存拼成一块。需要模型并行、张量并行等技术，而且通信开销可能抵消收益。NVLink 比 PCIe 更适合多卡并行。
  • 统一内存不等于全部可用：Apple Silicon 的统一内存虽然大，但系统和其他应用也要占用，实际能给模型的通常只有 70%~80%。

实战选型可以按这个顺序问自己：

  1. 模型多大？权重 + KV Cache 需要多少显存？
  2. 目标吞吐和延迟是多少？解码阶段带宽够不够？
  3. 单卡装不下，要不要多卡？互联带宽够不够？
  4. 功耗和散热能不能满足？
  5. 预算和生态（CUDA/ROCm/Metal）是否匹配？

关键结论：硬件选型是“显存容量、带宽、算力、互联、功耗”的联合优化，任何单一指标都不能决定成败。

常见误区

  • 只看显存容量选卡，忽略显存带宽和互联能力，导致大模型能装下但生成速度极慢。
  • 把不同精度的 TOPS 和 TFLOPS 直接比较，误以为 INT8 的 TOPS 高就代表所有任务都更快。
  • 认为多卡显存会自动合并成一块大显存，实际上需要模型并行且通信开销可能很大。
  • 把统一内存的全部容量都算作可用显存，忽略系统和应用占用，导致实际能跑的模型比预期小。

第5章 · 显存估算与部署选型

本章目标：能估算模型推理显存，区分装得下、跑得快、满足并发。

显存都去哪儿了？拆解推理时的显存组成

想象你要开一家餐厅：厨房（GPU）里要放食材（模型权重）、备菜台（KV Cache）、临时切菜板（激活与临时缓冲）、还有收银机、冰箱等固定设备（框架开销），最后还得留点空间给客人走动（必要余量）。显存就是厨房面积，任何一样放不下，餐厅就开不了张。

具体来说，推理时显存主要被以下部分占用：

  • 模型权重：模型参数本身，比如 FP16 下每个参数占 2 字节。
  • 量化元数据：如果用了量化（如 GPTQ、AWQ），除了权重还会存缩放因子、零点等，通常额外占 5%~15%。
  • KV Cache：自回归生成时缓存历史 Key/Value，避免重复计算。它随上下文长度和并发数线性增长。
  • 激活与临时缓冲：前向传播中的中间结果，通常不大，但长上下文或大 batch 时会显著增加。
  • 框架开销：CUDA context、cuDNN 工作区、通信缓冲等，一般 0.5~2 GB。
  • 必要余量：防止 OOM，建议留 10%~20%。

下面是一个最小估算函数，帮你快速算个大概：

def estimate_memory_gb(params_b, precision_bytes, context_len, batch_size, n_layers, n_kv_heads, head_dim, overhead_gb=1.5, reserve_ratio=0.15):
    # 模型权重
    weights = params_b * 1e9 * precision_bytes / (1024**3)
    # KV Cache: 2 (K和V) * layers * batch * seq_len * kv_heads * head_dim * precision_bytes
    kv_cache = 2 * n_layers * batch_size * context_len * n_kv_heads * head_dim * precision_bytes / (1024**3)
    # 激活与临时缓冲粗略估计为权重的 5%
    activations = weights * 0.05
    total = weights + kv_cache + activations + overhead_gb
    total_with_reserve = total * (1 + reserve_ratio)
    return weights, kv_cache, activations, overhead_gb, total_with_reserve

# 示例：8B 模型，FP16，上下文 4096，batch 1，32 层，8 个 KV 头，头维度 128
w, kv, act, ov, total = estimate_memory_gb(8, 2, 4096, 1, 32, 8, 128)
print(f"权重: {w:.2f} GB, KV Cache: {kv:.2f} GB, 激活: {act:.2f} GB, 总需求: {total:.2f} GB")

运行结果会告诉你，8B FP16 模型在 4K 上下文下单并发大约需要 18~19 GB 显存。记住：显存估算不是精确科学，而是快速判断“装不装得下”的工程近似。

手把手估算：8B、32B、70B 在不同精度与并发下的显存

我们用一个统一公式来估算：

总显存 ≈ 权重 + KV Cache + 激活 + 框架开销 + 余量

其中：

  • 权重 = 参数量 × 每参数字节数
  • KV Cache = 2 × 层数 × 并发数 × 上下文长度 × KV头数 × 头维度 × 每元素字节数
  • 激活 ≈ 权重的 5%~10%
  • 框架开销 ≈ 1~2 GB
  • 余量 ≈ 总和的 10%~20%

假设模型结构：层数 = 参数量(B) × 4，KV头数 = 8，头维度 = 128。我们写个脚本对比不同配置：

def estimate(params_b, precision, context_len, batch_size):
    bytes_per_param = {'fp32':4, 'fp16':2, 'int8':1, 'int4':0.5}[precision]
    n_layers = int(params_b * 4)
    n_kv_heads = 8
    head_dim = 128
    weights = params_b * 1e9 * bytes_per_param / (1024**3)
    kv = 2 * n_layers * batch_size * context_len * n_kv_heads * head_dim * bytes_per_param / (1024**3)
    act = weights * 0.05
    overhead = 1.5
    total = (weights + kv + act + overhead) * 1.15
    return weights, kv, total

configs = [
    (8, 'fp16', 4096, 1),
    (8, 'int4', 4096, 1),
    (32, 'fp16', 8192, 4),
    (70, 'int4', 4096, 8),
]
for p, prec, ctx, bs in configs:
    w, kv, total = estimate(p, prec, ctx, bs)
    print(f"{p}B {prec} ctx={ctx} bs={bs}: 权重 {w:.1f}GB, KV {kv:.1f}GB, 总需 {total:.1f}GB")

输出示例：

8B fp16 ctx=4096 bs=1: 权重 14.9GB, KV 0.5GB, 总需 19.5GB
8B int4 ctx=4096 bs=1: 权重 3.7GB, KV 0.5GB, 总需 6.6GB
32B fp16 ctx=8192 bs=4: 权重 59.6GB, KV 8.0GB, 总需 79.5GB
70B int4 ctx=4096 bs=8: 权重 32.6GB, KV 4.0GB, 总需 43.9GB

关键结论：

  • 8B FP16 单并发 4K 上下文，一张 24GB 卡（如 4090）刚好装下，但并发一高就爆。
  • 8B INT4 可以轻松跑在 8GB 显存上，适合边缘设备。
  • 32B FP16 需要至少 80GB 显存，单卡 A100/H100 可行，但并发 4 时已接近极限。
  • 70B INT4 在 48GB 卡（如 A6000）上可跑，但并发 8 时 KV Cache 会吃掉不少显存。

注意：这里假设 KV 头数为 8，实际模型可能不同（如 GQA 会减少 KV 头数），需要查模型配置。

MoE 模型：总参数与激活参数，别被名字骗了

MoE（混合专家）模型像一家大公司：公司有 1000 名员工（总参数），但每个任务只叫 10 个人干活（激活参数）。如果你只按 10 个人算工资（显存），那就大错特错了——因为公司得给所有 1000 人发工资（权重都得存着）。

MoE 模型有两个关键数字：

  • 总参数：所有专家加起来的参数量，决定权重显存。
  • 激活参数：每次前向实际用到的参数量，决定计算量（FLOPs）和部分激活显存。

例如，Mixtral 8x7B 总参数约 46.7B，但激活参数只有约 12.9B。如果你按 12.9B 估算权重显存，会严重低估。

估算 MoE 显存时，权重部分必须用总参数，KV Cache 和激活则与激活参数、层数、注意力头数相关。下面是一个简化示例：

def estimate_moe(total_params_b, active_params_b, precision, context_len, batch_size, n_layers, n_kv_heads, head_dim):
    bytes_per_param = {'fp16':2, 'int8':1, 'int4':0.5}[precision]
    weights = total_params_b * 1e9 * bytes_per_param / (1024**3)
    kv = 2 * n_layers * batch_size * context_len * n_kv_heads * head_dim * bytes_per_param / (1024**3)
    # 激活与激活参数相关，粗略按激活参数的 10% 估算
    act = active_params_b * 1e9 * bytes_per_param / (1024**3) * 0.1
    overhead = 1.5
    total = (weights + kv + act + overhead) * 1.15
    return weights, kv, total

# Mixtral 8x7B: 总参数 46.7B, 激活 12.9B, 32 层, 8 KV 头, 头维度 128
w, kv, total = estimate_moe(46.7, 12.9, 'int4', 4096, 1, 32, 8, 128)
print(f"权重: {w:.1f}GB, KV: {kv:.1f}GB, 总需: {total:.1f}GB")

输出：权重约 21.8GB，总需约 27GB。如果误用激活参数 12.9B 算权重，会得到约 6GB，差了三倍多。

记住：MoE 的权重显存看总参数，计算量看激活参数。部署时，显存按总参数准备，算力按激活参数评估。

选部署方式就像选交通工具：API 是打车，云 GPU 是租车，本地工作站是买私家车，多卡服务器是买大巴。没有绝对好坏，只有合不合适。

如何决策？问自己几个问题：

  • 数据敏感吗？敏感选本地或多卡服务器。

常见误区

  • 只按激活参数估算 MoE 模型的权重显存，导致严重低估，实际部署时 OOM。
  • 忽略 KV Cache 的显存占用，尤其是在长上下文和高并发场景下，KV Cache 可能超过模型权重。
  • 认为量化后显存按比例线性减少，实际上量化元数据、激活和框架开销不会同比减少，且低精度可能影响质量。

自测

一个 70B 模型，使用 INT4 量化，上下文长度 8192，并发数 4，假设 80 层，8 个 KV 头，头维度 128。请估算总显存需求（GB），并说明计算过程。

答案：权重：70e9 * 0.5 / (1024^3) ≈ 32.6 GB；KV Cache：2 * 80 * 4 * 8192 * 8 * 128 * 0.5 / (1024^3) ≈ 2.5 GB；激活：约 32.6 * 0.05 ≈ 1.6 GB；框架开销：1.5 GB；总和 = 32.6+2.5+1.6+1.5 = 38.2 GB；加 15% 余量 ≈ 43.9 GB。因此需要至少 48GB 显存的 GPU。

MoE 模型的总参数和激活参数分别影响显存估算的哪一部分？为什么不能只用激活参数估算权重显存？

答案：总参数决定权重显存，因为所有专家参数都需要加载到显存中；激活参数决定计算量和部分激活显存。不能只用激活参数估算权重显存，因为虽然每次前向只激活部分专家，但所有专家的权重都必须存储在显存中，否则无法在需要时切换。

第6章 · 综合项目：企业助手选型

本章目标：完成从需求到选型报告的完整项目，给出有证据的推荐方案。

从需求到验收标准：把业务语言翻译成可测量的指标

选型不是“哪个模型跑分高就选哪个”，而是“哪个模型最匹配业务约束”。先做需求翻译：把业务方的模糊诉求（“要准、要快、要便宜”）变成可测量的验收标准（Acceptance Criteria）。

以企业知识库问答 + 订单分析助手为例，业务约束通常有三类：效果（回答正确率、结构化字段准确率）、性能（P95 延迟、吞吐）、成本（每千次调用成本、TCO）。

把约束写成 SLO（Service Level Objective），例如：知识库问答答案正确率 ≥ 90%，订单字段提取 F1 ≥ 0.95，P95 延迟 ≤ 3s，单次调用成本 ≤ 0.01 元。这些数字就是后续评测的标尺。

关键结论：没有验收标准的选型是主观偏好，有验收标准的选型才是工程决策。

准备脱敏测试数据：让评测可复现、可对比

评测数据必须脱敏（Anonymized Data）：替换真实姓名、手机号、订单号，但保留分布特征（长度、格式、噪声）。数据要覆盖五类任务：

  • 订单信息提取：从自然语言中抽取结构化字段
  • 结构化输出：要求模型返回 JSON
  • 知识库问答：基于给定文档回答
  • 异常解释：解释订单异常原因
  • 受控工具调用：调用查询接口并传参

每类准备 30~50 条，标注标准答案。下面是一个最小可运行的数据构造与评测示例：

import json, re

# 脱敏后的测试样本
test_cases = [
    {"input": "客户张三买了2台A100，订单号ORD-1001，要求3天内发货",
     "expected": {"customer": "张三", "quantity": 2, "product": "A100", "order_id": "ORD-1001"}},
    {"input": "李四下单5块H100，订单号ORD-1002，加急",
     "expected": {"customer": "李四", "quantity": 5, "product": "H100", "order_id": "ORD-1002"}},
]

def extract(text):
    # 模拟模型输出（真实场景替换为 API 调用）
    return {
        "customer": re.search(r"客户?(\w+?)(?:买|下单)", text).group(1),
        "quantity": int(re.search(r"(\d+)(?:台|块)", text).group(1)),
        "product": re.search(r"(A100|H100)", text).group(1),
        "order_id": re.search(r"ORD-\d+", text).group(0),
    }

def score(pred, gold):
    correct = sum(1 for k in gold if pred.get(k) == gold[k])
    return correct / len(gold)

for case in test_cases:
    pred = extract(case["input"])
    print(case["input"][:20], "->", score(pred, case["expected"]))

比较模型与性能成本：设计评测并估算部署资源

评测要同时测四件事：效果、延迟、吞吐、成本。效果用准确率/F1；延迟看 P50/P95；吞吐看 QPS；成本按 token 计费或按 GPU 小时折算。

部署资源估算公式：显存 ≈ 参数量 × 精度字节数 × 1.2（KV Cache 与开销）。例如 7B 模型 FP16 约 14GB，INT8 约 7GB，INT4 约 3.5GB。并发高时 KV Cache 会显著增加显存。

下面是一个评测脚本骨架，输出效果与延迟：

import time, statistics

def evaluate(model_fn, cases):
    scores, latencies = [], []
    for c in cases:
        t0 = time.time()
        pred = model_fn(c["input"])
        latencies.append(time.time() - t0)
        scores.append(score(pred, c["expected"]))
    return {
        "accuracy": sum(scores) / len(scores),
        "p50_latency": statistics.median(latencies),
        "p95_latency": sorted(latencies)[int(len(latencies) * 0.95) - 1],
    }

关键结论：选型要算 TCO，不只看单价；延迟和吞吐必须用真实并发压测，不能只看单条测试。

撰写选型报告：结构、证据与适用边界

选型报告（Selection Report）要让决策者一眼看懂“为什么选它、什么情况下不选它”。推荐结构：

  1. 业务约束与验收标准
  2. 评测方法与脱敏数据说明
  3. 效果结果（表格对比）
  4. 性能结果（延迟/吞吐）
  5. 成本估算与 TCO
  6. 硬件需求
  7. 推荐方案
  8. 适用边界（Applicability Boundary）
  9. 待验证风险（Risks to Validate）

效果对比表示例：

模型提取 F1问答准确率P95 延迟单次成本
模型A0.960.912.1s0.001元
模型B0.930.881.2s0.0005元

推荐方案要写清适用边界：例如“模型A 适合高准确率场景，模型B 适合高并发低成本场景”。待验证风险包括：长尾订单格式、工具调用失败率、数据漂移。

关键结论：报告的价值在于证据链完整、边界清晰、风险可追踪，而不是给出一个绝对答案。

常见误区

  • 只看模型跑分（如 MMLU）就做选型，忽略业务验收标准和真实数据分布。
  • 用未脱敏的真实数据做评测，导致隐私泄露且结果无法复现。
  • 只算 API 单价，忽略 TCO（含重试、缓存、运维、GPU 折旧）和并发下的延迟劣化。
