LLM术语与算力实战(机器初稿)

课题:「LLM术语精通」 · 学习目标: 《LLM 技术与算力实战：从快速入门到独立评测与选型》 我希望系统掌握三个核心方向： ① LLM 的相关术语及其背后的原理； ② LLM 模型的能力、性能、成本与业务适用性评测； ③ 硬件算力设备的关键参数、性能评估和部署选型。 不要仅给我学习建议、资料链接或课程目录。你需要真正承担教师的角色，提供讲解、案例、练习、反馈和阶段验收。 一、我的背景与学习目标 我已有软件开发基础，接触过 AI 应用和模型 API，但希望系统补齐 LLM 原理、评测与算力知识。 请跳过 Python 入门、编程基础等内容；数学知识按需补充，先解释直觉，再介绍必要公式，不默认我已经掌握深度学习数学。 我偏好快速、项目驱动、能用于实际开发和技术决策的学习方式。业务案例优先采用企业知识库问答、电商订单分析、数据提取和业务助手。 完成课程后，我应该能够： 1. 读懂模型介绍、模型卡、评测报告和硬件规格表，解释核心术语及其关系。 2. 判断一个模型是否适合具体业务，而不是只根据排行榜选模型。 3. 设计小规模、可复现的模型评测，并解释结果和局限。 4. 根据模型规模、精度、上下文长度和并发需求，估算显存、算力与成本。 5. 对 API、云端 GPU 和本地部署做有依据的比较。 请把“快速入门”和“逐步精通”分开。不要承诺学几天就能精通，也不要把记住术语或看完课程等同于掌握。 二、课程组织方式 采用“先建立全景地图，再掌握高频知识，最后项目实战”的顺序。 设计两层路线： - 7 天快速入门：每天默认 60—90 分钟，优先掌握最常用、最影响决策的知识。 - 30 天进阶实践：通过实验、计算和项目，训练独立评测、部署与选型能力。 这两个时间安排是学习规划，不是掌握程度保证。根据我的实际表现调整进度。 所有知识标注为“必须掌握 / 了解即可 / 进阶选学”。不要为了全面而把所有内容塞进入门阶段。 三、必须覆盖的知识模块 模块 A：LLM 术语与核心原理 建立清晰的知识地图，覆盖以下内容： 基础概念： LLM、Token、Tokenizer、Embedding、参数量、上下文窗口、输入与输出 Token、训练与推理。 模型结构： Transformer、Attention、模型层数与隐藏维度、Dense 与 MoE、总参数与激活参数、位置编码；让人理解这些概念如何影响能力、显存和速度，不要求入门阶段推导全部数学。 训练与适配： 预训练、后训练、SFT、RLHF、DPO、蒸馏、微调、LoRA、QLoRA、量化。 应用与推理： Prompt、Context Engineering、RAG、向量检索、Reranker、Agent、工具调用、结构化输出、Temperature、Top-p、推理预算、Prefill、Decode、KV Cache、Batching。 重点对比容易混淆的概念，例如： 参数量与模型能力、上下文长度与有效利用能力、训练与推理、RAG 与微调、Agent 与普通模型调用、模型量化与训练精度。 术语首次出现时给出中文名、英文名或全称、缩写和直观解释。逐步积累一份约 40—60 个高频术语的速查表，不要一次性灌输全部术语。 模块 B：LLM 能力评测与评测可信度 从三个层次讲清楚： “模型本身的能力评测” “RAG / Agent 等完整系统的评测” “实际业务任务的验收” 能力维度至少包括： 知识与推理、数学、编程、中文与多语言、指令遵循、结构化输出、长上下文、工具调用、事实性与幻觉。 选择有代表性的公开基准讲解，例如 MMLU/MMLU-Pro、GPQA、AIME、HumanEval、SWE-bench 等。具体选择以授课时能核验的资料为准，不必全部展开。 对于每个选定基准，说明： 它测什么、如何计分、适用场景、不能说明什么，以及常见误读。 教我识别： 数据污染、测试集泄漏、样本过少、只报告最好结果、不同提示词或推理预算下的不公平比较，以及公开跑分与真实业务之间的差距。 讲清楚人工评测、自动指标、LLM-as-a-Judge 的适用边界，并介绍盲评、随机顺序、重复测试、人工校验和不确定性表达。 安排一个实操： 以同一批业务样本比较至少两个模型，设计评分标准，分析失败类型，并给出有证据的选型结论。区分开发集与最终测试集，避免反复针对测试集调优。 模块 C：推理性能与成本评测 解释并实际使用： TTFT、TPOT / ITL、端到端延迟、Tokens/s、单请求速度、系统总吞吐、并发、P50/P95/P99、成功率、错误率、超时率。 重点回答： 为什么“首字快”不一定“回答完成快”？ 为什么单用户很快，多用户并发后可能变慢？ 为什么两个 Tokens/s 数字不一定能直接比较？ 为什么最低 Token 单价不一定意味着最低业务成本？ 评测必须记录必要条件： 模型与版本、硬件、推理框架与版本、精度或量化方式、输入输出长度、并发、批处理、缓存、预热和测试次数。 比较不同模型时，说明 Tokenizer 差异及可见计费信息的限制。涉及推理预算时，仅使用可观察、可配置或官方披露的信息，不假设能够读取模型内部思维过程。 成本不仅看每百万 Token 价格，也要计算每次请求、每个成功任务的成本，并考虑重试、工具调用和额外推理开销。 模块 D：硬件设备参数与算力评估 覆盖 GPU、CPU、内存、存储、互联与网络的作用，区分消费级显卡、数据中心加速卡、Apple Silicon 统一内存设备及其他加速器的适用条件，不默认某一品牌永远最优。 重点讲解： 显存容量、显存带宽、内存容量与带宽、计算单元、Tensor Core 等专用单元、频率、PCIe、NVLink、网络带宽与延迟、功耗、供电与散热。 讲清楚以下单位和口径： FLOPs 与 FLOP/s、TFLOPS、PFLOPS、TOPS、GB 与 GiB、GB/s 与 Gb/s，以及 FP32、FP16、BF16、FP8、INT8、INT4。 对硬件宣传中的算力数字，必须检查： 计算精度、稠密或稀疏口径、峰值或实测、适用算子，以及软件栈能否实际利用。 重点解释： 为什么不能只看显存容量选显卡？ 为什么峰值算力更高不一定意味着 LLM 推理更快？ 为什么不同精度、不同统计口径的 TOPS / TFLOPS 不能直接横比？ 为什么多卡显存不能无条件当作单卡显存使用？ 为什么统一内存总容量不等于模型可全部使用的容量？ 用简单案例介绍计算瓶颈、带宽瓶颈和通信瓶颈，以及训练、Prefill、Decode 的资源需求差异。高级并行策略放入进阶阶段。 模块 E：显存估算、部署容量与选型 通过可复算的案例，教我估算： 模型权重、量化元数据、KV Cache、激活与临时缓冲、框架开销和必要余量。 训练部分另行解释梯度、优化器状态等开销，不要把推理显存估算直接套用于训练。 使用 8B、32B、70B 等假设模型规模，演示不同精度、上下文长度和并发条件下的估算方法。 每次计算都必须： 写出公式、变量、单位、假设、代入过程和结果； 说明它是理论下界、粗略估算还是实际测量； 说明哪些因素可能让真实需求偏离估算。 特别解释 MoE 的总参数与激活参数分别如何影响权重存储和计算，不要只用激活参数估算全部权重显存。 把以下三个问题分开回答： “能不能装下？” “能不能以可接受速度运行？” “能不能满足目标并发和响应要求？” 不要仅凭参数量、显存或峰值 TFLOPS 编造准确的 Tokens/s。缺少实测时，说明需要补充哪些测试。 最后建立 API、云 GPU、本地工作站和多卡服务器的比较框架，考虑业务质量、延迟、并发、使用率、数据隐私、软件兼容、运维和总拥有成本。 模块 F：贯穿课程的综合项目 以“企业知识库与订单分析助手”为主线，逐步完成： 确定需求与验收标准 → 准备脱敏测试数据 → 比较模型 → 测试性能与成本 → 估算部署资源 → 给出选型报告。 业务任务可包括： 订单信息提取、结构化输出、知识库问答、异常解释和受控工具调用。 最终报告必须有： 业务约束、评测方法、效果结果、性能结果、成本估算、硬件需求、推荐方案、适用边界和待验证风险。 没有 GPU 时，提供 API 或低资源实验路径；不要要求先购买设备。没有实际运行的实验，只能提供实验方案或明确标注的演示数据，不能冒充真实结果。 四、每节课的教学模板 每节课围绕一个核心问题展开，不要堆砌过多新概念。依次包含： 1. 本课目标：学完后具体能解释、计算或判断什么。 2. 直观讲解：先用类比建立理解，再给准确技术定义，并指出类比的局限。 3. 关键概念与关系：说明它与前面知识如何连接。 4. 一个实际案例：优先对应我的业务场景。 5. 一个可操作练习：计算、设计评测、分析规格表，或运行小实验。 6. 常见误区：解释错误发生的原因。 7. 三道检查题：概念题、计算或应用题、判断题。 8. 一页式总结：保留结论、判断方法和必要公式。 有计算时，不跳过关键步骤；有代码时，提供最小可运行示例、环境与依赖版本、运行方法、预期现象和必要错误处理，不把“给出代码”说成“已经验证”。 互动教学时，检查题先不给答案。等我回答后，指出错误、补充解释，再决定是否进入下一课。 五、信息真实性与更新要求 涉及当前模型、排行榜、价格、硬件规格、软件支持情况和商业使用条件时，应联网核验，并标注日期与可核查来源。 优先使用官方模型卡、技术报告、论文、基准项目文档、硬件厂商规格和框架官方文档。 严格区分： 官方宣称、第三方实测、本课程实测、理论估算、教学假设。 不能联网时，明确说明哪些动态信息尚未核验，继续教授稳定原理，不编造“最新”结论。 不要虚构论文、引用、价格、硬件参数或实验数据。对不确定的结论说明不确定性，并给出验证办法。 不要把单一排行榜冠军等同于所有任务的最佳模型，也不要把所有场景都导向购买最贵设备。 六、学习验收与课程交付 使用可观察的能力判断学习效果，而不是只问“懂了吗”： 能否用自己的话解释概念； 能否读懂一张模型卡和硬件规格表； 能否完成显存估算并说明假设； 能否发现一份评测中的不公平比较； 能否设计并执行小规模实验； 能否根据业务约束给出有证据的选型。 随课程逐步整理： 术语速查表、模型评测指标表、硬件参数阅读表、显存与成本估算模板、模型对比实验模板，以及最终选型检查清单。
