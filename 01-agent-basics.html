1.1 什么是智能体？

先给一个直觉定义：智能体（Agent）是一个能自主使用工具、多步推进任务的 AI 系统。 再给一个严格一点的定义（来自 Anthropic 的《Building Effective Agents》）：

定义

Agent 是这样一类系统：LLM 动态地决定自己的处理过程与工具使用，对完成任务的方式保有控制权，而不是按人写死的步骤执行。

拆开看，任何 Agent 都由四个要素组成——记住这个「四件套」，后面每一章都在给它们加深细节：

LLM · 大脑

负责理解、推理、决策。它不执行任何操作，只负责「想」：下一步该做什么？调用哪个工具？任务完成了吗？

Tools · 手脚

搜索、读写文件、调 API、执行代码……工具让模型突破「只会说话」的边界，能对真实世界产生影响。

Loop · 生命周期

思考 → 行动 → 观察 → 再思考……循环往复，直到任务完成。这是 Agent 区别于「一问一答」的根本特征。

Memory · 状态

短期记忆是不断增长的对话历史；长期记忆可以是向量库、文件，甚至知识图谱（第 5、6 章展开）。

一个对比感受

问 Chatbot「帮我订明天去上海的机票」→ 它只能输出一段文字："好的，建议您打开航空公司官网……"
问 Agent 同样的问题 → 它调用航班查询工具 → 比价 → 调用订票工具 → 消息你"已订好 MU5101，靠窗座位"。
Chatbot 负责说，Agent 负责做成。

1.2 Chatbot · Workflow · Agent：一张判定表

不是所有系统都叫 Agent。业界（沿用 Anthropic 的区分）通常划成三类，判定标准只有一个——控制流由谁决定？

Chatbot 对话Workflow 工作流Agent 智能体
控制流用户每问一次，模型答一次开发者写死的代码决定步骤顺序模型自己决定下一步做什么
工具使用无或固定每个节点绑定固定工具从工具清单里自主挑选
步骤数1预定（有限）不预定（由任务难度决定）
典型例子客服问答、翻译「先分类 → 再检索 → 再生成」的固定管道Claude Code、Devin、深度研究类产品
成本 / 可控性最低 / 最高可预测、易调试最灵活，但最难预测
实用建议：能用 Workflow 就别上 Agent

Anthropic 在同一篇文章里反复强调：Agent 的自主性是一把双刃剑——更贵、更慢、更难调试。当任务的步骤可以被预见时，写死的 Workflow 更便宜、更稳定；只有开放性、步数不可预知的任务（"修复这个 bug 并通过测试"）才值得上 Agent。

1.3 引擎的核心：Agent Loop

剥掉所有包装，Agent 的「发动机」就是一个几十行代码的循环：

用户任务→ 思考→ 行动→ 观察→ 未完成？回到 思考⤴ 完成 → 输出
Loop：模型每次都能看到之前所有的思考、行动与观察，再决定下一步

用伪代码写出来只有 10 行——这不是比喻，真实 Agent 框架的核心就这么简单：

pseudo · agent loop 伪代码
messages = [system_prompt, user_task]
while True:
    reply = llm(messages, tools=tool_schemas)   # ① 模型看着全部历史做决策
    if reply.requires_tool:                     # ② 模型说：我要用某工具
        result = execute_tool(reply.tool_name, reply.tool_args)  # ③ 你的代码去执行
        messages.append(reply, tool_result)     # ④ 观察结果送回历史
    else:                                       # ⑤ 不再需要工具 = 任务完成
        return reply.final_answer
本章最重要的一个观点

市面上的 LangChain、OpenAI Agents SDK、Claude Code……一切 Agent 框架，都是这个循环 + 周边工程的变体。把循环刻进脑子里，框架对你而言只是「不同牌子的发动机外壳」。

1.4 ReAct：让模型边想边做

2022 年论文《ReAct: Synergizing Reasoning and Acting in LLMs》（Yao et al.）确立了今天几乎所有 Agent 都在用的范式： 让模型在行动之前显式写出推理过程，即 Thought（想）→ Action（做）→ Observation（看）的交替序列。

text · 一段典型的 ReAct 轨迹
任务：帮我查 ArXiv 2201.11903 这篇论文的作者人数

Thought 1: 我需要先检索这篇论文的信息 →
Action 1:  search(query="arXiv 2201.11903")
Observation 1: 《Chain-of-Thought Prompting…》, 8 位作者…

Thought 2: 已找到论文条目，作者数可直接回答 →
…（直接给出最终答案）

为什么把推理「写出来」这么有效？两个原因：

  • 外化的思考可以纠错。模型每一步都能重新审视自己的 Thought，用户和开发者也能定位是哪一步想错了（可解释性）。
  • 行动有据可依。没有 Thought 直接给 Action 的模型，工具选择更随机；先写理由再选工具，准确率显著更高——这是论文的核心实验结论。
现代实现里 ReAct 去哪了？

今天的 Function Calling 接口里你看不到 "Thought:" 字样，但它换了个形态活着：模型在决定 tool_calls 前的内部推理（DeepSeek-Reasoner 会把这部分作为 reasoning_content 返回给你看）就是 Thought。范式没变，接口变优雅了。

论文精读入口

本章两大范式的原始论文：ReAct（1.3/1.4 节的出处，含「去掉 Thought 掉分」的关键消融实验）与 Chain-of-Thought（一切「先想再做」的起点）——按统一模板拆解见 论文精读页，逐段中译见 中文精读版。

1.5 Function Calling：模型只是「点名」，从不亲自动手

工具调用的完整流程是三步，请特别注意第二步的执行者：

  1. 声明

    你的代码把每个工具的「说明书」（名字、功能描述、参数的 JSON Schema）随请求发给模型。

  2. 决策

    模型不执行任何东西，只返回一个「调用意图」：{"name": "get_weather", "arguments": '{"city":"北京"}'}。这就是最常见的误解所在——模型没有上网，没有查天气，它只是「点名」要用这个工具。

  3. 执行与回填

    你的代码（也就是未来的 Harness，见第 7 章）真正执行该工具，把结果作为消息追加回对话，再请模型继续。

消灭一个流传最广的误解

「调用 get_weather 工具」≠「模型去查了天气」。模型自始至终只输出文字（结构化的文字）。执行永远发生在你的运行时里。理解这一点，你就理解了为什么「工具实现的质量」和「模型的质量」同样重要。

① 无工具时，模型的「自信错误」——输出语气笃定但内容是编的，这叫幻觉（hallucination），是工具存在的根本理由；② 两轮循环的分工：第一轮「获取信息」，第二轮「基于信息再行动」；③ 终止时机由模型自己判断，不是写死的。

1.6 什么时候该用 / 不该用 Agent

  • 任务开放、步骤无法预先枚举（"调研并写一份报告"）→ 适合 Agent
  • 需要组合多种工具、且组合方式依输入而变 → 适合 Agent
  • 步骤固定可枚举（"分类 → 检索 → 生成"）→ 用 Workflow，更便宜稳定
  • 一次回答即可解决（翻译、总结、改写）→ 普通 LLM 调用就够
  • 任务会产生不可逆的高危操作 → 必须加权限控制（第 7 章）或人在环

1.7 Agent 生态全景：现在都有谁、在做什么

带着四要素的透镜看市场，你会发现所有产品都是同一个模型的不同装配方式。认识它们，一是为了开阔思路，二是为了在你自己动手时有「参考答案」可抄：

类别代表解决什么拆开看（四要素）
编码 AgentClaude Code、Cursor Agent、Aider、Pi Agent读懂代码库、改代码、跑测试直到通过大脑：强推理模型；工具：读写文件 / 执行命令 / 搜索；循环：改→跑测试→再改；记忆：会话历史 + 项目文件
通用任务 AgentChatGPT Agent、Manus跨应用的开放式任务（订票、比价、做报告）工具：浏览器 / 虚拟机 / 代码执行；通常带「计划文件」外置记忆
深度研究Deep Research 类产品多轮检索并综合成长报告常是 Workflow + Agent 混合：计划定死大框架，检索子步骤由模型自主展开
企业流程 Agent各类客服 / 运营 / 数据 Agent接单、查库、填表、升级人工工具：内部 API；重权限与审计；大多严格限制步数
造 Agent 的框架LangGraph、OpenAI Agents SDK、CrewAI帮你搭「循环 + 工具 + 编排」它们不是 Agent，是 Harness 的现成零件包（第 7 章详谈）
分析任意 Agent 产品的三连问

① 它的大脑是什么模型（决定推理上限）？② 它有哪些工具、工具描述写得如何（决定能力边界）？③ 它的循环怎么终止、有没有步数限制（决定成本与风险）？答完这三问，一个产品你就算「看懂」了——剩下的差异都在 Harness 工程细节里。

自测

先自己回答，再点开看解析。

Agent 与 Workflow 最本质的区别是什么？

答案：控制流由谁决定。Workflow 的步骤顺序由开发者写死在代码里；Agent 由模型在运行时自主决定下一步做什么、用哪个工具、何时结束。因此 Workflow 可预测、易调试，Agent 灵活但行为不可完全预知。

模型输出 tool_calls 之后，是谁去真正执行工具？为什么这样设计？

答案：是你的运行时代码（Harness），模型从不执行工具。这样设计是因为：模型只能生成文本，没有任何对外通道；同时把「执行权」留在代码层，才能做权限校验、沙箱隔离、审计日志——这是安全性的根基（第 7 章详谈）。

ReAct 中的 Observation 从哪里来？它对模型意味着什么？

答案：Observation 是工具执行后返回的真实世界反馈，由运行时回填进对话历史。它对模型意味着「事实的锚点」：模型的后续推理必须建立在自己真的看到过的数据上，而不是训练记忆或想象。Observation 的质量（是否信息密集、是否可读）直接决定下一轮决策质量。

为什么「先写 Thought 再选工具」比直接让模型给 Action 更准确？

答案：外化的推理相当于强迫模型先构建理由、再输出决策，两者在同一个上下文里互相约束：写出的理由会暴露错误假设（可被下一步修正），也让工具选择有据可循而不是参数式地「猜」。ReAct 论文的核心实验就是这一点的对照验证。此外，显式 Thought 让开发者能定位错在哪一步，调试价值巨大。

「每天早上 9 点拉取昨天的销售数据、生成周报、发邮件给固定列表」——该用 Agent 还是 Workflow？如果需求改成「分析这份销售数据，找出值得注意的变化并写一份给我老板看的报告」呢？

答案：第一问用 Workflow：步骤固定、顺序固定、输入输出格式固定——写死代码更便宜、稳定、可审计，用 Agent 反而引入不必要的不可预测性。第二问值得用 Agent：「值得注意的变化」无法枚举，分析路径取决于数据本身，模型需要自主决定查什么、对比什么、怎么组织——这是开放性任务的特征。

动手练习（带参考答案）

练习是检验「会不会」的唯一标准。先自己完成，再展开参考答案对照。

练习 1 · 用四要素拆解一个你天天在用的 AI 产品

任务：任选一个你用过的 AI 产品（比如某个 AI 客服、ChatGPT 的联网搜索、你手机里的 AI 助手），写出它的四要素清单。答不出工具和循环的，说明它可能根本不是 Agent。

参考答案（以「ChatGPT 联网搜索」为例）：

  • 大脑：GPT 系列模型；
  • 工具：search（网页检索）+ browse（打开并阅读具体网页）——通常就这两个，少而正交；
  • 循环：问 → 决定搜什么 → 看结果 → 不够再搜 → 综合作答，一般 2~5 轮；
  • 记忆：仅本次会话历史，无跨会话长期记忆（所以它记不住你上周问过什么）。

如果你拆的产品工具栏是空的、永远一步作答——那它是个 Chatbot，不是 Agent。会判断「是不是 Agent」本身就是本章的核心技能。

练习 2 · 五个场景的选型判定

任务：对每个场景判断用「普通 LLM 调用 / Workflow / Agent」，一句话说理由。

  1. 把用户输入的地址标准化成省 / 市 / 区三级字段。
  2. 客服系统：先识别意图，退换货走固定流程，咨询类回答知识库问题。
  3. 「帮我调研三款洗碗机的差异并给出购买建议」。
  4. 把上传的 PDF 摘要成 100 字。
  5. 「把这个仓库里所有用到旧版 API 的地方迁移到新版，并保证测试通过」。

参考答案：

  1. 普通 LLM 调用（或干脆正则 + 地址库）：一步、格式固定，模型只做一次格式转换。
  2. Workflow：意图分类节点 + 两条固定管道；退换货流程绝不该让模型即兴发挥。
  3. Agent（或 Workflow+Agent 混合）：调研路径取决于搜到什么，步数不可预知。
  4. 普通 LLM 调用：一步任务。
  5. Agent：典型开放任务，Claude Code 类产品的核心场景。

规律：五题里只有两题值得上 Agent——现实业务里大部分需求都不需要 Agent，克制是美德。

练习 3 · 改造 Agent Loop：支持「用户中途补充输入」

任务：修改 1.3 的伪代码，使得循环进行中用户发来的新消息（比如「对了，改成经济舱」）能被模型看到。只用伪代码，5 行以内。

pseudo · 参考答案
messages = [system_prompt, user_task]
while True:
    for new_msg in poll_user_inbox():        # 每轮循环开始前，检查用户是否插话
        messages.append({"role": "user", "content": new_msg})
    reply = llm(messages, tools=tool_schemas)
    ...  # 其余不变：新消息自然进入模型视野，影响后续决策

要点：插话本质上就是往 messages 数组追加一条 user 消息。真正的产品（如 Claude Code 的 Esc 打断）做的都是这件事，外加「打断当前工具执行」的取消逻辑。你会发现所有改动都发生在 harness 层——模型一行不用改，这就是第 7 章的主题。
